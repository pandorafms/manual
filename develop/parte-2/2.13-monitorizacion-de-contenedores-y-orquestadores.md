# Monitorización de contenedores y orquestadores

Docker se monitoriza mediante un plugin ejecutado por un EndPoint. Kubernetes
y OpenShift se consultan desde Discovery a través de la API del clúster. La
forma de recoger los datos determina dónde configurar la integración y dónde
buscar sus resultados en la consola web de Pandora FMS.

| Destino | Recogida y resultado | Guía de la integración |
|---|---|---|
| Docker | El EndPoint ejecuta el plugin y añade módulos a su agente existente. | [Docker](https://pandorafms.com/docs/integrations/latest/es/plugins/docker/) |
| Kubernetes | Discovery consulta la API y genera agentes y módulos según la tarea. | [Kubernetes](https://pandorafms.com/docs/integrations/latest/es/discovery/kubernetes/) |
| OpenShift | Discovery consulta la API y genera agentes y módulos según la tarea. | [OpenShift](https://pandorafms.com/docs/integrations/latest/es/discovery/openshift/) |

La instalación de un paquete .disco y el ciclo común de sus tareas están en
[Cómo funciona la tarea de un paquete .disco](2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md#como-funciona-la-tarea-de-un-paquete-disco).
Las guías de la tabla reúnen los requisitos concretos, permisos, configuración,
parámetros, módulos, limitaciones y solución de problemas de cada integración.

Antes de configurar, hay que comprobar el acceso al destino desde el equipo que
recogerá los datos y autorizar solo las consultas necesarias. Las credenciales
deben quedar protegidas. También deben revisarse las condiciones de conexión y
seguridad de la guía correspondiente: usar HTTPS no basta para dar por supuestas
la validación de identidad del servidor ni la autenticación de las peticiones.

## Docker

El plugin Docker obtiene estadísticas de uso y rendimiento de los contenedores,
como CPU, memoria, red y E/S de bloques. Es un plugin convencional de EndPoint,
no una tarea de Discovery. Sus módulos se incorporan al agente existente del
EndPoint; no se crea un agente separado por contenedor.

La preparación del plugin y su integración con el EndPoint se siguen en la
[guía de Docker](https://pandorafms.com/docs/integrations/latest/es/plugins/docker/).
El acceso al daemon debe comprobarse con la cuenta y el entorno que ejecutan el
EndPoint, no solo desde una sesión administrativa. Después se comprueba en la
consola web que su agente recibe los datos de la integración.

## Kubernetes

Discovery consulta la API de Kubernetes para monitorizar la infraestructura y
las cargas de trabajo del clúster. La tarea genera agentes y módulos según su
alcance y los datos disponibles, sin instalar un EndPoint en cada nodo.

El recorrido consiste en preparar el acceso y las métricas que necesita la
integración, configurar la tarea y comprobar su primera ejecución. La
[guía de Kubernetes](https://pandorafms.com/docs/integrations/latest/es/discovery/kubernetes/)
detalla esa preparación, la selección de recursos, los resultados y sus límites.
La mecánica compartida de Discovery se explica en 2.3; los campos y opciones
propios del plugin se consultan en su guía.

## OpenShift

La integración de OpenShift también utiliza Discovery y la API del clúster para
recoger información de su infraestructura y cargas de trabajo. Los agentes y
módulos generados dependen de la tarea y de la información obtenida.

La preparación del acceso y la configuración se realizan conforme a la
[guía de OpenShift](https://pandorafms.com/docs/integrations/latest/es/discovery/openshift/).
No se deben trasladar a esta integración los campos y controles del asistente de
Kubernetes: cada una tiene su configuración y sus límites. Tras ejecutar la
tarea, se revisan sus resultados y los datos recibidos en la consola web.

## Resultados y primeras comprobaciones

Para Docker se revisa el agente del EndPoint. Para Kubernetes y OpenShift se
buscan los agentes y módulos generados por la tarea. La primera comprobación
debe cubrir tanto la recogida como la recepción de datos:

1. Revisar los errores de ejecución y confirmar que el acceso se realiza con
   la identidad autorizada y desde el equipo que ejecuta la integración.
2. Buscar los resultados esperados y comprobar que reciben datos recientes.
   Un resumen con agentes generados o una salida manual del plugin no demuestran
   por sí solos que los datos hayan llegado a Pandora FMS.
3. Contrastar una muestra de los valores con el destino. La ausencia de un
   módulo no prueba que falte el recurso, ni un indicador aislado confirma
   la salud de todo el entorno.

Si falta información, el diagnóstico específico corresponde a la guía de cada
integración. Para errores del ciclo de tarea, véase
[Cuando falla](2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md#cuando-falla).
Estas comprobaciones deben realizarse en el entorno que se va a monitorizar.
