    Monitorización de redes¶

    La monitorización remota es la otra mitad del oficio: todo lo que un EndPoint no puede contarte porque no vive dentro de la máquina, sino que se comprueba desde fuera —un router, un switch, una impresora, un SAI— o que conviene comprobar desde fuera aunque el equipo tenga agente propio, como la disponibilidad real de un servicio de cara a la red. Este capítulo cubre ICMP, TCP, SNMP, WMI, comandos remotos y el uso de plugins remotos de servidor: todo lo que hace un servidor de Pandora FMS al otro lado de la red, sin instalar nada en el destino. Los avisos que los equipos envían por su cuenta, los traps SNMP, tienen capítulo propio: Monitorización de traps SNMP.

    Monitorización remota: qué es y cuándo usarla¶

    Comprobar un equipo desde fuera no exige tocarlo: basta con que responda a una petición de red —un ping, una conexión TCP, una consulta SNMP o WMI, un comando por SSH— y con que algún servidor de Pandora FMS tenga visibilidad de red hasta él. Es el único camino posible para un dispositivo que no admite software propio (un router, un switch, una impresora, un SAI) y una alternativa razonable para un servidor que sí lo admite, cuando lo que interesa es lo que ve la red y no lo que ve el propio sistema operativo.

    No hace falta un EndPoint para tener un agente. Un agente lógico se puede dar de alta directamente desde la consola web, sin fichero de configuración detrás, y colgarle módulos de red: es lo que hace, por ejemplo, Discovery al escanear una red. Si un módulo deja vacío su campo de dirección de destino, usa la dirección IP del propio agente; así un agente sin EndPoint puede llevar todos sus módulos sin repetir la IP en cada uno.

    Comprobación Servidor que la ejecuta Token que lo activa
    ICMP (disponibilidad y latencia) Servidor de red de alto rendimiento, en lote con fping networkhpserver
    SNMP Servidor de red de alto rendimiento, en lote con pandorafsnmp (v1, v2c y v3) networkhpserver
    TCP Servidor de red networkserver
    Comandos remotos Servidor de red networkserver
    WMI Servidor de red, con el cliente pandorawmic networkserver
    Plugins remotos Servidor Heavy heavyserver

    Los tres vienen activados de fábrica y se reparten el trabajo solos: con el servidor de red de alto rendimiento en marcha, el servidor de red deja ICMP y SNMP en sus manos y se queda con el resto. Si se desactiva el de alto rendimiento, el servidor de red vuelve a encargarse de ICMP (con el ping del sistema) y de SNMP (con snmpget, consulta a consulta). Los detalles de este reparto están en Rendimiento, ajuste y diagnóstico.

    Cuando la red que hay que comprobar no es visible desde ningún servidor central —una sede sin ruta directa, una red aislada—, un servidor satélite hace exactamente el mismo trabajo desde dentro de esa red y entrega los datos como si fuera un servidor más.

    Un router sin EndPoint

    Se da de alta un agente «router-core» con dirección 192.168.10.1, sin instalar nada en él. A partir de ahí se le añaden módulos de red —ICMP para saber si responde, SNMP para leer sus interfaces— exactamente igual que a cualquier otro agente.

    Primeros pasos: crear un módulo de red¶

    Un módulo de red se crea desde la ficha del agente, en la pestaña Módulos (Modules), con el botón Crear (Create) → Crear módulo de red (Create network module). El formulario pide primero el tipo:

    Familia Para qué sirve Sección
    ICMP Disponibilidad y latencia de red Disponibilidad y latencia con ICMP
    TCP Puertos y servicios de red Servicios con TCP
    SNMP Equipos con agente SNMP (routers, switches, SAI…) Monitorización SNMP
    Comando remoto Comandos por SSH o Windows remoto Comandos remotos: SSH y Windows
    WMI Equipos Windows sin EndPoint Windows sin agente: WMI
    Plugin Comprobaciones empaquetadas en un script Plugins remotos de servidor

    La tabla completa de tipos internos, con qué devuelve cada uno y cómo se interpreta su estado, está en Referencia de tipos de módulo; cada sección de este capítulo enlaza a su fila.

    Todos los módulos de red comparten estos campos, con su valor por defecto:

    Campo Valor por defecto Qué hace
    IP objetivo (Target IP) vacío (auto) Si se deja vacío, usa la IP del agente. Admite las macros _agentname_ y _agentalias_ cuando el nombre o el alias del agente resuelven a una IP válida.
    Puerto vacío (161 en SNMP, 22 en comandos remotos por SSH) Puerto de destino, cuando la comprobación lo necesita.
    Intervalo 300 s Cada cuánto se repite la comprobación.
    Umbral de advertencia (min./máx.) 0 / 0 Rango que marca el módulo en estado de advertencia.
    Umbral crítico (min./máx.) 0 / 0 Rango que marca el módulo en estado crítico.
    Tiempo de espera 0 (usa el del servidor) Tiempo máximo antes de dar la comprobación por fallida.
    Reintentos 0 Intentos adicionales antes de descartar el dato.
    Umbral FF (flapping) 0 (desactivado) Número de cambios de estado seguidos que hay que ver antes de darlos por buenos; ver ejemplo más abajo.
    Instrucciones para desconocido vacío Texto que ve el operador cuando el módulo cae en estado desconocido.
    Mínimo / máximo 0 / 0 Cualquier dato fuera de este rango se descarta como inválido.

    Ping y latencia al router, con umbrales

    Sobre el agente «router-core» (192.168.10.1), dos módulos de red:

    • Disponible (remote_icmp_proc): sin más configuración que la IP objetivo, ya vale para saber si el router responde.
    • Latencia (remote_icmp): mismo objetivo, con advertencia a partir de 100 ms y crítico a partir de 300 ms.

    En cuanto el servidor de red ejecuta el módulo, el estado del agente pasa de «Sin datos» a normal y aparece el primer valor en su vista; es la señal de que el módulo está bien configurado.

    Propiedades avanzadas comunes¶

    Estas pestañas del editor aparecen en todos los módulos de red, con independencia del tipo:

    • ID personalizado (Custom ID, pestaña Categorización): un identificador libre para relacionar el módulo con un sistema externo, como una CMDB.
    • Posprocesado (Post process, pestaña Datos): multiplica el dato recibido por el factor indicado, antes de guardarlo. Sirve, por ejemplo, para convertir octetos en bits: un módulo que lee octetos por segundo con un posprocesado de 8 guarda ya el dato en bits por segundo.
    • Exportación (Export target, pestaña Datos): envía el dato también a un servidor de exportación.
    • Categoría (Category, pestaña Categorización): agrupación que usa la Command Center.
    • Cron (pestaña Intervalos): si se activa Cron desde (Cron from), el módulo deja de ejecutarse por intervalo y pasa a ejecutarse solo cuando la fecha y hora actuales coinciden con la expresión configurada.

    Ejecutar un módulo solo de noche

    Un módulo con Cron desde configurado para 0 2 * * * se ejecuta una vez al día, a las dos de la madrugada, en vez de cada 300 segundos.

    El umbral FF (de flapping, parpadeo) evita que una alerta se dispare por un cambio de estado aislado: exige ver el mismo número de cambios de estado seguidos antes de darlos por reales.

    Evitar un falso salto por flapping

    Un enlace WAN inestable pasa de normal a crítico y vuelta a normal varias veces en pocos minutos. Con un umbral FF de 3, el módulo no cambia de estado —ni dispara alertas— hasta ver tres lecturas seguidas del mismo signo; el parpadeo deja de generar ruido.

    Componentes de red: no empezar de cero¶

    Un componente de red es un módulo prefabricado: la misma configuración de un módulo de red, guardada como plantilla para no rellenarla cada vez. En el editor de un módulo nuevo, el campo Usando el componente de red (Using network component) permite elegir uno en vez de rellenar el formulario a mano; sigue disponible la opción manual (--Configuración manual--) para no usar ninguno.

    La instalación trae componentes agrupados por fabricante y tecnología: MIB de Cisco, sistemas UNIX, Microsoft Windows, WMI, bases de datos, y así con el resto de grupos incluidos de fábrica.

    Aplicar Host Alive y Host Latency desde componentes

    Al crear un módulo nuevo, seleccionar el componente Host Alive (grupo Network Management) da de alta el mismo módulo ICMP booleano que se configuraría a mano; Host Latency, del mismo grupo, hace lo propio con la latencia. Es la forma más rápida de dejar un agente sin EndPoint con lo mínimo cubierto. De hecho, el propio formulario de alta de agente trae una casilla, marcada por defecto, que crea estos dos módulos (Host Alive y Host Latency) automáticamente en cuanto se da de alta el agente, sin pasar por el editor de módulos.

    Crear un componente propio es tan sencillo como configurar un módulo de red cualquiera y guardarlo como componente en vez de aplicarlo directamente a un agente, desde Gestión → Módulos → Componentes de red. A partir de ahí se puede aplicar a cualquier agente, incluirlo en una política de monitorización o dejar que Discovery lo aplique en masa durante un escaneo.

    Macros en los campos del módulo¶

    Algunos campos de los módulos remotos admiten macros que el servidor sustituye por datos del agente cada vez que ejecuta el módulo. Así se evita escribir el mismo dato a mano en cada agente, y es lo que permite que un componente de red o un módulo de política sirva igual para agentes con datos distintos. El caso típico es la comunidad SNMP: si cada equipo tiene la suya, se guarda en un campo personalizado del agente y el módulo usa la macro en lugar de la comunidad.

    Los campos que admiten macros son estos:

    Campo Módulos
    IP objetivo ICMP, TCP y SNMP
    Comunidad SNMP SNMP v1 y v2c
    Usuario, contraseña de autenticación y contraseña de privacidad SNMP v3
    Usuario y contraseña WMI e inventario remoto por WMI

    En esos campos se pueden usar estas macros:

    Macro Se sustituye por Dónde
    _agentcustomfield_N_ Valor del campo personalizado del agente cuyo identificador es N Todos los campos de la tabla anterior
    _addressn_N_ Dirección IP número N del agente, con sus direcciones ordenadas Todos los campos de la tabla anterior
    _agent_, _agentalias_ Alias del agente IP objetivo
    _agentname_ Nombre del agente IP objetivo

    La macro solo se sustituye si el valor del campo empieza por ella: un valor como _agentcustomfield_3_ funciona; comunidad_agentcustomfield_3_ se envía tal cual. Los campos personalizados se crean en Gestión → Recursos → Campos personalizados. El identificador que aparece en esa lista es la N de la macro. El valor se rellena en cada agente.

    Una comunidad SNMP distinta por equipo

    Se crea el campo personalizado «Comunidad SNMP», que recibe el identificador 4, y se rellena en cada agente con su comunidad (sw-core-ro, sw-planta2-ro…). Un componente de red SNMP con Comunidad SNMP _agentcustomfield_4_ se aplica después a todos los switches, directamente o mediante una política: cada módulo consulta con la comunidad de su propio agente.

    Vigilar la segunda IP de un equipo

    En un servidor con dos interfaces dadas de alta en el agente, un módulo ICMP con IP objetivo _addressn_2_ comprueba la segunda dirección. El orden es el de las direcciones ordenadas, no el orden en que se añadieron.

    Los plugins remotos tienen su propio juego de macros, más amplio; se explican en Macros de los plugins.

    Disponibilidad y latencia con ICMP¶

    ICMP es la comprobación más básica y dos son sus tipos: Disponible (remote_icmp_proc), que devuelve si la IP responde o no, y Latencia (remote_icmp), que devuelve el tiempo de respuesta en milisegundos (ver Referencia de tipos de módulo). El servidor de red de alto rendimiento mide con fping, agrupando en una sola llamada todos los destinos pendientes (si está desactivado, lo hace el servidor de red con el ping del sistema): lanza tantos paquetes por intento y tantos reintentos como indiquen los tokens icmp_packets e icmp_checks, con el tiempo de espera de network_timeout. Si no hay respuesta dentro de esos límites, el módulo de disponibilidad marca estado crítico y el de latencia se queda sin dato.

    Disponibilidad de una impresora

    Módulo Disponible sobre 192.168.10.50: sin más ajuste que la IP objetivo, avisa en cuanto la impresora deja de responder a ping, sin necesidad de instalarle nada.

    Latencia de un enlace WAN

    Módulo Latencia sobre la IP del router remoto, con advertencia a 100 ms y crítico a 300 ms: un enlace que empieza a degradarse se ve venir antes de que se caiga del todo.

    Para algo más fino que la latencia —por ejemplo, el porcentaje de paquetes perdidos en vez de solo el tiempo de ida y vuelta— está el plugin de pérdida de paquetes que trae la instalación (ver Plugins remotos de servidor).

    Servicios con TCP¶

    TCP comprueba un servicio por su puerto, con cuatro tipos: puerto abierto (remote_tcp_proc, booleano), numérico (remote_tcp), texto (remote_tcp_string) e incremental (remote_tcp_inc); qué devuelve cada uno, en Referencia de tipos de módulo. Dos campos hacen el trabajo:

    • Enviar TCP (TCP Send): lo que se manda al puerto. Varios pasos de una conversación se separan con |; la secuencia ^M se sustituye por un retorno de carro real.
    • Recibir TCP (TCP Receive): lo que se espera de vuelta, comparado sin distinguir mayúsculas de minúsculas. Es obligatorio en los tipos texto e incremental; en el de puerto abierto, solo si se rellena.

    Puerto abierto

    Módulo de tipo puerto abierto sobre el puerto 443, sin Enviar TCP ni Recibir TCP: basta con que el puerto acepte la conexión para marcar estado normal.

    Cabecera de un servidor web

    Enviar TCP: GET / HTTP/1.0^M^M. Recibir TCP: 200 OK. El módulo pasa a normal en cuanto la respuesta contiene esa cadena, sin importar si el servidor la devuelve en mayúsculas o minúsculas.

    Conversación SMTP de tres pasos

    Enviar TCP: HELO midominio.com^M|MAIL FROM: <a@midominio.com>^M|RCPT TO: <b@destino.com>^M. Recibir TCP: 250|250|250. Cada paso se envía y se comprueba antes de pasar al siguiente.

    Banner SSH

    Puerto 22, sin Enviar TCP, y Recibir TCP con el texto SSH-2.0 para confirmar la versión de protocolo que anuncia el servidor al conectar.

    Reintentos y tiempo de espera se ajustan como en cualquier módulo de red, con los valores por defecto del servidor en tcp_checks y tcp_timeout.

    Monitorización SNMP¶

    SNMP en cinco minutos¶

    Para monitorizar un equipo por SNMP hace falta que tenga el agente SNMP activado y que Pandora FMS sepa cómo hablarle: qué versión de protocolo (v1, v2c con comunidad de lectura; v3 con usuario, autenticación y privacidad) y qué OID leer. Un OID (Object IDentifier) es la dirección de un dato concreto dentro del equipo —temperatura, CPU, estado de una interfaz—; puede escribirse en su forma numérica (.1.3.6.1.2.1.1.5.0) o, si el servidor tiene cargada la MIB que lo describe, en su forma textual (sysName.0). Cada OID que se monitoriza es un módulo de red distinto.

    OID Qué es
    .1.3.6.1.2.1.1.3.0 (sysUpTime) Tiempo que lleva encendido el equipo
    .1.3.6.1.2.1.1.5.0 (sysName) Nombre configurado del equipo
    .1.3.6.1.2.1.2.2.1.8 (ifOperStatus) Estado operativo de una interfaz
    .1.3.6.1.2.1.2.2.1.10 (ifInOctets) Octetos de entrada por interfaz (contador de 32 bits)
    .1.3.6.1.2.1.31.1.1.1.6 (ifHCInOctets) Igual, en su versión de 64 bits para enlaces rápidos

    Cuando el OID es textual, el servidor lo traduce a numérico con las MIB que tenga cargadas (ver Gestor de MIB); sin la MIB adecuada, el navegador y los módulos solo pueden trabajar con el número.

    La forma recomendada de dar de alta módulos SNMP es uno de los dos asistentes de la ficha del agente: exploran el equipo por SNMP y proponen los módulos ya configurados, sin buscar un solo OID a mano. Crear los módulos SNMP uno a uno, más adelante en esta sección, queda para los casos que un asistente no cubre: un OID suelto que no aparece en ninguna plantilla, una MIB propia del fabricante, o el ajuste fino de un módulo ya creado.

    Asistente de interfaces SNMP¶

    En la ficha del agente, pestaña Asistente de interfaces SNMP. Es el atajo para switches y routers: en vez de crear un módulo por cada interfaz y magnitud a mano, hace un recorrido por la rama IF-MIB::interfaces del equipo y propone todos los módulos de golpe.

    El primer paso pide la conexión SNMP —el mismo formulario que usa el asistente SNMP de la sección siguiente—:

    Campo Valor por defecto Qué hace
    IP objetivo vacío Dirección del equipo a explorar. Es un campo de texto libre: no admite las macros de agente _agentname_ ni _agentalias_, hay que escribir una IP real aunque el agente ya tenga una asociada.
    Puerto 161 Puerto SNMP del equipo.
    Servidor para ejecutar el comando Consola local Qué servidor de Pandora FMS hace la consulta SNMP real. Solo hace falta cambiarlo cuando la consola no tiene ruta directa hasta el equipo: ver Ejecutar asistentes y pruebas desde un servidor remoto (Exec Server).
    Importar desde el almacén de credenciales — Si hay algún juego SNMP guardado en el gestor de credenciales visible para el usuario, aparece aquí; al elegirlo rellena solos el resto de campos.
    Versión SNMP 2c 1, 2c o 3. Al elegir 3 aparece el formulario de autenticación de abajo.
    Comunidad SNMP public Comunidad de lectura, para v1 y v2c.

    Con versión 3, el formulario añade los campos habituales de SNMPv3: nivel de seguridad (sin autenticación ni privacidad, con autenticación sin privacidad, o con ambas), usuario, método y contraseña de autenticación (MD5, SHA, SHA256 o SHA512) y método y contraseña de privacidad (DES, AES, AES192 o AES256) — los mismos que en Módulos SNMP.

    Terminada la consulta, el asistente decide una sola vez, para todo el equipo, si trabaja con contadores de tráfico de 32 o de 64 bits: si el equipo responde a la rama de contadores de alta capacidad (pensada para enlaces rápidos), usa esa para todas sus interfaces; si no, se queda con los contadores clásicos de 32 bits. El resultado se presenta como un bloque plegable por interfaz, con un interruptor que la incluye o la excluye entera; solo vienen ya activadas las interfaces que están operativa y administrativamente activas, para no llenar el agente de módulos muertos por los puertos sin nada conectado. Por encima de los bloques hay una barra de filtro con búsqueda de texto libre por nombre o descripción de interfaz, dos interruptores para quedarse solo con las que están operativa o administrativamente activas, y un interruptor para seleccionar de golpe todas las interfaces que pasan el filtro. Dentro de cada bloque, otro interruptor marca o desmarca todos sus módulos a la vez, y cada módulo se puede activar o desactivar por separado y traer ya editados sus umbrales de advertencia y crítico antes de crear nada. Un bloque especial, al principio del listado, aplica el mismo conjunto de módulos a todas las interfaces seleccionadas de una vez, sin repetir la selección interfaz por interfaz.

    Por cada interfaz que queda marcada, el asistente propone:

    Módulo Qué mide Umbral
    Estado operativo Si la interfaz está activa, caída, en pruebas… Depende del estado administrativo de la interfaz: si está administrativamente activa, el umbral crítico espera que también lo esté operativamente (avisa o falla si no); si está administrativamente apagada, el umbral se invierte para no avisar de algo esperado; si está en pruebas, usa un tercer juego de rangos.
    Octetos de entrada / salida Tráfico en bytes por segundo Incremental, sin umbral por defecto
    Paquetes unicast de entrada / salida Paquetes por segundo Incremental, sin umbral por defecto
    Paquetes multicast y broadcast de entrada / salida (solo con contadores de 64 bits) Paquetes por segundo Incremental, sin umbral por defecto
    Errores CRC Tramas descartadas por error de trama Incremental, sin umbral por defecto
    Ancho de banda, uso de entrada, uso de salida Porcentaje de la capacidad del enlace en uso, calculado a partir del tráfico y la velocidad de la interfaz El módulo agregado de ancho de banda trae un 85 % como umbral crítico por defecto; los de uso de entrada y salida por separado, sin umbral

    Los tres módulos de porcentaje de uso no leen un OID directamente: los calcula un plugin interno a partir del tráfico y la velocidad nominal de la interfaz, así que cuentan como módulos de tipo plugin en el agente, aunque el asistente los presente igual que al resto. En equipos Cisco reconocidos por su PEN, el asistente añade además un módulo de discrepancia de dúplex por interfaz, cuando el equipo expone ese dato.

    Qué módulos de esta tabla vienen ya marcados por defecto, sin tocar nada, se decide en Configuración → Configuración del sistema → Rendimiento, pestaña Asistente de interfaces (ver 9.2 · Referencia completa de configuración de la consola): es un interruptor por módulo, válido para todos los agentes.

    Antes de crear, el asistente repasa la lista y marca en gris, con un aviso, los módulos que ya existen en el agente (o en la política, si se está editando una) con el mismo nombre; no impide seguir, pero avisa para no duplicar sin darse cuenta. Los módulos creados se comportan después como cualquier módulo SNMP: se editan, se les cambia el umbral o se les añade una alerta igual que a uno hecho a mano.

    Un switch de 24 puertos, solo interfaces activas y su tráfico

    IP objetivo 192.168.10.2, versión 2c, comunidad public. Tras el recorrido SNMP, se dejan marcadas solo las interfaces con estado operativo activo (el filtro OperStatus UP ayuda a comprobarlo de un vistazo) y, de los módulos que propone cada una, solo Estado operativo y los octetos de entrada y salida: la disponibilidad y el tráfico de cada puerto en uso, sin errores ni paquetes que en un switch de acceso rara vez hace falta vigilar.

    Un router con SNMPv3 desde el almacén de credenciales

    IP objetivo la del router, versión 3. En vez de escribir usuario y contraseñas a mano, se elige el juego ya guardado en el gestor de credenciales con nivel de seguridad authPriv, autenticación SHA y privacidad AES: el asistente rellena solo el resto del formulario y hace la exploración con esas credenciales.

    Asistente SNMP¶

    En la ficha del agente, pestaña Asistente SNMP. A diferencia del anterior, este asistente monitoriza el equipo en su conjunto, no solo sus interfaces, y comparte el mismo formulario de conexión de la sección anterior (IP objetivo sin macros de agente, puerto, servidor para ejecutar el comando, importar del almacén de credenciales, versión y comunidad o credenciales v3).

    Con la conexión hecha, el asistente identifica el fabricante del equipo por su PEN (Private Enterprise Number, el identificador que cada fabricante registra ante IANA dentro de la rama de identificación del equipo). Si el PEN no está registrado en Pandora FMS, el asistente lo dice y no propone nada: hace falta darlo de alta o, si no interesa, crear los módulos a mano desde Módulos SNMP. Si lo reconoce, ofrece la biblioteca de módulos ya preparados para ese fabricante —más los que valen para cualquier equipo— agrupados por bloques según lo que miden: CPU, memoria, discos, almacenamiento, y así con el resto. Cada bloque se activa o desactiva de golpe con su propio interruptor, y cada módulo dentro de un bloque se puede marcar o desmarcar por separado, con sus umbrales de advertencia y crítico ya editables antes de crear nada; un indicador junto a cada bloque avisa de cuántos de sus módulos están seleccionados.

    Este asistente crea dos clases de módulos:

    • De OID fijo: leen directamente un OID de la MIB del fabricante —CPU, memoria, sensores…—, igual que un módulo SNMP creado a mano.
    • Calculados por plugin: para datos que no salen de un solo OID —un porcentaje de disco usado, memoria libre expresada en porcentaje…—, el asistente se apoya en un plugin remoto llamado snmp_remote.pl. Si ese plugin no está registrado en la instalación (ver Plugins remotos de servidor), estos módulos quedan desactivados en el asistente aunque el fabricante sí esté reconocido.

    Igual que en el asistente de interfaces, antes de crear se marcan en gris los módulos que ya existen en el agente o que se repiten con el mismo nombre dentro de la propia selección, sin que eso impida continuar.

    El catálogo de fabricantes y componentes que usa este asistente no es cerrado: se puede ampliar con fabricantes nuevos y con componentes propios, de OID fijo o dinámico, leídos directamente o calculados por un plugin —ver Ampliar los asistentes SNMP y WMI con componentes propios.

    Un servidor Linux con net-snmp

    Sobre un servidor con el agente net-snmp instalado, el asistente reconoce el PEN de Net-SNMP/UCD y propone módulos de CPU, memoria y espacio en disco listos para marcar y crear, sin buscar un solo OID a mano.

    Un servidor Windows con el servicio SNMP

    Sobre un servidor Windows con el servicio SNMP activado y una comunidad de lectura configurada, se repite la misma conexión (versión 2c, comunidad del equipo): si el asistente reconoce el PEN que declara el servicio, ofrece igual que en Linux los bloques de módulos ya preparados; si no lo reconoce, avisa de que el PEN no está registrado y lo que corresponde es documentar el equipo con Módulos SNMP o darlo de alta a mano.

    Navegador SNMP¶

    Para cuando no se sabe qué OID hace falta: el Navegador SNMP (SNMP Browser) recorre el árbol completo del equipo, o solo una rama concreta si se quiere acortar la exploración, y permite buscar una cadena de texto con resaltado de coincidencias. Sobre cualquier OID encontrado hay acciones directas: crear un componente de red, un módulo de agente o un módulo de política, sin salir del navegador.

    Buscar la temperatura de un switch

    Se busca «temperature» en el árbol ya explorado del switch, se localiza el OID correspondiente al sensor y se crea el módulo de agente directamente desde el resultado, con Crear módulo de agente.

    Módulos SNMP¶

    Para lo que ningún asistente cubre: un OID suelto sin plantilla, una MIB propia del fabricante o el ajuste fino de un módulo ya creado. Cuatro tipos: numérico (remote_snmp), estado (remote_snmp_proc), texto (remote_snmp_string) e incremental (remote_snmp_inc, para contadores: ver Referencia de tipos de módulo). Campos propios, con su valor por defecto:

    Campo Valor por defecto
    Puerto 161
    OID —
    Versión 2c
    Comunidad (v1/v2c) vacía; public en los asistentes
    Nivel de seguridad (v3) noAuthNoPriv
    Usuario (v3) —
    Método de autenticación (v3) MD5, SHA, SHA256 o SHA512; MD5 por defecto (la consola pide un mínimo de 8 caracteres en la contraseña)
    Método de privacidad (v3) DES, AES, AES192 o AES256; DES por defecto

    El campo Credenciales permite elegir un juego guardado en el gestor de credenciales en vez de escribir comunidad o usuario a mano. Junto al campo OID, el botón Exploración SNMP (SNMP browse) abre el mismo navegador de la sección anterior sin salir del editor del módulo.

    Uptime por v2c

    OID .1.3.6.1.2.1.1.3.0, versión 2c, comunidad public: módulo numérico con el tiempo de actividad del equipo, en centésimas de segundo.

    CPU de un equipo con OID del fabricante

    Un switch expone su carga de CPU en un OID propio, fuera de MIB-II (por ejemplo, .1.3.6.1.4.1.9.9.109.1.1.1.1.7.1 en equipos Cisco). Módulo numérico con ese OID, versión 2c y la comunidad del dispositivo.

    Módulo v3 authPriv con SHA y AES

    Versión 3, nivel de seguridad authPriv, usuario pandora_ro, autenticación SHA con su contraseña, privacidad AES con la suya: el nivel más alto de seguridad SNMP que ofrece el formulario.

    Tráfico de una interfaz como incremental

    OID .1.3.6.1.2.1.31.1.1.1.6.1 (ifHCInOctets de la interfaz 1), tipo incremental. El contador SNMP crece sin parar mientras el equipo esté encendido; Pandora FMS guarda la diferencia entre dos lecturas dividida por el tiempo transcurrido, es decir, una tasa (octetos por segundo), no el valor bruto del contador.

    Gestor de MIB¶

    Las MIB describen qué significa cada OID de un fabricante; sin la MIB correspondiente cargada, un OID solo se ve en su forma numérica. El Gestor de MIB (MIB uploader) permite subir las del fabricante, en formato .mib o .zip, y las deja disponibles para traducir OID en el navegador, en los módulos y en los traps.

    Cargar la MIB de un SAI

    Se sube el fichero .mib que entrega el fabricante del SAI; a partir de ahí, sus OID aparecen traducidos en el navegador y se pueden usar traps de ese mismo fabricante ya identificados por su nombre.

    SNMP desde un EndPoint¶

    Tiene sentido cuando el equipo SNMP solo es alcanzable desde dentro de una red a la que únicamente llega un EndPoint, no el servidor central. El EndPoint Windows tiene una directiva nativa para ello:

    module_snmpget
module_snmp_version 2c
module_snmp_community public
module_snmp_agent 192.168.10.1
module_snmp_oid .1.3.6.1.2.1.1.3.0

    (las credenciales SNMPv3 se indican dentro de las opciones avanzadas del propio módulo, sin un sub-token dedicado por campo).

    Los EndPoints Go y Perl no tienen una directiva SNMP propia: se apoyan en module_exec para llamar al snmpget del sistema, igual que para cualquier otro comando externo.

    El mismo OID, desde cada EndPoint

    Windows: 

    module_snmpget
module_snmp_version 2c
module_snmp_community public
module_snmp_agent 192.168.10.1
module_snmp_oid .1.3.6.1.2.1.1.3.0
    Go o Perl: 
    module_exec snmpget -v 2c -c public 192.168.10.1 .1.3.6.1.2.1.1.3.0

    Ver 2.1 · Monitorización con EndPoints para el resto de directivas del fichero de configuración local.

    Todo lo anterior es polling: Pandora FMS pregunta y el equipo responde. Para lo contrario —el equipo avisa en el momento en que algo pasa— están los traps, que se reciben, filtran, traducen y convierten en alertas como se explica en Monitorización de traps SNMP.

    Windows sin agente: WMI¶

    WMI permite leer información de un equipo Windows sin instalarle un EndPoint, siempre que el acceso remoto a WMI esté habilitado en el destino. El módulo WMI se apoya en el cliente pandorawmic, que el servidor de red lanza con las credenciales indicadas —guardadas en el gestor de credenciales o escritas a mano— contra el equipo de destino. Sus cinco tipos (numérico, estado, texto e incrementales) están en Referencia de tipos de módulo.

    Campos propios del módulo:

    Campo Qué es
    IP Equipo Windows de destino
    Credencial WMI Del gestor de credenciales, o usuario y contraseña sueltos
    Espacio de nombres (Namespace) Espacio WMI donde vive la clase consultada; vacío por defecto
    Consulta WMI (WMI Query) La consulta en WQL, el dialecto de WMI parecido a SQL
    Campo número (Field number) Qué columna de la respuesta usar, si la consulta devuelve varias
    Cadena clave (Key string) Opcional: si se rellena, el módulo devuelve 1 o 0 según si la respuesta contiene esa cadena, en vez de la cadena en sí

    Espacio libre en C:

    Espacio de nombres root\cimv2, consulta SELECT FreeSpace FROM Win32_LogicalDisk WHERE DeviceID='C:', campo número 0: devuelve el espacio libre del disco en bytes.

    Servicio Spooler en marcha

    Consulta SELECT State FROM Win32_Service WHERE Name='Spooler', cadena clave Running: el módulo devuelve 1 mientras el servicio esté activo y 0 en cuanto se detenga.

    Consulta WQL propia

    Cualquier clase WMI del equipo se puede consultar igual, ajustando el número de campo a la columna que interese de la respuesta —por ejemplo, SELECT Name, Status FROM Win32_PnPEntity con campo número 1 para quedarse solo con el estado.

    El Asistente WMI, en la ficha del agente, agrupa las consultas más habituales en plantillas listas para marcar: servicios (booleano, activo o detenido), procesos, espacio en disco y componentes WMI registrados —el mismo mecanismo de componentes que en SNMP, pero para WMI—, sin escribir una sola consulta WQL a mano. Ese catálogo de componentes WMI también se puede ampliar con consultas propias, igual que el del asistente SNMP: ver Ampliar los asistentes SNMP y WMI con componentes propios.

    Para que el equipo Windows de destino responda a WMI hace falta que su cortafuegos deje pasar las conexiones entrantes correspondientes (ver requisitos de cortafuegos en Windows).

    Comandos remotos: SSH y Windows¶

    Un módulo de comando remoto ejecuta un comando en el equipo de destino y recoge su salida (tipos numérico, estado, texto e incremental: ver Referencia de tipos de módulo), con tres métodos de conexión: Heredado (usa el sistema operativo configurado en el propio agente), SSH para Linux y Control remoto de Windows (WinRM) para Windows. En los tres casos, el comando se conecta con una credencial del gestor de credenciales —del tipo credencial genérica— y el campo Comando, entre comillas simples cuando haga falta (las comillas dobles se escapan con \").

    El asistente de la ficha del agente trae tres plantillas listas: uso de disco, estado de un proceso y estado de un servicio.

    Uso de disco por SSH

    Método SSH, credencial del equipo Linux, comando: 

    df -h / | tail -1 | awk '{print $5}' | tr -d '%'
    devuelve el porcentaje de uso del disco raíz como valor numérico.

    Proceso nginx en marcha

    Método SSH, comando: 

    pgrep -c nginx
    Un módulo booleano que devuelve 0 si no hay ningún proceso nginx corriendo, y un número mayor si lo hay.

    El Control remoto de Windows (WinRM) necesita, igual que WMI, que el cortafuegos del equipo de destino deje pasar las conexiones entrantes correspondientes (ver requisitos de cortafuegos en Windows más abajo).

    Requisitos de cortafuegos en Windows para monitorización sin agente¶

    Tanto WMI como el control remoto de Windows necesitan que el cortafuegos del equipo de destino tenga habilitadas estas reglas de entrada:

    Requisito Detalle
    Uso compartido de archivos e impresoras (SMB) Regla File and Printer Sharing (SMB-In)
    RPC (asignador de puntos finales) Regla File and Printer Sharing (Spooler Service - RPC-EPMAP)
    WMI Regla Windows Management Instrumentation (WMI-In)

    Sin estas tres reglas activas, el equipo rechaza la conexión aunque las credenciales y la consulta o el comando sean correctos.

    Plugins remotos de servidor¶

    Un plugin remoto es un script o ejecutable que el servidor Heavy lanza con parámetros y del que recoge un único valor —numérico, booleano o de texto—; el tipo de dato lo decide el módulo (ver Referencia de tipos de módulo). Existen dos clases: estándar, que solo devuelve el valor, y Nagios, que además de un código de error puede devolver una cadena descriptiva. La instalación trae varios registrados de fábrica y el administrador puede registrar los que necesite desde Gestión → Servidores → Plugins.

    Al registrar un plugin se indica su tipo, el tiempo máximo de ejecución —15 s de partida— y las macros de campo (_field1_, _field2_…) que usará quien lo aplique a un módulo, cada una con su descripción, texto de ayuda, valor por defecto y si debe ocultarse en el formulario (para contraseñas y datos sensibles). El tiempo de espera efectivo de un plugin concreto es el menor entre el configurado en el servidor y el propio del plugin; si ninguno de los dos resulta válido, se usa 15 s de último recurso.

    En cuanto un plugin lo usa algún módulo o componente, el editor bloquea sus Parámetros del plugin y sus macros de campo: ya no se pueden añadir, quitar ni editar, para no romper los módulos que ya dependen de ellos. Para cambiar los parámetros hace falta antes dejar de usar el plugin en todos sus módulos y componentes.

    Macros de los plugins¶

    Las macros son lo que hace reutilizable un plugin: el comando se registra una sola vez con huecos, y cada módulo que lo usa rellena esos huecos con sus propios valores. Hay tres familias: las macros de campo, que define quien registra el plugin; las del agente y el módulo, que pone el servidor; y las que quedan disponibles para las alertas del módulo.

    Macros de campo. En Parámetros del plugin se escribe la línea de parámetros tal como la espera el script, con _field1_, _field2_… en el lugar de cada valor. En Macros de los parámetros se describe cada una:

    Campo Para qué sirve
    Descripción Etiqueta del campo en el formulario del módulo
    Valor por defecto Valor con el que aparece relleno el campo al crear el módulo
    Ayuda Texto de ayuda que se muestra junto al campo
    Ocultar valor El campo se muestra como una contraseña (puntos) y el valor se guarda cifrado

    La Vista previa del comando muestra la línea completa con los valores por defecto sustituidos, útil para comprobar el registro antes de guardar. Al crear un módulo de tipo plugin y elegir ese plugin, el formulario muestra un campo por macro, con su descripción, su ayuda y su valor por defecto. Los valores ocultos se descifran solo en el momento de lanzar el plugin.

    Plugin propio con usuario y contraseña

    Un script que consulta el estado de una aplicación se registra con estos Parámetros del plugin: 

    -H _field1_ -u _field2_ -p _field3_
    y tres macros: _field1_ con descripción «Servidor», _field2_ con descripción «Usuario» y valor por defecto monitor, y _field3_ con descripción «Contraseña» y Ocultar valor marcado. En el módulo se rellenan 192.168.10.20, monitor y la contraseña, que se muestra con puntos; el servidor ejecuta el script con -H 192.168.10.20 -u monitor -p <contraseña>.

    Macros del agente y del módulo. Además de las de campo, la línea de parámetros admite estas macros (más que los campos de los demás módulos remotos, ver Macros en los campos del módulo), que el servidor sustituye cada vez que ejecuta el plugin:

    Macro Se sustituye por
    _agent_, _agentalias_ Alias del agente
    _agentname_ Nombre del agente
    _agentdescription_ Descripción del agente
    _agentgroup_ Nombre del grupo del agente
    _agentstatus_ Estado del agente
    _address_ Dirección IP principal del agente
    _addressn_N_ Dirección IP número N del agente, con las direcciones ordenadas (_addressn_2_ es la segunda)
    _agentcustomfield_N_ Valor del campo personalizado del agente cuyo identificador es N
    _module_ Nombre del módulo
    _moduledescription_ Descripción del módulo
    _modulegroup_ Grupo del módulo
    _modulestatus_ Estado del módulo
    _moduletags_, _name_tag_ Tags del módulo
    _email_tag_, _phone_tag_ Correos y teléfonos asociados a los tags del módulo
    _interval_ Intervalo del módulo, o el del agente si el módulo no tiene uno propio
    _target_ip_, _target_port_ IP y puerto de destino configurados en el módulo
    _policy_ Nombre de la política de la que procede el módulo, si procede de una
    _id_agent_, _id_module_, _id_group_ Identificadores numéricos del agente, del módulo y del grupo

    El servidor sustituye primero las macros de campo y después estas, así que el valor de una macro de campo puede ser a su vez una de ellas. Es la forma de que un mismo módulo sirva para muchos agentes: con _address_ como valor, cada agente comprueba su propia IP.

    Un módulo de plugin para todos los agentes de una política

    En el plugin DNS Plugin, el campo DNS Server to check se rellena con _address_ en vez de una IP fija. Aplicado mediante una política de monitorización a los agentes de todos los servidores DNS de la empresa, cada módulo pregunta a la IP de su propio agente, sin tocar un solo módulo a mano.

    Campo personalizado como parámetro

    Si los agentes tienen un campo personalizado con el puerto de administración de cada equipo (identificador 3), el parámetro -p _agentcustomfield_3_ pasa al plugin el puerto de cada agente.

    Macros para las alertas. En las alertas de un módulo de plugin quedan disponibles _plugin_param1_, _plugin_param2_… con el valor de cada macro de campo, y _plugin_param1_desc_, _plugin_param2_desc_… con su descripción. Sirven para que el aviso diga contra qué se ejecutó la comprobación sin repetir los datos en el texto de la alerta. Una macro con Ocultar valor también se sustituye aquí, y en claro: no conviene usar en el texto de una alerta la macro de una contraseña.

    Alerta que dice qué servidor falló

    Con el plugin del primer ejemplo, el texto de la alerta Fallo en _plugin_param1_desc_ _plugin_param1_ (_module_) llega como «Fallo en Servidor 192.168.10.20 (Estado aplicación)».

    Monitorización de rutas¶

    El analizador de rutas traza el camino de red hasta un destino y avisa si cambia, algo que ni ICMP ni TCP hacen por sí solos: no basta con saber que el destino responde, sino por dónde pasa el tráfico para llegar a él. Se apoya en el plugin route_parser del EndPoint de origen, que combina ping y traceroute:

    route_parser -t <dirección_destino>

    Requiere un EndPoint en el punto de origen de la ruta y alcance por ICMP hasta el destino. Se da de alta desde la pestaña de plugins de la ficha del agente, igual que cualquier otro plugin local, y una vez activado genera una visualización con cada salto de la ruta y el tiempo hasta él.

    Ruta hacia una sede remota

    Sobre el EndPoint de la sede central, route_parser -t 172.16.0.2 (la IP de un equipo en la sede remota) deja ver, salto a salto, por qué routers pasa el tráfico entre ambas sedes y avisa si esa ruta cambia.

    Ejecutar asistentes y pruebas desde un servidor remoto (Exec Server)¶

    Cuando la consola no tiene ruta directa hasta una red, porque está detrás de un cortafuegos o en otro segmento, los asistentes SNMP y el navegador SNMP pueden ejecutarse desde otro servidor que sí llegue hasta ella, por ejemplo el servidor satélite de una sede remota. Se elige en el campo Servidor para ejecutar el comando del asistente. Cómo preparar ese servidor y qué requisitos tiene se explica en Servidores satélite.

    Referencia de tipos de módulo¶

    Tipo interno Familia Devuelve Para qué se usa
    remote_icmp_proc ICMP Booleano Disponibilidad por ping
    remote_icmp ICMP Numérico Latencia en milisegundos
    remote_tcp TCP Numérico Tiempo de conexión al puerto
    remote_tcp_proc TCP Booleano Puerto abierto o cerrado
    remote_tcp_string TCP Texto Respuesta textual de un servicio
    remote_tcp_inc TCP Incremental Contador leído por TCP
    remote_snmp SNMP Numérico Valor de un OID
    remote_snmp_inc SNMP Incremental Contador SNMP (tráfico, paquetes…)
    remote_snmp_string SNMP Texto OID de tipo cadena
    remote_snmp_proc SNMP Booleano Estado derivado de un OID
    remote_cmd Comando remoto Numérico Salida numérica de un comando
    remote_cmd_proc Comando remoto Booleano Éxito o fallo de un comando
    remote_cmd_string Comando remoto Texto Salida textual de un comando
    remote_cmd_inc Comando remoto Incremental Contador leído por comando
    wmi_generic_data WMI Numérico Valor numérico de una consulta WQL
    wmi_generic_proc WMI Booleano Resultado booleano de una consulta WQL
    wmi_generic_data_string WMI Texto Cadena devuelta por una consulta WQL
    wmi_generic_data_inc WMI Incremental Contador leído por WMI
    wmi_generic_data_inc_abs WMI Incremental absoluto Diferencia entre dos lecturas de un contador WMI
    generic_data Plugin Numérico Valor numérico devuelto por el plugin
    generic_proc Plugin Booleano Resultado correcto o fallido del plugin
    generic_data_string Plugin Texto Cadena devuelta por el plugin
    generic_data_inc Plugin Incremental Contador devuelto por el plugin, como tasa
    generic_data_inc_abs Plugin Incremental absoluto Contador devuelto por el plugin, como diferencia

    Un módulo de plugin no tiene familia propia de tipos: usa los tipos genéricos de la tabla y es quien crea el módulo quien elige el que corresponda a lo que devuelve el plugin.

    Los tipos booleanos (con sufijo _proc) se interpretan con la misma regla en todos los casos: 1 es estado correcto (normal) y 0 es estado crítico. Los incrementales guardan una tasa por segundo: la diferencia entre dos lecturas dividida por el tiempo transcurrido entre ellas, no el valor bruto del contador. Los incrementales absolutos (sufijo _inc_abs) guardan la diferencia entre dos lecturas, sin dividir por el tiempo. En ambos casos la primera lectura solo sirve de referencia: el servidor la descarta y el módulo no muestra dato hasta la segunda.

    Rendimiento, ajuste y diagnóstico¶

    La monitorización remota la reparten tres servidores, activados de fábrica: el servidor de red de alto rendimiento (ICMP y SNMP en lote), el servidor de red (TCP, comandos remotos y WMI, y los módulos SNMP que fallan de forma repetida) y el servidor Heavy (plugins remotos). Qué hace cada uno y cómo se reparten el trabajo se explica en Compatibilidad y migración a la nueva arquitectura de servidores. Cada uno tiene su propio número de hilos, que es lo primero que conviene subir cuando un tipo de comprobación empieza a llegar tarde. Los hilos, reintentos, tiempos de espera y rutas de binarios están en 9.3 · Referencia completa de configuración del servidor.

    Puertos que hace falta tener abiertos desde el servidor de Pandora FMS hasta los equipos monitorizados:

    Comprobación Puerto / protocolo
    ICMP Protocolo ICMP (sin puerto)
    SNMP get 161/udp
    WMI Los que use el propio WMI remoto en el equipo Windows de destino
    SSH (comandos remotos) 22/tcp, salvo que se configure otro

    Los traps SNMP van en sentido contrario, del equipo al servidor, por el 162/udp (ver Monitorización de traps SNMP).

    Cuando un módulo remoto se queda en desconocido, lo primero es repetir la misma comprobación a mano desde el servidor de Pandora FMS, no desde el puesto del administrador, con las mismas credenciales:

    snmpget -v 2c -c public 192.168.10.1 .1.3.6.1.2.1.1.3.0

    El diagnóstico completo (logs, comprobaciones por tipo de módulo y causas habituales) está en 9.13 · Troubleshooting con Pandora. El dimensionado de hilos y servidores para volúmenes grandes está en 9.14 · Análisis de volumetría y diseños para alta capacidad.
