    Exemples d'utilisation¶

    La référence dit quels paramètres accepte chaque opération ; ce chapitre montre comment les utiliser ensemble. Les exemples ont vraiment été exécutés, du début à la fin, sur une console de développement (version 8.0NG.805) avec des données de test supprimées ensuite. Les réponses sont réduites à l'essentiel, et vos identifiants et vos dates seront différents.

    Une large place est donnée aux filtres des listes, car la référence décrit les champs mais ne peut pas montrer comment ils se combinent, et c'est là que l'on perd le plus de temps.

    Avant de commencer¶

    Prérequis Détail
    Identifiant Un jeton d'API ou le access_token d'une session (chapitre 13.1).
    Outils curl et jq pour mettre en forme les réponses.
    Permissions Un utilisateur qui peut créer et supprimer des agents, des modules, des utilisateurs et des alertes. Les exemples d'écriture ont été exécutés avec admin.

    Tous les exemples partagent ces variables et cette fonction, qui ajoute l'en-tête d'authentification et le type de contenu :

    export PANDORA="http://localhost/pandora_console/api/v2"
export TOKEN="<jeton d'API ou access_token>"
api() { curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" "$@"; }

    Créer un agent et voir la réponse complète¶

    Le premier appel est aussi le plus révélateur : créer un agent et regarder tout ce qu'il renvoie. Seuls alias et idGroup sont nécessaires (plus bas, on voit ce qui se passe s'il en manque un).

    api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-first", "idGroup": 13}'

    La réponse est un 200 avec l'agent complet, pas seulement son identifiant. La voici telle quelle, sans filtre. L'API la renvoie sur une seule ligne ; elle est ici indentée pour être lisible :

    Les 53 champs de l'agent reviennent toujours.     Les autres exemples n'ont besoin que de l'identifiant, ou de quelques champs, et filtrent donc la réponse avec jq. La réponse complète est toujours celle-ci.

    Préparer les données pour les filtres¶

    Les exemples de filtres demandent quelques agents. Créez ces cinq-là ; tous portent docs-test dans l'alias pour les retrouver et les supprimer facilement :

    for spec in "docs-test-web-01 13 300" "docs-test-web-02 13 60" "docs-test-db-01 8 300" \
            "docs-test-net-01 9 120" "docs-test-old-01 2 300"; do
  set -- $spec
  api -X POST "$PANDORA/agent" -d "{\"alias\": \"$1\", \"idGroup\": $2, \"interval\": $3}" \
    | jq -c '{idAgent, alias, idGroup}'
done

    {"idAgent":9,"alias":"docs-test-web-01","idGroup":13}
{"idAgent":10,"alias":"docs-test-web-02","idGroup":13}
{"idAgent":11,"alias":"docs-test-db-01","idGroup":8}
{"idAgent":12,"alias":"docs-test-net-01","idGroup":9}
{"idAgent":13,"alias":"docs-test-old-01","idGroup":2}

    Lister avec pagination¶

    La liste simple est un GET. Avec sizePage vous demandez des pages de cette taille, et page commence à 0 :

    api "$PANDORA/agent/list?page=0&sizePage=2" \
  | jq -c '.paginationData, (.data[] | {idAgent, alias, idGroup})'

    {"totalPages":4,"sizePage":2,"currentPage":0,"totalRegisters":7,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"idAgent":13,"alias":"docs-test-old-01","idGroup":2}
{"idAgent":12,"alias":"docs-test-net-01","idGroup":9}

    Il y a sept agents (les cinq nouveaux plus les deux que fournit la console) et, avec des pages de deux, totalPages vaut 4. Sans tri, cette liste renvoie d'abord l'agent le plus récent.

    Filtrer par un champ et choisir les champs reçus¶

    Pour filtrer, on utilise POST avec le filtre dans le corps. Chaque champ que vous écrivez est une condition d'égalité exacte. Avec requestedFields vous ne recevez que les champs demandés, et la réponse pèse beaucoup moins que les 53 champs d'un agent complet :

    api -X POST "$PANDORA/agent/list?page=0&sizePage=10" \
  -d '{"idGroup": 13, "requestedFields": ["idAgent", "alias", "idGroup"]}' \
  | jq -c '.paginationData, .data[]'

    {"totalPages":1,"sizePage":10,"currentPage":0,"totalRegisters":2,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"idAgent":10,"alias":"docs-test-web-02","idGroup":13}
{"idAgent":9,"alias":"docs-test-web-01","idGroup":13}

    totalRegisters compte ce qui répond au filtre (2) et unfilteredTotalRegisters ce qu'il y aurait sans filtrer (7).

    Combiner des conditions avec des opérateurs¶

    Quand l'égalité ne suffit pas, fieldConditions accepte des opérateurs. Toutes les conditions sont reliées par ET. Cet exemple cherche les agents dont l'alias contient docs-test et qui sont dans les groupes 8 ou 9, triés par alias :

    api -X POST "$PANDORA/agent/list?page=0&sizePage=10&sortField=alias&sortDirection=ASC" \
  -d '{"requestedFields": ["idAgent", "alias", "idGroup"],
       "fieldConditions": [
         {"field": "alias", "operator": "LIKE", "value": "docs-test"},
         {"field": "idGroup", "operator": "IN", "value": [8, 9]}
       ]}' | jq -c '.paginationData, .data[]'

    {"totalPages":1,"sizePage":10,"currentPage":0,"totalRegisters":2,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"idAgent":11,"alias":"docs-test-db-01","idGroup":8}
{"idAgent":12,"alias":"docs-test-net-01","idGroup":9}

    Quels champs acceptent les conditions¶

    Tous les champs d'un agent ne fonctionnent pas dans fieldConditions (ni dans requestedFields, multipleSearch ou sortField) : seulement un sous-ensemble. interval, par exemple, non. Si vous en utilisez un qui n'est pas valable, la réponse est un 400 qui liste les champs valables :

    api -X POST "$PANDORA/agent/list" \
  -d '{"fieldConditions": [{"field": "interval", "operator": "=", "value": 300}]}'

    {"error":"Field interval is not a valid filter field. Valid fields: idAgent, name, alias, address, idGroup, disabled, idOs, lastContact, osName, osImagePath, normalCount, warningCount, criticalCount, unknownCount, notinitCount, totalCount, firedCount"}

    C'est une bonne astuce pour découvrir les champs de n'importe quelle liste : demandez-en un qui n'existe pas et lisez le message. En revanche, le filtre simple du corps ({"interval": 300}) accepte bien n'importe quel champ de l'entité, et un champ inexistant donne Field: <nom> is not a valid parameter.

    Comment se comporte chaque filtre¶

    Le tableau reprend ce qu'a renvoyé chaque filtre sur les cinq agents de test. Observez les deux premières lignes : le filtre simple ne cherche pas par morceaux.

    Corps de la requête Agents renvoyés
    {"alias": "docs-test-web-01"} docs-test-web-01
    {"alias": "docs-test-web"} Aucun : c'est de l'égalité exacte, pas un préfixe.
    {"idGroup": 13} docs-test-web-01, docs-test-web-02
    {"freeSearch": "web"} docs-test-web-01, docs-test-web-02 (correspondance partielle sur plusieurs champs)
    {"multipleSearch": {"field": "idGroup", "data": [8, 9]}} docs-test-db-01, docs-test-net-01 (l'une des valeurs)
    {"multipleSearchString": {"field": "alias", "data": ["docs-test-web-01", "docs-test-net-01"]}} docs-test-net-01, docs-test-web-01
    Condition alias LIKE web docs-test-web-01, docs-test-web-02 : il contient le texte.
    Condition alias LIKE docs-test-web% Aucun : le % n'est pas un joker, il est cherché tel quel.
    Condition alias REGEXP ^docs-test-web docs-test-web-01, docs-test-web-02
    Condition idGroup IN [8, 9] docs-test-db-01, docs-test-net-01
    Condition idGroup BETWEEN [8, 9] docs-test-db-01, docs-test-net-01
    Condition idGroup gt 9 (et alias LIKE docs-test) docs-test-web-01, docs-test-web-02

    LIKE est le point qui prête le plus à confusion : il signifie « contient », pas le LIKE de SQL, et il n'est pas nécessaire (ni utile) d'entourer le texte de %.

    Trier et paginer¶

    sortField et sortDirection (ASC ou DESC, sans distinguer majuscules et minuscules) vont dans l'adresse. Cette requête demande la deuxième page (page=1) de deux éléments, triés par alias du plus grand au plus petit :

    api -X POST "$PANDORA/agent/list?page=1&sizePage=2&sortField=alias&sortDirection=DESC" \
  -d '{"requestedFields": ["alias"],
       "fieldConditions": [{"field": "alias", "operator": "LIKE", "value": "docs-test"}]}' \
  | jq -c '.paginationData, .data[]'

    {"totalPages":3,"sizePage":2,"currentPage":1,"totalRegisters":5,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"alias":"docs-test-old-01"}
{"alias":"docs-test-net-01"}

    Pour parcourir un ensemble par fenêtres arbitraires, utilisez le mode par décalage (limit et offset, dans le corps). Ici, deux éléments à partir du deuxième ; notez que currentPage devient null et que limit et offset apparaissent :

    api -X POST "$PANDORA/agent/list" \
  -d '{"limit": 2, "offset": 1, "requestedFields": ["alias"],
       "fieldConditions": [{"field": "alias", "operator": "LIKE", "value": "docs-test"}]}' \
  | jq -c '.paginationData, .data[]'

    {"totalPages":3,"sizePage":2,"currentPage":null,"totalRegisters":5,"totalRegistersPage":2,"unfilteredTotalRegisters":7,"limit":2,"offset":1}
{"alias":"docs-test-net-01"}
{"alias":"docs-test-db-01"}

    Filtrer les événements¶

    Les événements n'utilisent pas fieldConditions : ils ont leurs propres filtres (severity, status, search, idAgent, eventType…) et une option à eux, dateRange. Celle-ci cherche les événements critiques et nouveaux des dernières 24 heures, du plus récent au plus ancien :

    api -X POST "$PANDORA/event/list?page=0&sizePage=2&sortField=idEvent&sortDirection=DESC" \
  -d '{"severity": [4], "status": "new", "dateRange": "{\"preset\": {\"value\": \"last_24_hours\"}}"}' \
  | jq -c '.paginationData, (.data[] | {idEvent, severity, status, event})'

    {"totalPages":7,"sizePage":2,"currentPage":0,"totalRegisters":13,"totalRegistersPage":2,"unfilteredTotalRegisters":13}
{"idEvent":30,"severity":"CRITICAL","status":"NEW","event":"Pandora DB maintenance tool has never been run."}
{"idEvent":29,"severity":"CRITICAL","status":"NEW","event":"Pandora DB maintenance tool has never been run."}

    Trois détails qui ne se devinent pas :

    • dateRange est un texte qui contient du JSON, pas une date. D'où les guillemets échappés de l'exemple. Une valeur qui n'est pas du JSON donne Invalid date range format. Must be valid JSON.
    • La gravité se filtre avec une liste de nombres ([4] est critique, [0] maintenance) ; à la lecture, l'événement porte le nom (CRITICAL).
    • L'état accepte new, validated, inprocess, not_validated, not_in_process et all.

    dateRange accepte une période prédéfinie ou un début et une fin :

    Forme Exemple
    Prédéfinie {"preset": {"value": "last_24_hours"}}. Valeurs : today, this_week, this_month, last_15_minutes, last_30_minutes, last_1_hours, last_24_hours, last_7_days, last_30_days, last_60_days, last_90_days, last_1_year.
    Relative {"start": {"mode": "relative", "value": 2, "unit": "hours"}, "end": {"mode": "now"}}. Unités : seconds, minutes, hours, days, weeks, months, years.
    Absolue {"start": {"mode": "absolute", "value": "2020-01-01 00:00:00"}, "end": {"mode": "absolute", "value": "2020-12-31 23:59:59"}}

    Une valeur de preset inconnue donne Invalid date range values.

    Créer, lire, modifier et supprimer un agent¶

    Créer un agent exige alias et idGroup ; s'il en manque un, le 400 dit lequel :

    api -X POST "$PANDORA/agent" -d '{"idGroup": 13}'
api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-crud"}'

    {"error":"Agent alias is missing"}
{"error":"Agent group is missing"}

    Avec les deux, l'agent est créé. La réponse est celle que vous avez déjà vue dans le premier exemple, l'agent complet ; ici on ne garde que son identifiant pour les appels suivants :

    ID=$(api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-crud", "idGroup": 13}' | jq -r .idAgent)

    PUT ne modifie que les champs que vous envoyez ; le reste reste comme avant :

    api -X PUT "$PANDORA/agent/$ID" -d '{"comments": "created from the docs", "interval": 120}' \
  | jq -c '{idAgent, alias, comments, interval, idGroup}'

    {"idAgent":14,"alias":"docs-test-crud","comments":"created from the docs","interval":120,"idGroup":13}

    Le supprimer répond 200 avec le corps null, et le redemander donne un 404 :

    api -X DELETE "$PANDORA/agent/$ID" -w 'HTTP %{http_code}\n'
api "$PANDORA/agent/$ID" -w ' HTTP %{http_code}\n'

    nullHTTP 200
{"error":" not found"} HTTP 404

    Créer un module¶

    Un module dépend d'un agent. Les champs obligatoires sont idAgent, name, idModule (le type de serveur du module : 1 dans cet exemple) et idModuleType (le type de donnée : 1 est generic_data ; GET /moduleType/list montre les autres). Sans idModule, la réponse est Unsupported module and module type combination.

    AG=$(api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-mod-agent", "idGroup": 13}' | jq -r .idAgent)
api -X POST "$PANDORA/agentModule" \
  -d "{\"idAgent\": $AG, \"name\": \"docs-test-module\", \"idModule\": 1, \"idModuleType\": 1}" \
  | jq -c '{idAgentModule, idAgent, idModuleType, name}'

    {"idAgentModule":92,"idAgent":15,"idModuleType":1,"name":"docs-test-module"}

    Pour retrouver les modules d'un agent, une liste filtrée ; et pour savoir où il en est, son état :

    MOD=$(api -X POST "$PANDORA/agentModule/list" \
  -d "{\"idAgent\": $AG, \"requestedFields\": [\"idAgentModule\"]}" | jq -r '.data[0].idAgentModule')
api "$PANDORA/agentModule/$MOD/agentModuleState" | jq -c '{idAgentModule, status, data}'

    {"idAgentModule":92,"status":4,"data":""}

    L'état 4 signifie « sans données », ce qui est normal pour un module qui vient d'être créé et n'en a pas encore reçu. Supprimer l'agent (DELETE /agent/$AG) supprime aussi ses modules.

    Créer un utilisateur¶

    On voit ici clairement que le swagger ne marque pas tous les champs obligatoires : la référence ne signale que fullName, mais le serveur en exige davantage. Les messages réclament chacun à leur tour (le premier, sans idUser ; le deuxième, sans password ; le troisième, sans passwordValidate) :

    api -X POST "$PANDORA/user" -d '{"fullName": "Docs Test"}'
api -X POST "$PANDORA/user" -d '{"idUser": "docs-test-user", "fullName": "Docs Test"}'
api -X POST "$PANDORA/user" \
  -d '{"idUser": "docs-test-user", "fullName": "Docs Test", "password": "Docs-test-Pass-1"}'

    {"error":"IdUser is missing"}
{"error":"Password is missing"}
{"error":"PasswordValidate is missing"}

    Il faut quatre champs : idUser, fullName, password et passwordValidate (le mot de passe répété). La référence n'en marque qu'un ; c'est le serveur qui dit la vérité :

    api -X POST "$PANDORA/user" \
  -d '{"idUser": "docs-test-user", "fullName": "Docs Test", "password": "Docs-test-Pass-1", "passwordValidate": "Docs-test-Pass-1"}' \
  | jq -c '{idUser, fullName, isAdmin}'

    {"idUser":"docs-test-user","fullName":"Docs Test","isAdmin":false}

    Créer une action d'alerte¶

    Une action d'alerte a besoin d'une commande. On crée d'abord la commande, puis l'action qui l'utilise :

    CMD=$(api -X POST "$PANDORA/alert/command" -d '{"name": "docs-test-command", "command": "echo _field1_"}' | jq -r .idAlertCommand)
ACT=$(api -X POST "$PANDORA/alert/action" -d "{\"name\": \"docs-test-action\", \"idAlertCommand\": $CMD}" | jq -r .idAlertAction)

    Comme les deux renvoient leur identifiant, on peut les enchaîner. Pour nettoyer, supprimez d'abord l'action, puis la commande.

    Nettoyer¶

    Les exemples laissent des données de test. Toutes portent docs-test dans le nom, donc on les retrouve avec un filtre et on les supprime :

    for id in $(api -X POST "$PANDORA/agent/list" \
  -d '{"requestedFields": ["idAgent"], "fieldConditions": [{"field": "alias", "operator": "LIKE", "value": "docs-test"}]}' \
  | jq -r '.data[].idAgent'); do api -X DELETE "$PANDORA/agent/$id"; done

    Créer ou supprimer des agents génère aussi des événements système (Agent [...] created by API). On les cherche avec {"search": "docs-test"} dans POST /event/list et on les supprime avec DELETE /event/{idEvent}.

    Les erreurs rencontrées¶

    Code Message Cause
    400 Agent alias is missing Un champ obligatoire manque (le message dit lequel).
    400 Field interval is not a valid filter field. Valid fields: … Un champ qui n'admet pas cette option ; le message liste les champs valables.
    400 Field: nope is not a valid parameter Un champ du corps qui n'existe pas dans l'entité.
    400 Operator foo is not a valid filter operator Opérateur inconnu.
    400 Field condition operator IN expects an array value IN et NOT IN demandent une liste.
    400 Field sizePage must be an integer greater than or equal to 1 Pagination non valable.
    400 limit/offset cannot be combined with page/sizePage Les deux modes de pagination ont été mélangés.
    400 Node identity filters can only be used on a metaconsole serverId a été utilisé sur une console autonome.
    404 not found L'élément n'existe pas (le message commence par une espace).

    Les autres codes (401, 403, 429, 500) se trouvent dans Conventions de l'API.
