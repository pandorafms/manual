# Premiers pas et authentification

Tout ce que vous faites dans la console à la souris (créer un agent, consulter un événement, affecter une alerte) peut aussi être fait par un programme. C'est la raison d'être de l'**API v2** de Pandora FMS : une interface HTTP qui parle JSON et que n'importe quel script, intégration ou outil externe peut utiliser sans passer par l'écran.

Avant d'appeler quoi que ce soit, il faut répondre à une question toute simple et décisive : qui appelle ? L'API ne répond pas aux inconnus, et les deux façons de se présenter (une session utilisateur ou un jeton d'API) ont des règles, des durées de vie et des usages différents. Ce chapitre les explique. Les conventions de tous les jours (pagination, filtres, erreurs) sont dans [Conventions de l'API](13.2-convenciones-de-la-api.md), et les endpoints, un par un, dans la [référence](13.4-referencia-de-endpoints/index.md).

## Ce dont vous avez besoin

| Prérequis | Détail |
|---|---|
| Adresse de l'API | Elle dépend de la console, sous `api/v2`. Si la console est à `https://pandora.example.com/pandora_console`, l'API est à `https://pandora.example.com/pandora_console/api/v2`. |
| Utilisateur | Un utilisateur de la console. Les requêtes s'exécutent avec son identité : il ne voit et ne modifie que ce que cet utilisateur peut voir et modifier. |
| Origine autorisée | Si la console limite l'API par adresse IP, la vôtre doit figurer dans la liste ; sinon la réponse est un `401` avec le message `IP <adresse> is not in ACL list`. |
| Connexion sécurisée | Utilisez HTTPS. Les identifiants et le jeton circulent à chaque requête. |

Les exemples du chapitre utilisent la variable `PANDORA` pour l'adresse de l'API :

```sh
export PANDORA="https://pandora.example.com/pandora_console/api/v2"
```

## Comment parler à l'API

- Le corps des requêtes s'envoie en **JSON**, avec l'en-tête `Content-Type: application/json`.
- Les réponses sont en JSON.
- Les erreurs ont toujours la même forme : `{"error": "message"}`, avec le code HTTP correspondant. Le tableau des codes se trouve dans [Conventions de l'API](13.2-convenciones-de-la-api.md#erreurs).

## Deux façons de s'identifier

| | Session utilisateur | Jeton d'API |
|---|---|---|
| S'obtient avec | `POST /auth/login` (utilisateur et mot de passe) | `POST /token`, avec une session ou avec un autre jeton |
| Durée | Le jeton d'accès dure **30 minutes** ; la session se renouvelle tant qu'il y a de l'activité et se termine après **7 jours sans utilisation** | Celle que vous fixez : sans date limite, il n'expire pas |
| Double facteur | Résolu à la connexion | N'intervient pas : le jeton est déjà l'identifiant |
| Sert pour | Une personne ou une application qui ouvre une session | Scripts, intégrations et tâches automatiques |

La règle pratique : si quelqu'un tape son mot de passe devant l'écran, une session ; si c'est une machine qui l'exécute à trois heures du matin, un jeton.

## Avec une session utilisateur

### Ouvrir la session

```sh
curl -s -c cookies.txt -X POST "$PANDORA/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"id_user": "admin", "password": "<mot de passe>"}'
```

| Champ | Obligatoire | Détail |
|---|---|---|
| `id_user` | Oui | Identifiant de l'utilisateur. |
| `password` | Oui | Mot de passe. |
| `isMobile` | Non | `true` si la session est celle d'une application mobile. |
| `deviceInfo` | Non | Données de l'appareil (identifiant, plateforme, version de l'application, langue, fuseau horaire). |

La réponse contient ce qu'il faut pour continuer :

| Champ | Ce que c'est |
|---|---|
| `status` | État de la connexion : `authenticated` si tout s'est bien passé, ou `mfa_required` si le second facteur est nécessaire (voir plus bas). |
| `access_token` | Le jeton que vous enverrez avec chaque requête. |
| `access_expires_in` | Durée de vie du jeton d'accès en secondes : `1800`. |
| `session_expires_at` | Date à laquelle la session se termine s'il n'y a pas d'activité. |
| `id_user` | L'utilisateur qui a ouvert la session. |

L'autre moitié de l'identifiant n'apparaît pas dans le corps : le serveur dépose le **jeton de renouvellement** dans un cookie nommé `pandora_refresh`, marqué `HttpOnly` et `SameSite=Strict` (et `Secure` si vous utilisez HTTPS), valable sept jours. Un script en ligne de commande ne le voit que s'il le conserve ; c'est pourquoi l'exemple utilise `-c cookies.txt`.

### Double facteur

Si le compte a le double facteur, la connexion ne renvoie pas de jetons : elle renvoie `status: mfa_required` et un `mfa_token` de courte durée (**180 secondes**). Vous la terminez avec le code à six chiffres :

```sh
curl -s -c cookies.txt -X POST "$PANDORA/auth/login/mfa" \
  -H "Content-Type: application/json" \
  -d '{"mfa_token": "<mfa_token>", "code": "<code à six chiffres>"}'
```

Cinq codes erronés invalident le `mfa_token`, et il faut recommencer depuis la connexion.

### Utiliser, renouveler et fermer la session

Le `access_token` s'envoie dans l'en-tête `Authorization`, comme expliqué [plus bas](#envoyer-le-jeton). Lorsqu'il expire (au bout de 30 minutes), inutile de redemander le mot de passe :

```sh
curl -s -b cookies.txt -c cookies.txt -X POST "$PANDORA/auth/refresh"
```

La réponse a la même forme que celle de la connexion. Le renouvellement **fait tourner** la session : les jetons d'accès et de renouvellement précédents cessent de valoir (l'ancien jeton d'accès reçoit un `401`) et vous recevez une nouvelle paire. Sans le cookie, le renouvellement répond `401` avec `Session expired`.

Pour fermer et révoquer la session, `POST /auth/logout` : il répond `{"status": "logged_out"}` et, à partir de là, ni le jeton d'accès ni le renouvellement ne servent.

!!! note "Les échecs de connexion sont limités"
    `/auth/login` et `/auth/refresh` répondent `429` avec un en-tête `Retry-After` (secondes d'attente) quand la limite est dépassée :

    | Règle | Limite | Blocage |
    |---|---|---|
    | Même adresse et même utilisateur | 5 échecs en 10 minutes | 10 minutes |
    | Même adresse, n'importe quel utilisateur | 20 échecs en 10 minutes | 10 minutes |
    | Même utilisateur, n'importe quelle adresse | 20 échecs en 30 minutes | 15 minutes |
    | Renouvellements depuis la même adresse | 60 en 1 minute | 1 minute |

    Un script qui réessaie sans regarder `Retry-After` ne réussit qu'à se bloquer plus longtemps. Lors des essais, la sixième tentative échouée consécutive du même utilisateur depuis la même adresse a reçu `429` avec `Retry-After: 600`. Un mot de passe incorrect, avant la limite, répond `401` avec `Invalid credentials`.

## Avec un jeton d'API

Un jeton d'API est l'identifiant des processus automatiques : il ne dépend d'aucun cookie, il n'y a pas de double facteur à résoudre et il dure ce que vous décidez.

Il se crée avec `POST /token`. Comme la création exige d'être identifié, le premier jeton vient d'une session : vous ouvrez une session, vous utilisez le `access_token` pour créer le jeton et, à partir de là, le script n'a plus besoin du mot de passe.

```sh
curl -s -X POST "$PANDORA/token" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"label": "sauvegarde-nocturne"}'
```

| Champ | Obligatoire | Détail |
|---|---|---|
| `label` | Oui | Nom pour le reconnaître dans la liste. |
| `validity` | Non | Date jusqu'à laquelle il est valable, au format `AAAA-MM-JJ HH:MM:SS` (par exemple, `2027-01-01 00:00:00`). Un autre format donne un `400`. Vide : il n'expire pas. |
| `idUser` | Non | Propriétaire. Par défaut, l'utilisateur qui le crée. |

La réponse inclut le jeton complet dans le champ `token`, sous la forme `<identifiant>-<secret>`. **C'est la seule fois où vous le verrez** : la console ne conserve pas le secret tel quel, seulement une empreinte pour le vérifier. Gardez-le là où vous gardez le reste de vos identifiants, jamais dans le code du script.

Pour les gérer : `GET /token/list` les liste, `PUT /token/{id}` les modifie et `DELETE /token/{id}` les révoque. Dans la liste, le champ `token` apparaît toujours vide (le secret ne s'affiche plus jamais) et vous verrez aussi, avec l'étiquette `API session`, les identifiants de vos sessions, d'accès comme de renouvellement. Un jeton révoqué cesse de valoir à la requête suivante : révoquer celui d'un script compromis est donc immédiat. Chaque utilisation met à jour la date de dernière utilisation, qui apparaît dans la liste et aide à repérer les jetons morts.

## Envoyer le jeton

Les deux types d'identifiant se présentent de la même façon, dans l'en-tête `Authorization` :

```sh
curl -s "$PANDORA/agent/list?page=0&sizePage=10" \
  -H "Authorization: Bearer <jeton>"
```

Avec une session, `<jeton>` est le `access_token` ; avec un jeton d'API, la valeur du champ `token`.

S'il manque, s'il est mal formé ou s'il a expiré, la réponse est `401` :

| Réponse | Cause |
|---|---|
| `401`, `You need to be authenticated to perform this action` | L'en-tête manque, le jeton n'existe pas, il a expiré ou le secret est incorrect. L'API ne distingue pas ces cas, volontairement. Cela arrive aussi si vous envoyez un jeton de renouvellement ou de double facteur : seuls les jetons d'accès fonctionnent en dehors de `/auth`. |
| `401`, `IP <adresse> is not in ACL list` | L'adresse d'origine ne figure pas dans la liste de la console. |
| `401`, `Invalid credentials` | Utilisateur ou mot de passe incorrects sur `/auth/login`. |
| `401`, `Session expired` | `/auth/refresh` sans cookie de renouvellement, ou avec une session déjà fermée ou expirée. |
| `403`, `This user account has been disabled` | L'utilisateur du jeton est désactivé. |

### Jetons Pandora AI

Les jetons Pandora AI sont un cas à part : la console les crée et les gère, et on ne peut ni les créer, ni les modifier, ni les supprimer par l'API. Si vous appelez avec l'un d'eux, **chaque requête** doit porter exactement un en-tête `X-Pandora-AI-Session` avec un identifiant de session (texte UTF-8 non vide, de 255 caractères au plus, sans caractères de contrôle). S'il manque ou n'est pas valide, la réponse est `400`, même si le jeton est correct. L'identifiant est conservé dans le journal d'audit de cette requête. Les jetons ordinaires ignorent l'en-tête.
