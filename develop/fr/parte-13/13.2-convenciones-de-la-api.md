# Conventions de l'API : pagination, filtres et erreurs

Une API de centaines d'opérations serait ingérable si chacune faisait les choses à sa façon. Celle de Pandora FMS ne le fait pas : presque toutes les listes paginent, filtrent et trient de la même manière, et toutes les erreurs ont la même forme. Apprendre ces règles une fois sert pour le reste de la référence.

Ce chapitre suppose que vous savez déjà vous identifier ([Premiers pas et authentification](13.1-primeros-pasos-y-autenticacion.md)). Ce qui suit est ce qu'il faut savoir pour demander des données avec discernement et pour comprendre ce que l'API vous dit quand quelque chose se passe mal. Tout ce qui est affirmé ici a été vérifié sur une console réelle ; les exemples complets se trouvent dans [Exemples d'utilisation](13.3-ejemplos-de-uso.md).

## Listes : `GET` et `POST`

Chaque entité avec une liste offre normalement deux routes de même nom :

| Route | À quoi elle sert |
|---|---|
| `GET /…/list` | Liste simple. La pagination et le tri vont dans l'adresse, comme paramètres (`?page=0&sizePage=50`). |
| `POST /…/list` | Liste avec filtres. Les filtres vont dans le corps JSON. La pagination et le tri peuvent aussi être passés comme paramètres de l'adresse. |

Le corps d'un `POST …/list` est le filtre propre de l'entité : chaque champ que vous renseignez est une condition d'**égalité exacte**, et toutes se combinent avec **ET**. Les champs disponibles sont ceux de l'entité, et chaque page de la référence les liste dans son tableau du corps de la requête. Un champ qui n'existe pas donne un `400` (`Field: nope is not a valid parameter`).

## Ce que renvoie une liste

Les listes paginées renvoient un objet en deux parties : les données et les informations de pagination.

```json
{
  "paginationData": {
    "totalPages": 3,
    "sizePage": 50,
    "currentPage": 0,
    "totalRegisters": 120,
    "totalRegistersPage": 50,
    "unfilteredTotalRegisters": 120
  },
  "data": [ ]
}
```

| Champ de `paginationData` | Ce que c'est |
|---|---|
| `totalPages` | Nombre de pages avec le filtre appliqué. |
| `sizePage` | Éléments par page. |
| `currentPage` | Page courante, en comptant à partir de 0. `null` si vous utilisez `limit` et `offset`. |
| `totalRegisters` | Éléments qui répondent au filtre. |
| `totalRegistersPage` | Éléments renvoyés dans cette page. |
| `unfilteredTotalRegisters` | Éléments qu'il y aurait sans filtrer. Dans certaines listes, comme celle des événements, il coïncide avec `totalRegisters`. |
| `limit`, `offset` | Seulement si vous utilisez ce mode de pagination ; voir plus bas. |

Les valeurs de l'exemple sont indicatives. Si vous ne demandez pas de pagination, `totalPages` vaut 0 et `sizePage` et `currentPage` sont `null`.

## Pagination

La pagination se contrôle avec `page` et `sizePage` :

| Paramètre | Détail |
|---|---|
| `page` | Numéro de page, **à partir de 0**. S'il est omis, c'est la première. |
| `sizePage` | Éléments par page, au minimum 1. |

!!! warning "Sans `sizePage`, il n'y a pas de limite"
    Si vous n'indiquez pas `sizePage`, la liste renvoie **tout** ce qui répond au filtre, en une seule réponse, même si vous indiquez `page`. Sur une grande console, cela peut faire beaucoup. Demandez toujours `sizePage`.

`page` et `sizePage` peuvent être passés dans l'adresse ou dans le corps du filtre d'un `POST …/list`. Demander une page qui n'existe pas n'est pas une erreur : cela renvoie `data` vide avec un `200`.

Il existe un second mode, par décalage, que l'on indique dans le corps : `limit` (combien d'éléments ; `0` n'en renvoie aucun) et `offset` (combien en sauter, 0 par défaut ; sans `limit`, il renvoie tout le reste). Il est utile pour parcourir un ensemble par fenêtres arbitraires. Les deux modes **ne se mélangent pas**, même si l'un est dans le corps et l'autre dans l'adresse : c'est un `400` (`limit/offset cannot be combined with page/sizePage`). Un `page` négatif ou un `sizePage` inférieur à 1 donnent aussi un `400` (`Field sizePage must be an integer greater than or equal to 1`).

## Tri

| Paramètre | Détail |
|---|---|
| `sortField` | Champ de tri. Les valeurs valables dépendent de l'entité ; une valeur non valable donne un `400` qui **liste les valeurs valables**. |
| `sortDirection` | `ASC` ou `DESC`, sans distinguer majuscules et minuscules. |

Si vous n'indiquez pas d'ordre, chaque liste utilise le sien (celle des agents renvoie d'abord le plus récent). Si vous avez besoin d'un ordre stable, indiquez `sortField`.

## Filtres avancés

En plus des champs de l'entité, le corps d'un `POST …/list` accepte presque toujours ces options communes. Presque, car certaines listes ont leurs propres filtres et ne les admettent pas (les événements, par exemple : voir [Exemples d'utilisation](13.3-ejemplos-de-uso.md#filtrer-les-evenements)). Le tableau du corps de chaque liste dans la référence indique lesquelles elle accepte :

| Option | Ce qu'elle fait |
|---|---|
| `requestedFields` | Liste des champs que vous voulez recevoir. Si vous ne les demandez pas tous, le serveur n'interroge que ceux-là. Chaque nom doit être un champ valide de l'entité. L'ancienne option `fields` reste acceptée. |
| `freeSearch` | Texte recherché dans plusieurs champs à la fois, pour les entités qui le permettent. |
| `multipleSearch` | Plusieurs valeurs **numériques** pour un champ : `{"field": "…", "data": [1, 2, 3]}`. |
| `multipleSearchString` | La même chose avec des valeurs **de texte**. |
| `fieldConditions` | Liste de conditions avec un opérateur, reliées par **ET** : `{"field": "…", "operator": "…", "value": …}`. |

**Ces options n'acceptent pas tous les champs de l'entité**, seulement un sous-ensemble : pour les agents, par exemple, `interval` sert pour le filtre simple du corps mais pas pour `fieldConditions`. Si vous utilisez un champ non valable, le `400` liste les champs valables ; c'est le moyen le plus rapide de les découvrir.

Les opérateurs de `fieldConditions` ne distinguent pas les majuscules des minuscules, et presque tous ont un alias :

| Opérateur | Alias |
|---|---|
| `=` | `eq` |
| `!=` | `ne` |
| `<>` | (aucun) |
| `>`, `>=` | `gt`, `gte` |
| `<`, `<=` | `lt`, `lte` |
| `LIKE`, `NOT LIKE` | `like`, `not_like` |
| `REGEXP`, `NOT REGEXP` | `regex`, `not_regex` |
| `IN`, `NOT IN` | `in`, `not_in` (la valeur doit être une liste) |
| `BETWEEN`, `NOT BETWEEN` | `between`, `not_between` |
| `IS NULL`, `IS NOT NULL` | `is_null`, `is_not_null` |
| `IS EMPTY`, `IS NOT EMPTY` | `is_empty`, `is_not_empty` |

Un opérateur absent du tableau donne un `400` (`Operator … is not a valid filter operator`) ; utiliser `IN` ou `NOT IN` sans liste aussi. Un point prête à confusion : **`LIKE` signifie « contient »**, pas le `LIKE` de SQL. Le `%` n'est pas un joker, il est cherché comme du texte : `LIKE` avec `web` trouve `docs-test-web-01`, et avec `docs-test-web%` il ne trouve rien.

## Consoles et nœuds

Sur une console autonome, inutile d'y penser. Dans un environnement avec **Command Center**, certaines ressources appartiennent à un nœud précis, et le paramètre `serverId` indique lequel. Qu'il soit obligatoire dépend de l'opération (par exemple, celles qui modifient des ressources fédérées l'exigent et certaines listes agrégées l'acceptent en option) ; la description de chaque paramètre `serverId` dans la référence le précise.

## Créer, modifier et supprimer

Les opérations d'écriture suivent le même schéma pour presque toutes les entités :

| Opération | Ce qu'elle fait | Réponse |
|---|---|---|
| `POST /entité` | Crée. | `200` avec l'objet créé et son identifiant. Ce que vous n'indiquez pas prend sa valeur par défaut. |
| `PUT /entité/{id}` | Modifie **uniquement les champs que vous envoyez** ; le reste ne change pas. | `200` avec l'objet modifié. |
| `DELETE /entité/{id}` | Supprime. | `200` avec le corps `null`. S'il n'existe plus, `404`. |

La référence ne marque comme obligatoires que les champs que déclare le swagger, et parfois le serveur en exige davantage (créer un utilisateur demande quatre champs et la référence n'en marque qu'un). S'il en manque un, le `400` dit lequel, comme `Agent alias is missing`.

## Erreurs

Toutes les erreurs renvoient le même corps, avec le code HTTP correspondant :

```json
{ "error": "message" }
```

| Code | Quand cela arrive | Que faire |
|---|---|---|
| `400` | La requête est mal formée : un corps qui n'est pas du JSON ou pas du type attendu, un paramètre qui n'est pas un entier, des bornes de pagination incorrectes, un opérateur de filtre non valide. | Lisez le message : il indique quel champ ou paramètre échoue. |
| `401` | Il n'y a pas d'identifiant valide, ou votre adresse ne figure pas dans la liste d'accès de l'API. | Vérifiez le jeton et l'en-tête `Authorization` ([chapitre 13.1](13.1-primeros-pasos-y-autenticacion.md#envoyer-le-jeton)). |
| `403` | L'utilisateur est désactivé ou n'a pas la permission pour cette opération. | Vérifiez l'utilisateur du jeton et ses permissions. |
| `404` | L'élément que vous nommez n'existe pas. | Vérifiez l'identifiant. |
| `429` | Trop de tentatives sur `/auth/*`. Il porte un en-tête `Retry-After`. | Attendez ce nombre de secondes. |
| `500` | Défaillance interne. Le message est toujours `Internal server error` : l'API ne divulgue pas de détails internes. | Consultez le journal d'erreurs du serveur web de la console, où le détail est conservé. |

Les défaillances d'un service externe dont l'opération a besoin (par exemple, l'envoi d'un e-mail) renvoient `502` ou `503` avec un message qui, lui, dit ce qui s'est passé.

## Comment lire la référence

La [référence des endpoints](13.4-referencia-de-endpoints/index.md) est organisée par domaines (agents, modules, alertes, événements, politiques…) et chaque opération se présente de la même façon :

| Partie | Ce qu'elle contient |
|---|---|
| Index | Chaque page commence par un tableau de toutes ses opérations (méthode, route et résumé), reliées à leur détail. |
| En-tête | La méthode, avec sa propre couleur, et la route, par exemple `GET /agent/{idAgent}`. |
| Description | Ce qu'elle fait et les conditions qui comptent. |
| Paramètres | Nom, où il se place (`path`, `query`), type, s'il est obligatoire et sa description. |
| Corps de la requête | Les champs du JSON. Les objets imbriqués s'affichent avec le chemin complet (`champ.sous-champ`) et les listes avec `[]`. Les champs que vous envoyez sont toujours ouverts. En dessous figure un exemple JSON, replié, généré à partir du schéma avec des valeurs de remplissage : il montre la forme du corps, pas un contenu à copier tel quel. Si plusieurs opérations de la page utilisent le même schéma, ses champs sont décrits une seule fois dans la section *Models* à la fin et les opérations y renvoient. |
| Réponse | Les champs de la réponse correcte, repliés : ils s'ouvrent au clic. |
| Erreurs | Les codes que cette opération peut renvoyer ; leur signification est celle du tableau ci-dessus. |

Une colonne **Required** vide signifie que la spécification ne marque pas le champ comme obligatoire ; le serveur peut l'exiger malgré tout.

Les réponses réelles s'écartent du tableau sur trois points, vérifiés sur une console réelle :

- Les valeurs d'énumération sont renvoyées en **majuscules** (`LEARNING`, `NEW`, `WARNING`) alors que la référence les montre en minuscules. Les requêtes acceptent les deux formes.
- Les champs qui sont seulement envoyés (par exemple, `password` à la création d'un utilisateur) figurent dans le tableau de la réponse mais ne sont pas renvoyés.
- Un champ que le tableau ne marque pas comme `nullable` peut revenir à `null` (par exemple, les compteurs d'un agent tout juste créé). La référence est en anglais et se régénère à chaque version de l'API.
