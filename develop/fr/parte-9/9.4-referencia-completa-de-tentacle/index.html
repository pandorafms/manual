    Référence complète de Tentacle (serveur et client)¶

    Référence technique brute du protocole Tentacle et de ses deux implémentations (Go et Perl). Elle se consulte, elle ne se lit pas d'un bout à l'autre ; le reste du site renvoie ici pour toute option ou tout jeton du binaire Tentacle. Pour les jetons de connexion de l'EndPoint (server_ip, server_opts…), voir 9.1 · Référence complète de configuration de l'EndPoint ; pour les jetons du serveur de synchronisation qui utilisent Tentacle en dessous, voir 9.3 · Référence complète de configuration du serveur.

    Introduction¶

    Tentacle est à la fois un protocole de transfert de fichiers et l'outil client/serveur qui le parle. Il a remplacé SCP/FTP en 2008 comme méthode d'envoi par défaut des XML de données des EndPoint, et le port IANA tcp/41121 lui est attribué.

    Dans le produit, Tentacle transporte : les XML de données qu'envoie chaque EndPoint, les fichiers de configuration distante, les collections, les commandes distantes (RMM), le trafic des serveurs satellite, le proxy Tentacle et l'instance dédiée de RMM.

    Il existe deux implémentations du même protocole, avec les mêmes options de ligne de commande (même lettre, même signification) :

    • Go (binaire statique tentacle_server/tentacle_client, sans dépendances à l'exécution) : c'est l'implémentation par défaut dans les paquets de Linux (serveur, EndPoint et serveur satellite) et la recommandée. Elle traite chaque connexion avec une goroutine au lieu du thread en attente active de Perl.
    • Perl (tentacle_server v0.6.2, tentacle_client v0.4.0) : l'implémentation de référence historique du protocole. C'est celle que les paquets de Windows continuent d'embarquer, compilée en .exe (EndPoint et serveur satellite).

    Elles sont interchangeables : un client Perl parle à un serveur Go et inversement, car les deux implémentent le même protocole avec les mêmes règles.

    Le chapitre s'organise en trois blocs : le protocole lui-même (indépendant de l'implémentation), le client et le serveur.

    1. Le protocole Tentacle¶

    La conception est volontairement simple :

    • La connexion est toujours lancée par le client ; le serveur n'envoie jamais de données avant que le client ne les demande ou ne les confirme.
    • Les commandes sont du texte terminé par un saut de ligne. Il n'y a ni salutation ni négociation de version : le premier message envoyé par le client est déjà une commande.
    • Quand une commande annonce une taille (SIZE <n>), un bloc binaire de exactement ce nombre d'octets suit, sans remplissage ni en-tête supplémentaire.

    Table des commandes¶

    Commande Sens Réponse correcte Erreurs
    SEND <fichier> SIZE <n> Client → serveur SEND OK (confirmation d'acceptation) et SEND OK (confirmation de réception) SEND ERR (invalid file name), SEND ERR (file is too big), SEND ERR (file already exists), SEND ERR (upload not allowed)
    ZSEND <fichier> SIZE <n> Client → serveur, compressé ZSEND OK (acceptation) et ZSEND OK (reçu) ZSEND ERR (invalid file name), ZSEND ERR (file is too big), ZSEND ERR (file already exists), ZSEND ERR (upload not allowed), ZSEND ERR (échec de décompression)
    RECV <fichier> Client ← serveur RECV SIZE <n>, puis le client répond RECV OK et le serveur envoie les données RECV ERR (file has an invalid file name), RECV ERR (file does not exist), SEND ERR (download not allowed)
    ZRECV <fichier> Client ← serveur, compressé identique à RECV avec le préfixe ZRECV ZRECV ERR (file has an invalid file name), ZRECV ERR (file does not exist), SEND ERR (download not allowed)
    LS <filtre> Client ← serveur (mode non sécurisé) LS SIZE <n>, le client répond LS OK et le serveur envoie la liste LS ERR (filtre au nom invalide, ou à l'ouverture du répertoire)
    MV <fichier> Client ← serveur (mode non sécurisé) MV SIZE <n>, le client répond MV OK, le serveur envoie le fichier et le supprime MV ERR (nom invalide ou inexistant), SEND ERR (download not allowed) (non autorisé)
    PASS <digest> Client → serveur PASS OK le serveur ferme la connexion sans message si le mot de passe ne correspond pas
    QUIT Client → serveur ferme la connexion sans réponse —
    Commande non reconnue — — le serveur enregistre Unknown command '<commande>' dans le journal et ferme la connexion, sans prévenir le client

    L'avis « téléchargement non autorisé » réutilise toujours la chaîne SEND ERR (download not allowed), que l'opération soit RECV, ZRECV ou MV : les deux implémentations partagent cette particularité héritée du protocole, ce n'est pas une erreur de transcription.

    Envoi de fichiers (SEND)¶

    Le client annonce SEND <nom> SIZE <n>. Le serveur vérifie, dans cet ordre, si la destination accepte l'envoi (selon download_only), si le nom est valide, si la taille est comprise entre 1 octet et le maximum configuré, et si un fichier de ce nom existe déjà (overwrite désactivé). Un fichier de taille 0 est refusé avec le même message qu'un fichier trop gros (SEND ERR (file is too big)) : c'est le comportement normal du protocole, pas une particularité d'une implémentation. Après un transfert correct, le client peut envoyer un nouveau SEND (ou une autre commande) dans la même session ; la fermeture définitive est marquée par QUIT.

    Client :  SEND <rapport.xml> SIZE 1024
Serveur : SEND OK
Client :  <1024 octets de données>
Serveur : SEND OK
Client :  QUIT

    Réception de fichiers (RECV)¶

    Le client demande RECV <nom>. Si le fichier existe et que la destination accepte le téléchargement (selon upload_only), le serveur répond RECV SIZE <n> ; le client, qui connaît déjà la taille, peut refuser le téléchargement sans autre forme de procès (simplement, il ne poursuit pas la session avec la commande attendue). Si le client confirme avec RECV OK, le serveur envoie le bloc de données.

    Client :  RECV <rapport.xml>
Serveur : RECV SIZE 1024
Client :  RECV OK
Serveur : <1024 octets de données>

    Compression (ZSEND/ZRECV)¶

    ZSEND et ZRECV sont les variantes compressées de SEND/RECV : le bloc de données est un fichier ZIP à une seule entrée (Deflate) au lieu du contenu en clair. Elles s'activent avec l'option -z du client ; le reste de la séquence de commandes est identique.

    Opérations du mode non sécurisé (LS, MV)¶

    LS (lister les fichiers qui correspondent à un filtre) et MV (télécharger un fichier puis le supprimer du serveur) ne fonctionnent que si le serveur a démarré avec l'option -I/insecure. Si le mode non sécurisé est désactivé — la valeur par défaut —, le serveur enregistre la tentative et ferme la connexion sans répondre à la commande.

    Authentification par mot de passe (PASS)¶

    Quand le serveur exige un mot de passe, PASS doit être la première commande de la session. Le client envoie, en hexadécimal, le MD5 du résumé MD5 binaire du mot de passe (un double MD5). Cela obscurcit le mot de passe, ne le protège pas : sur une connexion sans TLS, cela n'ajoute aucune sécurité réelle face à quelqu'un qui capture le trafic. Pour que l'authentification par mot de passe apporte quelque chose, elle doit passer par une connexion chiffrée.

    Chiffrement¶

    TLS enveloppe la connexion complète depuis le premier octet : il n'existe pas de phase en clair ni de STARTTLS ultérieur. Les deux extrémités doivent avoir TLS actif ; ce n'est pas négociable en cours de session.

    Gestion des erreurs¶

    Devant toute anomalie — commande inconnue, mot de passe incorrect, plus de données qu'annoncé, défaillance interne — le serveur ferme la connexion sans expliquer le motif au client. Le détail ne reste que dans le journal du serveur, s'il est actif.

    Noms de fichiers et taille de bloc¶

    Les noms de fichiers n'admettent pas les caractères ? [ ] / \ = + < > : ; ' , * ~ ni aucun chemin (seulement le nom simple). La taille de bloc de lecture et d'écriture réseau est de 1024 octets.

    Les deux proxys de Tentacle¶

    Il ne faut pas les confondre :

    • Le serveur Tentacle en mode proxy (-b/-g ou proxy_ip/proxy_port sur le serveur) : il renvoie la connexion complète vers un autre serveur Tentacle, sans rien stocker. Il est expliqué à la section 3, « Mode proxy ».
    • Le proxy HTTP du client (-y utilisateur:motdepasse@adresse:port) : le client Tentacle ouvre la connexion à travers un proxy HTTP avec CONNECT, avec authentification Basic facultative si un utilisateur et un mot de passe sont indiqués. Il est expliqué à la section 2, « Proxy HTTP ».

    2. Le client Tentacle¶

    Syntaxe : tentacle_client [options] [fichier] [fichier] .... Il faut au moins un fichier, sauf en mode réception (-g), où l'argument est le nom distant à télécharger.

    Options de ligne de commande¶

    Mêmes lettres dans les deux implémentations :

    Option Argument Ce qu'elle fait Par défaut
    -a adresse Adresse du serveur. 127.0.0.1
    -b adresse locale Adresse locale à laquelle lier la connexion sortante. non définie (choisie par le système)
    -c — Active TLS sans certificat client. Incompatible avec -e. désactivé
    -e certificat Fichier de certificat OpenSSL du client ; active TLS. Incompatible avec -c. —
    -f CA Vérifie que le certificat du serveur est signé par cette CA. Exige -e. —
    -g — Mode réception : télécharge des fichiers depuis le serveur au lieu de les envoyer. désactivé (mode envoi)
    -h — Affiche l'aide. —
    -k clé Fichier de clé privée OpenSSL du client. Exige -e. —
    -p port Port du serveur. 41121
    -q — Mode silencieux : n'affiche pas les messages d'erreur. désactivé
    -r nombre Tentatives des opérations réseau. Minimum 1 : une valeur inférieure fait terminer le client sur une erreur de démarrage. 3
    -t secondes Délai d'attente des opérations réseau. Minimum 1 : une valeur inférieure fait terminer le client sur une erreur de démarrage. 1 s
    -v — Mode détaillé (enregistre les événements du protocole). désactivé
    -w — Demande de façon interactive le mot de passe de la clé privée. N'a d'effet qu'avec -e. désactivé
    -x mot de passe Mot de passe du serveur (authentification PASS). vide
    -y utilisateur:motdepasse@adresse:port Proxy HTTP pour la connexion (CONNECT, avec Basic si des identifiants sont indiqués). sans proxy
    -z — Compresse les données en transit (ZSEND/ZRECV). désactivé

    Règles de combinaison¶

    • -c et -e sont incompatibles entre elles (deux façons différentes d'activer TLS : sans certificat propre ou avec un).
    • -f et -k exigent que -e soit présent ; sans certificat client, demander une CA ou une clé n'a pas de sens. -w n'a d'effet qu'avec -e.
    • IPv6 : pris en charge ; le client Perl a en plus besoin du module IO::Socket::INET6 installé.

    Proxy HTTP¶

    -y utilisateur:motdepasse@adresse:port fait ouvrir au client la connexion vers le proxy avec un CONNECT vers le vrai serveur Tentacle ; si un utilisateur et un mot de passe sont indiqués, il ajoute l'en-tête Proxy-Authorization: Basic. L'utilisateur et le mot de passe sont facultatifs dans la chaîne.

    Codes de sortie¶

    0 si tous les transferts de la ligne de commande se sont bien terminés, 1 si l'un d'eux a échoué ou s'il y a eu une erreur.

    Utilisation depuis l'EndPoint et le serveur satellite¶

    L'EndPoint et le serveur satellite invoquent le client Tentacle au moyen de quatre jetons de leur fichier de configuration : transfer_mode tentacle (le mode de transfert), server_ip et server_port (destination) et server_opts (les options du client de cette section, telles quelles, par exemple server_opts -v -r 5). Pour le détail complet de ces jetons et de leurs équivalents de serveur secondaire, voir 9.1 · Référence complète de configuration de l'EndPoint.

    Exemples d'utilisation¶

    Avec le serveur sur 192.168.1.1 et sans mot de passe sur la clé privée du client :

    Transfert simple, avec une taille maximale de fichier de 1 MB sur le serveur :

    tentacle_server -m 1048576 -s /tmp -v
tentacle_client -a 192.168.1.1 -v /home/user/myfile.dat

    Avec authentification par mot de passe :

    tentacle_server -x password -s /tmp -v
tentacle_client -a 192.168.1.1 -x password -v /home/user/myfile.dat

    TLS sans certificat client :

    tentacle_server -e cert.pem -k key.pem -w -s /tmp -v
tentacle_client -a 192.168.1.1 -c -v /home/user/myfile.dat

    TLS avec certificat client et mot de passe :

    tentacle_server -x password -e cert.pem -k key.pem -f cacert.pem -w -s /tmp -v
tentacle_client \
  -a 192.168.1.1 \
  -x password \
  -e cert.pem \
  -k key.pem \
  -v /home/user/myfile.dat

    3. Le serveur Tentacle¶

    Syntaxe : tentacle_server -s <répertoire> [options], ou bien tentacle_server -F <fichier> pour démarrer en lisant la configuration dans un fichier.

    Options de ligne de commande¶

    Option Jeton Ce qu'elle fait Par défaut
    -a addresses Adresses IPv4 sur lesquelles écouter, séparées par des virgules. 0.0.0.0
    -b proxy_ip Mode proxy : adresse du serveur Tentacle inaccessible vers lequel renvoyer. —
    -c max_connections Nombre maximal de connexions simultanées. 10
    -d daemon Exécute le serveur comme démon. Non disponible sous Windows (voir « Windows », plus bas). désactivé
    -e ssl_cert Certificat OpenSSL du serveur ; active TLS. —
    -f ssl_ca CA avec laquelle vérifier le certificat du client. —
    -F — Chemin complet du fichier de configuration. —
    -g proxy_port Mode proxy : port du serveur Tentacle inaccessible. 41121
    -h — Affiche l'aide. —
    -I insecure Active le mode non sécurisé (LS et MV). désactivé
    -i filters Filtres de répartition par sous-répertoire (regexp:dir;regexp:dir…). —
    -k ssl_key Clé privée OpenSSL du serveur. —
    -l log_file Fichier où écrire le journal. sortie standard si non indiqué
    -m max_size Taille maximale de fichier, en octets. 64000000
    -o overwrite Autorise l'écrasement d'un fichier existant du même nom. désactivé
    -p port Port sur lequel écouter. 41121
    -q quiet N'affiche pas les messages d'erreur. désactivé
    -r retries Tentatives des opérations réseau. Minimum 1. 3
    -s directory Répertoire de stockage. Obligatoire sauf en mode proxy. —
    -S — Gère le service Windows (install|uninstall|run). —
    -t timeout Délai d'attente des opérations réseau, en secondes. Minimum 1. 1
    -u ssl_cipher Restreint les suites de chiffrement TLS 1.2 admises, avec des noms OpenSSL séparés par :. négociation normale
    -v verbose 1 Mode détaillé : enregistre les erreurs. désactivé
    -V verbose 2 Mode détaillé étendu : enregistre les erreurs et les avertissements informatifs. désactivé
    -w — Demande en ligne de commande le mot de passe de la clé privée. S'applique aux clés PEM chiffrées du format traditionnel. désactivé
    -x password Mot de passe du serveur (authentification PASS). vide
    -z ssl_version Restreint la version de TLS admise à TLSv1_2 ou TLSv1_3. négociation normale (TLS 1.2 minimum)

    Fichier de configuration¶

    Le format est l'habituel de la maison : une ligne par jeton avec la valeur après un espace, et # commente la ligne entière. Le chemin habituel du fichier est /etc/tentacle/tentacle_server.conf. La ligne de commande a la priorité sur le fichier quand la même option se répète aux deux endroits. Il n'y a pas de rechargement à chaud : un changement dans le fichier exige de redémarrer le service.

    Plusieurs jetons n'ont pas d'option de ligne de commande équivalente :

    • block_size : taille de bloc de lecture/écriture réseau, en octets (par défaut, 1024 octets ; voir « Protocole », plus haut).
    • download_only et upload_only : répertoires, après application de filters, depuis lesquels on peut seulement télécharger ou seulement envoyer, respectivement, séparés par ;. Ils sont détaillés dans « Filtres et répertoires », plus bas.

    Modèle du paquet face aux valeurs internes¶

    Le modèle qu'installe le paquet (tentacle_server.conf.new) ne coïncide pas toujours avec la valeur par défaut qu'applique le binaire lui-même quand le jeton n'apparaît pas dans le fichier. Par exemple, le modèle active daemon 1 alors que la valeur interne par défaut est 0 (désactivé). Les autres jetons du tableau précédent indiquent, dans la colonne « Par défaut », la valeur interne du binaire, non celle du modèle.

    Filtres et répertoires¶

    filters (-i) répartit les fichiers entrants par sous-répertoire selon une expression régulière sur le nom ; la syntaxe est regexp:sous-répertoire;regexp:sous-répertoire;…. Un fichier dont le nom ne correspond à aucun filtre est enregistré directement dans le répertoire de stockage. Le modèle du serveur principal répartit, entre autres, les .conf vers conf, les .md5 vers md5, les .zip vers collections, les .lock vers trans, les .rcmd vers commands et les paquets d'installation d'EndPoint (.agent_setup.exe, .agent_setup.tar.gz) vers agent. Sur ces mêmes sous-répertoires (déjà filtrés) agissent download_only (-D) et upload_only (-U), en restreignant ce qui peut être envoyé ou téléchargé dans chacun. Après mise à jour du paquet, il faut redémarrer le serveur pour qu'il prenne les nouveaux filtres apportés par la version.

    Service systemd¶

    Le service principal est tentacle_serverd.service, avec l'utilisateur pandora, qui lance tentacle_server -F /etc/tentacle/tentacle_server.conf avec un ExecStartPre de nettoyage (clean_tentacle_serverd, qui vide les temporaires du TMPDIR fixé dans tentacle_server.env) et deux fichiers d'environnement (tentacle_server.env avec TMPDIR et tentacle_server_extra.env, ce dernier libre pour des ajustements locaux). La relation entre ce service et les jetons tentacle_service_cmd / tentacle_service_watchdog du serveur principal se trouve dans 9.3 · Configuration distante, Tentacle et synchronisation.

    Instance RMM¶

    RMM utilise sa propre instance de Tentacle, indépendante de celle du serveur principal : service tentacle_rmm.service (utilisateur root, port 41123, ExecStartPre avec clean_tentacle_rmm), son propre fichier de configuration, son propre répertoire de stockage (/var/spool/pandora/rmm_server) et ses propres certificats TLS. Les filtres (filters) répartissent par extension les fichiers de RMM dans des sous-répertoires propres (rmm, res, queue, keepalive, data), et download_only/upload_only restreignent ces mêmes sous-répertoires : on ne peut télécharger que depuis rmm, res et queue, et on ne peut envoyer que vers data et keepalive. Le modèle apporte un mot de passe d'exemple : il doit être changé avant de mettre le service en production, et comme tout secret, il se référence depuis la configuration, il ne se copie jamais dans la documentation ni dans un dépôt.

    Mode proxy¶

    Avec -b/proxy_ip et -g/proxy_port, le serveur Tentacle n'agit pas comme un stockage : il renvoie brut, octet par octet, tout ce qui arrive de chaque client vers un autre serveur Tentacle (l'« inaccessible » du point de vue des clients). Il peut terminer TLS et l'authentification par mot de passe sur le tronçon client-proxy, avec un tronçon proxy-serveur différent (ou sans chiffrement). Le serveur satellite résout le même renvoi avec ses propres jetons, proxy_tentacle_from/proxy_tentacle_to ; voir 6.2 · Serveurs satellites.

    Cas pratique — des EndPoint derrière un proxy Tentacle avec TLS et mot de passe, de bout en bout : on vérifie d'abord chaque tronçon à la main et, si cela fonctionne, on passe à la configuration permanente.

    Tests manuels :

    # 1. Serveur réel
sudo -u pandora tentacle_server \
  -x password \
  -e tentacle_cert \
  -k tentacle_key \
  -f ca_cert -s /tmp -v

# 2. Proxy
sudo -u pandora tentacle_server -b ip_serveur -g 41124

# 3. Client, contre le proxy
sudo -u pandora tentacle_client \
  -a ip_proxy \
  -x password \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -v fichier

    Configuration permanente, une fois l'envoi manuel vérifié :

    1. Serveur réel (/etc/tentacle/tentacle_server.conf) :
    password password
ssl_cert tentacle_cert
ssl_key tentacle_key
ssl_ca ca_cert
    1. Proxy (son propre /etc/tentacle/tentacle_server.conf) :
    proxy_ip ip_serveur
proxy_port 41124
    1. EndPoint (pandora_agent.conf), en pointant server_ip vers le proxy, non vers le serveur réel :
    server_opts -x password -e tentacle_client_cert -k tentacle_client_key
server_ip ip_proxy

    Chaque option de server_opts est indépendante : si, par exemple, le mot de passe n'est pas nécessaire, il suffit d'omettre -x password de la ligne.

    Sécurité : mot de passe, TLS et combinaisons de certificats¶

    Le mot de passe (-x/password) et TLS sont orthogonaux : ils peuvent se combiner ou s'utiliser séparément. Les quatre combinaisons de certificats possibles sont les suivantes ; toutes admettent l'ajout d'un mot de passe de la même façon.

    1. Serveur avec certificat, client sans vérification (le client ne vérifie pas l'identité du serveur) :

    Test manuel :

    tentacle_server -v -e tentacle_cert -k tentacle_key -s /tmp
tentacle_client -v -c -a <serveur> fichier

    Configuration permanente — serveur :

    ssl_cert tentacle_cert
ssl_key tentacle_key

    Configuration permanente — EndPoint et serveur satellite :

    server_opts -c

    2. Serveur avec certificat, client vérifiant contre une CA :

    Test manuel :

    tentacle_server -v -e tentacle_cert -k tentacle_key -s /tmp
tentacle_client -v -e tentacle_client_cert -f ca_cert -a <serveur> fichier

    Configuration permanente — serveur :

    ssl_cert tentacle_cert
ssl_key tentacle_key

    Configuration permanente — EndPoint et serveur satellite :

    server_opts -e tentacle_client_cert -f ca_cert

    3. Serveur vérifiant le client contre une CA (certificat client sans CA propre côté client) :

    Test manuel :

    tentacle_server -v -e tentacle_cert -k tentacle_key -f ca_cert -s /tmp
tentacle_client -v \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -a <serveur> fichier

    Configuration permanente — serveur :

    ssl_cert tentacle_cert
ssl_ca ca_cert
ssl_key tentacle_key

    Configuration permanente — EndPoint et serveur satellite :

    server_opts -e tentacle_client_cert -k tentacle_client_key

    4. Vérification mutuelle (serveur et client vérifient le certificat de l'autre contre une CA) :

    Test manuel :

    tentacle_server -v -e tentacle_cert -k tentacle_key -f ca_cert -s /tmp
tentacle_client -v \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -f ca_cert \
  -a <serveur> fichier

    Configuration permanente — serveur :

    ssl_cert tentacle_cert
ssl_ca ca_cert
ssl_key tentacle_key

    Configuration permanente — EndPoint et serveur satellite :

    server_opts -e tentacle_client_cert -k tentacle_client_key -f ca_cert

    Dans tous les cas, les chemins des certificats et des clés doivent être absolus dans les fichiers de configuration, et le paquet IO::Socket::SSL doit être installé pour utiliser TLS avec l'implémentation Perl. TLS exige, au minimum, la version 1.2.

    Pour la production, la combinaison recommandée est la 4 (vérification mutuelle), avec un mot de passe ajouté de façon facultative : c'est la seule des quatre où les deux extrémités vérifient l'identité de l'autre contre une CA.

    retries/timeout (-r/-t) ne sont pas seulement des paramètres réseau : en limitant les tentatives et le délai d'attente de chaque connexion, ils rendent aussi plus difficile une attaque par force brute contre le mot de passe. Le journal du serveur (-l/log_file, avec le détail que donnent -v/-V) est, outre un outil de diagnostic, le journal d'audit des connexions.

    Guide rapide des certificats OpenSSL¶

    Pour générer les certificats qu'utilisent les exemples précédents.

    Créer une CA propre :

    mkdir demoCA demoCA/newcerts demoCA/private
openssl req -new -x509 -keyout cakey.pem -out cacert.pem
mv cakey.pem demoCA/private/
mv cacert.pem demoCA/

    Demande de certificat et signature avec cette CA :

    openssl req -new -keyout tentaclekey.pem -out tentaclereq.pem -days 360
cat tentaclereq.pem tentaclekey.pem > tentaclenew.pem
touch demoCA/index.txt
echo "01" >> demoCA/serial
openssl ca -out tentaclecert.pem -in tentaclenew.pem

    Certificat autosigné, sans CA :

    openssl req -new -x509 -keyout tentaclekey.pem -out tentaclecert.pem -days 360

    Clé RSA sans mot de passe (évite d'avoir à la saisir côté client) :

    openssl genrsa -out tentaclekey.pem

    Exporter un certificat PEM vers DER (nécessaire sur certains systèmes) :

    openssl x509 -outform der -in tentaclecert.pem -out tentaclecert.der

    Windows¶

    Sous Windows, le serveur se gère comme un service avec tentacle_server -S install|uninstall|run ; l'option -d (démon Unix) n'est pas disponible sur cette plateforme.
