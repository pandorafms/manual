# Collections

Un `module_plugin` a souvent besoin de quelque chose de plus que la commande
écrite dans sa configuration : un script, un binaire, un fichier de
configuration propre. Copier ce fichier à la main sur chaque agent qui va
l'utiliser fonctionne la première fois et devient un problème la deuxième, quand
il faut le mettre à jour sur vingt machines à la fois. Une **collection** est la
réponse de Pandora FMS à ce problème : un paquet de fichiers qui est téléversé
une seule fois dans la console web et se déploie, compressé, vers les EndPoints
qui en ont besoin.

Une collection peut être affectée à un EndPoint individuel, à une politique de
supervision — qui la propage à tous ses agents — ou à un serveur satellite. La
console web prépare le paquet ; chaque destinataire se charge de le recevoir. Ce
chapitre parcourt comment une collection se crée et se modifie, comment elle
s'applique et se synchronise, et ce qui change selon l'endroit depuis lequel
elle est affectée.

## Créer et gérer une collection dans la console

La création d'une collection dans la console web se fait dans **Gestion →
Configuration → Collections**. Le formulaire de création demande un nom, un
groupe, une description et un nom court facultatif : s'il est laissé vide, la
console en génère un avec un horodatage (`fc_<timestamp>`). Ce nom court n'est
pas un détail cosmétique, c'est l'identifiant qui apparaît ensuite comme
répertoire dans la console et sur chaque EndPoint, il vaut donc mieux le définir
à la main et qu'il dise quelque chose.

| Exigence | Détail |
|---|---|
| Au moins un fichier dans la collection | Une collection vide n'arrive pas à générer le paquet compressé |
| Forme du nom court | Uniquement des lettres, des chiffres, `_` et `-` ; s'il est laissé vide, un nom automatique avec horodatage est généré |
| Utilitaire de compression ZIP sur le serveur de la console | Nécessaire pour générer le paquet lors de l'application des changements |
| Taille du paquet compressé non supérieure à la limite configurée | Voir l'avertissement ci-dessous |

La collection une fois créée, la modification ajoute ses ressources : téléverser
un fichier, créer un répertoire ou créer un fichier texte qui se modifie
directement depuis la console elle-même, sans passer par l'ordinateur de
l'administrateur. Tout cela est stocké du côté de la console, dans un répertoire
de pièces jointes portant le nom court de la collection.

Il existe une limite de taille pour le paquet compressé final
(`collection_max_size`). Lors de l'application des changements, la console web
crée d'abord un ZIP temporaire. S'il dépasse la limite, elle ne le publie pas
dans le chemin de configuration distante et ne calcule pas son MD5 ; la
collection reste en attente d'application. Il faut réduire son contenu et
appliquer de nouveau les changements.

!!! example "Une collection pour un plugin Apache"
    La collection `apache_plugin` contient un seul fichier, le script
    `pandora_apache_v1r1.pl` que Pandora FMS apporte installé par défaut :
    c'est le paquet qu'un `module_plugin` Apache s'attend à trouver sur
    l'EndPoint avant de pouvoir s'exécuter.

## Synchroniser les changements : appliquer une collection

Ajouter ou modifier des ressources d'une collection ne la déploie pas toute
seule : la console web signale dans la liste, par une icône de triangle jaune,
toute collection ayant des changements en attente d'application. Lorsqu'on
l'applique, le serveur de la console compresse le répertoire complet en un ZIP,
calcule son MD5 et laisse les deux fichiers dans le chemin de configuration
distante, prêts pour que les EndPoints les téléchargent à leur prochain cycle.

Une collection peut se trouver dans trois états : en attente d'application (les
changements n'ont pas été publiés), correcte (le ZIP et le MD5 sont à jour) et
répertoire perdu, si le répertoire de la collection disparaît du côté de la
console.

Le nom court de la collection n'identifie pas seulement le paquet : c'est aussi
le nom du répertoire de base de la collection du côté de la console
(`/pandora_console/attachment/collection/<nom_court>`), qui peut contenir des
sous-répertoires sans aucun problème.

## Affecter une collection à un EndPoint

Dans la console web, cela s'affecte depuis **Ressources → Gérer les agents**,
onglet **Collection** de l'EndPoint. L'onglet liste les collections disponibles
selon le groupe de l'EndPoint et un bouton pour les ajouter ; l'état de
synchronisation de chacune est visible grâce à une icône d'avertissement si elle
est encore vide ou n'a pas été appliquée.

Sans configuration distante activée sur l'EndPoint, la console web ne peut pas
lui livrer la collection — cela a déjà été expliqué dans
[Supervision avec des EndPoints](2.1-monitorizacion-con-endpoints.md) — cette
exigence n'est donc pas répétée ici. Quelques minutes après l'affectation,
l'EndPoint lui-même devrait apparaître dans l'onglet des agents de la
collection, confirmant qu'il la possède déjà.

!!! example "Affecter la collection d'Apache à un EndPoint"
    Avec `apache_plugin` déjà créée et appliquée, elle est affectée à l'EndPoint
    `Servidor-Apache-01` depuis son onglet Collection : au cycle suivant de
    configuration distante, l'EndPoint télécharge le paquet.

## Où se retrouve la collection sur l'EndPoint

Chaque EndPoint conserve ses collections dans un sous-répertoire propre à
l'intérieur de son dossier de collections, avec le nom court de la collection
comme nom de sous-répertoire : sous Windows,
`%ProgramFiles%\pandora_agent\collections\<nom_court>` ; sous Unix ou sur
l'EndPoint Go, `/usr/share/pandora_agent/collections/<nom_court>` dans une
installation par paquet, ou en général le sous-répertoire
`collections/<nom_court>` à côté du fichier de configuration de l'agent
lui-même. Que chaque collection ait son propre sous-répertoire n'est pas un
hasard : cela évite que deux collections différentes s'écrasent entre elles si
elles partagent le nom d'un fichier. Un `module_plugin` référence un fichier de
la collection par son chemin complet.

Décompresser le paquet ne fonctionne pas de la même façon sur tous les
EndPoints. L'EndPoint Perl (Unix) et l'EndPoint Windows font appel à un
utilitaire `unzip` externe — sous Windows, il est inclus depuis la version 3.2
de l'EndPoint, à l'intérieur de `%ProgramFiles%\pandora_agent\utils` —.
L'EndPoint Go, en revanche, décompresse en mémoire avec sa propre bibliothèque
standard, sans dépendre d'aucun binaire externe installé sur le système.

Quant au mode de transfert avec lequel le paquet arrive, il n'existe aucune
restriction propre aux collections : elles utilisent le même mode configuré pour
le reste de la configuration distante de l'EndPoint (voir
[Supervision avec des EndPoints](2.1-monitorizacion-con-endpoints.md)), sans
distinction particulière pour les collections.

!!! example "Chemin complet d'un fichier de la collection"
    Le script de la collection `apache_plugin` sur un EndPoint Unix installé
    par paquet se retrouve dans
    `/usr/share/pandora_agent/collections/apache_plugin/pandora_apache_v1r1.pl`,
    et c'est ainsi que le référence le `module_plugin` qui l'utilise.

## Comment elle reste synchronisée : contrôle par MD5

Le MD5 du paquet de la collection est calculé dans la console web lors de
l'application des changements et est envoyé à l'EndPoint avec le ZIP. À chaque
cycle, l'EndPoint compare ce MD5 distant avec celui qu'il garde localement :
s'ils coïncident, il ne fait rien ; s'ils diffèrent, il télécharge et
décompresse la collection entière de nouveau.

Cela a une conséquence pratique qu'il convient de garder en tête : si l'on
modifie à la main les fichiers d'une collection déjà déployée sur un EndPoint,
ces changements survivent tant que la collection ne change pas dans la console.
Dès qu'elle change, la synchronisation suivante écrase la collection complète et
ces modifications locales sont perdues.

Le nettoyage des collections qui ne figurent plus dans la configuration ne
garantit pas une suppression immédiate. L'EndPoint Perl exécute
`check_collections` à chaque cycle, sauf en mode `debug` ; il omet la
suppression s'il y a des agents broker ou s'il ne peut pas ouvrir le répertoire
de collections. L'EndPoint Go vérifie lui aussi à chaque cycle, mais il omet les
entrées dont le nom commence par `.` et peut échouer à lire ou supprimer des
fichiers. Sous Windows, la vérification des collections appelle
`purgeDiskCollections`, qui omet la suppression s'il y a des agents broker.
Lorsque l'affectation est retirée depuis la console web, la collection cesse de
figurer dans la configuration distante correspondante. Supprimer une collection
depuis la console web ne garantit pas non plus qu'elle disparaisse immédiatement
de l'EndPoint : la suppression des fichiers locaux dépend de l'exécution du
nettoyage et de sa capacité à aboutir.

## Collections et politiques de supervision

Depuis la console web, une collection peut aussi être affectée à une politique
de supervision complète au lieu d'un EndPoint individuel, avec le même mécanisme
de fond mais propagé à tous les agents de la politique. Cela se gère depuis
l'onglet **Collections** de la politique : ajouter ou retirer une collection
existante et appliquer la politique pour que la file d'attente des changements
la propage à tous ses agents. Le reste de la gestion d'une politique —
l'appliquer, la file d'attente des changements, ses autres onglets — sort du
cadre de ce chapitre ; voir
[Politiques de supervision](2.10-politicas-de-monitorizacion.md).

## Collections sur le serveur satellite

Un serveur satellite peut également recevoir des collections depuis la console
web : **Gestion → Serveurs → Gérer le serveur satellite**, icône
**Collections** : une liste des collections disponibles avec une colonne
d'actions pour les ajouter ou les retirer. Lors de l'ajout d'une collection, la
console web écrit `file_collection <nom_court>` dans la configuration distante
du satellite et met à jour le **MD5 de ce fichier de configuration**. Le
satellite compare ce MD5 pour détecter les changements de sa configuration ;
lorsqu'il traite `file_collection`, il consulte séparément le **MD5 du paquet**
de la collection. S'il diffère du local, il télécharge le ZIP et le décompresse
avec l'utilitaire configuré. Ce ne sont pas le même MD5, ni le même code que
celui qu'un EndPoint utilise pour recevoir des collections.

Avec la configuration incluse dans le paquet du serveur satellite
(`agent_conf_dir /etc/pandora/conf`), les collections se retrouvent dans
`/etc/pandora/satellite_collections/`. Le chemin se déduit de
`agent_conf_dir/../satellite_collections` et peut être changé avec
`collection_dir`. Le [wiki public des
collections](https://pandorafms.com/manual/!current/es/documentation/pandorafms/technical_annexes/28_pfms_file_collections#colecciones_de_ficheros_en_servidor_satelite)
indique également ce chemin.

## Collections depuis le Command Center

Depuis Pandora FMS 729 OUM, les collections peuvent aussi être gérées de façon
centralisée depuis la console web du Command Center : **Gestion centralisée →
Gestion des agents**, onglet **Collections**. Le fonctionnement est le même que
dans la console d'un nœud ; la seule chose qui change lorsqu'on opère depuis le
Command Center est que la synchronisation vers les nœuds se fait par son propre
mécanisme de synchronisation entre le nœud et le Command Center.

## Permissions

La gestion des collections dans la console web — créer, modifier, appliquer,
affecter — exige le droit d'écriture des agents (AW) sur le groupe de la
collection. La liste des collections disponibles est filtrée par les groupes où
l'utilisateur possède ce droit, plus le groupe « Tous ».

| Exigence | Détail |
|---|---|
| Voir la liste des collections | Elle est filtrée par les groupes ayant le droit d'écriture des agents (AW), plus le groupe « Tous » |
| Créer, modifier, appliquer ou affecter une collection | Droit d'écriture des agents (AW) sur le groupe de la collection |
