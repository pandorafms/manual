# Gestionnaire d'identifiants

Toute tâche qui doit se connecter à quelque chose avec un utilisateur et un mot
de passe — une ressource cloud, un appareil réseau, un équipement Windows —
finit par demander ces identifiants dans un formulaire. Les saisir chaque fois
est la façon la plus efficace de finir avec le même mot de passe copié à vingt
endroits et oublié à dix-neuf. Le gestionnaire d'identifiants évite cette
dispersion : ils sont enregistrés une seule fois dans la console web, sous un
nom, et, à partir de là, celui qui en a besoin les utilise.

## À quoi il sert

Le gestionnaire centralise l'utilisateur et le mot de passe — et, selon le type
d'identifiant, quelque champ supplémentaire — pour ne pas les répéter dans
chaque assistant de Discovery, chaque tâche de NCM ou chaque déploiement du
Deployment Center. Ces tâches n'enregistrent pas les valeurs, mais le nom de
l'identifiant, et le récupèrent à l'exécution : quand le mot de passe change,
il est mis à jour une fois dans le gestionnaire et toutes l'utilisent à leur
exécution suivante. Les modules et les politiques fonctionnent autrement,
comme expliqué dans [Où sont-ils utilisés](#ou-sont-ils-utilises).

Dans la console web, il se trouve dans **Configuration →
Magasin d'identifiants**.

## Accès et permissions

Entrer dans le gestionnaire d'identifiants exige de détenir à la fois les
permissions **PM** et **UM** ; avec une seule des deux, la console web refuse
l'accès et ce refus est audité. La portée dépend aussi du groupe : chaque
identifiant appartient à un groupe, et si ce groupe a la propagation vers les
groupes enfants activée, le filtre de visibilité les inclut. Le groupe **All**
est un cas à part : ses identifiants sont disponibles pour tout utilisateur,
sans qu'il soit nécessaire d'en faire partie, mais **créer ou modifier un
identifiant dans le groupe All exige en plus la permission d'administrateur de
ce groupe** (« ALL group manager »). Un administrateur de la console voit et
filtre par n'importe quel groupe sans aucune de ces restrictions.

## Créer, modifier et supprimer des identifiants

Le nom d'un identifiant n'admet que des caractères ASCII valides, et tout espace
devient un tiret à l'enregistrement. Le nom comme le type d'identifiant restent
**figés au moment de la création** : à la modification ultérieure, la console
web affiche les deux champs mais désactivés, il n'y a donc aucun moyen de
réutiliser un identifiant existant pour un autre type ni de le renommer ; il
faut en créer un nouveau. À la suppression d'un identifiant, la même
vérification de visibilité qu'à l'accès se répète : si l'utilisateur n'a pas de
permission sur cet identifiant par groupe ou par ACL, la suppression est refusée
même s'il connaît son nom.

## Types d'identifiant

Le formulaire change de champs selon le type d'identifiant choisi :

| Type | Champs du formulaire |
|---|---|
| Personnalisé | ID du compte, mot de passe |
| AWS | ID de la clé d'accès, clé d'accès secrète |
| Azure | ID du compte, secret de l'application, propriétaire ou nom du domaine, ID de l'abonnement |
| Google | JSON complet du compte de service (se colle en entier) |
| SAP | ID du compte, mot de passe |
| WMI | Utilisateur, mot de passe, espace de noms |
| SNMP | Version ; communauté (v1/v2) ; en v3 en plus : niveau de sécurité, utilisateur, méthode et mot de passe d'authentification, méthode et mot de passe de confidentialité |

**Google** est un cas particulier : le formulaire ne demande ni utilisateur ni
mot de passe, mais que l'on colle le JSON complet du compte de service. À
l'enregistrement, la console web extrait de ce JSON le courriel de service et
l'identifiant de clé, seulement pour les afficher dans la liste ; au moment
d'utiliser l'identifiant, c'est le JSON entier qui est réutilisé, pas ces deux
valeurs isolées.

## Où sont-ils utilisés

Le gestionnaire d'identifiants n'a pas d'équivalent par API ni en ligne de
commande : tout identifiant se crée, se modifie et se consomme depuis la console
web. Les points où un identifiant enregistré est utilisé sont :

- Les assistants de **Discovery** ([Supervision et découverte automatique avec
  Discovery](2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md)),
  tant Host&Devices que Cloud : la tâche enregistre le nom et récupère
  l'identifiant à l'exécution.
- **NCM** ([Gestion de configuration des équipements réseau
  (NCM)](../parte-3/3.6-gestion-de-configuracion-de-equipos-de-red-ncm.md)),
  pour l'accès aux équipements réseau gérés.
- Le **Deployment Center** ([Distribution et installation automatique
  d'agents](../parte-6/6.4-distribucion-e-instalacion-automatica-de-agentes.md)),
  lors du déploiement des EndPoint.
- L'éditeur de modules et les modules SNMP ou WMI d'une
  [politique de supervision](2.10-politicas-de-monitorizacion.md) : le
  sélecteur d'identifiant ne **remplit que le formulaire** du module ou de la
  politique avec les valeurs enregistrées ; il ne reste pas lié en direct à
  l'identifiant. Si l'identifiant change plus tard, le module ne le sait pas, et
  il faut l'appliquer de nouveau à la main.
- Les rapports **AWS**.

## Identifiants et chiffrement

Si la base de données n'a pas le chiffrement activé, l'écran même du
gestionnaire d'identifiants avertit que ce qui y sera enregistré le sera sans
chiffrement, avec un lien vers la documentation de chiffrement. Il convient d'en
tenir compte : un magasin de mots de passe en clair est, avant tout, un cadeau
pour qui obtient une copie de la base de données. Le chiffrement est une
fonctionnalité **Enterprise**. Activer, changer ou retirer la phrase de
chiffrement est expliqué dans
[Chiffrement de la base de données](../parte-9/9.5-cifrado-de-la-base-de-datos.md).
