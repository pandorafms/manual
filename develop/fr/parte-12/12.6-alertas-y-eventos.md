# Alertes et événements

Cette section rassemble les problèmes qui reviennent le plus avec les alertes.
Parfois elles ne se déclenchent pas alors qu'elles le devraient. Parfois elles se
déclenchent trop. Et parfois l'avis n'arrive pas dans de bonnes conditions. Toutes
les vérifications se font depuis la **console web**, dans **Alertes** et dans
**Gestion → Réglages**, sauf indication contraire.

## L'alerte ne se déclenche pas alors que la valeur est mauvaise

C'est presque toujours le **nombre minimum d'alertes** du modèle. Ce champ indique
combien de valeurs mauvaises consécutives il faut pour déclencher. Le décompte est
celui-ci :

- Avec un **minimum à 0**, l'alerte se déclenche à la première valeur mauvaise.
- Avec un **minimum à 1**, il faut **deux** valeurs mauvaises dans la période
  fixée par le **seuil de temps**.

Si le module remonte des pics isolés et que l'alerte ne se déclenche pas, le
minimum est bien réglé. Le problème ne vient pas de l'alerte : c'est le module qui
oscille. Abaissez le minimum à 0 ou ajustez la période du seuil. Vérifiez aussi la
**protection Flip Flop** du module : elle exige plusieurs contrôles consécutifs
avant de changer d'état.

## Ni les alertes ni les événements ne se déclenchent

Avant de toucher au modèle, écartez l'hypothèse d'un mécanisme qui les réduit au
silence. On vérifie dans cet ordre :

- La **protection contre les tempêtes d'événements** (*event storm protection*)
  n'est pas active dans **Gestion → Réglages → Configuration du système →
  Configuration générale**. Si elle l'est, la plateforme amortit les événements
  lorsqu'ils arrivent en masse et on peut croire qu'ils ne se déclenchent pas.
- L'**agent** n'est pas en mode silencieux (*quiet*).
- Le **module** non plus.
- Le **groupe** auquel appartient l'agent n'a pas les alertes ni les événements
  désactivés.

Si les quatre points sont bons, l'alerte doit se déclencher. Consultez le journal
du serveur pour voir si l'événement est bien évalué.

## L'alerte se déclenche toutes les cinq minutes

Le modèle a deux limites qu'il vaut la peine de distinguer : le **nombre maximum
d'alertes** et le **seuil de temps**. Pour qu'un problème qui persiste n'avertisse
qu'une seule fois par jour : **seuil de temps à un jour**, **minimum à 0** et
**maximum à 1**. Ainsi l'alerte se déclenche à la première valeur mauvaise. Et
elle ne se répète pas avant l'écoulement du seuil, même si le module reste
mauvais.

## Ce que signifie chaque limite du modèle

Les trois champs se confondent facilement et font des choses différentes :

| Champ | Ce qu'il contrôle |
|---|---|
| **Nombre minimum d'alertes** | Combien de fois la condition doit se répéter pour que l'action s'exécute la première fois |
| **Nombre maximum d'alertes** | Combien d'alertes peuvent être envoyées d'affilée dans le même intervalle |
| **Seuil de temps** (*time threshold*) | Temps qui doit s'écouler, l'état incorrect étant toujours actif, avant de prévenir de nouveau |

Un exemple avec le seuil à 24 heures. L'alerte prévient une fois. Elle ne se
répète pas avant qu'un jour soit passé, même si le module reste en mauvais état
tout ce temps-là.

## L'e-mail de l'alerte arrive sans sauts de ligne

C'est un problème de format du corps du message, pas de l'envoi. Dans l'**action**
de l'alerte (ou dans les champs avancés du modèle s'ils sont définis là), il faut
encadrer le texte entre les balises `<pre>` et `</pre>` :

```html
<pre>
Hello, this is an automated email coming from Pandora FMS

This alert has been fired because a CRITICAL condition in one of your monitored items:

Agent: _agent_
Module: _module_
Module description: _moduledescription_
Timestamp: _timestamp_
Current value: _data_

Thanks for your time.
Best regards,
Pandora FMS.
</pre>
```

Les macros (`_agent_`, `_module_`, `_data_` et les autres) sont remplacées à
l'envoi. Sans les balises, le client de messagerie met toutes les lignes bout à
bout.

## Le graphique n'apparaît pas dans l'e-mail de l'alerte

Les graphiques joints aux avis sont générés par le serveur avec un moteur de rendu
sans interface. S'ils ne sortent pas, on vérifie dans cet ordre :

1. **Le binaire du moteur est installé et correctement pointé.** Le réglage est
   **Chromium path** dans **Gestion → Réglages → Configuration du système →
   Configuration générale**, et par défaut c'est `/usr/bin/chromium-browser`. Si le
   moteur n'est pas installé sur le serveur, il n'y a pas de graphique.
2. **La configuration de l'API est correcte.** Vérifiez l'appel à l'API que la
   console utilise pour demander le graphique.
3. **La résolution de noms (DNS).** Si la console s'appelle elle-même par un nom
   qui ne se résout pas, l'API échoue. Pour en avoir le cœur net, utilisez son
   adresse IP.
4. **Ce qui est dehors :** un proxy ou un pare-feu au milieu.
5. **Ce qui est dedans :** SELinux et `iptables` sur le serveur lui-même.

!!! note "Avis"
    L'ancienne procédure parlait de **PhantomJS**. Ce moteur n'est plus utilisé :
    le rendu est fait par Chromium, avec le réglage **Chromium path**.
