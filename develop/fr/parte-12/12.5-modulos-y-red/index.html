    Modules et réseau¶

    Les contrôles et le protocole réseau : modules qui ne démarrent pas ou ne répondent pas, ICMP, WMI, SNMP et traps.

    Un module stocke une seule métrique et sa valeur s'interprète par seuils. Presque tous les problèmes de cette section relèvent de la configuration du module lui-même ou d'un contrôle qui n'arrive pas à s'exécuter correctement.

    Je ne peux pas changer le type d'un module¶

    C'est le comportement du produit : une fois créé, le type d'un module ne peut pas être changé. Si vous vous êtes trompé de type, il faut supprimer le module et le recréer, et son historique se perd avec lui. C'est pourquoi il vaut mieux tomber juste du premier coup ou essayer la définition sur un agent de test avant de la porter en production.

    Peut-on utiliser des modules locaux dans les modèles ?¶

    Non. Les modèles de modules sont pour les composants réseau. Pour appliquer des modules locaux à beaucoup d'agents à la fois, il y a les politiques, qui portent en plus des alertes et admettent aussi des modules réseau.

    Les modules de Ping (ICMP) ne fonctionnent pas¶

    On sépare le problème de réseau de celui de traitement :

    Réseau. La machine est éteinte ou hors connexion ; il y a une coupure dans le segment ; ou un élément intermédiaire (pare-feu, proxy) bloque l'ICMP. Depuis le serveur, ping ou fping vers la destination dit si le problème est de réseau.

    Traitement. Si l'intervalle du module est très bas, les exécutions se mettent en file et le module n'arrive pas à temps. Cela traîne aussi si le serveur est en file de façon générale. Mesurez avant de baisser les intervalles : depuis la version 784, l'ICMP admet jusqu'à 15 secondes, mais cela a un coût sur les grosses machines.

    Un module ICMP est en critique alors qu'il y a de la connectivité¶

    Pandora FMS n'utilise pas le ping classique : il utilise fping, qui est plus efficace. Le jeton icmp_checks du serveur décide combien de pings il lance par module et vaut 1 par défaut, donc seul le premier compte. Si le réseau perd le premier paquet de temps en temps, le module passe en critique sans raison.

    Augmentez-le à une valeur plus grande pour que le résultat ne dépende pas d'une seule tentative.

    Les modules WMI ne fonctionnent pas¶

    WMI doit être activé sur la machine Windows, pas seulement dans Pandora FMS :

    1. Ouvrez Gestion de l'ordinateur → Services et applications → Contrôle WMI.
    2. Dans les propriétés de l'espace de noms (on peut commencer par root), dans l'onglet Sécurité, accordez la permission d'Appel distant (Remote Enable) au compte avec lequel vous interrogez.
    3. Autorisez le passage par le pare-feu de Windows.

    Dans Pandora FMS, le client WMI par défaut est pandorawmic, configurable avec le jeton wmi_client du serveur. Il a besoin des identifiants d'un utilisateur ayant des permissions sur la machine interrogée.

    WMI ne fonctionne pas depuis un serveur satellite¶

    Quand le serveur satellite tourne comme utilisateur local sous Windows, certaines requêtes WMI distantes échouent pour des raisons de sécurité. La solution est d'exécuter le service du satellite avec un compte d'administrateur du domaine ou de la machine. Cela se change dans les propriétés du service, ou avec sc.exe config, et on redémarre.

    Le contrôle web est en critique et le site fonctionne¶

    Trois causes habituelles :

    • Le serveur Pandora FMS n'atteint pas l'URL : DNS, proxy ou pare-feu.
    • Le contenu a changé et ne correspond plus à la chaîne que cherche le module (check_string). Une refonte de la page casse le module même si le service est parfait.
    • La connexion se coupe en cours de route (proxy avec authentification, par exemple).

    Pour voir ce qui se passe exactement, on ajoute le débogage au module lui-même :

    task_begin
get https://www.example.com
cookie 1
resource 1
check_string <chaine_qui_doit_apparaitre>
debug /tmp/request.log
task_end

    À la nouvelle exécution, le fichier indique l'erreur en détail.

    Les interfaces SNMP sont actives mais la console les affiche en panne¶

    Avant de toucher au module, confirmez que la donnée arrive :

    • Interrogez l'état depuis le serveur avec snmpget ou avec l'explorateur SNMP de la console. Si là elle apparaît active et que dans le module non, le problème est dans le module.
    • Vérifiez la charge du serveur. Avec peu de ressources, les contrôles SNMP se perdent et l'état que vous voyez est le dernier arrivé, pas le réel.

    La macro _modulegraph_nh_ ne fonctionne pas¶

    Cette macro insère le graphique du module dans un courriel d'alerte, et pour le dessiner la console se demande l'image à elle-même. Si elle sort cassée, il manque l'accès à l'API. Il faut définir le mot de passe de l'API dans la console (Gestion → Réglages → Configuration du système → Configuration générale) et décommenter console_api_pass dans la configuration du serveur, avec le même mot de passe.

    WMIC et PandoraWMIC¶

    WMIC est l'interface en ligne de commandes de WMI que Windows apporte. Pandora FMS l'utilise uniquement pour interroger (par exemple, PROCESS GET NAME renvoie les processus en cours d'exécution), jamais pour changer quoi que ce soit sur la machine.

    PandoraWMIC est le client que le serveur utilise par défaut (wmi_client pandorawmic), pensé pour ces requêtes de supervision.

    Un plugin de serveur ne s'initialise pas¶

    Les plugins de serveur s'exécutent sur le serveur Pandora FMS lui-même, tels qu'ils se configurent dans Serveurs → Plugins. Pour le déboguer, on le lance à la main dans le terminal avec le même utilisateur que celui avec lequel tourne le serveur (par défaut root) et les mêmes paramètres.

    La sortie doit être une seule donnée, et du type que vous avez déclaré à la création du module (numérique ou alphanumérique). Si le type ne correspond pas, le module ne démarre pas (l'exception est le type incrémental, qui montre la sortie telle quelle). De plus, la commande doit se terminer sans erreurs : si l'errorlevel n'est pas 0, le serveur écarte le résultat.

    L'agent envoie des données mais elles n'apparaissent pas dans la console¶

    C'est souvent l'heure. Si l'horloge de la machine où tourne l'agent est décalée, les marques temporelles apparaissent déplacées par rapport au serveur et les données peuvent être difficiles à localiser dans la vue ou dans les graphiques.

    Vérifiez le décalage entre les deux machines et synchronisez-les par NTP. Ensuite, vérifiez l'intervalle suivant et consultez le journal du serveur si les données n'apparaissent toujours pas.

    Ajouter une MIB à Pandora FMS¶

    Les MIB se chargent depuis la console web elle-même. Dans le menu de supervision de SNMP se trouve la section de chargement de MIB (Monitoring → SNMP → MIB uploader). De là, on téléverse tous les fichiers nécessaires, l'un après l'autre. La MIB est un fichier texte. On peut l'ouvrir avec n'importe quel éditeur pour vérifier que c'est bien celle du fabricant et du modèle corrects.

    Après avoir chargé la MIB, la console ne reconnaît toujours pas les OID¶

    Charger la MIB dans la console ne suffit pas : le système d'exploitation doit savoir où elle est. On vérifie quels répertoires net-snmp consulte :

    net-snmp-config --default-mibdirs
snmpget -Dparse-mibs 2>&1 | grep directory

    Si le répertoire où vous avez laissé la MIB n'apparaît pas dans cette liste, déplacez-la vers un de ceux qui apparaissent. Ou ajoutez le vôtre à la configuration de net-snmp.

    L'assistant SNMP ne trouve pas les OID de l'appareil¶

    Avant de vous battre avec l'assistant, interrogez l'appareil directement depuis le serveur. Avec snmpwalk on parcourt ce qu'il expose et avec snmpget on demande une OID concrète :

    snmpwalk -v1 -c 'COMMUNAUTE' 192.0.2.10
snmpget  -v1 -c 'COMMUNAUTE' 192.0.2.10 1.3.6.1.2.1.43.5.1.1.1.1.0

    Remplacez COMMUNAUTE et 192.0.2.10 par les valeurs de votre appareil.

    Si l'appareil répond à ces commandes, le problème est dans la MIB ou dans l'assistant. S'il ne répond pas, il est dans le réseau ou dans la communauté SNMP. Et quoi que vous fassiez dans la console, cela ne change rien.

    Les traps n'arrivent pas¶

    Le premier endroit à regarder est le journal de traps de Pandora FMS :

    tail -f /var/log/pandora/pandora_snmptrap.log

    Si le message « No access configuration - dropping trap » apparaît, le démon de traps a son accès configuré mais n'autorise pas cette communauté. Cela se corrige en ajoutant la communauté au fichier de configuration de snmptrapd et en redémarrant :

    echo "authCommunity log <communaute_configuree>" >> /etc/snmp/snmptrapd.conf
systemctl restart pandora_server

    La communauté doit correspondre à celle qu'envoie l'appareil. N'utilisez pas public en production, sauf si c'est vraiment la communauté configurée.

    De plus, le serveur de console SNMP de Pandora FMS est désactivé par défaut : vérifiez que dans /etc/pandora/pandora_server.conf le jeton snmpconsole est à 1. Un serveur interne éteint ne donne pas d'erreur, il ne fait simplement pas son travail.

    « couldn't open udp:162 »¶

    Le port 162 est occupé par le snmptrapd du système d'exploitation, donc Pandora FMS ne peut pas écouter. On arrête le service de traps du système et on redémarre Pandora FMS. Si cela se reproduit après un redémarrage, on désactive celui du système :

    systemctl stop snmptrapd
systemctl disable snmptrapd
systemctl restart pandora_server

    Sous Debian et Ubuntu, seules les OID numériques fonctionnent¶

    Debian et Ubuntu fournissent l'arbre de MIB désactivé, donc leur SNMP ne comprend que les adresses numériques et la console ne résout pas les noms. On le reconfigure en deux étapes. D'abord, installer le téléchargeur de MIB. Ensuite, laisser le fichier de configuration de SNMP propre (/etc/snmp/snmp.conf, sans lignes actives).

    apt-get install snmp-mibs-downloader

    Supprimer les anciens traps¶

    Si ce que vous voulez est un nettoyage ponctuel, on peut le faire depuis Outils d'administration → Interface de la base de données avec une instruction sur la table ttrap :

    SELECT COUNT(*) FROM ttrap WHERE timestamp < '<AAAA-MM-JJ 00:00:00>';
DELETE FROM ttrap WHERE timestamp < '<AAAA-MM-JJ 00:00:00>';

    Remplacez la date par celle qui correspond et vérifiez le résultat du SELECT avant d'exécuter le DELETE.

    Pour que cela ne s'accumule plus, la console a le réglage « Jours max. avant suppression des traps SNMP » dans Gestion → Réglages → Configuration du système → Performances (jeton trap_purge). À partir de là, les traps qui dépassent cette ancienneté passent dans l'historique puis sont purgés.
