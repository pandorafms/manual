# Automatisation et plugins

Faire travailler Pandora FMS tout seul : ligne de commande, API, macros et
plugins.

Deux façons de travailler avec Pandora FMS sans passer par l'écran : la **CLI**,
qui s'exécute sur le serveur lui-même, et l'**API**, qui s'appelle depuis
l'extérieur. Les deux servent à automatiser et à faire en lot ce qui serait
interminable à la main.

## Ce qu'est la CLI et comment on l'utilise

C'est un outil d'administration en ligne de commande qui s'exécute **sur le
serveur de Pandora FMS**. Il sert à créer et supprimer des utilisateurs, des
agents et des modules, à configurer des alertes et des politiques, à gérer des
événements et bien plus encore : c'est donc la voie naturelle pour automatiser
des tâches avec des scripts.

On l'exécute sur le serveur avec `pandora_manage` et la configuration du
serveur :

```bash
/usr/bin/pandora_manage \
    /etc/pandora/pandora_server.conf OPCION PARAMETROS
```

Remplacez `OPCION` et `PARAMETROS` par les arguments de l'opération que vous allez
exécuter.

Un exemple réel : créer un groupe nommé « Virtuales » à l'intérieur d'un autre
nommé « Servidores » :

```bash
/usr/bin/pandora_manage /etc/pandora/pandora_server.conf \
    --create_group 'Virtuales' 'Servidores'
```

La liste des opérations est longue (agents, modules, alertes, modèles,
politiques, événements, utilisateurs, profils, collections, consoles visuelles…).
Pour la voir en entier, on exécute le binaire **sans options** : il affiche l'aide
avec la syntaxe de chacune.

## Ce qu'est l'API et comment on la protège

L'API est un fichier PHP de la console que l'on appelle par HTTP, avec `curl` ou
depuis un outil web. Elle a **trois couches de sécurité**, et il faut configurer
les trois avant de l'utiliser :

1. **Adresses IP autorisées.** Dans **Gestion → Réglages → Configuration du
   système → Configuration générale**, le champ **« IP list with API access »**
   accepte une IP par ligne. Le caractère générique `*` ouvre l'API à tout le
   monde, et ce n'est pas recommandé.
2. **Mot de passe de l'API.** Au même endroit, le champ **« API password »**.
3. **Identifiants de l'utilisateur.** Chaque appel identifie en plus l'utilisateur
   de Pandora FMS qui le fait, avec son mot de passe.

Comme le mot de passe de l'API voyage dans l'appel lui-même, il convient de les
faire en **HTTPS** pour que le canal soit chiffré.

Un appel de test, le plus simple, pour vérifier que tout est en place :

```
https://console.example.com/pandora_console/include/api.php?info=version
```

Remplacez `console.example.com` par le nom de votre console.

Les mots de passe ne sont pas publiés ici : chaque installation met les siens
dans la console.

## Créer et valider des événements par l'API depuis une autre machine

Le produit fournit un outil pour lancer des événements contre l'API **depuis un
système distant**, sans avoir à toucher la base de données ni à disposer d'un
EndPoint installé : **`/usr/bin/pandora_revent`**.

```bash
/usr/bin/pandora_revent \
    -p https://console.example.com/pandora_console/include/api.php \
    -u 'API_PASSWORD,USER_NAME,USER_PASSWORD' \
    -create_event \
    -name "Nom de l'événement" -group 0 -type "system" -status 0 -severity 4 \
    -user "USER_NAME" -owner_user "USER_NAME" -source "Commandline" \
    -user_comment "Commentaire de l'événement"
```

Le paramètre `-u` porte les trois identifiants ensemble, séparés par des virgules :
le mot de passe de l'API, l'utilisateur et son mot de passe.

Le même outil **valide** des événements, ce qui est utile pour les clôturer depuis
l'extérieur :

```bash
/usr/bin/pandora_revent -p https://console.example.com/pandora_console/include/api.php \
    -u 'API_PASSWORD,USER_NAME,USER_PASSWORD' -validate_event -id EVENT_ID
```

Remplacez les valeurs d'exemple par l'hôte et les identifiants de votre
installation.

Exécuté **sans options**, il affiche son aide avec la syntaxe complète.

## Macros dans les alertes

Une macro est une chaîne entourée de caractères de soulignement (`_macro_`). La
console la remplace par un texte au moment de lancer l'action d'une alerte. Elles
servent à ce que l'avis indique de quel agent il vient, quel module l'a déclenché
et avec quelle valeur, sans l'écrire à la main.

Les groupes les plus utilisés :

| Groupe | Exemples |
|---|---|
| Agent | `_agentname_` (nom), `_agentalias_`, `_address_` (son adresse), `_agentstatus_`, `_agentos_`, `_agentgroup_`, `_agentcustomfield_n_` |
| Module | `_module_` (nom), `_data_` (la valeur qui a déclenché), `_modulegraph_nh_` (le graphique) |
| Alerte | `_alert_name_`, `_alert_priority_`, `_alert_text_severity_` |

La liste complète se trouve dans l'aide de la console elle-même. Les macros sont
remplacées dans l'objet et dans le corps de l'action. Sans elles, chaque alerte
devrait porter le message écrit à la main.

## Macros personnalisées

En plus de celles fournies d'origine, on peut définir les siennes. C'est la façon
qu'a un avis de dire quelque chose de spécifique à votre environnement.

Elles se créent dans l'**édition du module lui-même**, dans la section **« Macros
personnalisées »**. On ajoute des paires de **clé et valeur**, et la clé s'écrit
entre caractères de soulignement. Par exemple :

```
_clé_          _technology_
valeur          le système de logs
```

Ensuite, cette macro se référence dans l'alerte comme n'importe quelle autre :

```
L'agent signale du nouveau contenu dans _technology_
```

et la console la remplace par la valeur que **ce module** a configurée. Comme la
valeur vit dans le module, chacun peut porter la sienne.

## Plugins d'agent

Un plugin d'agent est un programme ou un script qui s'exécute **sur la machine
supervisée**. Il renvoie un morceau de **XML** que l'agent insère dans le paquet
qu'il envoie au serveur. Un seul plugin peut renvoyer des données de **plusieurs
modules**.

On l'ajoute de deux manières :

- Dans `pandora_agent.conf`, avec une ligne :
  ```
  module_plugin /chemin/vers/plugin
  ```
- Depuis la console, dans la configuration de l'agent, dans la section des
  **plugins** (l'icône de la pièce de puzzle) : on indique le chemin complet du
  plugin.

À partir de là, il fonctionne comme un module local de plus. On peut l'écrire dans
n'importe quel langage de script ; s'il a besoin de bibliothèques (par exemple
Java), il faut les distribuer avec lui.

## Plugins de serveur

Un plugin de serveur est un script qui s'exécute **sur le serveur de Pandora FMS
lui-même**, pas sur la machine supervisée. Il renvoie **une seule valeur**
(numérique, booléenne ou de texte) et on peut lui passer des paramètres.

- Ils vivent par défaut dans `/usr/share/pandora_server/util/plugin`, et le
  produit en fournit déjà quelques-uns en exemple (par exemple,
  `iface_bandwith.pl`).
- Ils s'enregistrent dans **Servers → Plugins** : nom, type (standard ou de
  Nagios), *timeout* maximum, la commande et ses paramètres (qui acceptent des
  macros).
- **Qui les exécute** : le **Heavy Server**. Il n'existe aucun serveur
  `pluginserver` à activer, comme le disaient les anciennes fiches. Le Heavy
  Server est actif par défaut et se charge des plugins, du NCM et de
  l'inventaire.

La façon la plus rapide de les déboguer est de les lancer à la main dans le
terminal, avec les mêmes paramètres. Presque tous fournissent une aide avec `-h`,
`-help` ou sans argument.

!!! warning "Le timeout est le piège habituel"
    Si le plugin prend plus de temps que le *timeout* configuré, il est coupé et le
    module se retrouve sans donnée. Mesurez le temps que met le script et laissez
    une marge.

## Le module du plugin apparaît comme « Inconnu »

Lorsqu'un plugin définit ses propres modules, le XML qu'il génère doit respecter
le **`module_interval`** que vous avez configuré. Si le plugin ne le déclare pas,
la console attend les données à un autre rythme. Les modules finissent en
**Inconnu** alors que le plugin fonctionne.

Cela se corrige dans le plugin lui-même : que le XML inclue l'intervalle avec
lequel il s'exécute. C'est un petit réglage qui évite une cascade de faux
inconnus.
