# Serveur et base de données

Les deux pièces dont tout le reste dépend : le serveur qui traite et la base de données qui stocke. Quand l'une tombe, l'autre le ressent.

Le serveur de Pandora FMS est une application avec plusieurs serveurs internes.
Quand il ne démarre pas, redémarre seul ou tombe, le journal dit pourquoi.
Presque tout se règle en le lisant avant de toucher à quoi que ce soit.

## Le serveur ne démarre pas

La première chose, ce sont les deux fichiers de journal :

- `/var/log/pandora/pandora_server.log`
- `/var/log/pandora/pandora_server.error`

L'erreur précise y apparaît. Vérifiez aussi MySQL, qui est bien une dépendance du
serveur. `tentacle_serverd` est un service à part : s'il est arrêté, les
EndPoints ne pourront pas livrer de données par Tentacle, mais cela n'empêche
pas à lui seul `pandora_server` de démarrer.

## Le serveur redémarre en boucle

Quand quelque chose le tue et le relance toutes les quelques minutes, le suspect
est le **temps de démarrage**. Le jeton **`server_keepalive`** du
`/etc/pandora/pandora_server.conf` vaut **45** secondes par défaut. Si le serveur
met plus que cela à devenir opérationnel, le système de haute disponibilité ne
le voit pas actif et le redémarre, et ainsi de suite en boucle.

La cause habituelle est d'avoir augmenté les threads des serveurs internes
(`*_threads`) : plus il y a de threads, plus le démarrage est long. On corrige
en augmentant `server_keepalive` pour qu'il couvre ce démarrage.

## Le serveur tombe

On consulte le même journal et, si rien n'apparaît, on écarte ces causes dans
l'ordre :

- **Mémoire insuffisante.** Le serveur manque de RAM et le système le tue.
- **MySQL.** Une base de données qui ralentit ou qui tombe entraîne le serveur.
- **Nœuds pleins.** Dans un Command Center, un nœud sans espace cesse de
  répondre.
- **Une mise à jour à moitié faite.** Paquets incorrects ou mise à jour du schéma
  de la base de données qui ne s'est pas terminée.

## « Segmentation fault » au démarrage du serveur

Elle peut apparaître quand on a assigné plus de threads que le matériel ne peut
en initialiser et en soutenir. Vérifiez les jetons `*_threads` du fichier et
réduisez ceux qui ont été augmentés sans une mesure qui le justifie. Il n'y a pas
d'équivalence fixe entre threads et modules : cela dépend du type de contrôle, de
l'intervalle, de la concurrence et du matériel. Mesurez avant de les augmenter à
nouveau.

## Activer ou arrêter des serveurs internes

Chaque serveur interne s'allume et s'éteint avec son jeton dans
`/etc/pandora/pandora_server.conf` : **`1`** l'active et **`0`** le désactive.
Ceux qui sont nécessaires selon l'usage sont expliqués dans
[Introduction et architecture](../parte-1/1.2-introduccion-y-arquitectura.md).

Après avoir modifié le fichier, il faut redémarrer le service :

```bash
systemctl restart pandora_server
```

Un serveur interne arrêté ne donne pas d'erreur : il ne fait simplement pas son
travail, donc si quelque chose « n'est pas traité » et que le jeton est à 0, vous
savez déjà où chercher.

## Lancer la purge de la base de données à la main

La maintenance s'installe dans `/etc/cron.hourly/pandora_db` et appelle l'outil
avec la configuration du serveur :

```bash
/usr/bin/pandora_db /etc/pandora/pandora_server.conf
```

Le binaire est `/usr/bin/pandora_db` ; le paquet le programme dans
`/etc/cron.hourly/pandora_db`.

Si elle ne s'est jamais exécutée, la première passe peut prendre des **heures** :
lancez-la en arrière-plan et ne la coupez pas à moitié.

## Le noyau signale « possible SYN flooding on port 41121 »

Le port de Tentacle est le **41121/TCP**. Un décompte élevé de connexions
`TIME_WAIT` peut servir d'indice, mais ne prouve pas à lui seul que la file SYN
est saturée. Regardez aussi les connexions `SYN_RECV` et les compteurs de
retransmission avant de changer des paramètres du noyau :

```bash
netstat -an | grep TIME_WAIT | wc -l
```

Certains déploiements actuels fixent `tcp_max_syn_backlog` à **65536**. Ce n'est
pas une valeur universelle et cela ne corrige pas à soi seul un problème de
réseau ou de capacité : identifiez d'abord où les connexions sont écartées.

```
net.ipv4.tcp_max_syn_backlog = 65536
```

!!! warning "N'utilisez pas `tcp_tw_recycle`"
    Le paramètre `net.ipv4.tcp_tw_recycle` que recommandaient les anciens guides
    a été retiré du noyau Linux dans la version 4.12. Ne le cherchez pas et ne
    l'ajoutez pas.

Dans la base de données, les causes habituelles sont la maintenance qui ne
s'exécute pas, une table endommagée, un stockage lent ou une rétention de
données mal dimensionnée.

## Comment sauvegarder la base de données

Le produit apporte son propre outil : **`pandora_backup.sh`**, dans
`/usr/share/pandora_server/util/`. Le chemin de la console se passe avec `-c` ;
la destination de la sauvegarde, avec `-d` :

```bash
# Sauvegarde (base de données + fichiers de la console)
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console -d /tmp

# Restaurer la base de données depuis une sauvegarde
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console \
    -s /chemin/vers/la/sauvegarde/pandorafms_backup_date.tar.gz

# Restaurer aussi les fichiers et la configuration (en plus de la base de données)
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console \
    -s /chemin/vers/la/sauvegarde/pandorafms_backup_date.tar.gz -f
```

Le chemin de la console passé avec **`-c` est aussi nécessaire lors de la
restauration** : l'outil s'en sert pour lire les identifiants de la base de
données. Sans `-f`, il restaure la base de données, mais pas les fichiers de la
console ni la configuration. Avec `-f`, il restaure aussi ces fichiers et le
spool ; **`-b`** exclut la base de données. La restauration de la base **supprime
et recrée la base configurée**. Vérifiez le fichier et faites une copie de l'état
actuel avant de continuer.

Si vous préférez le faire à la main, la base de données et l'utilisateur
s'appellent généralement `pandora`. L'exemple de restauration suppose que la
base existe déjà :

```bash
mysqldump -u pandora -p pandora > /chemin/pandora_backup_date.sql
mysql -u pandora -p pandora < /chemin/pandora_backup_date.sql
```

Les identifiants se consultent dans `/etc/pandora/pandora_server.conf`, dans les
champs `dbuser`, `dbpass` et `dbname`. **Ils ne sont pas copiés ici.**

## La base de données ralentit

Avant de toucher à la configuration de MySQL, écartez ces quatre causes, dans
l'ordre :

1. **La maintenance ne s'exécute pas.** Le paquet laisse le script dans
   `/etc/cron.hourly/pandora_db`, qui appelle
   `/usr/bin/pandora_db` avec la configuration du
   serveur. S'il s'est perdu ou si le cron ne tourne pas, la base croît sans
   limite. Lancez-le à la main et regardez s'il renvoie une erreur.
2. **La rétention ne correspond pas à l'usage.** Vérifiez les périodes de purge
   et, dans les grands environnements, s'il convient de déplacer les données
   anciennes vers une **base de données historique**. Il n'y a pas de période
   universelle : cela dépend de la quantité de données collectées et de ce qu'il
   faut pouvoir consulter.
3. **Le stockage.** Vérifiez la latence, l'espace libre et la charge de lecture
   et d'écriture. Un disque saturé affecte autant MySQL que le serveur.
4. **Le réglage fin de MySQL.** Des paramètres comme `innodb_buffer_pool_size` ou
   `innodb_io_capacity` s'ajustent à la taille réelle de la machine et au volume
   de données. Il n'y a pas de valeurs universelles : on part d'une
   recommandation pour la taille du serveur et on mesure.

## La console signale « Maintenance de la base de données »

Cet avertissement signifie que la maintenance ne s'exécute pas. La base de
données a besoin de ce script **toutes les heures** : il purge les données
anciennes, compacte et déplace vers l'historique ce qui correspond.

Vérifiez qu'il existe et qu'il fonctionne :

```bash
/usr/bin/pandora_db /etc/pandora/pandora_server.conf
```

Si le script répond qu'**« une autre instance semble être en cours
d'exécution »**, le verrou nommé de MySQL indique qu'une autre connexion exécute
la maintenance. Le verrou se libère quand elle se termine ou que la connexion se
ferme. Vérifiez s'il y a une autre exécution active et consultez ses journaux ; ne
supprimez pas à la main un supposé indicateur de verrou dans la table de
configuration.

## Erreur de base de données au démarrage du serveur

Si le journal du serveur montre un échec de connexion au démarrage
(`DBI connect ... failed`), vérifiez d'abord ces deux points :

- **Le mot de passe ou l'utilisateur ne sont pas corrects.** On teste à la main
  avec `mysql -u pandora -p -h 127.0.0.1 -D pandora` et on les compare avec les
  champs `dbuser`, `dbpass` et `dbname` de `/etc/pandora/pandora_server.conf`.
- **L'hôte configuré est `localhost` et le socket ne correspond pas.** Certains
  empaquetages de MySQL utilisent `/var/lib/mysql/mysql.sock` au lieu de
  `/tmp/mysql.sock`. La valeur actuelle par défaut de `dbhost` est `127.0.0.1`,
  qui utilise TCP ; si votre installation utilise `localhost`, vérifiez d'abord
  le chemin réel du socket avant de le changer.

Dans les versions actuelles, **`dbhost`** est fourni avec `127.0.0.1`, ce qui
évite les problèmes de résolution de `localhost` en IPv6.

## La base de données ne répond pas et il y a trop de données

Il n'y a pas de nombre universel d'enregistrements à partir duquel la base cesse
de répondre. Le volume de données, le taux d'écriture, les requêtes, la rétention
et le matériel entrent en jeu. Avant de reconstruire quoi que ce soit, consultez
le journal de MySQL, l'espace et la charge ; confirmez que la maintenance
fonctionne et que la politique de purge et d'historique correspond à ce dont vous
avez besoin. Faites une copie avant toute réparation. Une reconstruction ou une
restauration de la base doit être planifiée avec un DBA : ne supprimez pas le
répertoire de données ni la base à l'aveugle.

## « Table is marked as crashed and should be repaired »

`REPAIR TABLE` ne sert qu'aux moteurs qui admettent cette opération, comme
MyISAM. Les tables principales de Pandora FMS utilisent InnoDB : vérifiez d'abord
le moteur et l'erreur précise avant de tenter une réparation :

```sql
SHOW TABLE STATUS LIKE 'nom_de_la_table';
```

Si la table utilise MyISAM, `REPAIR TABLE nom_de_la_table;` peut être approprié.
Si elle utilise InnoDB, ce n'est pas la procédure : conservez le journal de
l'erreur et consultez le diagnostic du moteur ou restaurez une copie validée avec
un DBA.

## Corruption dans la base de données

Avant de tenter une réparation, identifiez le moteur de la table. `mysqlcheck
--auto-repair` ne sert qu'aux moteurs qui admettent cette opération, comme
MyISAM ; il ne répare pas InnoDB. Les tables principales de Pandora FMS utilisent
InnoDB. Conservez le journal de l'erreur, faites une copie et consultez la
procédure de récupération pour ce moteur avec un DBA. Ne supprimez pas
`/var/lib/mysql` et ne recréez pas la base de données comme premier essai.

## Erreur « PROCESS privilege » lors d'un dump

Dans MySQL 8, si `mysqldump` échoue faute du privilège `PROCESS` à la lecture des
*tablespaces*, essayez d'abord de les omettre avec `--no-tablespaces` :

```bash
mysqldump --no-tablespaces -u pandora -p pandora > /chemin/backup.sql
```

Ainsi, il n'est pas nécessaire d'accorder `PROCESS` global à l'utilisateur de
l'application juste pour créer une copie. Si votre version n'accepte pas
l'option, consultez le DBA avant de changer les privilèges.

## La maintenance traite aussi la base de données historique

La maintenance horaire standard gère l'historique quand il est configuré. Le
serveur lit les paramètres de connexion enregistrés dans la configuration de la
base principale et se connecte avec l'hôte, la base et l'utilisateur indiqués
là. Il n'est pas nécessaire de créer une autre tâche cron avec une copie
manuelle de `pandora_server.conf`. Vérifiez que la base historique est activée et
que la connexion configurée fonctionne.
