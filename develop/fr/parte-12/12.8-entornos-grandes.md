# Grands environnements

Command Center, plusieurs nœuds et haute disponibilité : ce qui change lorsque
l'environnement grandit.

Cette section regroupe les incidents qui apparaissent lorsqu'il faut coordonner
plusieurs nœuds, répartir la charge et configurer la haute disponibilité.

## Le serveur d'un nœud ne démarre pas dans un Command Center

Le serveur de chaque nœud se connecte à la base de données configurée dans son
propre `pandora_server.conf`. S'il ne démarre pas, vérifiez d'abord cette
connexion. Pour un incident de réplication vers le Command Center, consultez la
question « Les événements n'arrivent pas au Command Center » plus bas.

1. **Le moteur de base de données du nœud est en marche.** Vérifiez le service
   MySQL, MariaDB ou Percona qu'utilise ce nœud.
2. **Le nœud atteint l'hôte indiqué par `dbhost`.** Testez la connexion depuis le
   serveur du nœud lui-même, avec les valeurs `dbname`, `dbuser` et `dbhost` de sa
   configuration.
3. **L'utilisateur peut accéder depuis cet hôte.** Si les identifiants sont
   corrects mais que la connexion est refusée, contrôlez les permissions de la
   base de données du nœud.

Les valeurs de connexion et les mots de passe se consultent dans le fichier de
configuration du serveur ; ils ne sont pas recopiés ici.

## Supprimer des agents dans un Command Center en mode centralisé

Dans un environnement où la gestion centralisée est activée, l'administration des
agents entre nœuds se coordonne depuis **Gestion centralisée → Gestion des agents**
(**Centralised management → Agent management**).

Pour la suppression définitive d'un agent, il faut agir selon son origine :

- S'il s'agit d'un **EndPoint**, désinstallez ou arrêtez le service sur la machine
  pour qu'il n'envoie plus de XML, puis supprimez-le dans la console de son nœud
  ou au moyen des opérations massives d'agents.
- S'il a été découvert par un serveur satellite ou généré par un plugin distant,
  supprimez la définition sur le satellite ou la vérification d'origine avant de
  le supprimer dans la console.

Supprimer un agent uniquement dans l'écran, sans arrêter son origine, fait que le
serveur le recrée dès qu'il reçoit le paquet de données suivant.

## Comment supprimer un agent

Cela dépend de l'origine de l'agent, et le supprimer dans la console ne suffit pas
toujours :

| Type d'agent | Comment on le retire |
|---|---|
| **Fictif** | Celui qui est créé à la main dans la console : on le supprime là et c'est tout |
| **EndPoint** | Celui qui est installé sur la machine : on le supprime dans la console et on désinstalle l'EndPoint, si vous ne voulez plus le revoir |
| **Broker** | Il est créé par l'agent principal du dispositif : si on le supprime seulement dans la console, il réapparaît |
| **De satellite** | Il est créé par un serveur satellite à partir de sa configuration : il faut retirer la définition sur le satellite |
| **De plugin** | Il est généré par un plugin lors de son exécution : tant que le plugin continue à créer ce XML, l'agent revient |

La règle générale est simple : **si l'agent est généré par autre chose, supprimez-le
à l'origine**. Dans la console, on peut les supprimer par lots depuis les
opérations massives d'agents.

## Plusieurs serveurs et haute disponibilité

Pandora FMS accepte **plusieurs serveurs de données et de réseau contre la même
base de données**, en répartissant la charge. Cela permet de faire croître le
nombre d'agents sans changer de produit. Trois pièces soutiennent l'ensemble :

- **MySQL bien dimensionné.** C'est le goulot d'étranglement habituel : sans
  mémoire et sans réglage, les serveurs supplémentaires ne servent à rien.
- **Un cluster MySQL** pour la haute disponibilité et pour répartir la charge de
  la base de données.
- **L'outil de haute disponibilité** (`pandora_ha`), qui peut surveiller le
  serveur et tenter de le récupérer. Son installation et son démarrage dépendent
  du packaging et du runbook du cluster.

Les serveurs d'une même installation et leur répartition du travail sont expliqués
dans [Introduction et architecture](../parte-1/1.2-introduccion-y-arquitectura.md).

## Mode centralisé : ce que c'est et ce qu'il faut vérifier avant de l'activer

Le **mode centralisé** permet d'administrer depuis le Command Center des groupes
d'agents, des tags, des alertes, des utilisateurs, des politiques et des
collections sur plusieurs nœuds. Il s'active en fusionnant l'environnement avec
la **Merging tool** (voir [6.3 · Command Center](../parte-6/6.3-command-center.md)) ;
à partir de là, le Command Center devient la source de configuration des nœuds.

!!! warning "À vérifier deux fois avant de l'activer"
    Si l'environnement fonctionnait depuis longtemps avec le Command Center et
    plusieurs nœuds séparés, il est normal que chacun ait **des choses
    différentes** de créées (groupes, tags, politiques). À l'activation du mode,
    le Command Center devient la source de configuration. Ce qui existait sur les
    nœuds peut être écrasé ou devenir incohérent.

    Avec l'environnement en marche, il convient d'**inventorier d'abord** ce qu'il
    y a sur chaque nœud, de décider quelle version est la bonne et de l'activer
    dans une fenêtre, avec une sauvegarde de toutes les bases de données.

## Les événements n'arrivent pas au Command Center

La réplication des événements se configure sur **chaque nœud**, pas dans le
Command Center. Si les événements d'un nœud n'apparaissent pas en haut, on
vérifie :

1. **Les données de la base de données de réplication** dans **Setup →
   Enterprise** du nœud : serveur, nom de la base et utilisateur
   (`replication_dbhost`, `replication_dbname`, `replication_dbuser`). S'ils sont
   erronés, le nœud n'a nulle part où écrire.
2. **La connectivité** du nœud vers cette base de données.
3. **Le journal du serveur du nœud**, où chaque réplication laisse sa trace (une
   ligne par lot d'événements répliqués). Si rien n'y apparaît, le problème vient
   de la configuration. Si quelque chose apparaît mais que le Command Center ne
   les affiche pas, le problème vient de la lecture.

Dans la console du nœud elle-même, on peut voir la date de la dernière
réplication, ce qui est la vérification la plus rapide.

## L'historique d'un module n'est pas visible dans le Command Center

Lorsque l'on ouvre le graphique d'un module dans le Command Center et qu'une
erreur du type **« Error connecting to database history at … »** apparaît, il
manque au Command Center les **privilèges sur la base de données d'historique** de
ce nœud.

Le Command Center se connecte à l'historique avec **l'utilisateur, l'hôte, le mot
de passe et le nom de base que le nœud a configurés** pour son historique. Le
droit s'accorde sur la machine d'historique, à cet utilisateur et pour l'IP du
Command Center. Si le nœud change ces données, il faut mettre à jour le droit.

Les mots de passe se consultent dans la configuration de chaque installation ; ils
ne sont pas publiés ici.

## Récupérer un nœud tombé dans un environnement HA

En haute disponibilité, lorsqu'un nœud tombe ou que le réseau est coupé,
**l'esclave prend le relais** comme maître. Au retour du nœud tombé, sa base de
données est restée désynchronisée. Il faut la **resynchroniser depuis le maître
actuel** avant de le remettre en service. C'est ce que l'on appelle un « nœud
cassé ».

La procédure, en résumé :

1. Placer le nœud tombé en **standby** dans le cluster, pour qu'il ne tente pas de
   prendre du travail.
2. **Arrêter son MySQL** et mettre de côté son répertoire de données.
3. Faire une **copie du maître** et la restaurer sur le nœud tombé.
4. Resynchroniser avec le cluster et remettre le nœud en service.

!!! warning "Opération de DBA"
    Cela se fait avec les outils du cluster (Percona XtraBackup, et
    Pacemaker/Corosync pour le cluster) et avec une fenêtre devant soi. Un pas
    mal exécuté laisse les deux nœuds hors service : il convient donc de suivre
    le runbook de haute disponibilité et de ne pas improviser sur un
    environnement en production.

Les paramètres du service de haute disponibilité se trouvent dans le fichier du
serveur : **`ha_interval`**, **`ha_hosts`**, **`ha_dbuser`** et **`ha_dbpass`**.
