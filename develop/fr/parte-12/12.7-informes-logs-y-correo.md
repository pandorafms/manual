# Rapports, logs et courrier

Cette section regroupe les incidents liés aux rapports, aux collections, à la
visionneuse de logs et au courrier.

## Les rapports PDF ne se génèrent pas

Le PDF d'un rapport est composé par la console avec un **Chromium en mode sans
interface**. Le premier point à vérifier n'est donc pas PHP, mais le moteur de
rendu :

- Vérifiez que **Chromium est installé** sur le serveur.
- Contrôlez le réglage **Chromium path** dans **Gestion → Réglages →
  Configuration du système → Configuration générale** : il doit pointer vers le
  binaire réel (par défaut, `/usr/bin/chromium-browser`).
- Si vous venez de toucher à la configuration de PHP, redémarrez le service web
  pour qu'elle soit prise en compte.

!!! note "Avis"
    Les anciennes fiches parlaient de `curl` et de `allow_url_fopen` pour générer
    les PDF. C'était le mécanisme précédent : aujourd'hui le rapport est rendu par
    Chromium, et c'est donc là qu'il faut regarder en premier.

## Manque de mémoire lors de la génération d'un rapport ou d'une mise à jour

L'erreur que vous voyez vient de PHP, pas de Pandora FMS :

```
Fatal error: Allowed memory size of XXXXX bytes exhausted
```

La limite se relève dans `php.ini` (`/etc/php.ini` ou
`/etc/php/8.x/apache2/php.ini` selon le système), dans la variable
**`memory_limit`**, et si le processus met trop de temps, également
**`max_execution_time`**. Ensuite, redémarrez le service web.

Ne relevez pas la valeur sans mesure : un `memory_limit` énorme peut faire tomber
la machine lorsque plusieurs requêtes coïncident. Relevez juste ce qu'il faut et
vérifiez.

## Les collections de fichiers ne fonctionnent pas

L'agent a besoin d'**`unzip`** pour décompresser les collections. Sous Linux,
c'est une dépendance du paquet de l'agent : vérifiez donc qu'il est installé et
que l'utilisateur avec lequel tourne l'agent le trouve dans son `PATH`.

Si la collection ne s'applique toujours pas, regardez le répertoire de collections
de l'agent, **`/etc/pandora/collections`**. Chaque collection téléchargée laisse un
fichier `.md5` à côté de son dossier :

- S'il existe un `.md5` **sans dossier** qui lui corresponde, supprimez-le.
- Au cycle suivant, l'agent téléchargera de nouveau la collection et la
  décompressera.

Sous Windows, il n'y a rien à installer : `unzip` voyage avec l'agent.

## « Unable to create the collection »

Lors de la création d'une collection depuis la console, cette erreur vient
généralement des chemins ou des permissions. On vérifie les deux chemins
qu'utilise le processus :

- Le dossier de collections du serveur : `data_in/collections`.
- Le dossier de pièces jointes de la console : le répertoire **Attachment
  directory** configuré dans **Gestion → Réglages → Configuration du système →
  Configuration générale** (par défaut, le dossier `attachment` de la console).

Les deux doivent **exister** et être lisibles et modifiables par l'utilisateur du
serveur web. Si le chemin des pièces jointes de la console ne correspond pas au
chemin réel, la collection ne se crée pas, même si les permissions sont bonnes.

## Les alertes s'exécutent mais l'e-mail n'arrive pas

On vérifie dans cet ordre :

1. **Où le courrier est configuré.** La console ou le fichier du serveur, mais
   **pas les deux à la fois** : s'ils cohabitent, ils s'écrasent.
2. **Les identifiants du compte.** Si quelqu'un a changé le mot de passe, l'envoi
   cesse de fonctionner sans autre avertissement.
3. **Les permissions du compte.** Beaucoup de fournisseurs exigent d'activer
   l'accès depuis des applications tierces.
4. **Le journal du serveur.** Avec la verbosité à 10, les erreurs de courrier
   apparaissent dans `/var/log/pandora/pandora_server.log`. Si le MTA est Postfix,
   sa trace se trouve dans `/var/log/maillog`.

## Les e-mails arrivent avec un expéditeur erroné

L'expéditeur par défaut est `pandora@localhost`, que beaucoup de serveurs de
courrier rejettent. On le change avec le jeton **`mta_from`** de
`/etc/pandora/pandora_server.conf` :

```
mta_from Pandora FMS <pandora@tudominio.com>
```

Après la modification, le serveur est redémarré.

## Pas d'envoi d'e-mail avec authentification

Vérifiez d'abord qu'il y a un MTA sur le serveur, que le service est démarré et
que le port SMTP est ouvert. Ensuite, que les paramètres de courrier sont corrects
dans **l'un des deux endroits** :

| Jeton (dans `pandora_server.conf`) | Pour quoi faire |
|---|---|
| `mta_address` | Adresse du serveur de courrier |
| `mta_port` | Port (par défaut, 25) |
| `mta_user` et `mta_pass` | Utilisateur et mot de passe, si le serveur les demande |
| `mta_auth` | Système d'authentification (LOGIN, PLAIN, CRAM-MD5, DIGEST-MD5) |
| `mta_from` | Expéditeur que verra le destinataire |

L'alternative est de le configurer dans la console, dans **Gestion → Réglages →
Configuration du système → Configuration générale → Configuration des alertes**,
bloc **Configuration du courrier**. Nous insistons : **l'un des deux**, pas les
deux.

Si le courrier est configuré dans la console, vérifiez aussi le mécanisme
d'authentification (**SMTP authentication**). La valeur par défaut utilise le
premier annoncé par le fournisseur et n'essaie pas les suivants : avec un
fournisseur qui annonce `DIGEST-MD5` et le refuse, l'envoi échoue et il faut
choisir `LOGIN`. Dans `pandora_server.log`, l'échec apparaît comme `[ERROR]
Sending email to …`.

## Erreur de résolution de noms lors de l'envoi d'e-mail

Dans le journal de la console apparaît une erreur du type :

```
PHP Warning: fsockopen(): php_network_getaddresses: getaddrinfo failed:
Temporary failure in name resolution
```

C'est un problème de **DNS du serveur**, pas de Pandora FMS. On vérifie la
résolution de noms du système (`/etc/resolv.conf`) et que le nom du serveur de
courrier se résout depuis cette machine. Redémarrer le service web peut débloquer
l'envoi un moment, mais ne corrige pas la cause.

## Les heures ne concordent pas

Le décalage peut se trouver dans trois couches différentes et il vaut mieux les
vérifier toutes avant de toucher à quoi que ce soit :

| Couche | Comment on le vérifie |
|---|---|
| Système | `date`, et le fuseau avec `timedatectl` |
| MySQL | `SELECT now();` et `SELECT @@global.time_zone, @@session.time_zone;` |
| PHP | Un fichier isolé qui affiche `date("Y/m/d H:i:s O e")` |

Une fois la couche décalée identifiée, corrigez-la là : le fuseau du système,
celui du serveur de base de données ou celui de PHP. Les horodatages peuvent
apparaître décalés dans la console ; consultez le journal du serveur si des
données manquent en plus.

## La visionneuse de logs n'affiche rien

Les logs sont stockés dans **OpenSearch**. Si la visionneuse est vide, on vérifie :

1. **Le service d'OpenSearch** est en marche.
2. **La connexion existe** depuis le serveur de Pandora FMS vers le port **9200**.
3. **Le serveur syslog est activé.** Le jeton **`syslogserver`** vaut **0** par
   défaut dans `pandora_server.conf` : sans lui, personne ne traite les logs.
4. **La taille des index.** Des index énormes font que la visionneuse ralentit ou
   ne charge pas ; on les contrôle et on effectue la rotation nécessaire.

## Configurer rsyslog pour le serveur syslog

Le serveur syslog doit recevoir les logs des dispositifs dans un fichier pour les
traiter ensuite. Sur le serveur, il faut avoir **rsyslog** installé et, dans
`/etc/rsyslog.conf`, la réception par **UDP et TCP sur le port 514**, en plus du
fichier où les messages sont écrits.

!!! note "OpenSearch, pas Elasticsearch"
    Les anciennes fiches disent que les logs sont envoyés à Elasticsearch. Le
    stockage qu'utilise la documentation actuelle est **OpenSearch**.

## Intégrer un outil de ticketing

La voie habituelle est l'ouverture et la fermeture d'incidents avec des
**alertes** : l'action de l'alerte appelle l'outil. Cela fonctionne aussi bien
avec un e-mail vers la boîte de réception du ticketing qu'avec un script ou un
appel en ligne de commande.

Pour que l'incident se ferme aussi lorsque le service se rétablit, il faut
connaître la méthode de fermeture et conserver l'identifiant du ticket au moment
de le créer, dans la base de données ou dans un fichier d'échange. Cet identifiant
est la seule chose dont l'alerte de rétablissement a besoin pour fermer le bon
ticket.
