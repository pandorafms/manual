    Agents et systèmes¶

    L'EndPoint collecte des données depuis la machine. Cette section couvre le démarrage, les files d'attente XML et la supervision propre à Windows et à Linux : PowerShell, services et journaux.

    Le nouvel EndPoint n'apparaît pas dans la console web¶

    On vérifie dans cet ordre :

    1. L'agent pointe vers le bon serveur. Dans pandora_agent.conf, le jeton server_ip porte l'adresse du serveur Pandora FMS et server_port le port de Tentacle, qui est 41121. Si le port n'est pas celui-là, l'agent écrit dans le vide.
    2. Le serveur accepte les nouveaux agents. Dans /etc/pandora/pandora_server.conf, le jeton autocreate 1 fait que les agents qui arrivent sans enregistrement préalable se créent seuls, dans le groupe fixé par autocreate_group. Avec autocreate à 0 et un agent qui ne déclare pas de groupe, ses données sont écartées sans autre avis.
    3. Le réseau. C'est l'EndPoint qui lance la connexion vers le serveur, donc le pare-feu doit laisser passer le 41121/TCP depuis la machine jusqu'au serveur.

    Tester Tentacle depuis la ligne de commandes¶

    Le client lance la connexion au serveur Tentacle, par défaut sur le port 41121/TCP. Pour un test, envoyez depuis la machine de l'agent un fichier de données valide :

    tentacle_client -a 192.0.2.10 -v /chemin/vers/l/agent.data

    Remplacez l'IP et le chemin par ceux de votre environnement. Faites le test sur une machine de test ou avec un XML de données réel : le serveur reçoit le fichier et le traite. S'il échoue, vérifiez que tentacle_serverd est actif, qu'il écoute sur le port attendu et que le pare-feu autorise le trafic. Les options de mot de passe, de certificats, de port alternatif et de proxy sont dans la référence de Tentacle.

    Le service de l'EndPoint ne démarre pas sous Windows¶

    Vérifiez deux choses avant de toucher à quoi que ce soit :

    • Il a été installé sans permissions d'administrateur. L'installateur doit s'exécuter en tant qu'administrateur et le service a besoin des permissions SYSTEM. Sinon, il ne démarre pas.
    • Il y a un PandoraAgent.exe isolé dans le dossier de l'installateur. Si l'installateur trouve un exécutable dans son propre chemin, le service pointe vers celui-là et non vers celui qui est dans le dossier de l'agent, et il échoue donc au démarrage. Avant d'installer, laissez le dossier propre.

    Pour distinguer un problème du service d'un problème de l'EndPoint lui-même, exécutez le script de démarrage du dossier scripts avec Exécuter en tant qu'administrateur. S'il démarre ainsi, vérifiez le compte configuré dans les propriétés du service.

    Les XML s'accumulent dans data_in¶

    Les fichiers que les EndPoint déposent dans /var/spool/pandora/data_in s'accumulent quand le traitement ne suffit plus. L'ordre de vérification est :

    1. Le serveur est en marche. Avec le serveur arrêté, la file grandit, un point c'est tout. On le vérifie avec systemctl status pandora_server.
    2. Combien de BADXML il y a. Ce sont des fichiers que le serveur n'a pas pu lire : 
      ls /var/spool/pandora/data_in | grep -c BADXML
      S'il y en a beaucoup, on les nettoie et on cherche la cause (section suivante).
    3. Les threads du Data server. Le jeton dataserver_threads du /etc/pandora/pandora_server.conf vaut 1 par défaut. Sur un serveur avec beaucoup de machines, l'augmenter accélère le vidage de la file.

    Il y a des fichiers BADXML¶

    Un BADXML est un XML que le serveur n'a pas pu analyser, presque toujours parce qu'un module a introduit une valeur qui casse le fichier. On localise l'erreur sans deviner :

    xmllint TempTHXDF01.211810.data_BADXML

    La commande indique la ligne exacte. Avec cela, on va au XML, on regarde quel module génère ce contenu et on corrige le module pour qu'il renvoie une donnée valide. Les BADXML déjà générés peuvent être supprimés : l'agent les renverra corrigés à l'intervalle suivant.

    Beaucoup de données sont arrivées d'un coup et le serveur est en retard¶

    Après une chute du serveur, les EndPoint ont continué à collecter des données et la file se remplit d'un coup. Le serveur a un mode de traitement pensé pour cela : le jeton dataserver_smart_queue, qui dans les versions actuelles est déjà activé (1). Si l'installation est ancienne et qu'il est à 0, on le met à 1. Et si le volume est élevé, on augmente les dataserver_threads.

    Les données arrivent en double¶

    Ce n'est pas que le serveur les duplique : il y a quelque chose de répété à la source. On vérifie dans cet ordre :

    • Deux agents avec le même nom. C'est le plus courant. Pour les localiser, ajoutez temporairement à cet agent un module qui renvoie l'IP de la machine (ipconfig sous Windows, ip address sous Linux) et regardez combien d'IP répondent avec le même nom.
    • Deux modules avec le même nom dans l'agent, ou un module et un plugin qui obtiennent la même donnée.
    • Un module qui renvoie plus d'une valeur. On l'exécute à la main sur la machine et on vérifie que sa sortie est une seule donnée.

    L'inventaire de l'agent n'arrive pas¶

    Depuis la version 784, il n'y a plus de serveur d'inventaire propre : cette tâche a été absorbée par le Heavy Server, qui est actif par défaut (heavyserver 1). Si l'inventaire n'apparaît pas, vérifiez que l'EndPoint a son plugin d'inventaire activé et que le Heavy Server est en marche. L'ancien jeton inventoryserver n'existe plus.

    Configurer l'EndPoint depuis la console¶

    Cela peut se faire si l'agent l'autorise : le jeton remote_config de pandora_agent.conf vaut 1 par défaut, donc l'agent accepte que sa configuration soit modifiée depuis la console web. Si quelqu'un l'a mis à 0, l'agent cesse d'accepter les changements à distance et il faut éditer le fichier à la main.

    Caractères à éviter dans les noms d'agents et de modules¶

    Pour que les chemins et les commandes internes ne s'embrouillent pas, il vaut mieux éviter /, \, |, %, #, & et $ dans le nom d'un agent ou d'un module. Ce sont des caractères que le système interprète dans les chemins et les exécutions, et avoir des problèmes avec eux n'est qu'une question de temps.

    Supervision de base sous Windows¶

    Une fois l'EndPoint installé, le plus rapide est de ne pas écrire de modules à la main :

    • Appliquez une des politiques que la console apporte pour les machines Windows, qui inclut déjà le jeu de base de contrôles.
    • Ou utilisez les modèles de modules dans la configuration de l'agent, dans la section Module templates.

    À l'application de la politique ou du modèle, les modules sont écrits dans le fichier de configuration de l'agent. Ils commencent à rapporter à l'intervalle suivant. Pour des choses concrètes de votre environnement, on ajoute des modules propres (ou des scripts et des plugins) par-dessus cette base.

    Supervision de base sous Linux¶

    C'est le même chemin : politiques par système d'exploitation que la console apporte, ou modèles de modules depuis la configuration de l'agent. Avec cela, ils rapportent déjà le CPU, la mémoire, le disque, les processus et les services habituels ; le spécifique s'ajoute à la main ou avec un plugin.

    Exécuter un script PowerShell dans un module¶

    L'EndPoint de Windows sait exécuter PowerShell. On lui indique le chemin de l'exécutable et le script :

    module_begin
module_name Nom_du_module
module_type generic_data
module_exec C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -Command "C:\Chemin\script.ps1"
module_end

    Le type du module se choisit selon ce que renvoie le script :

    Type À quoi il sert
    generic_data Une donnée numérique
    generic_data_string Une donnée alphanumérique
    generic_proc Une valeur booléenne (1 ou 0)

    Si le script renvoie du texte, generic_data ne convient pas : le module apparaîtra comme Inconnu.

    Démarrer ou arrêter un service ou un processus¶

    Il y a deux mécanismes, et il vaut mieux ne pas les confondre :

    • Postconditions : le module, en plus de mesurer, exécute quelque chose lorsqu'une condition sur sa valeur est remplie. module_condition porte un opérateur, une valeur et la commande de réponse. La syntaxe et les opérateurs sont détaillés dans la référence de l'EndPoint.
    • Watchdog de Windows : module_proc peut relancer un processus tombé avec module_watchdog et module_start_command. module_service surveille un service Windows et le redémarre directement. C'est aussi expliqué dans la référence de l'EndPoint.

    Superviser les journaux de Windows¶

    L'EndPoint de Windows apporte trois voies :

    • Logevent : lit les événements système de Windows ; on choisit la catégorie qui intéresse.
    • Regexp : cherche un motif dans un fichier de journal précis.
    • Plugins de journaux : la même recherche, avec un script, utile quand le format est propre.

    Superviser les journaux de Linux¶

    Les deux plugins utilisés sont :

    • grep_log : à partir d'un chemin, il cherche le contenu que vous indiquez et crée le module avec le résultat.
    • grep_log_module : pareil, mais il envoie en plus le journal au collecteur de journaux de Pandora FMS avec la source Syslog, pour qu'il reste dans la visionneuse.

    La différence pratique : le premier mesure, le second archive en plus.

    Variables d'utilisateur quand l'EndPoint ne tourne pas en root¶

    Si l'EndPoint s'exécute avec un utilisateur autre que root, les modules qui dépendent de l'environnement de cet utilisateur peuvent échouer. On vérifie :

    1. Que le home de l'utilisateur existe.
    2. Qu'il a un shell valide (par exemple, /bin/bash) ; par sécurité, il est fourni désactivé.
    3. Que les variables d'environnement dont il a besoin sont dans son $HOME/.bashrc (ce fichier n'existe pas par défaut : il faut le créer).
    4. Que le fichier est lisible et que tout le home appartient à cet utilisateur.

    Avec ces quatre choses en ordre, l'EndPoint hérite de l'environnement au démarrage.
