    Groupes, utilisateurs, profils et tags¶

    La console web de Pandora est pensée pour que plusieurs utilisateurs travaillent sur la même installation sans se voir entre eux. C'est possible parce que le système de permissions est multitenant : un même serveur, la même base de données, et chacun ne voyant et ne touchant que ce qui lui revient.

    L'astuce n'a rien de mystérieux, mais elle repose sur deux pièces qu'il faut comprendre avant de créer le premier utilisateur : groupes et profils.

    Un groupe décide ce que voit un utilisateur. Un profil décide ce qu'il peut faire avec. La combinaison des deux, assignée à un utilisateur, est la permission. Et comme un même utilisateur peut avoir des profils différents dans des groupes différents, on peut aller du technicien qui ne regarde que son service jusqu'à l'administrateur qui voit tout.

    Le modèle de permissions¶

    Les groupes sont des ensembles d'éléments avec leurs propres règles et ils existent pour contrôler l'accès aux agents et à tout ce qui en dépend. La règle à avoir claire dès le départ : un agent appartient à un seul groupe, mais un utilisateur peut avoir accès à plusieurs groupes.

    À cette règle il y a une exception qu'il vaut mieux connaître tout de suite : un agent peut être, en plus, dans plusieurs groupes secondaires à la fois, et les utilisateurs de tous ces groupes le voient alors. Nous le détaillons un peu plus bas.

    Les profils définissent quelles opérations un utilisateur peut faire. C'est un ensemble de bits d'accès (voir, écrire, gérer les alertes, administrer…) qui s'assignent par groupe. Ainsi, le même utilisateur peut être en lecture seule dans le groupe « Production » et administrateur dans le groupe « Laboratoire », ce qui est justement ce que demande un environnement multitenant bien monté.

    D'où l'avertissement qui a déjà valu plus d'une frayeur : un utilisateur sans aucun profil ni groupe ne peut pas se connecter. Ce n'est pas un défaut, c'est la conception. Avant de créer des utilisateurs, il vaut mieux avoir décidé les groupes et les profils, pas l'inverse.

    Exigence Détail
    Groupes définis L'utilisateur a besoin d'au moins un groupe auquel accéder
    Profils définis L'utilisateur a besoin d'au moins un profil assigné dans ce groupe
    Utilisateur administrateur Un utilisateur marqué comme administrateur (superadmin) contourne l'ACL et a accès à tout

    Groupes d'agents¶

    Les groupes fonctionnent comme des conteneurs d'agents : un service, une entreprise, un site, un client. Ils sont la base du multitenant, parce qu'ils permettent une visibilité différenciée sur le même inventaire. Le menu se trouve dans Gestion → Ressources → Gérer les groupes.

    À la création d'un groupe (Créer un groupe), voici les champs qui comptent :

    • Nom. Si vous allez utiliser le groupe dans l'approvisionnement automatique d'EndPoints, laissez-le sans espaces ni caractères bizarres. Ils sont pris en charge, mais vous vous épargnez des ennuis.
    • Parent. Un groupe peut dépendre d'un autre. Les permissions peuvent se propager aux enfants (voir Propager l'ACL, plus bas).
    • Mot de passe. Facultatif. Il restreint l'auto-création d'agents : seuls se créent ceux qui apportent ce même mot de passe. Utile pour que personne n'invente des agents dans un groupe qui ne lui revient pas. N'utilisez ni espaces ni symboles.
    • Alertes. S'il est coché, les agents du groupe peuvent envoyer des alertes. C'est l'interrupteur rapide pour couper les alertes d'un groupe entier.
    • Propager l'ACL. S'il est actif, les groupes enfants héritent des permissions du parent. Le groupe All l'a activé par défaut.
    • ID personnalisé. Un identifiant propre pour l'intégrer à un système externe (une CMDB, par exemple).
    • Contact et Autres. Informations de contact et notes, disponibles dans les macros _groupcontact_ et _group_other_.
    • Nombre maximal d'agents autorisés. Limite d'agents du groupe. Par défaut 0, ce qui signifie sans limite.

    Chaque groupe peut avoir son propre thème visuel dans Configuration du groupe → Configuration de style. Si un utilisateur appartient à plusieurs groupes avec un thème propre, la console applique celui du premier groupe autre que All qui en ait un configuré. Et le thème que l'utilisateur choisit lui-même dans ses préférences l'emporte sur celui du groupe.

    Groupes secondaires¶

    Un agent appartient à un groupe, oui, mais Pandora FMS admet qu'il appartienne en plus à d'autres groupes : ce sont les groupes secondaires. L'agent conserve son groupe principal et on lui ajoute les secondaires nécessaires.

    À quoi cela sert, avec le cas qui s'explique tout seul : un agent vit dans « Applications », mais l'équipe « Réseaux » a aussi besoin de le voir. Au lieu de dupliquer l'agent ou de tout mettre dans un groupe commun, on marque « Réseaux » comme groupe secondaire et les utilisateurs qui ont la permission dans « Réseaux » se mettent à voir cet agent comme ceux d'« Applications ». C'est la façon propre pour que deux utilisateurs avec des permissions différentes accèdent au même agent sans partager de groupe.

    Ils s'assignent dans la fiche de l'agent, dans le champ Groupes secondaires, sous Ressources → Gérer les agents. On peut aussi y toucher depuis les opérations en masse d'agents. Un détail qui évite la confusion : le groupe principal ne peut pas être répété comme secondaire ; le formulaire lui-même l'empêche.

    Ce qui change quand un agent a des groupes secondaires :

    • Visibilité. L'agent est visible pour qui a la permission dans son groupe principal ou dans l'un de ses secondaires. La relation vaut pour tout ce qui dépend de l'agent : modules, événements, alertes, traps SNMP, inventaire et rapports.
    • Filtres. Dans les vues d'événements et d'alertes il y a une case, Rechercher dans les groupes secondaires, pour que cette recherche tienne compte des groupes secondaires. Si un utilisateur n'est lié à l'agent que par un groupe secondaire et que cette case est décochée, il peut ne pas voir ses informations. L'activer a un coût : elle oblige le serveur à croiser plus de données.

    Trois avertissements qui épargnent des appels au support :

    • La Tree view peut afficher l'agent en double. Si un agent est dans plusieurs groupes, il apparaît une fois par groupe. C'est normal, pas une erreur.
    • Supprimer un groupe supprime ses liens comme secondaire. Si ce groupe était marqué comme secondaire sur un agent, ces agents cessent d'y appartenir.
    • Cela a un coût en performances. C'est une fonction facultative : si aucun agent n'utilise de groupes secondaires, la console s'épargne les croisements supplémentaires. Dès qu'on l'utilise, beaucoup de listes et de compteurs ajoutent du travail. Mieux vaut l'employer avec discernement, pas comme substitut d'une bonne organisation des groupes.

    Le groupe « All »¶

    Le groupe All (« Tous ») n'existe pas comme tel dans la base de données : c'est un groupe contrôlé par le code avec l'identifiant réservé 0. Selon le contexte il signifie tous les groupes ou l'un quelconque d'entre eux, et il sert à ne pas avoir à cocher les groupes un par un. C'est la pièce qui rend commode le fait de dire « cet utilisateur administre tout ».

    Supprimer un groupe est irréversible¶

    Ici il vaut mieux lire deux fois avant de cliquer. La suppression d'un groupe ne se défait pas. Et le pire : les agents qu'il contenait existent et fonctionnent toujours, mais ils cessent d'apparaître nulle part dans la console web. Ils restent orphelins.

    Pour les récupérer il faut les réassigner à un nouveau groupe depuis le CLI, avec une commande du style :

    pandora_manage /etc/pandora/pandora_server.conf \
  --update_agent "pandora.internals" "group_name" "New_group" "use_alias"

    Le groupe de destination ne doit comporter ni espaces ni symboles. Avant de supprimer un groupe, regardez combien d'agents il contient.

    Importer des groupes depuis un CSV¶

    S'il faut créer beaucoup de groupes d'un coup, on peut les importer depuis un fichier dans Gestion → Outils d'administration → Gestionnaire d'extensions → CSV import group. Le fichier porte les champs dans cet ordre et séparés par le caractère que vous choisissez (la virgule par défaut) :

    Nom du groupe, icône, id du parent, propagation (1 ou 0)

    On choisit le fichier avec Sélectionner un fichier, on règle le Séparateur et on clique sur Aller.

    Récursion de groupes dans les vues¶

    Propager l'ACL et la récursion de groupes se ressemblent et ne sont pas la même chose. Propager l'ACL décide si les permissions descendent par l'arbre des groupes. La récursion est autre chose : c'est une case qui apparaît dans les filtres de beaucoup de vues (événements, rapports, politiques…) et qui fait que, en choisissant un groupe, la vue inclut aussi ses sous-groupes.

    Elle est commode quand vous filtrez par un groupe parent et voulez voir tout ce qui en dépend, mais elle n'est pas gratuite : la console elle-même prévient qu'elle peut affecter les performances. Activez-la quand vous en avez besoin, pas par habitude.

    Utilisateurs¶

    Les utilisateurs se gèrent dans Gestion → Profils → Gérer les utilisateurs. À la création ou à la modification d'un utilisateur, voici les champs qu'il vaut la peine de connaître :

    • Utilisateur administrateur. Un superadmin n'est pas régi par l'ACL interne : il a accès à tout. L'utilisateur standard, lui, est régi par les permissions qui lui sont assignées.
    • Login Error. S'il est coché, l'utilisateur ne peut entrer que par l'API, pas de façon interactive par la console web.
    • Local user. Force l'authentification contre la base de données propre à Pandora FMS. Il existe d'autres méthodes d'authentification (voir la Partie 04 · Authentification externe).
    • Session timeout based on. Activé par défaut. Ferme la session s'il n'y a pas d'activité pendant le temps configuré.
    • Session timeout (mins). La valeur par défaut est 0 ; dans ce cas c'est la valeur de la configuration générale d'authentification qui s'applique. Pour que la session n'expire jamais on met -1. Attention : un écran ouvert avec auto-rafraîchissement ne compte pas comme inactivité.
    • Language. La langue dans laquelle cet utilisateur verra la console. Par défaut, celle du système.
    • Block size for pagination. Combien de lignes par page voit cet utilisateur.
    • Timezone. Le fuseau horaire avec lequel les données lui sont montrées.
    • Login allowed IP list. S'il est activé, il limite la connexion à une liste d'adresses ou de plages séparées par des virgules. Le caractère générique * autorise n'importe quelle adresse.
    • Homescreen. L'écran d'accueil de l'utilisateur à la connexion : par défaut, une console visuelle, la liste d'événements, la vue de groupes, la vue tactique, le détail des alertes ou un lien externe. Attention à ne pas lui assigner comme accueil un tableau de bord d'un groupe qui n'est pas le sien : il ne verra que les dashboards des groupes auxquels il appartient.
    • Profiles/Groups assigned to this user. Ici s'assignent les profils et les groupes de l'utilisateur ; c'est ce qui lui donne réellement des permissions.

    Chaque utilisateur peut retoucher une partie de sa propre fiche dans Opération → Espace de travail → Modifier mon utilisateur, mais pas ses permissions de groupe. Là se trouve aussi l'API Token pour s'authentifier par en-tête HTTP avec un bearer token.

    Notifications¶

    Pandora FMS dispose d'un système de notifications pour les utilisateurs, avec une gestion par groupes pour ne pas devenir fou à les administrer. Il se configure dans Gestion → Réglages → Configuration du système → Notifications, et il y a six catégories :

    • System status. Générées par le serveur Pandora FMS lui-même.
    • Message. Messages entre utilisateurs.
    • Pending task. Tâches en attente de fonctionnalités comme Discovery.
    • Advertisement. Avis et propositions de Pandora FMS.
    • Official communication. Communiqués officiels pour des affaires extraordinaires.
    • Suggestions. Suggestions et conseils.

    L'interrupteur ENABLE USER CONFIGURATION décide, pour chaque catégorie, si les utilisateurs peuvent activer ou désactiver ces notifications dans Opération → Espace de travail → Configurer les notifications de l'utilisateur, aussi bien dans la console que par courriel.

    Deux règles qui expliquent presque toutes les surprises :

    • Pour qu'elles arrivent par courriel, l'utilisateur doit avoir son adresse configurée et le serveur doit savoir envoyer du courrier.
    • Si un groupe entier est abonné à une catégorie, ses utilisateurs reçoivent ces notifications de console et ne peuvent pas les désactiver, même si l'interrupteur de configuration utilisateur est actif. L'appartenance au groupe pèse plus que la préférence personnelle.

    Un superadmin finit dans toutes les catégories, qu'il le veuille ou non, quand il est créé ou modifié depuis la console web. Un superadmin créé ou modifié par CLI n'est pas ajouté au système de notifications : si quelqu'un « ne reçoit rien », commencez par regarder d'où le compte a été créé.

    Notifications push du navigateur¶

    En plus de celles de la console et du courriel, Pandora FMS peut lancer des notifications surgissantes vers le système d'exploitation par l'intermédiaire du navigateur avec lequel on a accédé à la console. Elles s'activent dans Gestion → Réglages → Configuration du système → Notifications → Notifications push web.

    L'exigence qui fait échouer plus de la moitié des tentatives : il faut HTTPS. Si la console passe par HTTP, le navigateur lui-même rejette les notifications. Et même avec HTTPS, elles ne fonctionnent ni en mode navigation privée ni en mode invité de Chromium ou Chrome, ni si le profil du navigateur les a bloquées. Pandora FMS ne notifie que dans le profil de navigateur avec lequel on est entré dans la console, pas dans les autres.

    Quand on active l'interrupteur Activer les notifications push web, le navigateur demande à l'utilisateur s'il les autorise. Le bouton Envoyer une notification de test sert à vérifier que cela fonctionne, mais avec modération : le message arrive à toutes les souscriptions enregistrées, pas seulement à la vôtre. Chaque souscription stockée n'identifie pas son propriétaire.

    Si un utilisateur veut les retirer, il a plusieurs voies : nettoyer les données de navigation de ce profil, bloquer les notifications dans le profil, supprimer le profil (avec précaution, il emporte les autres sites) ou créer un profil nouveau et répondre Non quand la question est posée.

    Profils¶

    Les profils définissent ce qu'un utilisateur peut faire. Ils se gèrent dans Gestion → Profils → Gérer les profils. Cinq viennent d'usine et on peut en créer autant qu'il faut :

    Profil De quoi il s'agit
    Operator (Read) Celui de la consultation seule : voir sans toucher
    Operator (Write) Celui de l'opération quotidienne : consultation et écriture
    Chief Operator Opération étendue
    Group coordinator Coordination de groupes, avec la gestion des groupes et des utilisateurs
    Pandora Administrator Administration complète de la plateforme

    Quel bit porte chacun, exactement, c'est le tableau ci-dessous : un profil n'est rien d'autre qu'une combinaison de ces bits.

    Un profil est une collection de bits d'accès. Voici ceux que le produit apporte et ce que chacun habilite :

    Bit Ce qu'il permet
    AR Voir les données d'agent (toutes les vues), vue tactique, vue de groupes, voir les utilisateurs, console SNMP, Tree view, groupes d'extension et barre de recherche
    AW Vue de gestion d'agent, édition de l'agent et de son .conf, opérations en masse, création d'agent, duplication de configuration distante, voir et gérer les politiques, gérer les filtres
    AD Gérer les arrêts de service et désactiver un agent, un module ou une alerte
    LW Assigner des alertes déjà créées et gérer les alertes
    LM Définir et modifier des modèles et des actions d'alerte
    LF Forcer des alertes et forcer des vérifications de modules
    UM Gestion des utilisateurs
    DM Maintenance de la base de données
    ER Voir les événements
    EW Valider et commenter des événements, gérer les filtres et exécuter des réponses
    EM Supprimer des événements, changer de propriétaire et rouvrir des événements
    RR Voir les rapports et les graphiques, appliquer des modèles de rapport et voir les Cronjobs
    RW Créer des consoles visuelles, des rapports et des graphiques combinés ; voir, éditer, exécuter et créer des Cronjobs
    RM Créer des modèles de rapport ; voir, éditer, exécuter, créer et supprimer des Cronjobs
    MR Voir les cartes réseau
    MW Éditer les cartes réseau et supprimer les siennes
    MM Supprimer n'importe quelle carte réseau
    VR Voir les consoles visuelles
    VW Éditer les consoles visuelles et supprimer les siennes ou n'importe laquelle
    VM Gérer les consoles visuelles
    NR Voir les données de NCM
    NW Exploiter NCM
    NM Administrer NCM
    PM Administration de Pandora : gérer les réponses, les colonnes d'événements, l'update manager, les modules d'inventaire, les modules, la console SNMP, les profils, les serveurs, l'audit, le setup, les extensions et toute sorte de Cronjobs
    GW Gestion de groupes : un utilisateur non superadmin ne peut éditer que le groupe de son profil, et les enfants si le groupe a Propager l'ACL

    Il existe en plus des combinaisons qui activent des fonctions concrètes : EW + IW permet de créer une incidence depuis un événement, et LM + AR ou AW + LW permettent de valider des alertes.

    Un avertissement qui épargne des discussions : les superadmin sont exemptés de l'ACL, même s'ils ont le profil d'administrateur assigné. L'ACL ne lie que les autres.

    Assignation des permissions¶

    Les permissions se donnent depuis l'édition de l'utilisateur, en assignant groupes et profils dans la fiche. Et ici il vaut mieux avoir présentes les règles de cohabitation entre administrateurs et gestionnaires d'utilisateurs (permission UM), parce qu'elles sont à l'origine de la moitié des questions :

    • Un gestionnaire avec UM dans le groupe All peut gérer n'importe quel utilisateur, quel que soit son groupe.
    • Un gestionnaire ne voit et n'édite que les profils et les groupes des utilisateurs qu'il peut voir, c'est-à-dire des groupes qu'il gère avec UM.
    • Un gestionnaire sans UM sur un groupe ne peut même pas voir quels utilisateurs appartiennent à ce groupe.
    • Un gestionnaire ne peut pas retirer l'UM à un autre utilisateur qui a les mêmes permissions sur le même groupe. Seul un administrateur y touche.
    • Un administrateur, lui, peut créer d'autres administrateurs et gérer n'importe qui.

    Quand on va supprimer la dernière relation profil/groupe d'un utilisateur qui va en plus être supprimé, la console avertit avant. Cela vaut la peine de lire l'avertissement.

    Hiérarchie¶

    La propagation des permissions aux groupes enfants se contrôle avec Propager l'ACL dans le groupe parent. Si vous voulez la couper pour un utilisateur concret, à l'assignation de la permission on coche No hierarchy et l'ACL ne descend pas par l'arbre.

    La hiérarchie de groupes est indépendante des groupes secondaires, qui sont autre chose et sont expliqués dans « Groupes secondaires ».

    Tags et permissions étendues par tag¶

    Groupes et profils donnent des permissions « en bloc » : un groupe entier, un profil complet. Pour affiner davantage il y a les tags de modules. Avec eux on peut décider qu'un utilisateur voie certains modules et pas d'autres à l'intérieur du même groupe, ce que les permissions par groupe n'atteignent justement pas.

    Ce qu'est un tag et où il s'applique¶

    Un tag est une marque nommée qui se définit une fois et se réutilise. Ils se créent dans Gestion → Ressources → Tags de modules, et l'écran demande :

    • Nom. L'identifiant du tag. Il n'admet pas de virgules.
    • Description.
    • URL. Un lien d'aide qui doit exister avant de le mettre.
    • Courriel et Téléphone. Données de contact utilisées ensuite dans les alertes associées au tag (voir plus bas).

    Le listage des tags montre, pour chacun, combien de modules et combien de modules de politique le portent. Les gérer exige un profil d'administration ; dans un Command Center en mode centralisé, l'information est en lecture seule et s'administre depuis le Command Center lui-même.

    Et une nuance qui épargne des recherches inutiles : les tags s'assignent à des modules, pas à des agents ni à des groupes. On les met (et on les retire) dans la fiche du module, dans la section de catégorisation, champ Tags. Comme un module de politique peut aussi en porter, les tags voyagent avec la politique et s'appliquent à tous les agents qui la reçoivent. Il existe en plus une opération en masse pour taguer des modules et des modules de politique d'un coup. Un module peut porter plusieurs tags.

    Permissions par tag (ACL)¶

    Ici est la finesse. Dans l'assignation de profil et de groupe de l'utilisateur il y a un sélecteur de Tags, à côté du groupe et du profil. La règle est simple :

    • Si on le laisse vide, l'utilisateur voit tous les modules de ce groupe.
    • Si on remplit un ou plusieurs tags, l'utilisateur ne voit que les modules qui portent ces tags à l'intérieur de ce groupe.

    La restriction est par combinaison de profil, de groupe et de tags : le même utilisateur peut voir certains modules dans un groupe et d'autres différents dans un autre. Les tags complètent l'accès par groupes, ils ne le remplacent pas : le groupe et le profil restent nécessaires.

    Deux avertissements qui valent leur pesant d'or :

    • Un profil sans tags ouvre tout. Si l'utilisateur a plusieurs profils sur un même groupe et que l'un quelconque d'entre eux ne restreint pas par tags, l'utilisateur voit tous les modules. La restriction la plus permissive gagne.
    • Les tags se propagent avec le groupe. Si le groupe a Propager l'ACL activé, la restriction par tags descend aussi vers les groupes enfants.

    Limites, coût et visionneuse¶

    Le mode de sécurité basé sur les tags a un coût en performances : il oblige à croiser les modules avec les tags à chaque requête. Il est pensé pour donner accès à des portions réduites d'information, il ne convient donc pas de dépasser deux ou trois tags par combinaison d'utilisateur, de profil et de groupe. Pour segmenter sérieusement, le raisonnable, ce sont les groupes ; les tags sont le scalpel, pas la massue.

    Et une nuance qui évite les malentendus : dans certaines vues globales (vue tactique, vue de groupe, comptages de l'arbre) les totaux montrent tous les modules, pas seulement ceux que l'utilisateur voit par ses tags.

    Pour explorer la supervision par tag il y a la Visionneuse de tags (Tag view), disponible dans les installations Enterprise, dans Supervision → Vues.

    Tags dans les alertes¶

    Comme un tag garde un courriel et un téléphone, les alertes peuvent utiliser ces données du module qui le porte. Elles sont utiles quand l'avis doit arriver à qui s'occupe réellement de ce système, pas toujours à la même boîte :

    • _moduletags_ et _name_tag_ remplacent les noms des tags du module.
    • _email_tag_ remplace les courriels des tags du module.
    • _phone_tag_ remplace les téléphones des tags du module.

    C'est-à-dire : taguer un module n'affine pas seulement les permissions, cela peut aussi dire qui prévenir quand ce module se détraque.

    Pour le contrôle fin par pages et par menus, au-delà des groupes, des profils et des tags, il y a le système d'ACL avancée, traité dans la Partie 04 · Sécurité et visibilité avancées.
