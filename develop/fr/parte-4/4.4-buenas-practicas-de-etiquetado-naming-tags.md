# Bonnes pratiques de noms et de tags

Les trois chapitres précédents expliquent **comment** fonctionnent les groupes, les
profils et les tags. Celui-ci explique **comment bien les utiliser**. Il n'y a pas
une seule bonne façon de faire, mais il y a des décisions qui coûtent cher plus
tard : un nom mal posé ou un tag de trop traînent pendant des années, et les
changer ensuite coûte plus que de les avoir pensés le premier jour.

## Pourquoi cela compte

Une petite installation se range toute seule. Une installation avec des centaines
d'agents, non : si les noms sont un chaos, chaque recherche est une loterie et
chaque rapport, une négociation. La nomenclature et les tags sont ce qui permet de
**trouver** un élément, de le **regrouper** pour les rapports et de le
**déléguer** avec des permissions sans exposer ce qu'il ne faut pas. Plus tôt la
convention est fixée, moins il y a à défaire.

## Conventions de noms

La règle d'or est ennuyeuse et elle fonctionne : **un nom prévisible vaut mieux
qu'un nom joli**. Voici les principes qui évitent de vrais problèmes.

**Agents.** Un motif qui fonctionne souvent est `SERVICIO-ENTORNO-NN`, par exemple
`WEB-PROD-01` ou `BBDD-PRE-03`. Le motif choisi importe peu ; ce qui compte, c'est
qu'il soit **cohérent** et que le nom dise d'un coup d'œil ce qu'est la machine et
où elle vit. Évitez les **espaces** dans le nom du groupe auquel ils vont (voir
plus bas) et soyez cohérent avec les majuscules : la recherche de la console peut
normaliser l'alias, et un `Web-Prod-01` n'apparaît pas comme un `WEB-PROD-01`.

**Modules.** Le nom du module devrait dire **ce qu'il mesure et dans quelles
unités**, pas comment la métrique s'appelle dans le système d'origine :
`CPU usage (%)` se comprend mieux que `hrProcessorLoad`. Si le module concerne un
service, incluez-le dans le nom (`Apache requests/s`).

**Groupes.** Ici il y a une recommandation qui n'est pas esthétique, elle est
fonctionnelle : pour utiliser le nom du groupe dans le **provisionnement
automatique d'agents**, il vaut mieux qu'il **ne comporte ni espaces ni caractères
étendus**. C'est pris en charge, mais c'est une source connue d'échecs : il existe
des cas documentés où un groupe dont le nom contient des espaces n'est pas assigné
lors de la création automatique de l'agent. Un `Redes-CPD1` évite le problème ;
`Redes CPD 1` l'invite.

**Autres identifiants.** Le même critère vaut pour tout ce qui sert de clé dans des
intégrations ou des scripts :

- Le **mot de passe de groupe** (pour restreindre la création automatique d'agents)
  ne doit comporter ni espaces ni symboles.
- L'**identifiant du stockage des identifiants** s'écrit sans espaces ni caractères
  spéciaux.
- En CLI, les noms de **groupe** et de **calendrier** n'admettent ni espaces ni
  caractères spéciaux.
- Les **champs personnalisés** aux noms très longs sont tronqués dans certaines
  vues : mieux vaut un nom court et descriptif.

Et deux détails qui surprennent :

- Dans les **consoles visuelles**, un nom qui commence par `_`, `,`, `[` ou `(`
  fait apparaître l'élément dans le menu de gauche. C'est une fonction, pas un
  caprice : si vous ne voulez pas de ce comportement, ne commencez pas le nom par
  ces caractères.
- Les **caractères de contrôle** et certains **accents** posent problème à
  l'enregistrement selon l'endroit (champs personnalisés, politiques avec un
  encodage précis). Si un nom doit passer par l'API, la CLI ou des scripts,
  laissez-le en ASCII simple.

## Usage des tags

Les tags **complètent** les groupes, ils ne les remplacent pas. La façon de ne pas
se tromper est d'avoir clair ce à quoi sert chaque chose :

- **Les groupes organisent la hiérarchie et les permissions.** C'est la structure
  principale, et celle qui sert à déléguer (groupes secondaires compris).
- **Les tags affinent.** Ils servent à marquer des modules selon un critère
  transversal qui ne coïncide pas avec la hiérarchie : par technologie, par
  criticité, par responsable.

Des critères qui épargnent des ennuis :

- **Ne transformez pas les tags en seconde hiérarchie.** Si un tag reproduit un
  groupe, il est superflu.
- **Peu et stables.** Le mode de sécurité par tags a un coût de performance et la
  console recommande de ne pas dépasser deux ou trois par combinaison
  d'utilisateur, de profil et de groupe. Un tag que personne n'utilise n'est
  qu'une dette.
- **Nommez-les comme dans le reste de l'installation.** Si vous appelez `prod` les
  tags de production, ne les appelez pas `Produccion` ailleurs.
- **Rappelez-vous où ils s'appliquent** : aux **modules** (et aux modules de
  politique), pas aux agents ni aux groupes.

## Antipatrons et un exemple

Les erreurs qui se répètent le plus :

- **Le nom qui ne dit rien.** `Agente1`, `prueba`, `test2` : dans un mois,
  personne ne sait ce que c'est ni si on peut le supprimer.
- **La date ou le nom de celui qui l'a monté** comme identifiant. Le système
  change de main ; le nom reste.
- **Mélanger les langues et les majuscules** dans le même inventaire (`web`,
  `WEB`, `Web`).
- **Utiliser des espaces ou des symboles** dans tout ce qui passera par une
  intégration.
- **Taguer pour taguer**, jusqu'à ce que le système de permissions par tags
  commence à ralentir.
- **Des groupes en double** avec des noms presque identiques.

Une convention d'exemple, appliquée à un environnement avec deux sites et deux
environnements :

| Élément | Convention | Exemple |
|---|---|---|
| Agent | `SERVICIO-ENTORNO-SEDE-NN` | `WEB-PROD-MAD-01` |
| Groupe | `SERVICIO-SEDE` (sans espaces) | `WEB-MAD` |
| Module | `Ce qu'il mesure (unité)` | `CPU usage (%)` |
| Tag | Technologie ou criticité, en minuscules | `apache`, `critico` |

Ce n'est pas la seule valable, et il n'en faut pas. Ce qui compte, c'est qu'elle
existe, qu'elle soit écrite et que tout le monde la suive. C'est le vrai travail
du chapitre.
