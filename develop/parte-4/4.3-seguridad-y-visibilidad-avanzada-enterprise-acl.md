# Seguridad y visibilidad avanzada (ACL avanzada)

Los grupos y perfiles del capítulo anterior deciden **qué puede hacer** un
usuario. Pero hay una pregunta que no responden: **qué páginas ve**. Un perfil de
administrador da acceso a todo, y muchas veces no quieres eso; quieres que alguien
pueda tocar una parte de la consola y no el resto. Para eso está el sistema de
**ACL avanzada** (antes llamado ACL Enterprise), que define, perfil a perfil, a
qué páginas tiene acceso cada usuario.

Dos reglas que conviene saber antes de tocar nada. La primera: **los
*superadmin* están exentos** del sistema, y el resto están obligados por él,
incluso si tienen el perfil *Pandora Administrator*. La segunda: el ACL avanzado
y el clásico (grupos y perfiles) son **paralelos y compatibles**, pero el clásico
se evalúa **antes**. Si algo no lo permite el ACL clásico, el avanzado no lo
abre.

## Qué añade el sistema ACL avanzada

El modelo clásico es de estilo Unix: *rol, acción, grupo, usuario*. El avanzado
va un paso más allá y permite **restringir la administración página a página**:
qué secciones y qué pantallas concretas puede abrir cada perfil. Es la
herramienta para dar permisos de bajo nivel muy concretos sin abrir la mano
entera.

## Activar el sistema

El sistema viene **desactivado**. Se activa así:

- **En un nodo**: **Gestión → Ajustes → Configuración del sistema →
  Configuración general → Características → Utilizar el sistema ACL Enterprise**
  (*Use Advanced ACL System*), se activa y se pulsa **Actualizar**.
- **En un Command Center**: **Configuración → Metasetup → Utilizar el sistema
  ACL Enterprise**.

En un Command Center, el sistema se configura de forma **independiente** en el
propio Command Center y en cada nodo.

!!! warning "Se puede perder el acceso a la consola"
    Al activar el ACL avanzado, se restringen **todas** las páginas a **todos**
    los grupos, incluido el de administrador, y solo quedan permitidas las
    páginas que hayas definido. Si un perfil de administrador no tiene ninguna
    página incluida, **no verá nada**. Antes de activarlo, deja definidas las
    reglas del perfil con el que vas a entrar.

Si por un descuido te quedas fuera, no hay que reinstalar: desde el servidor se
apaga el sistema por CLI.

```bash
pandora_manage /etc/pandora/pandora_server.conf --disable_eacl
```

Y para volver a encenderlo, `--enable_eacl`.

## Cómo se definen las reglas

Se configuran en **Gestión → Perfiles → Editor avanzado de ACL** (*Management →
Profiles → Advanced ACL Setup*); en un Command Center, en **Gestión centralizada
→ Gestión → Editor avanzado de ACL**. Hay dos formas de añadir páginas, y un
botón al lado de **Añadir** alterna entre ellas: **Asistente** (*Wizard*) y
**Personalizado** (*Custom*).

**El asistente** va por desplegables: eliges el **perfil del usuario**, la
**Sección**, la **Sección 2** y, si hace falta, la **Sección 3**. Si eliges
**Todo** (*All*) en la sección, ese perfil verá toda la sección; con **Todo** en
todas, verá todo, como si el sistema no estuviera activo. Tres cosas que
sorprenden la primera vez:

- El desplegable solo lista las páginas **accesibles desde el menú**. Para una
  página a la que se llega de otra forma hay que usar el editor personalizado.
- Muestra **todas** las opciones de menú, tenga o no acceso el perfil. Añadir una
  que el perfil no puede usar no la hace aparecer.
- El perfil por defecto del desplegable es **Chief Operator**. Cámbialo antes de
  añadir nada, o le estarás dando permisos a quien no es.

![Pantalla del editor avanzado de ACL con el asistente de secciones](../../assets/img/parte-04/acl-asistente.png)

**El editor personalizado** sirve para las páginas que no están en el menú: se
pega a mano el parámetro `sec2` de la página. Por ejemplo, para dar acceso a la
vista principal de un agente, entras en la vista de cualquier agente, copias el
`sec2` de la URL (`operation/agentes/ver_agente`) y lo pones en la caja
**Sección 2**.

![Editor personalizado de ACL con una página añadida por su sec2](../../assets/img/parte-04/acl-editor-personalizado.png)

Un detalle que explica menús que «no salen»: para que una sección aparezca en el
menú, el usuario necesita acceso **al menos a su primera página**. Y para
consultar en cualquier momento qué páginas tiene permitidas un perfil, está
**Filtrar por perfil** (*Filter by profile*).

![Filtro por perfil aplicado en el editor avanzado de ACL](../../assets/img/parte-04/acl-filtrar-por-perfil.png)

## Seguridad

El sistema no es decorativo. Una página limitada **no se muestra en el menú y no
se puede usar**, ni siquiera escribiendo la URL a mano. Además, una página que no
permita el ACL clásico tampoco la va a permitir el avanzado.

Hay un control extra que comprueba si una página pertenece a su sección, lo que
refuerza la seguridad frente a URLs retocadas. Ese control se salta las páginas
añadidas con el editor personalizado y las secciones enteras permitidas, para no
penalizar la carga.

## Permisos de visibilidad en elementos compartidos

Hay elementos que no son agentes ni módulos y se comportan de forma distinta:
**informes**, **consolas visuales**, **mapas de red** y ***dashboards*** actúan
como **contenedores**. Un usuario con visibilidad de todos los datos crea un
informe y lo asigna a un grupo general. A partir de ahí, cualquiera con acceso a
ese grupo verá el informe y **todo su contenido**, aunque no tenga permiso sobre
los elementos individuales que lo componen. Es cómodo, y por eso conviene saberlo
antes de compartir un informe.

Hay excepciones a tener en cuenta:

- Algunos *widgets* del *dashboard*, como el *treeview* o el control de eventos,
  porque permiten interactuar con los datos.
- Elementos de una consola visual, que se pueden restringir a un grupo concreto.

Y una regla de convivencia para quien tenga lectura **y** escritura: al editar un
contenedor, solo podrá **añadir** elementos a los que tiene acceso y podrá
**borrar** elementos a los que no lo tiene, pero no volver a añadirlos.

El resto de elementos compartidos se rigen por su menú y su permiso:

- **Servidores**: *Gestionar servidores*, *Gestionar consolas* y *Gestionar base
  de datos HA*.
- **Almacén de credenciales**: cada credencial se ve según el grupo que tenga
  asignado.
- **Paradas planificadas**, **registro de auditoría** y ***logs*** del servidor
  local.
- **Gestión de la base de datos** desde la consola y **herramientas externas**.
- **Registro de plugins**, **Insert data**, **registro de recursos** y
  **exportación e importación de recursos**.
- **Traductor de cadenas**, **espacio de trabajo** y **repositorio de
  EndPoints**.

## Personalización y ejemplos

El ACL avanzado no solo cierra puertas; también abre las justas. Tres ejemplos
que aparecen siempre que se activa:

- Para que un usuario pueda **cambiar sus propios datos**, hay que darle acceso a
  **Workspace → Edit my user → Todo**.
- Para que pueda **generar sus propios tokens**, **Workspace → Edit my Tokens →
  Todo**.
- Para que pueda **leer sus notificaciones**, **Workspace → Messages → Todo**; y
  si además tiene que **responder** un mensaje, se añade en el editor
  personalizado el `sec2` `operation/messages/message_edit`.

La misma mecánica vale para cualquier página suelta: se busca su `sec2` y se
añade a mano. Es la forma de ajustar la consola a lo que cada rol necesita, sin
abrir secciones enteras.

## ACL estricta

La ficha del usuario tiene una casilla de **ACL estricta** (*Strict ACL*). No es
la opción por defecto y la propia consola avisa de que **no se recomienda**,
porque afecta al rendimiento. Lo que hace, en corto: un usuario con ACL estricta
**no ve ninguna etiqueta**, es decir, el sistema de permisos por etiquetas deja
de mostrarle módulos. Actívala solo si sabes por qué la necesitas.
