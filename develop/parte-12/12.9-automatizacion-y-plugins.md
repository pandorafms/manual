# Automatización y plugins

Hacer que Pandora FMS trabaje sola: línea de comandos, API, macros y plugins.

Dos formas de trabajar con Pandora FMS sin pasar por la pantalla: el **CLI**, que
se ejecuta en el propio servidor, y la **API**, que se llama desde fuera. Las dos
sirven para automatizar y para hacer en lote lo que a mano sería interminable.

## Qué es el CLI y cómo se usa

Es una herramienta de administración por línea de comandos que se ejecuta **en el
servidor de Pandora FMS**. Sirve para crear y borrar usuarios, agentes y módulos,
configurar alertas y políticas, gestionar eventos y mucho más, así que es la vía
natural para automatizar tareas con scripts.

Se ejecuta en el servidor con `pandora_manage` y la configuración del
servidor:

```bash
/usr/bin/pandora_manage \
    /etc/pandora/pandora_server.conf OPCION PARAMETROS
```

Sustituye `OPCION` y `PARAMETROS` por los argumentos de la operación que vayas a
ejecutar.

Un ejemplo real, crear un grupo llamado «Virtuales» dentro de otro llamado
«Servidores»:

```bash
/usr/bin/pandora_manage /etc/pandora/pandora_server.conf \
    --create_group 'Virtuales' 'Servidores'
```

La lista de operaciones es larga (agentes, módulos, alertas, plantillas,
políticas, eventos, usuarios, perfiles, colecciones, consolas visuales…). Está
completa, con la sintaxis de cada una, en la
[referencia del CLI de administración](../parte-9/9.11-referencia-completa-del-cli-de-administracion.md).

## Qué es la API y cómo se protege

La API es un fichero PHP de la consola al que se llama por HTTP, con `curl` o
desde una herramienta web. Tiene **tres capas de seguridad**, y hay que
configurar las tres antes de usarla:

1. **Direcciones IP permitidas.** En **Administración → Configuración → General**,
   el campo **«IP list with API access»** admite una IP por línea. El comodín
   `*` abre la API a cualquiera, y no es recomendable.
2. **Contraseña de API.** En el mismo sitio, el campo **«API password»**.
3. **Credenciales de usuario.** Cada llamada identifica además al usuario de
   Pandora FMS que la hace, con su contraseña.

Como la contraseña de la API viaja en la propia llamada, conviene hacerlas por
**HTTPS** para que el canal vaya cifrado.

Una llamada de prueba, la más sencilla, para comprobar que todo está en su sitio:

```
https://console.example.com/pandora_console/include/api.php?info=version
```

Sustituye `console.example.com` por el nombre de tu consola.

Las contraseñas no se publican aquí: cada instalación pone las suyas en la
consola.

## Crear y validar eventos por la API desde otra máquina

El producto trae una herramienta para lanzar eventos contra la API **desde un
sistema remoto**, sin necesidad de tocar la base de datos ni de tener un EndPoint
instalado: **`/usr/bin/pandora_revent`**.

```bash
/usr/bin/pandora_revent \
    -p https://console.example.com/pandora_console/include/api.php \
    -u 'API_PASSWORD,USER_NAME,USER_PASSWORD' \
    -create_event \
    -name "Nombre del evento" -group 0 -type "system" -status 0 -severity 4 \
    -user "USER_NAME" -owner_user "USER_NAME" -source "Commandline" \
    -user_comment "Comentario del evento"
```

El parámetro `-u` lleva las tres credenciales juntas, separadas por comas: la
contraseña de la API, el usuario y su contraseña.

La misma herramienta **valida** eventos, que es lo útil para cerrarlos desde
fuera:

```bash
/usr/bin/pandora_revent -p https://console.example.com/pandora_console/include/api.php \
    -u 'API_PASSWORD,USER_NAME,USER_PASSWORD' -validate_event -id EVENT_ID
```

Sustituye los valores de ejemplo por el host y las credenciales de tu instalación.

Ejecutada **sin opciones**, muestra su ayuda con la sintaxis completa.

## Macros en las alertas

Una macro es una cadena rodeada de caracteres de subrayado (`_macro_`). La
consola la sustituye por un texto al lanzar la acción de una alerta. Sirven para
que el aviso diga de qué agente viene, qué módulo lo disparó y con qué valor, sin
escribirlo a mano.

Los grupos que más se usan:

| Grupo | Ejemplos |
|---|---|
| Agente | `_agentname_` (nombre), `_agentalias_`, `_address_` (su dirección), `_agentstatus_`, `_agentos_`, `_agentgroup_`, `_agentcustomfield_n_` |
| Módulo | `_module_` (nombre), `_data_` (el valor que disparó), `_modulegraph_nh_` (la gráfica) |
| Alerta | `_alert_name_`, `_alert_priority_`, `_alert_text_severity_` |

La lista completa está en la ayuda de la propia consola. Las macros se sustituyen
en el asunto y en el cuerpo de la acción. Sin ellas, cada alerta tendría que
llevar el mensaje escrito a mano.

## Macros personalizadas

Además de las de serie, se pueden definir las propias. Es la forma de que un
aviso diga algo específico de tu entorno.

Se crean en la **edición del propio módulo**, en el apartado **«Macros
personalizadas»**. Se añaden pares de **clave y valor**, y la clave se escribe
entre caracteres de subrayado. Por ejemplo:

```
_clave_        _technology_
valor          el sistema de logs
```

Después, esa macro se referencia en la alerta como cualquier otra:

```
El agente informa de contenido nuevo en _technology_
```

y la consola la sustituye por el valor que tenga configurado **ese módulo**. Como
el valor vive en el módulo, cada uno puede llevar el suyo.

## Plugins de agente

Un plugin de agente es un programa o script que se ejecuta **en la máquina
monitorizada**. Devuelve un trozo de **XML** que el agente inserta en el paquete
que envía al servidor. Un solo plugin puede devolver datos de **varios módulos**.

Se añade de dos maneras:

- En `pandora_agent.conf`, con una línea:
  ```
  module_plugin /ruta/al/plugin
  ```
- Desde la consola, en la configuración del agente, en la sección de **plugins**
  (el icono de la pieza de puzle): se indica la ruta completa del plugin.

A partir de ahí funciona como un módulo local más. Se puede escribir en cualquier
lenguaje de scripting; si necesita librerías (por ejemplo, Java), hay que
distribuirlas con él.

## Plugins de servidor

Un plugin de servidor es un script que se ejecuta **en el propio servidor de
Pandora FMS**, no en la máquina monitorizada. Devuelve **un único valor**
(numérico, booleano o de texto) y se le pueden pasar parámetros.

- Viven por defecto en `/usr/share/pandora_server/util/plugin`, y el producto ya
  trae unos cuantos de ejemplo (por ejemplo, `iface_bandwith.pl`).
- Se registran en **Servers → Plugins**: nombre, tipo (estándar o de Nagios),
  *timeout* máximo, el comando y sus parámetros (que admiten macros).
- **Quién los ejecuta**: el **Heavy Server**. No existe ningún servidor
  `pluginserver` que activar, como decían las fichas antiguas. El Heavy Server
  viene activo por defecto y se encarga de los plugins, NCM e inventario.

La forma más rápida de depurarlos es lanzarlos a mano en la terminal, con los
mismos parámetros. Casi todos traen ayuda con `-h`, `-help` o sin argumentos.

!!! warning "El timeout es la trampa habitual"
    Si el plugin tarda más que el *timeout* configurado, se corta y el módulo se
    queda sin dato. Mide cuánto tarda el script y pon margen.

## El módulo del plugin aparece en «Desconocido»

Cuando un plugin define sus propios módulos, el XML que genera tiene que respetar
el **`module_interval`** que hayas configurado. Si el plugin no lo declara, la
consola espera los datos con otro ritmo. Los módulos acaban en **Desconocido**
aunque el plugin esté funcionando.

Se corrige en el propio plugin: que el XML incluya el intervalo con el que se
ejecuta. Es un ajuste pequeño que evita una cascada de falsos desconocidos.
