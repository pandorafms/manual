# Entornos grandes

Command Center, varios nodos y alta disponibilidad: lo que cambia cuando el entorno crece.

Aquí se agrupan las incidencias que aparecen al coordinar varios nodos, distribuir
la carga y configurar la alta disponibilidad.

## No arranca el servidor de un nodo en un Command Center

El servidor de cada nodo se conecta a la base de datos configurada en su propio
`pandora_server.conf`. Si no arranca, comprueba esa conexión primero. Para una
incidencia de réplica al Command Center, consulta la pregunta «No llegan los
eventos al Command Center» más abajo.

1. **El motor de base de datos del nodo está en marcha.** Comprueba el servicio
   MySQL, MariaDB o Percona que use ese nodo.
2. **El nodo llega al host indicado por `dbhost`.** Prueba la conexión desde el
   propio servidor del nodo con los valores `dbname`, `dbuser` y `dbhost` de su
   configuración.
3. **El usuario puede acceder desde ese host.** Si las credenciales son correctas
   pero la conexión se rechaza, revisa los permisos de la base de datos del nodo.

Los valores de conexión y las contraseñas se consultan en el fichero de
configuración del servidor; no se copian aquí.

## Borrar agentes en un Command Center en modo centralizado

En un entorno con gestión centralizada activada, la administración de agentes
entre nodos se coordina desde **Gestión centralizada → Gestión de agentes**
(**Centralised management → Agent management**).

Para la eliminación definitiva de un agente, se debe actuar según su origen:

- Si es un **EndPoint**, desinstala o detén el servicio en la máquina para que no
  vuelva a enviar XML, y bórralo en la consola de su nodo o mediante las
  operaciones masivas de agentes.
- Si fue descubierto por un servidor satélite o generado por un plugin remoto,
  elimina la definición en el satélite o el chequeo de origen antes de borrarlo
  en la consola.

Borrar un agente únicamente en la pantalla sin detener su origen hace que el
servidor vuelva a crearlo en cuanto reciba el siguiente paquete de datos.

## Cómo se elimina un agente

Depende de dónde venga el agente, y borrarlo en la consola no siempre es
suficiente:

| Tipo de agente | Cómo se quita |
|---|---|
| **Ficticio** | El que se crea a mano en la consola: se borra ahí y ya está |
| **EndPoint** | El instalado en la máquina: se borra en la consola y se desinstala el EndPoint, si no quieres volver a verlo |
| **Broker** | Lo crea el agente principal del dispositivo: si se borra solo en la consola, volverá a aparecer |
| **De satélite** | Lo crea un servidor satélite a partir de su configuración: hay que quitar la definición en el satélite |
| **De plugin** | Lo genera un plugin al ejecutarse: mientras el plugin siga creando ese XML, el agente vuelve |

La regla general es sencilla: **si el agente lo genera otro, bórralo en el
origen**. En la consola se pueden borrar por lotes desde las operaciones masivas
de agentes.

## Varios servidores y alta disponibilidad

Pandora FMS admite **varios servidores de datos y de red contra la misma base de
datos**, repartiendo la carga. Con eso crece el número de agentes sin cambiar de
producto. Tres piezas sostienen el conjunto:

- **MySQL bien dimensionado.** Es el cuello de botella habitual: sin memoria y
  sin ajuste, los servidores de más no sirven de nada.
- **Clúster de MySQL** para alta disponibilidad y para repartir la carga de la
  base de datos.
- **La herramienta de alta disponibilidad** (`pandora_ha`), que puede vigilar el
  servidor y tratar de recuperarlo. Su instalación y arranque dependen del
  empaquetado y del runbook del clúster.

Los servidores de la misma instalación y su reparto de trabajo están explicados
en [Introducción y arquitectura](../parte-1/1.2-introduccion-y-arquitectura.md).

## Modo centralizado: qué es y qué mirar antes de activarlo

El **modo centralizado** permite administrar desde el Command Center grupos de
agentes, etiquetas, alertas, usuarios, políticas y colecciones en varios nodos.
Se activa al unificar el entorno con la **Merging tool** (ver [6.3 ·
Command Center](../parte-6/6.3-command-center.md)); a partir de ahí, el Command
Center pasa a ser la fuente de configuración de los nodos.

!!! warning "Míralo dos veces antes de activarlo"
    Si el entorno ya llevaba tiempo funcionando con el Command Center y varios nodos
    por separado, lo normal es que cada uno tenga **cosas distintas** creadas
    (grupos, etiquetas, políticas). Al activar el modo, el Command Center pasa a
    ser la fuente de configuración. Lo que hubiera en los nodos puede quedar
    sobrescrito o descuadrado.

    Con el entorno en marcha, conviene **inventariar antes** lo que hay en cada
    nodo, decidir qué versión es la buena y activarlo en una ventana, con copia de
    seguridad de todas las bases de datos.

## No llegan los eventos al Command Center

La réplica de eventos se configura en **cada nodo**, no en el Command Center. Si los
eventos de un nodo no aparecen arriba, se revisa:

1. **Los datos de la base de datos de replicación** en **Setup → Enterprise** del
   nodo: servidor, nombre de la base y usuario (`replication_dbhost`,
   `replication_dbname`, `replication_dbuser`). Si están mal, el nodo no tiene
   dónde escribir.
2. **La conectividad** del nodo hacia esa base de datos.
3. **El registro del servidor del nodo**, donde cada réplica deja su rastro
   (una línea por cada tanda de eventos replicados). Si ahí no aparece nada, el
   problema está en la configuración. Si aparece, pero el Command Center no los
   muestra, el problema está en la lectura.

En la propia consola del nodo se puede ver la fecha de la última réplica, que es
la comprobación más rápida.

## No se ve el histórico de un módulo en el Command Center

Cuando se abre la gráfica de un módulo en el Command Center y sale un error del tipo
**«Error connecting to database history at …»**, al Command Center le faltan
**privilegios en la base de datos de histórico** de ese nodo.

El Command Center se conecta al histórico con **el usuario, el host, la contraseña
y el nombre de base que el nodo tiene configurados** para su histórico. El permiso
se concede en la máquina de histórico, a ese usuario y para la IP del Command
Center. Si el nodo cambia esos datos, hay que actualizar el permiso.

Las contraseñas se consultan en la configuración de cada instalación; aquí no se
publican.

## Recuperar un nodo caído en un entorno HA

En alta disponibilidad, cuando un nodo se cae o se corta la red, el **esclavo
toma el relevo** como maestro. Al volver el nodo caído, su base de datos se ha
quedado desincronizada. Hay que **resincronizarla desde el actual maestro** antes
de devolverlo al servicio. Es lo que se conoce como «nodo roto».

El procedimiento, en resumen:

1. Poner el nodo caído en **standby** en el clúster, para que no intente asumir
   trabajo.
2. **Detener su MySQL** y apartar su directorio de datos.
3. Hacer una **copia del maestro** y restaurarla en el nodo caído.
4. Resincronizar con el clúster y devolver el nodo al servicio.

!!! warning "Operación de DBA"
    Esto se hace con las herramientas del clúster (Percona XtraBackup, y
    Pacemaker/Corosync para el clúster) y con una ventana delante. Un paso mal
    dado deja los dos nodos sin servicio, así que conviene seguir el runbook de
    alta disponibilidad y no improvisar sobre un entorno en producción.

Los parámetros del servicio de alta disponibilidad están en el fichero del
servidor: **`ha_interval`**, **`ha_hosts`**, **`ha_dbuser`** y **`ha_dbpass`**.
