# Agentes y sistemas

El **EndPoint** recoge datos desde la máquina. Este apartado cubre el arranque,
las colas de XML y la monitorización propia de Windows y Linux: PowerShell,
servicios y registros.

## El EndPoint nuevo no aparece en la Consola web

Se revisa en este orden:

1. **El agente apunta al servidor correcto.** En `pandora_agent.conf`, el token
   **`server_ip`** lleva la dirección del servidor de Pandora FMS y
   **`server_port`** el puerto de Tentacle, que es **41121**. Si el puerto no es
   ese, el agente escribe en el vacío.
2. **El servidor acepta agentes nuevos.** En `/etc/pandora/pandora_server.conf`,
   el token **`autocreate 1`** hace que los agentes que llegan sin alta previa se
   creen solos, en el grupo que fija **`autocreate_group`**. Con `autocreate` a 0
   y un agente que no declara grupo, sus datos se descartan sin más aviso.
3. **La red.** El EndPoint es quien inicia la conexión hacia el servidor, así que
   el cortafuegos tiene que dejar pasar el **41121/TCP** desde el equipo hasta el
   servidor.

## Probar Tentacle desde la línea de comandos

El cliente inicia la conexión al servidor Tentacle, por defecto en el puerto
**41121/TCP**. Para una prueba, envía desde el servidor del agente un fichero de
datos válido:

```bash
tentacle_client -a 192.0.2.10 -v /ruta/al/agente.data
```

Sustituye la IP y la ruta por las de tu entorno. Haz la prueba en una máquina de
test o con un XML de datos real: el servidor recibe el fichero y lo procesa. Si
falla, comprueba que `tentacle_serverd` está activo, que escucha en el puerto
esperado y que el cortafuegos permite el tráfico. Las opciones de contraseña,
certificados, puerto alternativo y proxy están en la
[referencia de Tentacle](../parte-9/9.4-referencia-completa-de-tentacle.md).

## El servicio del EndPoint no arranca en Windows

Comprueba dos cosas antes de tocar nada:

- **Se instaló sin permisos de administrador.** El instalador tiene que ejecutarse
  como administrador y el servicio necesita permisos de **SYSTEM**. Si no, no
  arranca.
- **Hay un `PandoraAgent.exe` suelto en la carpeta del instalador.** Si el
  instalador encuentra un ejecutable en su propia ruta, el servicio apunta a ese
  y no al que está en la carpeta del agente, con lo que falla al arrancar. Antes
  de instalar, deja la carpeta limpia.

Para distinguir un problema del servicio de uno del propio EndPoint, ejecuta el
script de arranque de la carpeta `scripts` con **Ejecutar como administrador**.
Si así arranca, revisa la cuenta configurada en las propiedades del servicio.

## Los XML se acumulan en `data_in`

Los ficheros que los EndPoint dejan en `/var/spool/pandora/data_in` se acumulan
cuando el procesamiento no da abasto. El orden de comprobación es:

1. **El servidor está en marcha.** Con el servidor parado, la cola crece y punto.
   Se comprueba con `systemctl status pandora_server`.
2. **Cuántos BADXML hay.** Son ficheros que el servidor no ha podido leer:
   ```bash
   ls /var/spool/pandora/data_in | grep -c BADXML
   ```
   Si hay muchos, se limpian y se busca la causa (siguiente apartado).
3. **Los hilos del Data server.** El token **`dataserver_threads`** del
   `/etc/pandora/pandora_server.conf` viene a **1** por defecto. En un servidor
   con muchas máquinas, subirlo acelera el vaciado de la cola.

## Hay ficheros BADXML

Un BADXML es un XML que el servidor no ha podido parsear, casi siempre porque un
módulo ha metido un valor que rompe el fichero. Se localiza el error sin adivinar:

```bash
xmllint TempTHXDF01.211810.data_BADXML
```

El comando señala la línea exacta. Con eso se va al XML, se mira qué módulo
genera ese contenido y se corrige el módulo para que devuelva un dato válido.
Los BADXML ya generados se pueden borrar: el agente los volverá a enviar
corregidos en el siguiente intervalo.

## Llegaron muchos datos de golpe y el servidor va con retraso

Después de una caída del servidor, los EndPoint han seguido recogiendo datos y la
cola se llena de golpe. El servidor tiene un modo de procesamiento pensado para
eso: el token **`dataserver_smart_queue`**, que en las versiones actuales **ya
viene activado** (`1`). Si la instalación es antigua y está a 0, se pone a 1. Y
si el volumen es alto, se suben los **`dataserver_threads`**.

## Los datos llegan duplicados

No es que el servidor los duplique: hay algo repetido en el origen. Se comprueba
por este orden:

- **Dos agentes con el mismo nombre.** Es lo más habitual. Para localizarlos,
  añade temporalmente a ese agente un módulo que devuelva la IP del equipo
  (`ipconfig` en Windows, `ip address` en Linux) y mira cuántas IP responden con
  el mismo nombre.
- **Dos módulos con el mismo nombre dentro del agente**, o un módulo y un plugin
  que obtienen el mismo dato.
- **Un módulo que devuelve más de un valor.** Se ejecuta a mano en el equipo y se
  comprueba que su salida es un único dato.

## El inventario del agente no llega

Desde la versión 784 **no hay servidor de inventario propio**: esa tarea la
absorbió el **Heavy Server**, que viene activo por defecto (`heavyserver 1`). Si
el inventario no aparece, se comprueba que el EndPoint lleva habilitado su plugin
de inventario y que el Heavy Server está en marcha. El antiguo token
`inventoryserver` ya no existe.

## Configurar el EndPoint desde la consola

Puede hacerse si el agente lo permite: el token **`remote_config`** de
`pandora_agent.conf` viene a **1** por defecto, así que el agente admite que le
cambien la configuración desde la Consola web. Si alguien lo puso a 0, ahí deja
de aceptar cambios remotos y hay que editar el fichero a mano.

## Caracteres que conviene no usar en nombres de agentes y módulos

Para que las rutas y los comandos internos no se líen, conviene evitar **`/`**,
**`\`**, **`|`**, **`%`**, **`#`**, **`&`** y **`$`** en el nombre de un agente o
de un módulo. Son caracteres que el sistema interpreta en rutas y ejecuciones, y
dar problemas con ellos es cuestión de tiempo.

## Monitorización básica de Windows

Una vez instalado el EndPoint, lo más rápido es no escribir módulos a mano:

- Aplica una de las **políticas** que trae la consola para equipos Windows, que
  ya incluye el juego básico de comprobaciones.
- O usa las **plantillas de módulos** en la configuración del agente, en la
  sección **Module templates**.

Al aplicar la política o la plantilla, los módulos se escriben en el fichero de
configuración del agente. Empiezan a reportar en el siguiente intervalo. Para
cosas concretas de tu entorno, se añaden módulos propios (o scripts y plugins)
encima de esa base.

## Monitorización básica de Linux

Es el mismo camino: políticas por sistema operativo que trae la consola, o
plantillas de módulos desde la configuración del agente. Con eso ya reportan CPU,
memoria, disco, procesos y los servicios habituales; lo específico se añade a
mano o con un plugin.

## Ejecutar un script de PowerShell en un módulo

El EndPoint de Windows sabe ejecutar PowerShell. Se le indica la ruta del
ejecutable y el script:

```
module_begin
module_name Nombre_del_modulo
module_type generic_data
module_exec C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -Command "C:\Ruta\script.ps1"
module_end
```

El **tipo** del módulo se elige según lo que devuelva el script:

| Tipo | Para qué |
|---|---|
| `generic_data` | Un dato numérico |
| `generic_data_string` | Un dato alfanumérico |
| `generic_proc` | Un valor booleano (1 o 0) |

Si el script devuelve texto, `generic_data` no vale: el módulo aparecerá en
Desconocido.

## Levantar o parar un servicio o proceso

Hay dos mecanismos, y conviene no confundirlos:

- **Postcondiciones**: el módulo, además de medir, ejecuta algo cuando se cumple
  una condición sobre su valor. `module_condition` lleva operador, valor y el
  comando de respuesta. La sintaxis y los operadores se detallan en la
  [referencia del EndPoint](../parte-9/9.1-referencia-completa-de-configuracion-del-endpoint.md).
- **Watchdog de Windows**: `module_proc` puede relanzar un proceso caído con
  `module_watchdog` y `module_start_command`. `module_service` vigila un servicio
  de Windows y lo reinicia directamente. También se explica en la
  [referencia del EndPoint](../parte-9/9.1-referencia-completa-de-configuracion-del-endpoint.md).

## Monitorizar logs de Windows

El EndPoint de Windows trae tres vías:

- **Logevent**: lee los **eventos del sistema** de Windows; se elige la categoría
  que interesa.
- **Regexp**: busca un patrón dentro de un **fichero de log** concreto.
- **Plugins** de logs: la misma búsqueda, con un script, útil cuando el formato
  es propio.

## Monitorizar logs de Linux

Los dos plugins que se usan son:

- **`grep_log`**: dada una ruta, busca el contenido que le indiques y crea el
  módulo con el resultado.
- **`grep_log_module`**: igual, pero además **envía el log al colector de logs**
  de Pandora FMS con origen *Syslog*, para que quede en el visor.

La diferencia práctica: el primero mide, el segundo además archiva.

## Variables de usuario cuando el EndPoint no corre como root

Si el EndPoint se ejecuta con un usuario distinto de `root`, los módulos que
dependen del entorno de ese usuario pueden fallar. Se comprueba:

1. Que el **home** del usuario existe.
2. Que tiene una **shell válida** (por ejemplo, `/bin/bash`); por seguridad, viene
   desactivada.
3. Que las **variables de entorno** que necesita están en su `$HOME/.bashrc` (ese
   fichero no existe por defecto: hay que crearlo).
4. Que el fichero es legible y que todo el home pertenece a ese usuario.

Con las cuatro cosas en orden, el EndPoint hereda el entorno al arrancar.
