# Informes, logs y correo

Aquí se agrupan las incidencias de informes, colecciones, visor de logs y correo.

## Los informes PDF no se generan

El PDF de un informe lo compone la consola con un **Chromium en modo sin
interfaz**. Así que lo primero no es PHP, es el motor de renderizado:

- Comprueba que **Chromium está instalado** en el servidor.
- Revisa el ajuste **Chromium path** en **Administración → Configuración →
  General**: tiene que apuntar al binario real (por defecto,
  `/usr/bin/chromium-browser`).
- Si acabas de tocar la configuración de PHP, reinicia el servicio web para que
  la recoja.

!!! note "Aviso"
    Las fichas antiguas hablaban de `curl` y de `allow_url_fopen` para generar los
    PDF. Ese era el mecanismo anterior: hoy el informe lo renderiza Chromium, y es
    ahí donde hay que mirar primero.

## Falta memoria al generar un informe o al actualizar

El error que ves es de PHP, no de Pandora FMS:

```
Fatal error: Allowed memory size of XXXXX bytes exhausted
```

Se sube el límite en `php.ini` (`/etc/php.ini` o `/etc/php/8.x/apache2/php.ini`
según el sistema), en la variable **`memory_limit`**, y si el proceso tarda
demasiado, también **`max_execution_time`**. Después, reinicia el servicio web.

No subas el valor sin medida: un `memory_limit` enorme puede tumbar la máquina
cuando varias peticiones coinciden. Sube lo justo y comprueba.

## Las colecciones de ficheros no funcionan

El agente necesita **`unzip`** para descomprimir las colecciones. En Linux es una
dependencia del paquete del agente, así que comprueba que está instalado y que el
usuario con el que corre el agente lo encuentra en su `PATH`.

Si sigue sin aplicarse, mira el directorio de colecciones del agente,
**`/etc/pandora/collections`**. Cada colección descargada deja un fichero `.md5`
junto a su carpeta:

- Si hay un `.md5` **sin carpeta** que le corresponda, bórralo.
- En el siguiente ciclo, el agente volverá a descargar la colección y la
  descomprimirá.

En Windows no hay que instalar nada: `unzip` viaja con el agente.

## «Unable to create the collection»

Al crear una colección desde la consola, ese error suele ser de rutas o de
permisos. Se revisan las dos rutas que usa el proceso:

- La carpeta de colecciones del servidor: `data_in/collections`.
- La carpeta de adjuntos de la consola: el directorio de **Attachment directory**
  configurado en **Administración → Configuración → General** (por defecto, el
  `attachment` de la consola).

Ambas tienen que **existir** y ser legibles y escribibles por el usuario del
servidor web. Si la ruta de adjuntos de la consola no coincide con la real, la
colección no se crea por mucho que los permisos estén bien.

## Las alertas se ejecutan pero no llega el correo

Se revisa en este orden:

1. **Dónde está configurado el correo.** Vale la consola o el fichero del
   servidor, pero **no los dos a la vez**: si conviven, se pisan.
2. **Las credenciales de la cuenta.** Si alguien cambió la contraseña, el envío
   deja de funcionar sin más aviso.
3. **Los permisos de la cuenta.** Muchos proveedores exigen habilitar el acceso
   desde aplicaciones de terceros.
4. **El registro del servidor.** Con la verbosidad a 10 aparecen los errores de
   correo en `/var/log/pandora/pandora_server.log`. Si el MTA es Postfix, su
   rastro está en `/var/log/maillog`.

## Los correos llegan con el remitente equivocado

El remitente por defecto es `pandora@localhost`, que muchos servidores de correo
rechazan. Se cambia con el token **`mta_from`** de
`/etc/pandora/pandora_server.conf`:

```
mta_from Pandora FMS <pandora@tudominio.com>
```

Tras el cambio, se reinicia el servidor.

## No envía correo con autenticación

Comprueba primero que hay un MTA en el servidor, que el servicio está arrancado y
que el puerto SMTP está abierto. Después, que los parámetros de correo están bien
en **uno de los dos sitios**:

| Token (en `pandora_server.conf`) | Para qué |
|---|---|
| `mta_address` | Dirección del servidor de correo |
| `mta_port` | Puerto (por defecto, 25) |
| `mta_user` y `mta_pass` | Usuario y contraseña, si el servidor los pide |
| `mta_auth` | Sistema de autenticación (LOGIN, PLAIN, CRAM-MD5, DIGEST-MD5) |
| `mta_from` | Remitente que verá quien recibe |

La alternativa es configurarlo en la consola, en **Ajustes → Configuración del
sistema → Configuración general → Configuración de alertas**, bloque
**Configuración de correo**. Insistimos: **una de las dos**, no las dos.

Si el correo se configura en la consola, revisa también el mecanismo de
autenticación (**SMTP authentication**). El valor por defecto usa el primero
que anuncie el proveedor y no prueba los demás: con un proveedor que anuncia
`DIGEST-MD5` y lo rechaza, el envío falla y hay que elegir `LOGIN`. En
`pandora_server.log`, el fallo aparece como `[ERROR] Sending email to …`.

## Error de resolución de nombres al enviar correo

En el registro de la consola aparece un error del tipo:

```
PHP Warning: fsockopen(): php_network_getaddresses: getaddrinfo failed:
Temporary failure in name resolution
```

Es un problema de **DNS del servidor**, no de Pandora FMS. Se revisa la
resolución de nombres del sistema (`/etc/resolv.conf`) y que el nombre del
servidor de correo resuelva desde esa máquina. Reiniciar el servicio web puede
desatascar el envío un rato, pero no arregla la causa.

## Las horas no cuadran

El desajuste puede estar en tres capas distintas y conviene comprobarlas todas
antes de tocar nada:

| Capa | Cómo se comprueba |
|---|---|
| Sistema | `date`, y la zona con `timedatectl` |
| MySQL | `SELECT now();` y `SELECT @@global.time_zone, @@session.time_zone;` |
| PHP | Un fichero suelto que imprima `date("Y/m/d H:i:s O e")` |

Localizada la capa que va desfasada, corrígela allí: la zona del sistema, la del
servidor de base de datos o la de PHP. Las marcas temporales pueden aparecer
desplazadas en la consola; consulta el registro del servidor si además faltan
datos.

## El visor de logs no muestra nada

Los logs se guardan en **OpenSearch**. Si el visor está vacío, se comprueba:

1. **El servicio de OpenSearch** está en marcha.
2. **Hay conexión** desde el servidor de Pandora FMS al puerto **9200**.
3. **El servidor de syslog está activado.** El token **`syslogserver`** viene a
   **0** por defecto en `pandora_server.conf`: sin él, nadie procesa los logs.
4. **El tamaño de los índices.** Índices enormes hacen que el visor tarde o no
   cargue; se revisan y se rota lo que haga falta.

## Configurar rsyslog para el servidor syslog

El servidor syslog necesita recibir los logs de los dispositivos en un fichero
para luego procesarlos. En el servidor hay que tener **rsyslog** instalado y, en
`/etc/rsyslog.conf`, la recepción por **UDP y TCP en el puerto 514**, además del
fichero donde se escriben los mensajes.

!!! note "OpenSearch, no Elasticsearch"
    Las fichas antiguas dicen que los logs se envían a Elasticsearch. El
    almacén que usa la documentación actual es **OpenSearch**.

## Integrar una herramienta de ticketing

La vía habitual es la apertura y cierre de incidencias con **alertas**: la acción
de la alerta llama a la herramienta. Sirve tanto un correo a la bandeja de
entrada del ticketing como un script o una llamada por línea de comandos.

Para que además se cierre la incidencia al recuperarse el servicio, hace falta
conocer el método de cierre y guardar el identificador del ticket al crearlo, en
la base de datos o en un fichero de intercambio. Ese identificador es lo único
que la alerta de recuperación necesita para cerrar el ticket correcto.
