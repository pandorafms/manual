# Alertas y eventos

Esta sección recoge los problemas que más se repiten con las alertas. Unas veces
no saltan cuando deberían. Otras saltan demasiado. Y otras el aviso no llega en
condiciones. Todas las comprobaciones se hacen desde la **Consola web**, en
**Alertas** y **Administración → Configuración**, salvo donde se indique otra
cosa.

## La alerta no salta aunque el valor sea malo

Casi siempre es el **número mínimo de alertas** de la plantilla. Ese campo dice
cuántos valores malos seguidos hacen falta para disparar. La cuenta es esta:

- Con **mínimo 0**, la alerta se dispara con el primer valor malo.
- Con **mínimo 1**, hacen falta **dos** valores malos dentro del periodo que fija
  el **umbral de tiempo**.

Si el módulo reporta picos sueltos y la alerta no dispara, el mínimo está bien
puesto. El problema no es la alerta: es que el módulo oscila. Baja el mínimo a 0
o ajusta el periodo del umbral. Y revisa la **protección Flip Flop** del módulo:
exige varios chequeos seguidos antes de cambiar de estado.

## Ni las alertas ni los eventos se lanzan

Antes de tocar la plantilla, descarta que algo los esté silenciando. Se comprueba
en este orden:

- La **tormenta de eventos** (*event storm protection*) no está activa en
  **Administración → Configuración → General**. Si lo está, la plataforma
  amortigua los eventos cuando llegan en tromba y puede parecer que no se lanzan.
- El **agente** no está en modo silencioso (*quiet*).
- El **módulo** tampoco.
- El **grupo** al que pertenece el agente no tiene las alertas o los eventos
  deshabilitados.

Si las cuatro cosas están bien, la alerta tiene que disparar. Comprueba el
registro del servidor para ver si el evento llega a evaluarse.

## La alerta salta cada cinco minutos

La plantilla tiene dos límites que conviene distinguir: el **número máximo de
alertas** y el **umbral de tiempo**. Para que un problema que se mantiene avise
una sola vez al día: **umbral de tiempo a un día**, **mínimo en 0** y **máximo en
1**. Así la alerta se dispara con el primer valor malo. Y no vuelve a repetirse
hasta que pase el umbral, por mucho que el módulo siga mal.

## Qué significa cada límite de la plantilla

Los tres campos se confunden con facilidad y hacen cosas distintas:

| Campo | Qué controla |
|---|---|
| **Número mínimo de alertas** | Cuántas veces debe repetirse la condición para que se ejecute la acción la primera vez |
| **Número máximo de alertas** | Cuántas alertas se pueden enviar seguidas dentro del mismo intervalo |
| **Umbral de tiempo** (*time threshold*) | Tiempo que debe pasar, con el estado incorrecto todavía activo, antes de volver a avisar |

Un ejemplo con el umbral a 24 horas. La alerta avisa una vez. No repite hasta que
pasa un día, aunque el módulo siga en mal estado todo ese tiempo.

## El correo de la alerta llega sin saltos de línea

Es un problema de formato del cuerpo del mensaje, no del envío. En la **acción**
de la alerta (o en los campos avanzados de la plantilla si se definen ahí), hay
que envolver el texto entre las etiquetas `<pre>` y `</pre>`:

```html
<pre>
Hello, this is an automated email coming from Pandora FMS

This alert has been fired because a CRITICAL condition in one of your monitored items:

Agent: _agent_
Module: _module_
Module description: _moduledescription_
Timestamp: _timestamp_
Current value: _data_

Thanks for your time.
Best regards,
Pandora FMS.
</pre>
```

Las macros (`_agent_`, `_module_`, `_data_` y el resto) se sustituyen al enviar.
Sin las etiquetas, el cliente de correo junta todas las líneas.

## La gráfica no aparece en el correo de la alerta

Las gráficas que se adjuntan a los avisos las renderiza el servidor con un motor
de renderizado sin interfaz. Si no salen, se revisa en este orden:

1. **El binario del motor está instalado y bien apuntado.** El ajuste es
   **Chromium path** en **Administración → Configuración → General**, y por
   defecto es `/usr/bin/chromium-browser`. Si el motor no está instalado en el
   servidor, no hay gráfica.
2. **La configuración de la API es correcta.** Comprueba la llamada a la API que
   usa la consola para pedir la gráfica.
3. **La resolución de nombres (DNS).** Si la consola se llama a sí misma por un
   nombre que no resuelve, la API falla. Para salir de dudas, usa su dirección IP.
4. **Lo de fuera:** proxy o cortafuegos por medio.
5. **Lo de dentro:** SELinux e `iptables` en el propio servidor.

!!! note "Aviso"
    El procedimiento antiguo hablaba de **PhantomJS**. Ese motor ya no se usa: la
    renderización la hace Chromium, con el ajuste **Chromium path**.
