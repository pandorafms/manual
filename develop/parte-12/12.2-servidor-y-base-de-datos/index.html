    Servidor y base de datos¶

    Las dos piezas de las que depende todo lo demás: el servidor que procesa y la base de datos que guarda. Cuando una falla, la otra lo nota.

    El servidor de Pandora FMS es una aplicación con varios servidores internos. Cuando no arranca, se reinicia solo o se cae, el registro dice por qué. Casi todo se resuelve leyéndolo antes de tocar nada.

    El servidor no arranca¶

    Lo primero son los dos ficheros de registro:

    • /var/log/pandora/pandora_server.log
    • /var/log/pandora/pandora_server.error

    Ahí aparece el error concreto. Comprueba también MySQL, que sí es una dependencia del servidor. tentacle_serverd es un servicio aparte: si está parado, los EndPoints no podrán entregar datos por Tentacle, pero eso no impide por sí solo que arranque pandora_server.

    El servidor se reinicia en bucle¶

    Cuando algo lo mata y lo vuelve a levantar cada pocos minutos, el sospechoso es el tiempo de arranque. El token server_keepalive del /etc/pandora/pandora_server.conf viene a 45 segundos por defecto. Si el servidor tarda más que eso en quedar operativo, el sistema de alta disponibilidad no lo ve activo y lo reinicia, y así en bucle.

    La causa habitual es haber subido los hilos de los servidores internos (*_threads): cuantos más hilos, más tarda en arrancar. Se corrige subiendo server_keepalive para que cubra ese arranque.

    El servidor se cae¶

    Se mira el mismo registro y, si no aparece nada, se descartan estas causas por orden:

    • Memoria insuficiente. El servidor se queda sin RAM y el sistema lo mata.
    • MySQL. Que la base de datos vaya lenta o se caiga arrastra al servidor.
    • Nodos llenos. En un Command Center, un nodo sin espacio deja de responder.
    • Una actualización a medias. Paquetes incorrectos o una actualización del esquema de la base de datos que no terminó.

    «Fallo de segmentación» al iniciar el servidor¶

    Puede aparecer cuando se han asignado más hilos de los que el hardware puede inicializar y sostener. Revisa los tokens *_threads del fichero y reduce los que se hayan subido sin una medición que lo justifique. No hay una equivalencia fija entre hilos y módulos: depende del tipo de chequeo, el intervalo, la concurrencia y el hardware. Mide antes de volver a aumentarlos.

    Activar o parar servidores internos¶

    Cada servidor interno se enciende y se apaga con su token en /etc/pandora/pandora_server.conf: 1 lo activa y 0 lo desactiva. Los que hacen falta según el uso están explicados en Introducción y arquitectura.

    Después de cambiar el fichero hay que reiniciar el servicio:

    systemctl restart pandora_server

    Un servidor interno parado no da error: simplemente no hace su trabajo, así que si algo «no se procesa» y el token está a 0, ya sabes por dónde va.

    Ejecutar el purgado de la base de datos a mano¶

    El mantenimiento se instala en /etc/cron.hourly/pandora_db y llama a la herramienta con la configuración del servidor:

    /usr/share/pandora_server/util/pandora_db.pl /etc/pandora/pandora_server.conf

    Las instalaciones antiguas de Enterprise tenían además un ejecutable en /usr/bin/pandora_db; hoy la ruta buena es la de util/.

    Si nunca se ha ejecutado, la primera pasada puede tardar horas: lánzala en segundo plano y no la cortes a medias.

    El kernel avisa de «possible SYN flooding on port 41121»¶

    El puerto de Tentacle es el 41121/TCP. Un recuento alto de conexiones TIME_WAIT puede servir de pista, pero no demuestra por sí solo que la cola SYN esté saturada. Mira también las conexiones SYN_RECV y los contadores de retransmisión antes de cambiar parámetros del kernel:

    netstat -an | grep TIME_WAIT | wc -l

    Algunos despliegues actuales fijan tcp_max_syn_backlog en 65536. No es un valor universal ni corrige por sí solo un problema de red o de capacidad: identifica primero dónde se descartan las conexiones.

    net.ipv4.tcp_max_syn_backlog = 65536

    No uses tcp_tw_recycle

    El parámetro net.ipv4.tcp_tw_recycle que recomendaban guías antiguas se retiró del kernel Linux en la versión 4.12. No lo busques ni lo añadas.

    En la base de datos, las causas habituales son el mantenimiento que no se ejecuta, una tabla dañada, almacenamiento lento o una retención de datos mal dimensionada.

    Cómo hacer una copia de seguridad de la base de datos¶

    El producto trae su propia herramienta: pandora_backup.sh, en /usr/share/pandora_server/util/. La ruta de la consola se pasa con -c; el destino de la copia, con -d:

    # Copia de seguridad (base de datos + ficheros de la consola)
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console -d /tmp

# Restaurar la base de datos de una copia
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console \
    -s /ruta/a/la/copia/pandorafms_backup_fecha.tar.gz

# Restaurar también ficheros y configuración (además de la base de datos)
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console \
    -s /ruta/a/la/copia/pandorafms_backup_fecha.tar.gz -f

    La ruta de la consola con -c es necesaria también al restaurar: la herramienta la usa para leer las credenciales de la base de datos. Sin -f, restaura la base de datos, pero no los ficheros de la consola ni la configuración. Con -f restaura también esos ficheros y el spool; -b excluye la base de datos. La restauración de base elimina y recrea la base configurada. Comprueba el fichero y haz una copia del estado actual antes de continuar.

    Si se prefiere hacerlo a mano, la base de datos y el usuario suelen llamarse pandora. El ejemplo de restauración presupone que la base ya existe:

    mysqldump -u pandora -p pandora > /ruta/pandora_backup_fecha.sql
mysql -u pandora -p pandora < /ruta/pandora_backup_fecha.sql

    Las credenciales se consultan en /etc/pandora/pandora_server.conf, en los campos dbuser, dbpass y dbname. No se copian aquí.

    La base de datos va lenta¶

    Antes de tocar la configuración de MySQL, descarta estas cuatro causas, por orden:

    1. El mantenimiento no se está ejecutando. El paquete deja el script en /etc/cron.hourly/pandora_db, que llama a /usr/share/pandora_server/util/pandora_db.pl con la configuración del servidor. Si se ha perdido o el cron no corre, la base crece sin límite. Lánzalo a mano y mira si da error.
    2. La retención no encaja con el uso. Revisa los periodos de purga y, en entornos grandes, si conviene mover los datos antiguos a una base de datos de histórico. No hay un periodo universal: depende de cuánto dato se recoge y cuánto se necesita consultar.
    3. El almacenamiento. Comprueba latencia, espacio libre y carga de lectura y escritura. Un disco saturado afecta tanto a MySQL como al servidor.
    4. El ajuste fino de MySQL. Parámetros como innodb_buffer_pool_size o innodb_io_capacity se ajustan al tamaño real de la máquina y al volumen de datos. No hay valores universales: se parte de una recomendación para el tamaño de servidor y se mide.

    La consola avisa de «Mantenimiento de base de datos»¶

    Ese aviso significa que el mantenimiento no se está ejecutando. La base de datos necesita ese script cada hora: purga datos antiguos, compacta y mueve al histórico lo que corresponda.

    Comprueba que existe y funciona:

    /usr/share/pandora_server/util/pandora_db.pl /etc/pandora/pandora_server.conf

    Si el script responde que «otra instancia parece estar en ejecución», el bloqueo con nombre de MySQL indica que otra conexión está ejecutando el mantenimiento. El bloqueo se libera cuando termina o se cierra la conexión. Comprueba si hay otra ejecución activa y revisa sus registros; no borres a mano un supuesto indicador de bloqueo de la tabla de configuración.

    Error de base de datos al arrancar el servidor¶

    Si el registro del servidor muestra un fallo de conexión al arrancar (DBI connect ... failed), comprueba primero estos dos puntos:

    • La contraseña o el usuario no son correctos. Se prueba a mano con mysql -u pandora -p -h 127.0.0.1 -D pandora y se comparan con los campos dbuser, dbpass y dbname de /etc/pandora/pandora_server.conf.
    • El host configurado es localhost y el socket no coincide. Algunos empaquetados de MySQL usan /var/lib/mysql/mysql.sock en vez de /tmp/mysql.sock. El valor actual por defecto de dbhost es 127.0.0.1, que usa TCP; si tu instalación usa localhost, comprueba primero la ruta real del socket antes de cambiarla.

    En versiones actuales dbhost viene con 127.0.0.1, que evita problemas de resolución de localhost por IPv6.

    La base de datos no responde y hay demasiados datos¶

    No hay un número universal de registros a partir del cual la base deje de responder. Influyen el volumen de datos, la tasa de escritura, las consultas, la retención y el hardware. Antes de reconstruir nada, revisa el registro de MySQL, el espacio y la carga; confirma que el mantenimiento funciona y que la política de purga e histórico coincide con lo que necesitas. Haz una copia antes de cualquier reparación. Una reconstrucción o restauración de la base se debe planificar con un DBA: no borres el directorio de datos ni la base a ciegas.

    «Table is marked as crashed and should be repaired»¶

    REPAIR TABLE solo sirve para motores que admiten esa operación, como MyISAM. Las tablas principales de Pandora FMS usan InnoDB: comprueba primero el motor y el error concreto antes de intentar reparar:

    SHOW TABLE STATUS LIKE 'nombre_de_la_tabla';

    Si la tabla usa MyISAM, REPAIR TABLE nombre_de_la_tabla; puede ser apropiado. Si usa InnoDB, ese no es el procedimiento: conserva el registro del error y consulta el diagnóstico del motor o restaura una copia validada con un DBA.

    Corrupción en la base de datos¶

    Antes de intentar reparar, identifica el motor de la tabla. mysqlcheck --auto-repair solo sirve para motores que admiten esa operación, como MyISAM; no repara InnoDB. Las tablas principales de Pandora FMS usan InnoDB. Conserva el registro del error, haz una copia y consulta el procedimiento de recuperación para ese motor con un DBA. No borres /var/lib/mysql ni recrees la base de datos como primer intento.

    Error «PROCESS privilege» al hacer un volcado¶

    En MySQL 8, si mysqldump falla por falta del privilegio PROCESS al leer tablespaces, prueba primero a omitirlos con --no-tablespaces:

    mysqldump --no-tablespaces -u pandora -p pandora > /ruta/backup.sql

    Así no hace falta dar PROCESS global al usuario de la aplicación solo para crear una copia. Si tu versión no acepta la opción, consulta con el DBA antes de cambiar los privilegios.

    El mantenimiento también procesa la base de datos histórica¶

    El mantenimiento horario estándar gestiona el histórico cuando está configurado. El servidor lee los parámetros de conexión guardados en la configuración de la base principal y conecta con el host, la base y el usuario indicados allí. No hace falta crear otra tarea de cron con una copia manual de pandora_server.conf. Comprueba que la base histórica está activada y que la conexión configurada funciona.
