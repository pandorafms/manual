    CLI de la API v2 (pandora-cli)¶

    pandora-cli es un cliente de línea de comandos de la API v2. Cada comando es una petición HTTP: el binario autentica, convierte los argumentos y pinta la respuesta. Nada más. Toda la validación, los permisos y las reglas de negocio se quedan en la consola, que es donde tienen que estar.

    Eso marca lo que se puede y lo que no se puede hacer con él. No sustituye al CLI de administración pandora_manage: la API v2 todavía no expone todo lo que hace la herramienta clásica —desbloquear usuarios, gestionar clústeres, tocar los ficheros de configuración locales, crear gráficas personalizadas o reiniciar contadores, entre otras—. La comparación de las tres herramientas (pandora_manage, pandora_revent y pandora-cli) está en la referencia del CLI de administración, en la Parte 09.

    Cómo se obtiene¶

    El binario se distribuye con el paquete del servidor, donde lo usa el servicio de Pandora AI, y estará disponible también en el Marketplace (https://marketplace.pandorafms.com/), donde se podrá descargar cuando esté publicado. Este capítulo no da pasos de instalación: cuando exista la ficha del Marketplace, ese es el sitio.

    Se compila para Linux (x86-64 y ARM64), macOS (Intel y Apple silicon) y Windows (x86-64). La versión probada para esta edición es Linux x86-64.

    Requisitos¶

    Tres cosas, y ninguna es opcional:

    • Un token de la API v2. Se crea en la consola bajo el usuario cuyos permisos debe usar el CLI. Cada comando se ejecuta con el perfil ACL de ese usuario. Cómo se crea y cómo se envía está en el capítulo 13.1.
    • Acceso de red a la consola, por HTTP o HTTPS.
    • La dirección del cliente permitida por la ACL de la API. La consola restringe el acceso por IP. Si la dirección no está en la lista, cualquier llamada falla con:
    401 IP 10.0.0.5 is not in ACL list

    Eso se arregla en la consola, no en el CLI: el campo «IP list with API access» de Administración → Configuración → General. Una IP por línea.

    Configurar el acceso¶

    Guardar un token¶

    auth login comprueba el token contra la consola antes de escribir nada. Si lo rechaza, no guarda nada.

    pandora-cli auth login --token <token> --url https://console.example.com/pandora_console/api/v2/

    La dirección debe apuntar a la raíz de la API y terminar en /api/v2/. Si se omite, el valor por defecto es http://localhost/pandora_console/api/v2/.

    Las credenciales quedan en ~/.pandora-cli/config.json, con el directorio en 0700 y el fichero en 0600. El token se guarda en base64: eso lo mantiene fuera de una mirada casual en el terminal, pero no es cifrado; lo que protege el fichero son los permisos. El CLI se niega a leer una configuración con permisos más amplios que 0600. Para guardarla en otro sitio, PANDORA_CLI_HOME.

    Varias consolas¶

    Cada consola es un contexto con nombre:

    pandora-cli auth login --token <token> --url https://prod/pandora_console/api/v2/ --context prod
pandora-cli auth login --token <token> --url https://lab/pandora_console/api/v2/  --context lab --insecure

pandora-cli auth context list
pandora-cli auth context use prod
pandora-cli user list --context lab

    --token y --url también se pueden pasar a cualquier comando. Usados así, el token no se escribe en disco, que es lo que conviene en un trabajo de CI que ya lo tiene en un secreto. El precio es que queda en el historial del intérprete y en la lista de procesos del sistema operativo: no lo uses en una máquina compartida.

    Certificados autofirmados¶

    --insecure desactiva la verificación TLS. Nunca se aplica por defecto. Pasado a auth login, se recuerda para ese contexto; pasado a cualquier otro comando, vale solo para esa ejecución.

    Comprobar que funciona¶

    pandora-cli auth status

    Context:  prod
URL:      https://console.example.com/pandora_console/api/v2/
Insecure: false
Config:   /home/user/.pandora-cli/config.json
Token:    valid
Version:  v8.0NG.805 (build PC260915)
MR:       805
Package:  805
LTS:      Feature Release

Console specification: 519 operations, 69 entities (read 2026-10-23T09:12:37Z)

    Token: valid significa que la consola lo aceptó. Si no, el comando termina con código distinto de cero. Las líneas de versión, MR, paquete y LTS son lo que la consola dice de sí misma, y aparecen solo cuando lo dice. Con -o json la salida lleva los mismos datos en un objeto, más un objeto console con la versión cuando la consola la publica. --refresh vuelve a leer la descripción de la API después de actualizar la consola.

    Después, algo de verdad:

    pandora-cli user list

    IDUSER  FULLNAME  EMAIL              ISADMIN  DISABLED
admin   Pandora   admin@example.com  true     false

1 shown, 1 total.

    Correlación con sesiones de Pandora AI¶

    --ai-session-id añade una cabecera de correlación (X-Pandora-AI-Session) a cada petición. Sirve para agrupar en la auditoría las llamadas de una misma sesión de trabajo.

    • En auth login, un identificador explícito se guarda en ese contexto; sin la opción, el contexto conserva el que tuviera; y --ai-session-id= lo borra.
    • En cualquier otro comando es transitorio: vale para esa ejecución y no toca el valor guardado. --ai-session-id= desactiva la cabecera en esa llamada.
    • Un auth login fallido no escribe nada.

    El orden de resolución es: opción explícita, luego el contexto activo, luego nada. Es metadato de correlación, no una credencial: no autentica ni concede permisos. Que la consola lo registre o lo muestre en la auditoría se explica en Auditoría de Pandora AI.

    La salida¶

    La salida es una tabla en el terminal y JSON cuando se redirige o se encauza, para que un script no tenga que pedir formato:

    pandora-cli user list                      # tabla
pandora-cli user list | jq '.[].idUser'    # JSON
pandora-cli user list > users.json         # JSON

    Se puede forzar con -o json, -o table o -o yaml. Las líneas informativas (1 shown, 1 total.) salen solo en tabla; en JSON y YAML no, así que lo que se encauza siempre es válido. El comando termina con 0 si fue bien y distinto de cero si no, de modo que se puede usar directamente en un if.

    Paginación y filtros¶

    Aquí está la trampa número uno del CLI, y es de origen: --page empieza en 1, mientras que el parámetro page de la API empieza en 0. El CLI traduce, pero conviene saberlo para no mezclar los dos mundos. Las reglas de paginación de la API están en Convenciones de la API.

    Opción del CLI Qué hace
    --page <n> Número de página, 1-based. --page 1 es la primera.
    --size <n> Filas por página.
    --limit <n> Máximo de filas a devolver. Alternativa a --page/--size.
    --offset <n> Filas que se saltan. Alternativa a --page/--size.

    --limit y --offset no se pueden mezclar con --page y --size; el CLI lo rechaza antes de enviar nada. Una lista cuyo endpoint no los admite, como event list, no las ofrece. Si se pasa --size sin --page, el CLI envía las dos igualmente, porque hay endpoints que ignoran el tamaño sin número de página.

    La correspondencia con la API¶

    Los tres filtros avanzados del CLI son los parámetros de la API con otro nombre:

    Opción del CLI Parámetro de la API
    --where fieldConditions
    --fields requestedFields
    --in multipleSearchString

    --filter es distinto: acepta cualquier campo de la entidad y se combina con Y. Cuando el esquema declara el campo como array, repetir --filter acumula valores en vez de sumar condiciones, y un null explícito limpia el campo.

    La aceptación de --where, --fields e --in se decide por entidad, no por consola: /user/list puede aceptar fieldConditions y /event/list rechazarlo. El CLI valida ambos conjuntos en local y, cuando se equivoca uno, lista los nombres válidos. event es la excepción: no valida esos tres filtros y deja que la consola decida.

    Cuando la consola rechaza un filtro¶

    Si la entidad no admite el parámetro, la respuesta es un 400 y el CLI nombra la opción que lo envió:

    Error: POST event/list failed: 400 Field: fieldConditions is not a valid parameter
--where (fieldConditions) is not available on this console.

    El resto de la llamada no se ve afectado: solo falla la petición rechazada. Para ver qué admite la entidad en la versión instalada, pandora-cli <entidad> --help.

    Un caso especial: dateRange¶

    El filtro de fechas de event list no acepta la cadena "<inicio> - <fin>": quiere un JSON. Un preset y un intervalo relativo:

    pandora-cli event list --filter 'dateRange={"preset":{"value":"last_24_hours"}}'
pandora-cli event list --filter 'dateRange={"start":{"mode":"relative","value":1,"unit":"hours"},"end":{"mode":"now"}}'

    La cadena antigua falla con 400 Invalid date range format. Must be valid JSON. En Windows PowerShell 5.1 (y en PowerShell 7 anterior a 7.3) las comillas dobles del argumento se pierden antes de llegar al CLI, así que hay que escaparlas:

    pandora-cli event list --filter 'dateRange={\"preset\":{\"value\":\"last_24_hours\"}}'

    Los valores se convierten a su tipo JSON: true y false son booleanos, los dígitos son números y null es nulo. Para forzar una cadena, se entrecomilla: --filter name='"42"'.

    Crear y modificar¶

    --set añade un campo al cuerpo y se puede repetir. Para un cuerpo completo, --from-file lee un JSON de un fichero o de la entrada estándar:

    pandora-cli user create --set idUser=jdoe --set fullName='Jane Doe' --set password=secret
pandora-cli user update jdoe --set email=jane@example.com
pandora-cli user delete jdoe --yes

pandora-cli user create --from-file user.json
cat user.json | pandora-cli user create --from-file -

    --set y --from-file no se combinan. --from-file acepta un objeto o un array completo, tolera un BOM UTF-8 al principio (los editores de Windows) y es la única forma de enviar objetos y arrays anidados.

    --set convierte los valores a su tipo JSON, y ahí hay una trampa clásica: un campo de texto cuyo valor parece un número se envía como número. --set permissions=0755 manda 755. Se entrecomilla para forzar la cadena:

    pandora-cli <entidad> <verbo> --set permissions='"0755"'

    En un campo declarado como array, repetir --set acumula elementos, y un null explícito limpia el array. --set no interpreta literales de objeto ni de array: --set rules='{"agentGroup":2}' viaja como texto. Para eso, --from-file.

    delete pide confirmación. En una sesión no interactiva se niega en vez de preguntar, así que un script que olvidó --yes falla en voz alta en lugar de borrar en silencio.

    Algunas reglas viven solo en la consola y no aparecen en la lista de campos:

    • agent create necesita un grupo real: idGroup=0 se rechaza con 400 Agent group is missing. El nombre del agente lo genera la consola; para la etiqueta que controlas tú, se usa alias.
    • module create necesita idModule (el tipo de servidor) junto con idModuleType, no solo las columnas de los filtros.
    • Un usuario no administrador recién creado necesita al menos un perfil asignado con user profile add antes de poder entrar.
    • La primera regla de un event-alert-rule debe llevar operation=NOP; la consola rechaza cualquier otra.
    • module force-check pide una comprobación inmediata y responde 202 sin cuerpo: la comprobación termina por su cuenta. Los módulos que no admiten comprobación inmediata, como los de datos empujados, dan 400.

    Entidades anidadas y grupos¶

    Una entidad anidada lleva delante el identificador del padre:

    pandora-cli report-design-page list 12
pandora-cli report-design-page-widget list 12 3

    Las listas anidadas toman las mismas opciones de listado que las de primer nivel, cada una solo si el comando la declara. Dar la misma propiedad con una opción y con --set falla en local:

    Error: --page conflicts with "page" already present in the payload: give it once

    Algunas entidades agrupan parte de sus comandos en grupos, con la forma <entidad> <grupo> <verbo> <ids…>: policy, collection, service, agent, module, log, pandora-ai-audit, rmm y notification. pandora-cli <entidad> --help lista los grupos de cada una.

    pandora-cli policy module list 7
pandora-cli collection file upload 3 --file ./a.conf
pandora-cli service element add 2 --set description='Frontend CPU' --set idAgenteModulo=42

    Recetas y límites de la API v2¶

    Lo que sigue no es el manual del CLI: es lo que la API hace y no cuenta. Se agrupa por dominio porque cada uno tiene sus manías.

    Bloque Origen
    Agentes, módulos, políticas, colecciones, paradas, gráficas, contadores y 2FA Probado contra consola
    NCM: vendors, modelos, firmware, scripts, plantillas y ncm agent list Probado contra consola
    NCM sobre dispositivo (enable, bulk, update, backup, queue, script) Documentado desde --help
    RMM, notificaciones, correo, SIEM y tareas de Pandora AI Documentado desde --help

    En los bloques «documentado desde --help» se describe la interfaz, no el comportamiento verificado: comprueba la respuesta antes de confiar en ella.

    Agentes y módulos¶

    monitoring create empuja datos de agente. El cuerpo es un array con claves en snake_case: agent_data y module_data.

    cat > payload.json << 'EOF'
[
  {
    "agent_data": {"agent_name": "web1", "address": "10.0.0.5", "interval": 300},
    "module_data": [
      {"name": "cpu_usage", "type": "generic_data", "data": 12.5}
    ]
  }
]
EOF
pandora-cli monitoring create --from-file payload.json

    agent_name, address e interval son obligatorios; cada entrada de module_data necesita type. Reenviar el mismo agente, módulo y marca de tiempo actualiza el valor en vez de duplicarlo.

    Hay dos trampas que cuestan una tarde cada una:

    • Los datos de un agente que ya existe se descartan en silencio si el payload no lo nombra como lo guarda la consola: agent_name debe ser el name, no el alias, y el agente necesita un serverName que coincida con el nodo. Se ven con pandora-cli agent get <id> -o json. Un agente creado por la API tiene el name en hash, un alias para mostrar y ningún serverName.
    • Los módulos escritos así necesitan un tipo asíncrono (async_data, async_proc, async_string) para tener estado y disparar alertas. Un generic_* guarda el valor pero no calcula estado.

    Políticas¶

    La cola de políticas es asíncrona: policy purge y las operaciones de policy queue encolan trabajo y vuelven sin esperar. Una política no se puede borrar mientras tenga cola pendiente o agentes asignados: mira policy queue list —o policy queue summary— y usa policy queue clear, o espera.

    Quitar no es borrar. remove, delete y bulk-delete sobre un hijo de la política (agente, alerta, colección, grupo, módulo, plugin) solo lo marcan pendingDelete; el efecto llega cuando se aplica la cola, y restore deshace la marca. policy alert-action remove y policy queue delete son la excepción: se ejecutan al momento.

    Quitar un agente son dos pasos: policy agent remove lo marca, y policy queue apply-pending ignora los agentes en ese estado. Hay que encolar la operación:

    pandora-cli policy agent remove 7 25
pandora-cli policy queue add 7 --set operation=delete --set idAgent=42

    policyLinked tiene cuatro estados: 0 sin enlazar, 1 enlazado, 10 desenlace pendiente y 11 enlace pendiente. module policy link y unlink los mueven. Las operaciones bulk-* de plugins toman un array JSON de identificadores, que --set no puede construir: van con --from-file. El detalle del día a día de las políticas, con su cola y sus marcas, está en Políticas de monitorización.

    Colecciones¶

    collection file upload manda multipart/form-data: los ficheros con --file (repetible, al menos uno) y los campos de texto con --set. collection file download devuelve bytes, así que exige --output-file; un fichero existente solo se reemplaza con --force y una descarga fallida no deja un fichero a medias.

    Asignar una colección a un agente (agent collection add) exige un agente con configuración remota (remote=1) disponible en la consola. La asignación solo queda en su configuración remota; después de cambiar los ficheros hay que ejecutar collection apply para que los agentes recojan el paquete. El capítulo de colecciones cuenta el resto.

    Paradas planificadas¶

    dateFrom y dateTo son marcas Unix, no fechas legibles. La parada y lo que cubre son entidades distintas: scheduled-downtime-agent y scheduled-downtime-module se crean aparte, con el identificador de la parada delante. scheduled-downtime-module no tiene update: se quita el módulo y se vuelve a añadir. El módulo de idAgentModule tiene que pertenecer al agente de idAgent o la consola responde 404.

    Gráficas¶

    module graph no devuelve una imagen binaria: devuelve la imagen en base64 en el campo graph, con su mimeType y su encoding al lado. period va en segundos (mínimo 300; por defecto, un día).

    pandora-cli module graph 12 --set period=3600 -o json | jq -r .graph | base64 -d > graph.png

    graphType acepta solo data o histogram; los estilos de línea, área y barras son de chartType. Cualquier otro graphType da 400 Invalid value for graphType.

    SIEM y auditoría¶

    • siem-event y siem-log son de solo lectura y necesitan un backend SIEM configurado en la consola; sin él, 503 Invalid or missing log backend configuration. No son lo mismo: siem-event busca eventos y siem-log busca los registros decodificados. Sin fechas, cubren las últimas 24 horas.
    • log lee los registros retenidos por agente y pagina con cursor: usa --size y, para la página siguiente, --cursor con el valor que devolvió la anterior. No tiene --page.
    • audit-log (alias audit) es de solo lectura y lee el rastro de auditoría de la consola. get <idSession> devuelve una entrada con sus datos extendidos.

    Notificaciones y correo¶

    notification gestiona los mensajes de la consola, sus fuentes (solo lectura) y las preferencias de cada usuario. message create exige idUser, subject y message; message update ignora read, que es de solo lectura. email send manda un correo por el transporte de la consola y email config enseña la configuración sin credenciales.

    Pandora AI¶

    ai-task gestiona las tareas programadas de Pandora AI: create exige firstRun (marca Unix) y periodicity acepta hourly, daily, weekly, monthly o yearly; notifySuccess y notifyError aceptan never, on_request o always. ai-notify send avisa al dueño de una tarea y exige idScheduledTask, event, subject y message. La auditoría de las conversaciones se lee con pandora-ai-audit, que es de solo lectura.

    RMM¶

    rmm cubre la monitorización y gestión remotas: agentes, scripts, recursos, rutinas, programaciones, trabajos por lotes y sus colas. Son grupos, no verbos sueltos: rmm agent, rmm batch, rmm pending-software, rmm queue, rmm resource, rmm routine, rmm rule, rmm schedule, rmm script y rmm settings. Los campos que llevan arrays, como inputs o idAgentsRmm, se envían con --from-file. Las rutinas no tienen delete para sus agentes ni para sus programaciones: se marcan con --set pendingDelete=true.

    NCM¶

    ncm gestiona la configuración de equipos de red: agentes bajo gestión, firmware, scripts, plantillas y fabricantes. Es una sola entidad con grupos, y tiene 51 comandos. Los tipos de script son TEST, GET_CONFIGURATION, SET_CONFIGURATION, GET_FIRMWARE, SET_FIRMWARE, CUSTOM_TASK, SNIPPET y GET_OS_VERSION.

    El campo regexp de un script es una lista de pares [expresión, booleano], así que va con --from-file:

    echo '{"name":"Show version","idGroup":0,"type":"SNIPPET","content":"show version","regexp":[["^.*$",true]]}' \
  | pandora-cli ncm script create --from-file -

    Una plantilla toma el identificador de un script existente en idScript; su tipo viene de ese script y no se puede fijar. El capítulo de NCM cuenta la parte de consola.

    2FA y sesiones web¶

    user 2fa gestiona el segundo factor: status, reset (crea o rota el secreto; sale solo en esa respuesta), disable, bulk-disable y disable-all. reason es opcional y queda en la auditoría. bulk-disable y disable-all piden confirmación; disable-all afecta a toda la consola, así que comprueba dónde lo lanzas.

    token session gestiona sesiones de consola, las que abren la web y las aplicaciones móviles, que no son los tokens de API de token create:

    pandora-cli token session login --set id_user=jdoe --set password='...'
pandora-cli --token <access_token> token session logout

    login no necesita token. Devuelve access_token, access_expires_in y session_expires_at; si la cuenta tiene segundo factor, devuelve status: mfa_required con un mfa_token, y se completa con token session login-mfa. Una sesión no se puede renovar desde el CLI: la renovación necesita la cookie HttpOnly que pone la consola, y la herramienta no guarda cookies. Cuando caduca, se vuelve a entrar. El token de acceso se trata como una contraseña: fuera del historial y de los registros.

    Inspeccionar la API y diagnosticar¶

    spec lee la descripción que la consola publica de sí misma, sin abrir el swagger.json a mano:

    pandora-cli spec list                # esquemas publicados
pandora-cli spec show EventFilter    # un esquema, con allOf resuelto
pandora-cli spec raw                 # el swagger completo

    Los nombres son los que publica la consola (EventFilter, ReportDataSource), no los nombres con guion del CLI; spec list los lista y spec show sugiere el más parecido si te equivocas.

    Para ver qué se envía y qué vuelve, --verbose traza la petición y el estado de la respuesta por la salida de error, y deja la salida estándar limpia para encauzar:

    pandora-cli user list --filter isAdmin=true -v -o json > users.json

    → POST https://console.example.com/pandora_console/api/v2/user/list
→ body: {"isAdmin":true}
← 200, 1834 bytes

    pandora-cli docs imprime la referencia completa de la build instalada, y pandora-cli skill install deja una skill de uso para agentes que trabajan en terminal. Se vuelve a ejecutar después de actualizar, para que la skill siga describiendo el binario que hay.

    Problemas habituales¶

    Síntoma Causa y remedio
    401 ... token was rejected Token incorrecto o caducado. Vuelve a hacer auth login.
    401 IP ... is not in ACL list La dirección no está en la ACL de la API. Añádela en la consola.
    403 ... lacks permission El token es válido, pero el perfil ACL de su usuario no permite la operación.
    404 ... or the API base URL is wrong Comprueba auth status: la dirección debe terminar en /api/v2/.
    TLS verification failed Certificado autofirmado. --insecure, o guárdalo en el contexto al hacer login.
    has permissions 0644 El fichero de configuración lo puede leer otro. chmod 0600 ~/.pandora-cli/config.json.
    --fields ... is not available on this console La entidad no admite ese parámetro; el CLI nombra la opción que lo envió.
    unknown field "..." El campo no existe en la entidad; el mensaje lista los válidos.
    the "..." entity does not exist on this console La consola no publica esa entidad. Prueba auth status --refresh si la actualizaste.
    Un valor como 0755 llega como 755 --set convierte lo que parece número. Entrecomilla el valor o usa --from-file.
    Un objeto o array de --set llega como texto --set no interpreta {...} ni [...]. Usa --from-file.
    unknown flag: --limit Ese listado no admite --limit/--offset. Usa --page y --size.
    Una política no se puede borrar Tiene cola pendiente o agentes asignados. policy queue clear o policy purge, y espera.
    Un hijo de política sigue ahí tras remove Solo está marcado pendingDelete. Aplica la cola o usa restore.
    Una colección no se asigna a un agente El agente necesita configuración remota (remote=1) disponible.
