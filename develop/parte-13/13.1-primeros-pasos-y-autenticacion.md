# Primeros pasos y autenticación

Todo lo que haces en la consola con el ratón (crear un agente, revisar un evento, asignar una alerta) puede hacerlo también un programa. Esa es la razón de ser de la **API v2** de Pandora FMS: una interfaz HTTP que habla JSON y que cualquier script, integración o herramienta externa puede usar sin pasar por la pantalla.

Antes de llamar a nada hay que resolver una pregunta tonta y decisiva: ¿quién llama? La API no atiende a desconocidos, y las dos formas de presentarse (una sesión de usuario o un token de API) tienen reglas distintas, duraciones distintas y usos distintos. Este capítulo las explica. Las convenciones del día a día (paginación, filtros, errores) están en [Convenciones de la API](13.2-convenciones-de-la-api.md) y los endpoints, uno por uno, en la [referencia](13.4-referencia-de-endpoints/index.md).

## Qué necesitas

| Requisito | Detalle |
|---|---|
| Dirección de la API | Cuelga de la consola, bajo `api/v2`. Si la consola está en `https://pandora.example.com/pandora_console`, la API está en `https://pandora.example.com/pandora_console/api/v2`. |
| Usuario | Un usuario de la consola. Las peticiones se ejecutan con su identidad, así que solo ve y toca lo que ese usuario puede ver y tocar. |
| Origen permitido | Si la consola limita la API por dirección IP, la tuya debe estar en la lista; si no, la respuesta es un `401` con el mensaje `IP <dirección> is not in ACL list`. |
| Conexión segura | Usa HTTPS. Las credenciales y el token viajan en cada petición. |

Los ejemplos del capítulo usan la variable `PANDORA` para la dirección de la API:

```sh
export PANDORA="https://pandora.example.com/pandora_console/api/v2"
```

## Cómo se habla con la API

- El cuerpo de las peticiones se envía en **JSON**, con la cabecera `Content-Type: application/json`.
- Las respuestas son JSON.
- Los errores tienen siempre la misma forma: `{"error": "mensaje"}`, con el código HTTP que corresponda. La tabla de códigos está en [Convenciones de la API](13.2-convenciones-de-la-api.md#errores).

## Dos formas de identificarse

| | Sesión de usuario | Token de API |
|---|---|---|
| Se obtiene con | `POST /auth/login` (usuario y contraseña) | `POST /token`, con una sesión o con otro token |
| Duración | El token de acceso dura **30 minutos**; la sesión se renueva mientras haya actividad y termina tras **7 días sin usarla** | La que le pongas: sin fecha límite, no caduca |
| Doble factor | Se resuelve al iniciar sesión | No interviene: el token ya es la credencial |
| Sirve para | Una persona o una aplicación que inicia sesión | Scripts, integraciones y tareas desatendidas |

La regla práctica: si hay alguien delante que escribe su contraseña, sesión; si lo ejecuta una máquina a las tres de la madrugada, token.

## Con una sesión de usuario

### Iniciar sesión

```sh
curl -s -c cookies.txt -X POST "$PANDORA/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"id_user": "admin", "password": "<contraseña>"}'
```

| Campo | Obligatorio | Detalle |
|---|---|---|
| `id_user` | Sí | Identificador del usuario. |
| `password` | Sí | Contraseña. |
| `isMobile` | No | `true` si la sesión es de una aplicación móvil. |
| `deviceInfo` | No | Datos del dispositivo (identificador, plataforma, versión de la aplicación, idioma, zona horaria). |

La respuesta trae lo que necesitas para seguir:

| Campo | Qué es |
|---|---|
| `status` | Estado del inicio de sesión: `authenticated` si todo ha ido bien, o `mfa_required` si hace falta el segundo factor (ver más abajo). |
| `access_token` | El token que enviarás en cada petición. |
| `access_expires_in` | Segundos de vida del token de acceso: `1800`. |
| `session_expires_at` | Fecha en la que termina la sesión si no hay actividad. |
| `id_user` | El usuario que ha iniciado sesión. |

La segunda mitad de la credencial no aparece en el cuerpo: el servidor deja el **token de renovación** en una cookie llamada `pandora_refresh`, marcada `HttpOnly` y `SameSite=Strict` (y `Secure` si usas HTTPS), con una vida de siete días. Un script de línea de comandos no la ve a menos que la guarde; por eso el ejemplo usa `-c cookies.txt`.

### Doble factor

Si la cuenta tiene doble factor, el inicio de sesión no devuelve tokens: devuelve `status: mfa_required` y un `mfa_token` de vida corta (**180 segundos**). Lo completas con el código de seis dígitos:

```sh
curl -s -c cookies.txt -X POST "$PANDORA/auth/login/mfa" \
  -H "Content-Type: application/json" \
  -d '{"mfa_token": "<mfa_token>", "code": "<código de seis dígitos>"}'
```

Cinco códigos erróneos invalidan el `mfa_token`, y hay que empezar de nuevo desde el inicio de sesión.

### Usar la sesión, renovarla y cerrarla

El `access_token` se envía en la cabecera `Authorization`, como se explica [más abajo](#enviar-el-token). Cuando caduca (a los 30 minutos), no hace falta pedir la contraseña otra vez:

```sh
curl -s -b cookies.txt -c cookies.txt -X POST "$PANDORA/auth/refresh"
```

La respuesta tiene la misma forma que la del inicio de sesión. La renovación **rota** la sesión: el token de acceso y el de renovación anteriores dejan de valer (el token de acceso viejo recibe un `401`) y recibes un par nuevo. Sin la cookie, la renovación responde `401` con `Session expired`.

Para cerrar la sesión y revocarla, `POST /auth/logout`: responde `{"status": "logged_out"}` y, a partir de ahí, ni el token de acceso ni la renovación sirven.

!!! note "Los intentos fallidos se limitan"
    `/auth/login` y `/auth/refresh` responden `429` con una cabecera `Retry-After` (segundos de espera) cuando se supera el límite:

    | Regla | Límite | Bloqueo |
    |---|---|---|
    | Misma dirección y mismo usuario | 5 fallos en 10 minutos | 10 minutos |
    | Misma dirección, cualquier usuario | 20 fallos en 10 minutos | 10 minutos |
    | Mismo usuario, cualquier dirección | 20 fallos en 30 minutos | 15 minutos |
    | Renovaciones desde la misma dirección | 60 en 1 minuto | 1 minuto |

    Un script que reintenta sin mirar `Retry-After` solo consigue bloquearse más tiempo. En las pruebas, el sexto intento fallido seguido del mismo usuario desde la misma dirección recibió `429` con `Retry-After: 600`. Una contraseña incorrecta, antes del límite, responde `401` con `Invalid credentials`.

## Con un token de API

Un token de API es la credencial de los procesos desatendidos: no depende de ninguna cookie, no hay doble factor que resolver y dura lo que tú decidas.

Se crea con `POST /token`. Como la propia creación exige estar identificado, el primer token sale de una sesión: inicias sesión, usas el `access_token` para crear el token y, desde ahí, ya no necesitas la contraseña en el script.

```sh
curl -s -X POST "$PANDORA/token" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"label": "backup-nocturno"}'
```

| Campo | Obligatorio | Detalle |
|---|---|---|
| `label` | Sí | Nombre para reconocerlo en el listado. |
| `validity` | No | Fecha hasta la que vale, en formato `AAAA-MM-DD HH:MM:SS` (por ejemplo, `2027-01-01 00:00:00`). Otro formato da un `400`. Vacío: no caduca. |
| `idUser` | No | Propietario. Por defecto, el usuario que lo crea. |

La respuesta incluye el token completo en el campo `token`, con la forma `<identificador>-<secreto>`. **Es la única vez que lo verás**: la consola no guarda el secreto tal cual, solo una huella para comprobarlo. Guárdalo donde guardas el resto de credenciales, nunca dentro del código del script.

Para gestionarlos: `GET /token/list` los lista, `PUT /token/{id}` los modifica y `DELETE /token/{id}` los revoca. En el listado el campo `token` aparece siempre vacío (el secreto no se vuelve a mostrar) y verás también, con la etiqueta `API session`, las credenciales de tus sesiones, tanto las de acceso como las de renovación. Un token revocado deja de valer en la petición siguiente, así que revocar el de un script comprometido es inmediato. Cada uso actualiza la fecha de último uso, que aparece en el listado y ayuda a saber qué tokens están muertos.

## Enviar el token

Las dos formas de credencial se presentan igual, en la cabecera `Authorization`:

```sh
curl -s "$PANDORA/agent/list?page=0&sizePage=10" \
  -H "Authorization: Bearer <token>"
```

Con una sesión, `<token>` es el `access_token`; con un token de API, el valor del campo `token`.

Si falta, está mal formado o ha caducado, la respuesta es `401`:

| Respuesta | Causa |
|---|---|
| `401`, `You need to be authenticated to perform this action` | Falta la cabecera, el token no existe, ha caducado o el secreto es incorrecto. La API no distingue entre estos casos a propósito. También ocurre si se envía un token de renovación o de doble factor: solo los de acceso sirven fuera de `/auth`. |
| `401`, `IP <dirección> is not in ACL list` | La dirección de origen no está en la lista de la consola. |
| `401`, `Invalid credentials` | Usuario o contraseña incorrectos en `/auth/login`. |
| `401`, `Session expired` | `/auth/refresh` sin cookie de renovación, o con una sesión ya cerrada o caducada. |
| `403`, `This user account has been disabled` | El usuario del token está deshabilitado. |

### Tokens de Pandora AI

Los tokens de Pandora AI son un caso aparte: los crea y gestiona la consola, y no se pueden crear, modificar ni borrar por la API. Si llamas con uno, **cada petición** debe llevar exactamente una cabecera `X-Pandora-AI-Session` con un identificador de sesión (texto UTF-8 no vacío, de hasta 255 caracteres y sin caracteres de control). Si falta o no es válida, la respuesta es `400`, aunque el token sea correcto. El identificador queda en el registro de auditoría de esa petición. Los tokens normales ignoran la cabecera.
