# Ejemplos de uso

La referencia dice qué parámetros acepta cada operación; este capítulo enseña a usarlas juntas. Los ejemplos se han ejecutado de verdad, de principio a fin, contra una consola de desarrollo (versión 8.0NG.805) con datos de prueba que se borraron después. Las respuestas están recortadas a lo esencial y tus identificadores y fechas serán otros.

Se da mucho espacio a los **filtros de los listados**, porque la referencia describe los campos pero no puede mostrar cómo se combinan, y es donde más tiempo se pierde.

## Antes de empezar

| Requisito | Detalle |
|---|---|
| Credencial | Un token de API o el `access_token` de una sesión ([capítulo 13.1](13.1-primeros-pasos-y-autenticacion.md)). |
| Herramientas | `curl` y [`jq`](https://jqlang.github.io/jq/) para dar formato a las respuestas. |
| Permisos | Un usuario que pueda crear y borrar agentes, módulos, usuarios y alertas. Los ejemplos de escritura se hicieron con `admin`. |

Todos los ejemplos comparten estas variables y esta función, que añade la cabecera de autenticación y el tipo de contenido:

```sh
export PANDORA="http://localhost/pandora_console/api/v2"
export TOKEN="<token de API o access_token>"
api() { curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" "$@"; }
```

## Crear un agente y ver la respuesta completa

La primera llamada es también la más reveladora: crear un agente y mirar todo lo que devuelve. Solo hacen falta `alias` e `idGroup` (más abajo se ve qué pasa si falta uno).

```sh
api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-first", "idGroup": 13}'
```

La respuesta es un `200` con el **agente completo**, no solo su identificador. Esta es tal cual, sin filtrar. La API la devuelve en una sola línea; aquí va con sangría para leerla:

## Preparar los datos para los filtros

Para los ejemplos de filtros hacen falta unos cuantos agentes. Crea estos cinco; todos llevan `docs-test` en el alias para encontrarlos y borrarlos fácilmente:

```sh
for spec in "docs-test-web-01 13 300" "docs-test-web-02 13 60" "docs-test-db-01 8 300" \
            "docs-test-net-01 9 120" "docs-test-old-01 2 300"; do
  set -- $spec
  api -X POST "$PANDORA/agent" -d "{\"alias\": \"$1\", \"idGroup\": $2, \"interval\": $3}" \
    | jq -c '{idAgent, alias, idGroup}'
done
```

```json
{"idAgent":9,"alias":"docs-test-web-01","idGroup":13}
{"idAgent":10,"alias":"docs-test-web-02","idGroup":13}
{"idAgent":11,"alias":"docs-test-db-01","idGroup":8}
{"idAgent":12,"alias":"docs-test-net-01","idGroup":9}
{"idAgent":13,"alias":"docs-test-old-01","idGroup":2}
```

## Listar con paginación

El listado simple es un `GET`. Con `sizePage` pides páginas de ese tamaño y `page` empieza en 0:

```sh
api "$PANDORA/agent/list?page=0&sizePage=2" \
  | jq -c '.paginationData, (.data[] | {idAgent, alias, idGroup})'
```

```json
{"totalPages":4,"sizePage":2,"currentPage":0,"totalRegisters":7,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"idAgent":13,"alias":"docs-test-old-01","idGroup":2}
{"idAgent":12,"alias":"docs-test-net-01","idGroup":9}
```

Hay siete agentes (los cinco nuevos más los dos que trae la consola) y, con páginas de dos, `totalPages` es 4. Sin ordenar, este listado devuelve primero el agente más reciente.

## Filtrar por un campo y elegir qué campos recibir

Para filtrar se usa `POST` con el filtro en el cuerpo. Cada campo que escribes es una condición de **igualdad exacta**. Con `requestedFields` recibes solo los campos que pides, y la respuesta pesa mucho menos que los 53 campos completos de un agente:

```sh
api -X POST "$PANDORA/agent/list?page=0&sizePage=10" \
  -d '{"idGroup": 13, "requestedFields": ["idAgent", "alias", "idGroup"]}' \
  | jq -c '.paginationData, .data[]'
```

```json
{"totalPages":1,"sizePage":10,"currentPage":0,"totalRegisters":2,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"idAgent":10,"alias":"docs-test-web-02","idGroup":13}
{"idAgent":9,"alias":"docs-test-web-01","idGroup":13}
```

`totalRegisters` cuenta lo que cumple el filtro (2) y `unfilteredTotalRegisters` lo que habría sin filtrar (7).

## Combinar condiciones con operadores

Cuando una igualdad no basta, `fieldConditions` admite operadores. Todas las condiciones se unen con **Y**. Este ejemplo busca los agentes cuyo alias contiene `docs-test` y que están en los grupos 8 o 9, ordenados por alias:

```sh
api -X POST "$PANDORA/agent/list?page=0&sizePage=10&sortField=alias&sortDirection=ASC" \
  -d '{"requestedFields": ["idAgent", "alias", "idGroup"],
       "fieldConditions": [
         {"field": "alias", "operator": "LIKE", "value": "docs-test"},
         {"field": "idGroup", "operator": "IN", "value": [8, 9]}
       ]}' | jq -c '.paginationData, .data[]'
```

```json
{"totalPages":1,"sizePage":10,"currentPage":0,"totalRegisters":2,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"idAgent":11,"alias":"docs-test-db-01","idGroup":8}
{"idAgent":12,"alias":"docs-test-net-01","idGroup":9}
```

### Qué campos admiten las condiciones

No todos los campos de un agente sirven en `fieldConditions` (ni en `requestedFields`, `multipleSearch` o `sortField`): solo un subconjunto. `interval`, por ejemplo, no. Si usas uno que no vale, la respuesta es un `400` que **lista los válidos**:

```sh
api -X POST "$PANDORA/agent/list" \
  -d '{"fieldConditions": [{"field": "interval", "operator": "=", "value": 300}]}'
```

```json
{"error":"Field interval is not a valid filter field. Valid fields: idAgent, name, alias, address, idGroup, disabled, idOs, lastContact, osName, osImagePath, normalCount, warningCount, criticalCount, unknownCount, notinitCount, totalCount, firedCount"}
```

Es un buen truco para descubrir los campos de cualquier listado: pide uno que no existe y lee el mensaje. En cambio, el filtro simple del cuerpo (`{"interval": 300}`) sí acepta cualquier campo de la entidad, y uno que no exista da `Field: <nombre> is not a valid parameter`.

### Cómo se comporta cada filtro

La tabla recoge lo que devolvió cada filtro sobre los cinco agentes de prueba. Fíjate en las dos primeras filas: el filtro simple no busca por trozos.

| Cuerpo de la petición | Agentes devueltos |
|---|---|
| `{"alias": "docs-test-web-01"}` | `docs-test-web-01` |
| `{"alias": "docs-test-web"}` | Ninguno: es igualdad exacta, no prefijo. |
| `{"idGroup": 13}` | `docs-test-web-01`, `docs-test-web-02` |
| `{"freeSearch": "web"}` | `docs-test-web-01`, `docs-test-web-02` (coincidencia parcial en varios campos) |
| `{"multipleSearch": {"field": "idGroup", "data": [8, 9]}}` | `docs-test-db-01`, `docs-test-net-01` (cualquiera de los valores) |
| `{"multipleSearchString": {"field": "alias", "data": ["docs-test-web-01", "docs-test-net-01"]}}` | `docs-test-net-01`, `docs-test-web-01` |
| Condición `alias` `LIKE` `web` | `docs-test-web-01`, `docs-test-web-02`: **contiene** el texto. |
| Condición `alias` `LIKE` `docs-test-web%` | Ninguno: el `%` no es un comodín, se busca tal cual. |
| Condición `alias` `REGEXP` `^docs-test-web` | `docs-test-web-01`, `docs-test-web-02` |
| Condición `idGroup` `IN` `[8, 9]` | `docs-test-db-01`, `docs-test-net-01` |
| Condición `idGroup` `BETWEEN` `[8, 9]` | `docs-test-db-01`, `docs-test-net-01` |
| Condición `idGroup` `gt` `9` (y alias `LIKE` `docs-test`) | `docs-test-web-01`, `docs-test-web-02` |

`LIKE` es el punto que más confunde: significa «contiene», no el `LIKE` de SQL, y no hace falta (ni sirve) rodear el texto de `%`.

## Ordenar y paginar

`sortField` y `sortDirection` (`ASC` o `DESC`, sin distinguir mayúsculas) van en la dirección. Esta petición pide la segunda página (`page=1`) de dos elementos, ordenados por alias de mayor a menor:

```sh
api -X POST "$PANDORA/agent/list?page=1&sizePage=2&sortField=alias&sortDirection=DESC" \
  -d '{"requestedFields": ["alias"],
       "fieldConditions": [{"field": "alias", "operator": "LIKE", "value": "docs-test"}]}' \
  | jq -c '.paginationData, .data[]'
```

```json
{"totalPages":3,"sizePage":2,"currentPage":1,"totalRegisters":5,"totalRegistersPage":2,"unfilteredTotalRegisters":7}
{"alias":"docs-test-old-01"}
{"alias":"docs-test-net-01"}
```

Para recorrer un conjunto por ventanas arbitrarias, el modo por desplazamiento (`limit` y `offset`, dentro del cuerpo). Aquí, dos elementos a partir del segundo; fíjate en que `currentPage` pasa a ser `null` y aparecen `limit` y `offset`:

```sh
api -X POST "$PANDORA/agent/list" \
  -d '{"limit": 2, "offset": 1, "requestedFields": ["alias"],
       "fieldConditions": [{"field": "alias", "operator": "LIKE", "value": "docs-test"}]}' \
  | jq -c '.paginationData, .data[]'
```

```json
{"totalPages":3,"sizePage":2,"currentPage":null,"totalRegisters":5,"totalRegistersPage":2,"unfilteredTotalRegisters":7,"limit":2,"offset":1}
{"alias":"docs-test-net-01"}
{"alias":"docs-test-db-01"}
```

## Filtrar eventos

Los eventos no usan `fieldConditions`: tienen sus propios filtros (`severity`, `status`, `search`, `idAgent`, `eventType`…), y una opción propia, `dateRange`. Esta busca los eventos críticos y nuevos de las últimas 24 horas, del más reciente al más antiguo:

```sh
api -X POST "$PANDORA/event/list?page=0&sizePage=2&sortField=idEvent&sortDirection=DESC" \
  -d '{"severity": [4], "status": "new", "dateRange": "{\"preset\": {\"value\": \"last_24_hours\"}}"}' \
  | jq -c '.paginationData, (.data[] | {idEvent, severity, status, event})'
```

```json
{"totalPages":7,"sizePage":2,"currentPage":0,"totalRegisters":13,"totalRegistersPage":2,"unfilteredTotalRegisters":13}
{"idEvent":30,"severity":"CRITICAL","status":"NEW","event":"Pandora DB maintenance tool has never been run."}
{"idEvent":29,"severity":"CRITICAL","status":"NEW","event":"Pandora DB maintenance tool has never been run."}
```

Tres detalles que no se adivinan:

- **`dateRange` es un texto que contiene JSON**, no una fecha. De ahí las comillas escapadas del ejemplo. Un valor que no sea JSON da `Invalid date range format. Must be valid JSON`.
- **La gravedad se filtra con una lista de números** (`[4]` es crítica, `[0]` mantenimiento); al leerlos, el evento trae el nombre (`CRITICAL`).
- **El estado** admite `new`, `validated`, `inprocess`, `not_validated`, `not_in_process` y `all`.

`dateRange` acepta un periodo predefinido o un inicio y un final:

| Forma | Ejemplo |
|---|---|
| Predefinido | `{"preset": {"value": "last_24_hours"}}`. Valores: `today`, `this_week`, `this_month`, `last_15_minutes`, `last_30_minutes`, `last_1_hours`, `last_24_hours`, `last_7_days`, `last_30_days`, `last_60_days`, `last_90_days`, `last_1_year`. |
| Relativo | `{"start": {"mode": "relative", "value": 2, "unit": "hours"}, "end": {"mode": "now"}}`. Unidades: `seconds`, `minutes`, `hours`, `days`, `weeks`, `months`, `years`. |
| Absoluto | `{"start": {"mode": "absolute", "value": "2020-01-01 00:00:00"}, "end": {"mode": "absolute", "value": "2020-12-31 23:59:59"}}` |

Un valor de `preset` desconocido da `Invalid date range values`.

## Crear, leer, modificar y borrar un agente

Crear un agente exige **`alias` e `idGroup`**; si falta uno, el `400` dice cuál:

```sh
api -X POST "$PANDORA/agent" -d '{"idGroup": 13}'
api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-crud"}'
```

```json
{"error":"Agent alias is missing"}
{"error":"Agent group is missing"}
```

Con los dos, el agente se crea. La respuesta es la que ya viste en [el primer ejemplo](#crear-un-agente-y-ver-la-respuesta-completa), el agente completo; aquí solo se guarda su identificador para las llamadas siguientes:

```sh
ID=$(api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-crud", "idGroup": 13}' | jq -r .idAgent)
```

`PUT` **modifica solo los campos que envías**; el resto se queda como estaba:

```sh
api -X PUT "$PANDORA/agent/$ID" -d '{"comments": "created from the docs", "interval": 120}' \
  | jq -c '{idAgent, alias, comments, interval, idGroup}'
```

```json
{"idAgent":14,"alias":"docs-test-crud","comments":"created from the docs","interval":120,"idGroup":13}
```

Borrarlo responde `200` con el cuerpo `null`, y volver a pedirlo da un `404`:

```sh
api -X DELETE "$PANDORA/agent/$ID" -w 'HTTP %{http_code}\n'
api "$PANDORA/agent/$ID" -w ' HTTP %{http_code}\n'
```

```text
nullHTTP 200
{"error":" not found"} HTTP 404
```

## Crear un módulo

Un módulo cuelga de un agente. Los obligatorios son `idAgent`, `name`, `idModule` (el tipo de servidor del módulo: `1` en este ejemplo) e `idModuleType` (el tipo de dato: `1` es `generic_data`; `GET /moduleType/list` enseña los demás). Sin `idModule` la respuesta es `Unsupported module and module type combination`.

```sh
AG=$(api -X POST "$PANDORA/agent" -d '{"alias": "docs-test-mod-agent", "idGroup": 13}' | jq -r .idAgent)
api -X POST "$PANDORA/agentModule" \
  -d "{\"idAgent\": $AG, \"name\": \"docs-test-module\", \"idModule\": 1, \"idModuleType\": 1}" \
  | jq -c '{idAgentModule, idAgent, idModuleType, name}'
```

```json
{"idAgentModule":92,"idAgent":15,"idModuleType":1,"name":"docs-test-module"}
```

Para encontrar los módulos de un agente, un listado con filtro; y para saber cómo está, su estado:

```sh
MOD=$(api -X POST "$PANDORA/agentModule/list" \
  -d "{\"idAgent\": $AG, \"requestedFields\": [\"idAgentModule\"]}" | jq -r '.data[0].idAgentModule')
api "$PANDORA/agentModule/$MOD/agentModuleState" | jq -c '{idAgentModule, status, data}'
```

```json
{"idAgentModule":92,"status":4,"data":""}
```

El estado `4` significa «sin datos», que es lo normal en un módulo recién creado que aún no ha recibido ninguno. Al borrar el agente (`DELETE /agent/$AG`) se borran también sus módulos.

## Crear un usuario

Aquí se ve con claridad que **el swagger no marca todos los campos obligatorios**: la referencia solo señala `fullName`, pero el servidor exige más. Los mensajes van pidiendo cada uno (el primero, sin `idUser`; el segundo, sin `password`; el tercero, sin `passwordValidate`):

```sh
api -X POST "$PANDORA/user" -d '{"fullName": "Docs Test"}'
api -X POST "$PANDORA/user" -d '{"idUser": "docs-test-user", "fullName": "Docs Test"}'
api -X POST "$PANDORA/user" \
  -d '{"idUser": "docs-test-user", "fullName": "Docs Test", "password": "Docs-test-Pass-1"}'
```

```json
{"error":"IdUser is missing"}
{"error":"Password is missing"}
{"error":"PasswordValidate is missing"}
```

Hacen falta cuatro campos: `idUser`, `fullName`, `password` y `passwordValidate` (la contraseña repetida). La referencia solo marca uno; el servidor es quien dice la verdad:

```sh
api -X POST "$PANDORA/user" \
  -d '{"idUser": "docs-test-user", "fullName": "Docs Test", "password": "Docs-test-Pass-1", "passwordValidate": "Docs-test-Pass-1"}' \
  | jq -c '{idUser, fullName, isAdmin}'
```

```json
{"idUser":"docs-test-user","fullName":"Docs Test","isAdmin":false}
```

## Crear una acción de alerta

Una acción de alerta necesita un comando. Se crea primero el comando y después la acción que lo usa:

```sh
CMD=$(api -X POST "$PANDORA/alert/command" -d '{"name": "docs-test-command", "command": "echo _field1_"}' | jq -r .idAlertCommand)
ACT=$(api -X POST "$PANDORA/alert/action" -d "{\"name\": \"docs-test-action\", \"idAlertCommand\": $CMD}" | jq -r .idAlertAction)
```

Como los dos devuelven su identificador, se pueden encadenar. Para limpiar, borra primero la acción y después el comando.

## Limpiar

Los ejemplos dejan datos de prueba. Todos llevan `docs-test` en el nombre, así que se encuentran con un filtro y se borran:

```sh
for id in $(api -X POST "$PANDORA/agent/list" \
  -d '{"requestedFields": ["idAgent"], "fieldConditions": [{"field": "alias", "operator": "LIKE", "value": "docs-test"}]}' \
  | jq -r '.data[].idAgent'); do api -X DELETE "$PANDORA/agent/$id"; done
```

Crear o borrar agentes genera además eventos del sistema (`Agent [...] created by API`). Se buscan con `{"search": "docs-test"}` en `POST /event/list` y se borran con `DELETE /event/{idEvent}`.

## Los errores que has visto

| Código | Mensaje | Causa |
|---|---|---|
| `400` | `Agent alias is missing` | Falta un campo obligatorio (el mensaje dice cuál). |
| `400` | `Field interval is not a valid filter field. Valid fields: …` | Un campo que no admite esa opción; el mensaje lista los válidos. |
| `400` | `Field: nope is not a valid parameter` | Un campo del cuerpo que no existe en la entidad. |
| `400` | `Operator foo is not a valid filter operator` | Operador desconocido. |
| `400` | `Field condition operator IN expects an array value` | `IN` y `NOT IN` necesitan una lista. |
| `400` | `Field sizePage must be an integer greater than or equal to 1` | Paginación no válida. |
| `400` | `limit/offset cannot be combined with page/sizePage` | Se mezclaron los dos modos de paginación. |
| `400` | `Node identity filters can only be used on a metaconsole` | Se usó `serverId` en una consola independiente. |
| `404` | ` not found` | El elemento no existe (el mensaje empieza por un espacio). |

El resto de códigos (`401`, `403`, `429`, `500`) está en [Convenciones de la API](13.2-convenciones-de-la-api.md#errores).
