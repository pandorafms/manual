# Command Center

## Introducción: qué es el Command Center y cuándo usarlo

Un solo servidor de Pandora FMS llega hasta donde llega. [1.1 ·
Instalación](../parte-1/1.1-instalacion.md) sitúa el techo de un nodo en el
entorno de las 80.000 métricas: por encima de ahí no se trata de comprar una
máquina más grande, sino de repartir el trabajo entre varias. El Command Center
es la pieza que permite hacerlo sin renunciar a una visión única.

El Command Center es una interfaz web que presenta y opera **como una sola**
varias instalaciones de Pandora FMS, llamadas **nodos** o instancias. No las
sustituye: cada nodo conserva su servidor y su base de datos, y sigue
funcionando por su cuenta. El Command Center añade su propia consola web y su
propia base de datos, y desde ahí los coordina.

![Un Command Center por encima de tres nodos: el Command Center tiene consola, servidor y base de datos, y cada nodo conserva las suyas](../../assets/img/parte-06/command-center-arquitectura-general.png){ .diagrama .diagrama-ancho }

Gracias a esa capa se monitorizan cientos de miles de dispositivos sin mirar
nodo por nodo. La escalabilidad es **horizontal**: cuando el entorno se queda
corto se añade un nodo, no se agranda el que ya hay. Y como el punto de acceso
es único, el Command Center sirve también para dar servicio **multiempresa**
desde una sola consola: una empresa entra por ahí y ve lo suyo, sin que la
infraestructura se duplique.

¿Cuándo conviene montarlo? Hay tres señales claras:

- **Un solo nodo se queda corto.** Es el caso de las instalaciones que superan
  el orden de magnitud que aguanta una consola suelta.
- **Hay varias instalaciones y se quieren ver juntas.** El Command Center las
  presenta como una sola y permite operar sobre todas.
- **Se da servicio multiempresa.** Un único punto de acceso sirve a varias
  empresas y, dentro de cada una, a varios usuarios.

!!! info "La sincronización es automática"
    La sincronización entre el Command Center y los nodos se realiza de forma
    automática gracias a la **Merging tool**, de la cual hablaremos más adelante.

Dónde encaja esta pieza dentro del resto de la arquitectura está en [1.2 ·
Introducción y arquitectura](../parte-1/1.2-introduccion-y-arquitectura.md). La
licencia, que es adicional a la de los nodos y se cuenta por nodo activo, se
explica en [1.5 · Licenciamiento](../parte-1/1.5-licenciamiento.md).

## Arquitectura y sincronización

### Arquitectura: nodos y nodo central

Un **nodo** (o instancia) es una instalación normal de Pandora FMS: una consola
web como capa de presentación, un servidor como capa de acceso a datos y su
propia base de datos. El **Command Center** es otra instalación, con su servidor
y su base de datos, pero no monitoriza nada por sí mismo: coordina. La
arquitectura tiene dos tipos de pieza:

- un **nodo central**, el Command Center, con su propio servidor;
- tantos **nodos servidores** como se necesiten.

Hay dos servicios que solo existen cuando hay un Command Center por encima, y
que ya presenta [1.2 · Introducción y
arquitectura](../parte-1/1.2-introduccion-y-arquitectura.md):

- **Migration Server**: mueve agentes de un nodo a otro cogiendo las tareas de
  una cola priorizada.
- **Autoprovision Server**: recibe a los agentes que llegan sin destino y decide
  en qué nodo se dan de alta. Su funcionamiento se desarrolla en [6.6 ·
  Mecanismos de autoprovisión](../parte-6/6.6-mecanismos-de-autoprovision.md).

De la relación entre el Command Center y cada nodo se derivan tres condiciones
que conviene tener resueltas antes de montar nada:

| Condición | Detalle |
|---|---|
| Comunicación bidireccional | El Command Center tiene que poder alcanzar a cada nodo, y cada nodo al Command Center. |
| Nodos independientes entre sí | Los nodos **no** necesitan comunicarse entre ellos en ningún momento; solo con el nodo central. |
| Reloj sincronizado | La hora del Command Center y la de los nodos debe ser la misma. Cuanto mejor sincronizados estén los relojes, más exactos serán los datos que se ven desde arriba. |

Las condiciones de red y los puertos implicados se detallan en [1.1 ·
Instalación](../parte-1/1.1-instalacion.md#requisitos-de-seguridad-y-redes).

### ¿Dónde vive cada dato?

Antes de buscar algo en el sitio equivocado conviene tener claro qué vive en
cada lado. Esta es la tabla que evita perder media tarde:

| Dónde vive | Qué |
|---|---|
| **Solo en el nodo** | Agentes, módulos y su histórico, alertas y políticas en ejecución. |
| **Solo en el Command Center** | La configuración del propio Command Center, los componentes, las plantillas de informes, los mapas de red, los mapas visuales y los filtros de NetFlow. |
| **En ambos, replicado** | Usuarios y perfiles, grupos, plantillas, acciones y comandos de alerta, etiquetas y categorías. |

Los usuarios, grupos, plantillas y etiquetas están en los dos lados porque
tienen que estar donde se usan. Las tablas propias del Command Center
(`tmetaconsole_*`) y su sincronización se describen en [10.1 · Esquema de la
base de datos](../parte-10/10.1-esquema-de-la-base-de-datos.md).

### Cómo se obtiene y modifica la información

El Command Center obtiene y modifica la información de los nodos de dos formas
distintas, y saber cuál aplica a cada dato decide dónde se diagnostica cuando
algo falla:

- **Modo activo.** El Command Center entra por sí mismo en la base de datos o en
  la API del nodo y administra lo que le corresponde: agentes, módulos, alertas
  y políticas.

![Modo activo: el Command Center llega por la API y la base de datos de cada nodo para administrar sus agentes, módulos, alertas y políticas](../../assets/img/parte-06/command-center-modo-activo.png){ .diagrama .diagrama-ancho }

- **Modo pasivo.** El nodo escribe hacia la base de datos del Command Center lo
  que se genera de forma continua. El caso típico son los eventos: el nodo los
  replica y, a partir de ahí, su gestión se hace desde arriba.

![Modo pasivo: cada nodo envía sus eventos a la base de datos del Command Center](../../assets/img/parte-06/command-center-modo-pasivo.png){ .diagrama .diagrama-ancho }

Según de qué modo dependa un dato, el problema se busca en un sitio u otro. Si
los eventos no llegan, la causa suele estar en la configuración de replicación
del nodo; si
un agente no se administra desde arriba, la causa está en la conexión del
Command Center con ese nodo. Los síntomas concretos y por dónde empezar están en
[12.8 · Entornos grandes](../parte-12/12.8-entornos-grandes.md).

## Instalación y puesta en marcha

### Requisitos y particularidades

El Command Center no es un producto aparte: se instala el mismo software que en
cualquier instalación de Pandora FMS —consola web, servidor y base de datos— y se
convierte en Command Center al activar una **licencia de Command Center** (el
detalle, en [«Activación de la licencia»](#activacion-de-la-licencia)). No hay
que instalar nada más.

Los nodos normales se van uniendo después, desde **Management → Settings → System
Settings → Command Center** (ver
[«Alta y registro de nodos»](#alta-y-registro-de-nodos)).

Frente a un nodo, hay tres particularidades: su propia licencia, su servidor en
marcha y que una instalación no puede ser a la vez nodo y Command Center. El
procedimiento genérico de instalación de la consola es el de [1.1 ·
Instalación](../parte-1/1.1-instalacion.md); aquí va solo lo diferencial.

| Requisito | Detalle |
|---|---|
| Edición | **Pandora ONE**, **Pandora NMS** o **Pandora RMM**, más una **licencia de Command Center** adicional (ver [«Activación de la licencia»](#activacion-de-la-licencia) y [1.5 · Licenciamiento](../parte-1/1.5-licenciamiento.md)). |
| Instalación | El mismo software que un nodo (consola web, servidor y base de datos). No hay paquete propio: lo que cambia el papel de la instalación es la licencia. El procedimiento general está en [1.1 · Instalación](../parte-1/1.1-instalacion.md). |
| Servidor de Pandora FMS | El servidor de la propia instalación tiene que estar en marcha: de él dependen la migración de agentes, el aprovisionamiento y la cola de políticas. |
| Comunicación | Bidireccional entre el Command Center y cada nodo (ver [«Arquitectura: nodos y nodo central»](#arquitectura-nodos-y-nodo-central)). |
| Reloj | La hora del Command Center y la de los nodos debe estar sincronizada. |
| Puertos | 80, 443 y 3306 entre el Command Center y los nodos. La tabla completa está en [1.1 · Instalación](../parte-1/1.1-instalacion.md#requisitos-de-seguridad-y-redes). |
| Sistema operativo | RHEL, Rocky Linux y AlmaLinux 9 o 10, o Ubuntu Server 22.04 o 24.04. Para el Command Center se recomienda **RHEL**, **Rocky Linux** y **AlmaLinux**. |

!!! warning "Un servidor, un papel"
    No se puede usar a la vez la consola web de Pandora FMS y el Command
    Center. Si la instalación se activa como Command Center, esa consola deja de
    ser un nodo.

### Activación de la licencia

La licencia se activa desde la propia consola web, como la de cualquier
instalación. Se accede a la URL de la consola:

```text
http://<dir_IP_o_URL>/pandora_console/
```

y aparece la pantalla de bienvenida en la que se acepta la licencia.

La diferencia con un nodo es qué licencia se introduce. Para levantar el Command
Center **hace falta una licencia de Command Center**; si se activa una licencia
de nodo, lo que aparece es la consola normal, no el Command Center. Al introducir
una licencia de Command Center en una instalación que era nodo, la consola avisa
de que va a cambiar de papel y, al confirmar, la instalación pasa a ser Command
Center sin reinstalar nada. La pantalla de licencia muestra después el tipo
contratado —consola o Command Center— junto al resto de límites. El modelo de
licencia y el significado de cada campo están en [1.5 ·
Licenciamiento](../parte-1/1.5-licenciamiento.md).

### Metalicencia

La **metalicencia** es la licencia única del entorno. Se pone en el Command
Center y cubre a todos los nodos: se pueden crear tantos nodos como se quiera
sin volver a licenciar cada uno, siempre que no se supere el total de agentes
contratado. Las réplicas de alta disponibilidad no cuentan. Para nodos que deban
permanecer desconectados del Command Center durante periodos largos hay que
hablar con el equipo comercial de Pandora FMS.

**La licencia va primero.** Sin ella la instalación no funciona como Command
Center y no hay dónde dar de alta los nodos. A partir de ahí, el orden es este:

1. **Activar la licencia del Command Center.** Se hace en la instalación, cuando
   todavía es un nodo: en **Management → Settings → License**. Es la misma
   pantalla que la de cualquier nodo; lo que cambia es la licencia que se
   introduce (ver [«Activación de la
   licencia»](#activacion-de-la-licencia)).
2. **Dar de alta cada nodo** en **Setup → Metasetup → Consoles setup**, con **su
   propia clave de licencia generada y validada** en la consola del nodo (ver
   [«Alta y registro de nodos»](#alta-y-registro-de-nodos)).
3. **Dejar los estados en verde.** Si alguno no lo está, el botón
   **Synchronize all** de **Consoles setup** recorre los nodos registrados y
   fuerza su sincronización.
   ![Lista de nodos en Consoles setup con los indicadores en verde, el botón Synchronize all y el botón New node](../../assets/img/parte-06/command-center-metalicencia.png){ .diagrama .diagrama-ancho }

4. **Repartir la metalicencia.** Con los nodos ya en orden, se vuelve a
   **Setup → License** —ahora ya es el menú del Command Center— y se pulsa
   **Validate**: guarda la licencia del Command Center y la propaga a todos los
   nodos.

Un nodo que no valida (indicador **Sync** en rojo) tiene una clave que no
coincide con la del Command Center o no está marcado como nodo
(`node_metaconsole`). El botón de sincronización lo resuelve. Una vez propagada,
la licencia del Command Center activa los nodos automáticamente, sin tener que
activarlos uno a uno.

La licencia agregada suma el consumo de todos los nodos activos; las réplicas no
entran en la cuenta. Los detalles del modelo están en [1.5 ·
Licenciamiento](../parte-1/1.5-licenciamiento.md).

### Alta y registro de nodos

Este es el procedimiento que deja al Command Center con nodos que gestionar.
Se hace en **Setup → Metasetup → Consoles setup**![Icono de documento con engranaje de la opción Consoles setup del menú Metasetup](../../assets/img/parte-06/metasetup_icon_consoles_setup.png){ .icono-en-linea }, con el botón
**New node**.

![Lista de nodos en Consoles setup con los indicadores en verde, el botón Synchronize all y el botón New node](../../assets/img/parte-06/command-center-metalicencia.png){ .diagrama .diagrama-ancho }

Al dar de alta un nodo hay que conocer una serie de datos de esa instalación.
Los campos son estos:

| Campo | Qué es | Valor por defecto |
|---|---|---|
| **Label** | Etiqueta con la que se identifica el nodo en el Command Center. | Sin valor |
| **Console URL** | Ruta completa a la consola del nodo, sin `index.php`; conviene terminarla con barra. | Sin valor |
| **API password** | Contraseña de la API del nodo. | Sin valor |
| **Console user** | Usuario de consola del nodo, para el acceso delegado. | Sin valor |
| **Console password** | Contraseña de ese usuario. | Sin valor |
| **DB host** | Dirección de la base de datos del nodo. | Sin valor |
| **DB name** | Nombre de la base de datos. | Sin valor |
| **DB user** | Usuario de la base de datos. | Sin valor |
| **DB password** | Contraseña de la base de datos. | Sin valor |
| **DB port** | Puerto de la base de datos. | `3306` |

Las credenciales de API y de consola (contraseña de la API, usuario y
contraseña de consola) se guardan juntas como token de autenticación del nodo.
La URL de la consola debe terminar en barra: el Command Center la usa tal cual
para construir las llamadas.

![Formulario de alta de un nodo en Consoles setup, con los campos de la consola, la contraseña de la API, los datos de su base de datos y el conmutador Enable SSL](../../assets/img/parte-06/command-center-nodo-formulario.png){ .diagrama .diagrama-ancho }

La conexión a la base de datos del nodo admite SSL. Al
activar **Enable SSL** aparecen los campos de la clave y el certificado del
servidor, el certificado y la ruta de la CA, y la verificación del certificado
del servidor:

| Campo | Qué es |
|---|---|
| **SSL server key** | Fichero PEM con la clave SSL del servidor MySQL. |
| **SSL server cert** | Fichero PEM con el certificado de esa clave. |
| **SSL CA cert** | Fichero PEM con la lista de certificados emitidos por una autoridad de certificación. |
| **SSL CA path** | Directorio con certificados de una autoridad de certificación, en formato PEM. |
| **SSL verify server cert** | Si se activa, verifica el certificado en la conexión (CN); si no coincide, no conecta. |

**Campos avanzados.** El bloque de opciones avanzadas define la conexión en
sentido contrario: la que establecerá el **nodo** contra la base de datos del
Command Center. Aquí se indican el host, el nombre, el usuario, la contraseña y
el puerto de la base de datos del propio Command Center, y su SSL. Si no se
rellenan, se toman los valores de la propia configuración del Command Center.

![Formulario de alta de un nodo en Consoles setup, con los campos de la consola y de su base de datos, el bloque SSL y las opciones avanzadas de conexión al Command Center](../../assets/img/parte-06/command-center-nodo-avanzado.png){ .diagrama .diagrama-ancho }

**Los dos botones de alta.** Al guardar, el botón que se elige decide qué pasa
con los datos que ya hubiera en el nodo:

![Botones Register node with data to merge y Register empty node al pie del formulario de alta](../../assets/img/parte-06/command-center-nodo-botones.png){ .diagrama .diagrama-ancho }

- **Register empty node**: los datos del nodo se borran y se reemplazan por los
  del Command Center. Se usa cuando el nodo no tiene nada que conservar.
![Aviso al registrar un nodo vacío: la información que contenga se borrará y se reemplazará por la del Command Center](../../assets/img/parte-06/command-center-nodo-registrar-vacio.png){ .diagrama }

- **Register node with data to merge**: el nodo se registra pero queda
  desactivado, a la espera de que se lance una fusión que combine lo que hay en
  el entorno con lo que trae el nodo. Se usa cuando el nodo sí tiene datos que
  interesan.
![Confirmación al registrar un nodo con datos: después hay que lanzar una fusión que combine el entorno con lo que trae el nodo](../../assets/img/parte-06/command-center-nodo-registrar-fusion.png){ .diagrama }

!!! info "Cuándo aparecen estos botones"
    Los dos botones de alta aparecen cuando la **gestión centralizada** está
    activa. Si no lo está, el alta se hace con un único botón **Add**.

**Indicadores de comprobación.** En la lista de nodos configurados hay varios
indicadores que comprueban la conexión y el estado de cada nodo. Los chequeos se
lanzan al cargar la vista y también se pueden repetir uno a uno haciendo clic
sobre ellos:

![Lista de nodos en Consoles setup con las columnas de indicadores DB, API, Compatibility, Agent cache, Sync y Database sync, la versión, la URL de la consola y las acciones de gestión](../../assets/img/parte-06/command-center-nodo-indicadores.png){ .diagrama .diagrama-ancho }

| Indicador | Qué comprueba |
|---|---|
| **DB** | La conexión a la base de datos del nodo con las credenciales indicadas. En rojo, informa del problema: faltan credenciales, no se alcanza el host o la base de datos no existe. |
| **API** | Una prueba contra la API del nodo con la contraseña de API y las credenciales de consola. Distingue entre error de autenticación, error de conexión y host no resoluble. |
| **Compatibility** | Conecta a la base de datos del nodo y compara su *maintenance release* (`MR`) con el del Command Center. Si no coinciden, el nodo no es compatible. |
| **Agent cache** | Que los últimos estados de agentes y módulos del nodo se guarden correctamente en la base de datos del Command Center. |
| **Sync** | Que la licencia del nodo coincida con la del Command Center y que el nodo esté marcado como tal (`node_metaconsole`). |
| **Database sync** | Solo con la gestión centralizada activa: consulta la cola de sincronización y avisa si hay consultas pendientes de aplicar. |

Los tres primeros (DB, API y Compatibility) tienen que estar en verde para que
el nodo esté bien enlazado y empiecen a verse sus datos. El resto informa de su
parcela. La columna **Version** muestra la versión del servidor del nodo.

!!! warning "La misma frase de cifrado en todas partes"
    Si está habilitado el cifrado de la base de datos, **todos los nodos y el
    Command Center deben usar la misma** `encryption_passphrase`. Los datos de
    conexión de cada nodo se guardan cifrados con esa frase; si no coincide, el
    Command Center no puede descifrarlos. Ver [9.5 · Cifrado de la base de
    datos](../parte-9/9.5-cifrado-de-la-base-de-datos.md).

**Ejemplo.** Para dar de alta un nodo en `192.168.80.37` con la base de datos en
SSL:

1. En **Consoles setup**, pulsar **New node**.
2. Rellenar **Label** con `nodo-37`, **Console URL** con
   `https://192.168.80.37/pandora_console/` (con barra final), las credenciales
   de API y consola, y los datos de la base de datos: host `192.168.80.37`,
   nombre `pandora`, usuario `pandora`, puerto `3306`.
3. Activar **Enable SSL**, indicar la clave y el certificado del servidor MySQL
   y el certificado de la CA, y activar **SSL verify server cert**.
4. Guardar con **Register empty node** si el nodo está recién instalado, o con
   **Register node with data to merge** si ya tenía datos.
5. Volver a la lista y comprobar que **DB**, **API** y **Compatibility** están
   en verde. Si alguno queda en rojo, hacer clic sobre él para ver el motivo.

La referencia de campos, con su valor por defecto, vive en el apartado 22.2 de
[9.2 · Referencia completa de configuración de la
consola](../parte-9/9.2-referencia-completa-de-configuracion-de-la-consola.md);
aquí está el procedimiento.

### Tareas de la consola del Command Center

Hay tres cosas que conviene dejar funcionando para que el resto del capítulo
funcione: la programación de informes, el acceso a la API y la autoautenticación
hacia los nodos.

**Programación de informes.** Para lanzar el mantenimiento de base de datos
(`pandora_db`) hacen falta los paquetes del servidor instalados en la máquina
del Command Center, y ese proceso programado en el **cron** cada hora. Si además
se usan los informes bajo demanda (enviados por correo), hay que programar la
extensión de cron igual que en una consola normal, añadiendo una línea a la
crontab que llame a `cron.php`:

```text
* * * * * <usuario> wget -q -O - http://x.x.x.x/pandora_console/enterprise/extensions/cron/cron.php >> /var/www/pandora_console/log/console.log
```

Las tareas de consola y su programación se explican con detalle en [2.5 ·
Tareas de consola](../parte-2/2.5-tareas-de-consola.md).

**API.** Para que el Command Center pueda hablar con la API de cada nodo hacen
falta:

- un **usuario y una contraseña válidos** en el nodo;
- la **contraseña de la API** configurada en el nodo;
- la **lista de direcciones IP con acceso a la API** en el nodo, donde se admite
  el asterisco (`*`) como comodín para dar acceso a todas las direcciones o a
  una subred.

**Autoautenticación.** El Command Center salta a la consola web de un nodo en
varios sitios; por ejemplo, al hacer clic en el agente asociado a un evento, se
abre la vista de ese agente en la consola del nodo al que pertenece. Para que
ese salto no vuelva a pedir credenciales se usa la **autoautenticación**: la
opción **Auto login in node**, en **Metasetup → General setup**, que corresponde
al token `JWT_signature` y viene activada por defecto.

## Merging tool: unificar las bases de datos

Unificar no es copiar. Cuando hay varios nodos, lo normal es que el mismo grupo,
la misma etiqueta o la misma plantilla existan en más de uno con ajustes
distintos. La **Merging tool** decide, para cada elemento, qué versión se queda,
y deja el entorno listo para gestionarse desde el Command Center. Por eso se
lanza con los servidores parados y con copia de seguridad, no un viernes a las
seis de la tarde.

### Qué es y cuándo hace falta

La Merging tool recorre las bases de datos de todos los nodos y del Command
Center y unifica los elementos que se gestionan de forma centralizada. Un
entorno que ya estaba centralizado con el sistema de sincronización anterior
tiene que pasar por aquí una vez.

Solo entran en la fusión los nodos configurados en el Command Center que **no**
estén deshabilitados. El proceso establece un **orden de prioridad** entre el
propio Command Center y los nodos: los de arriba mandan sobre los de abajo. Ese
orden es el que resuelve los conflictos cuando un mismo elemento existe en
varios sitios con configuración distinta.

![Merging tool con el orden de prioridad de nodos y el progreso de la fusión de cada uno, con el resultado y las operaciones pendientes](../../assets/img/parte-06/command-center-merging-cuando.png){ .diagrama .diagrama-ancho }

Arriba de la lista está el propio Command Center y, debajo, cada nodo
registrado, con las columnas **DB** y **API** comprobando la conexión con cada
uno. El orden se cambia arrastrando las filas por el asa lateral y se guarda al
soltar.

!!! info "Cómo se decide qué configuración gana"
    Si dos o más elementos tienen el mismo campo único, se toma la configuración
    del que está en el nodo con **mayor prioridad**. Si el mismo elemento
    aparece repetido dentro del nodo de mayor prioridad, gana el de **ID más
    bajo**.

Las políticas de monitorización son un caso aparte: sus módulos, alertas,
colecciones y demás elementos se consideran elementos independientes de la
política y se fusionan por su cuenta.

¿Cuándo hace falta lanzarla?

- Al pasar a un Command Center un entorno que ya existía con varios nodos.
- Al incorporar a un entorno centralizado un nodo que ya tiene datos.
- Al actualizar un entorno centralizado con el antiguo sistema de sincronización.

### Qué centraliza

La Merging tool se lleva al Command Center los elementos que después se gestionan
desde él. Para cada uno, dos versiones se consideran «el mismo elemento» cuando
coinciden en una **clave de identidad**. Casi todo se identifica por nombre; los

### Requisitos previos

Antes de pulsar **Unify databases**, el proceso
comprueba una lista de requisitos. Si alguno falla, la fusión no arranca y el
error indica qué queda pendiente.

| Requisito | Detalle |
|---|---|
| Conexión del Command Center a los nodos | El Command Center tiene que alcanzar la base de datos y la API de **todos** los nodos. En la configuración de consolas los indicadores deben estar en verde. |
| Conexión de los nodos al Command Center | Las consolas de los nodos tienen que alcanzar la base de datos del Command Center. Solo es un problema si consolas y servidores viven en máquinas distintas. |
| Configuración de Enterprise en el nodo | En **Management → Settings → System Settings → Command Center** del nodo, los datos del Command Center (base URL, host, nombre, puerto, usuario y contraseña de su base de datos) tienen que ser correctos. |
| API del Command Center | Los servidores de todos los nodos tienen que alcanzar la API del Command Center. Se recomienda configurar la **Public URL** en el Command Center. |
| API del nodo | Los servidores de cada nodo necesitan su configuración de API correcta: `console_api_url` y `console_api_pass` en `pandora_server.conf`, o la **Public URL** en la configuración de la consola. Si no se configura, el servidor tiene que estar en la misma máquina que su consola. |
| Histórico de cada nodo | Cada nodo tiene que poder conectarse a su propia base de datos de histórico. |
| Versión | Todos los nodos y el Command Center en la **misma versión**. |
| Maintenance release | Todos en el **mismo MR**. |
| Tamaño de colección | Todos con el **mismo tamaño máximo de colección** configurado. |
| Memoria de PHP | `memory_limit` a `-1` (sin límite) en todos, solo durante la fusión. |
| Subida de ficheros | `post_max_size` de cada nodo **mayor o igual** que el del Command Center y, a su vez, **mayor o igual** que `upload_max_filesize` y que la colección más pesada. |
| `upload_max_filesize` | En cada nodo, **mayor o igual** que en el Command Center y que la colección más pesada. |
| Espacio en disco | Suficiente en el directorio `attachment` de todos para los respaldos de base de datos y colecciones. |
| Fecha y hora | Correctamente configurada en todos (se recomienda NTP). |
| Tarea cron de la consola | Cada nodo tiene que tener su tarea cron de consola creada; si nunca se ha accedido a su consola, el proceso pide iniciar sesión en el nodo antes. |
| Extensión ZIP | La extensión `zip` de PHP tiene que estar cargada. |

![Página Command center de la configuración del nodo, con la URL base y los datos de conexión a la base de datos del Command Center](../../assets/img/parte-06/command-center-merging-requisitos.png){ .diagrama }


!!! warning "Devuelve `php.ini` a su sitio"
    Terminada la fusión, restaura los valores de `php.ini`, sobre todo
    `memory_limit`. Cada vez que se toca `php.ini` hay que **reiniciar Apache
    (`httpd`) y PHP-FPM** para que los cambios surtan efecto.

### Recomendaciones antes de lanzarlo

No son requisitos, pero ahorran disgustos:

- **Detén los servidores** de todos los nodos y del Command Center mientras dure
  el proceso. Se van a cambiar elementos fundamentales (por ejemplo, los IDs de
  los grupos) y no conviene que el servidor genere nuevas referencias a medio
  camino. En la mayoría de los casos no sería un problema, pero no hay razón
  para probarlo.
- **Detén temporalmente `pandora_db`** del cron, por el mismo motivo.

!!! info "Modo mantenimiento durante la fusión"
    Al arrancar la fusión, tanto los nodos como el Command Center entran en modo
    mantenimiento para los usuarios estándar, no para los administradores. La
    idea es la misma que la de parar los servidores: que nadie modifique un
    elemento a mitad del proceso y lo descuadre.

!!! warning "El proceso escribe y borra"
    La fusión **modifica y borra datos** en los nodos. No hay vuelta atrás más
    allá de los respaldos que genera el propio proceso, y esos respaldos pueden
    no recuperarse si el fallo impide leerlos. Ten copia de seguridad de
    **todas** las bases de datos antes de empezar.

### Ejecución del proceso

La fusión se lanza desde **Centralised
management → Merging tool**, con el botón **Unify
databases**. Tiene **dos fases**, y cada una se divide a su vez en dos barras de
progreso.

**Fase 1: sincronización del entorno.** Recorre los elementos de las bases de
datos de los nodos que se gestionan desde el Command Center. Se divide en:

- **Initialize**: comprueba los requisitos, genera los
  respaldos y calcula en memoria el resultado de la fusión. Si falla aquí, las
  bases de datos aún no se han tocado y no hay que restaurar nada. Los respaldos
  quedan en `attachment/merge_backups` de cada nodo y del Command Center, con
  una subcarpeta `backup_<id_nodo>` por nodo.
- **Apply**: aplica la fusión, de forma secuencial y en orden de
  prioridad. Cuando termina con un nodo, empieza con el siguiente.

Si algo falla durante la aplicación, el proceso intenta restaurar los respaldos
por su cuenta; aparece entonces una tercera barra roja de **Restore**.

![Proceso de fusión terminado en el Command Center y dos nodos, con las barras de Inicializar y Aplicar en verde, el botón Process detail y el resultado Successful con operaciones pendientes](../../assets/img/parte-06/18_merge_success.png){ .diagrama }

![Proceso de fusión con error en el Command Center y dos nodos: barras de Inicializar y Aplicar a medias, barra de Restaurar en rojo, botón Display errors y resultado Error, sincronización abortada y respaldo restaurado](../../assets/img/parte-06/19_merge_error.png){ .diagrama }

!!! warning "Si el respaldo no se puede restaurar"
    Si el fallo impide recuperar los respaldos, la restauración hay que hacerla a
    mano. Algunos errores (una pérdida momentánea de conexión, un disco lleno
    que impide crear el respaldo) dan un mensaje genérico; si no se resuelve,
    toca contactar con el soporte de Pandora FMS.

**Fase 2: actualización de eventos.** Actualiza las referencias de los eventos a
los elementos que se acaban de sincronizar (por ejemplo, a grupos). Solo afecta
a los eventos anteriores a la fusión; los nuevos ya nacen con las referencias
correctas. Se divide en dos:

- **Events**: los de la base de datos principal. Se actualiza en paralelo con
  el funcionamiento normal: en este punto ya se pueden volver a arrancar el
  servidor y `pandora_db`, y los usuarios estándar ya pueden entrar. Verán la
  barra de progreso en la vista de eventos y, para los eventos antiguos, aún
  puede haber incongruencias en filtros. Lo lanza cada nodo mediante una tarea
  del **cron** de su consola, y puede tardar bastante.
- **Events History**: lo mismo sobre la base de datos de histórico.

![Proceso de fusión de eventos terminado en el Command Center y dos nodos, con las barras Events y Events History en verde y estado Finished](../../assets/img/parte-06/20_events_success.png){ .diagrama }

Los errores de la fusión quedan registrados y se pueden consultar desde el propio
Merging tool (**Display errors**). Si algo queda a medias, se puede reintentar el
proceso.

### Entorno ya centralizado

Terminada la fase 1, el entorno se considera centralizado y ya se puede gestionar
todo desde el Command Center. La sincronización de elementos también cambia de
sistema: cuando en el Command Center se hace un cambio (crear un usuario, por
ejemplo), se encolan para cada nodo las consultas necesarias (`INSERT`,
`UPDATE`, etc.) en la tabla `tsync_queue`. El `pandora_ha` de cada nodo las lee
de la base de datos del Command Center en orden y las va aplicando. Si un
servidor está parado un tiempo, cuando vuelve se pone al día.

Las consultas pendientes se ven desde el Command Center en **Setup → Metasetup → Consoles
setup**, en el indicador **Database
sync**. Si una consulta falla, el nodo no
sigue con las siguientes y el error queda a la vista en esa misma pantalla; lo
normal es resolverlo relanzando la fusión desde el Merging tool.

**Incorporar un nodo nuevo.** Se da de alta en **Setup → Metasetup → Consoles
setup → New node**, como se explicó en
[«Alta y registro de nodos»](#alta-y-registro-de-nodos). Al guardar:

- **Register empty node** si el nodo no tiene nada que
  conservar: sus datos se borran y se reemplazan por los del Command Center.
- **Register node with data to
  merge** si el nodo ya tiene datos: el nodo queda desactivado a la espera de
  que se lance la fusión.

## Gestión centralizada

### Qué cambia al activar la gestión centralizada

Con la gestión centralizada activa, el Command Center pasa a ser la **fuente de
configuración** de los nodos para una serie de secciones, y esas secciones dejan
de aceptar cambios locales: en el nodo solo se pueden listar. No es un
interruptor que se pueda encender a la ligera, porque lo que hubiera en cada nodo
puede quedar sobrescrito.

¿Dónde se activa? La marca la pone el propio **Merging tool** al unificar el
entorno: deja el token `centralized_management` a `1` en el Command Center y en
todos los nodos registrados. No hay un interruptor en la configuración general
del Command Center, así que el camino para activarlo es fusionar el entorno.

!!! warning "Actívalo con la casa en orden"
    Si el entorno llevaba tiempo funcionando por separado, lo normal es que cada
    nodo tenga cosas distintas (grupos, etiquetas, políticas, usuarios). Al
    centralizar, el Command Center manda y lo de los nodos puede quedar
    sobrescrito o descuadrado. Inventaría antes lo que hay en cada nodo, decide
    qué versión es la buena y hazlo en una ventana, con copia de seguridad de
    todas las bases de datos. En [12.8 · Entornos
    grandes](../parte-12/12.8-entornos-grandes.md) está el aviso con más
    detalle.

Los elementos afectados son los mismos que centraliza la Merging tool (ver «Qué
centraliza»). El resto de la consola se comporta igual que en un nodo.

### Agentes y aprovisionamiento

**Mover agentes.** La opción **Agent management**![Icono de la opción Gestión de agentes](../../assets/img/parte-06/gm_agent_icon_command_center.png){ .icono-en-linea } reubica agentes de un nodo a otro. Se
localizan con los filtros de grupo o de nombre (con recursión de grupo si hace
falta), se pasan a la lista de seleccionados y se eligen nodo origen y destino.
La casilla **Discard history data** borra el
histórico del agente al moverlo, para no arrastrar datos que no se necesitan; el
movimiento se confirma con **Move**.

!!! tip "Registro de movimientos"
    Al pie de la pantalla queda un registro con la **última acción completada de
    cada agente y las pendientes posteriores**. Los agentes con módulos
    sintéticos se omiten del movimiento, porque pueden depender de módulos de
    otros agentes.

**Aprovisionamiento.** La opción **Provisioning management**![Icono de la opción Gestión de aprovisionamiento](../../assets/img/parte-06/write_paper_icon_command_center.png){ .icono-en-linea } decide en qué nodo se dan de alta
los agentes nuevos que llegan sin destino. Hay tres estrategias:

- **Round robin**: reparte los agentes nuevos en orden circular
  entre los servidores.
- **Less loaded**: asigna cada agente nuevo al servidor con
  menos carga.
- **Custom**: aplica reglas propias basadas en la información
  que reporta el agente (su alias y su rango de IP), con operadores `AND` y
  `OR`.

Para que el aprovisionamiento reconozca los nodos, cada nodo tiene que tener
configurada **su propia dirección IP** en el Data server:

![Edición del Data server de un nodo, con el campo IP Address resaltado y el nombre del nodo](../../assets/img/parte-06/command-center-aprovisionamiento-datos.png){ .diagrama .diagrama-ancho }

nodos; la segunda es la misma operación con la interfaz en forma de árbol.

!!! warning "Editar grupos toca la sincronización"

### Políticas

En un Command Center, la cola de políticas es distinta de la de un nodo: **no
guarda histórico**. Solo muestra las políticas no aplicadas o en curso,
indicando a qué nodo pertenecen. El histórico de las aplicadas queda en el nodo,
que es lo único que se puede gestionar desde allí.

**Quién las aplica.** No las aplica la consola: la consola solo apunta la
operación en la cola. Las ejecuta un hilo del propio servidor de Pandora FMS, el
**Policy Manager** (`policy_manager`), que va vaciando esa cola. Se lanza solo,
en el servidor maestro de cada instalación —igual en un nodo suelto que en un
Command Center—; si se desactiva, la cola deja de vaciarse y las políticas no
llegan a los agentes.

El Command Center tiene el token **Max. number of queue operations per node** para no sobrecargar la
visualización y la operación de las colas. Su valor por defecto es **100.000
operaciones por nodo**.

**Integridad de los datos.** Los datos de una política tienen que ser iguales en
los nodos y en el Command Center: módulos, alertas, módulos de inventario,
colecciones, etc. Al aplicar una política desde el Command Center, todo eso se
copia a los nodos implicados. Si algo falla al copiar, la consola muestra el
error y el nodo hace un **rollback** a los datos anteriores. En instalaciones
nuevas no hay problema; si los nodos tienen políticas configuradas a mano,
conviene borrarlas y pasarlas al Command Center para sincronizarlas desde allí.

Las políticas y su cola se documentan en [2.10 · Políticas de
monitorización](../parte-2/2.10-politicas-de-monitorizacion.md).

### Categorías y servidores

**Gestión de categorías.** Permite administrar las categorías de módulos

**Gestión de servidores.** La opción **Server
management** muestra el tipo, el estado, la versión y otros datos de los
servidores del Command Center y de cada nodo. Se elige el nodo en **Show server status of**:

![Lista de servidores del Command Center con columnas de nombre, estado, tipo, versión, módulos, lag, hilos y cola, actualización y acciones](../../assets/img/parte-06/pfms-command_center-server_management-image_010.png){ .diagrama .diagrama-ancho }

![Lista de servidores de un nodo con columnas de nombre, estado, tipo, versión, módulos, lag, hilos y cola, actualización y acciones](../../assets/img/parte-06/pfms-command_center-server_management-image_020.png){ .diagrama .diagrama-ancho }

**Qué servidores aparecen.** La lista no se rellena a mano: la crea el propio
servidor al arrancar, con una fila por cada módulo que tenga activo (aparecen con

arranca cuatro:

- **Network server**: el único módulo del núcleo que se carga en un Command
  Center; las tareas de servicio del propio Command Center las ejecuta él.
- **Events server**: la replicación de eventos desde los nodos.
- **Autoprovision server**: asigna los agentes que llegan sin destino.
- **Migration server**: mueve agentes entre nodos.

Al elegir un nodo en **Show server status of** se ven los servidores de ese nodo.

!!! info "Configuración remota, solo en el primero"
    La opción de configuración remota solo se muestra en el primer servidor de
    cada nombre; los repetidos son réplicas y se administran a través del
    primero.

La configuración de los servidores de Pandora FMS está en [9.3 · Referencia
completa de configuración del
servidor](../parte-9/9.3-referencia-completa-de-configuracion-del-servidor.md).

### Operaciones masivas

Las **Bulk operations** del Command Center van en dos
pasos: se elige el destino (agentes, usuarios, módulos...) y el tipo de tarea
(editar, borrar...). En las operaciones sobre agentes se selecciona el nodo sobre
el que actuar.

!!! info "Los campos en blanco no se tocan"
    Al editar en bloque, los campos que se dejen en **No
    change** quedan como estaban.

El número de operaciones que se pueden lanzar de una vez lo limita el token
**Limit for bulk operations**: por defecto,
la mitad del valor de `max_input_vars` de PHP, con un rango configurable de 100 a
2000.

Las operaciones masivas se explican en [12.10 · Operaciones
masivas](../parte-12/12.10-operaciones-masivas.md).

### Informes, dashboards y consolas visuales

**Informes.** Los informes del Command Center se generan en varios formatos (PDF,
CSV, etc.) y se guardan en el Command Center, pero **los datos salen de los nodos
que se elijan**. Esa es la diferencia con los informes de un nodo. Se pueden
crear uno a uno o mediante plantillas parametrizables, que se aplican a un grupo
de agentes cuando se solicitan. Ver [5.2 · Informes](../parte-5/5.2-informes.md).

**Dashboards.** Funcionan como los de un nodo, con una ventaja: al buscar un
agente basta con escribir al menos dos caracteres y aparece una lista ordenada

**Consolas visuales.** Ofrecen a pantalla completa una panorámica hecha a medida.

con sesión iniciada como mediante un enlace público, y se actualizan según el

zonas geográficas. Ver [5.6 · Consolas
visuales](../parte-5/5.6-consolas-visuales.md).

## Ajustes exclusivos del Command Center

Metasetup mezcla dos tipos de páginas: las que replican la configuración de un
nodo y las que solo tienen sentido cuando hay un Command Center por encima. Las
primeras no se repiten aquí; su referencia es el apartado 22 de [9.2 ·
Referencia completa de configuración de la
consola](../parte-9/9.2-referencia-completa-de-configuracion-de-la-consola.md).
Estas son las exclusivas.

### Normas de relación

Las **Relations rules**![Icono de la opción Normas de relación](../../assets/img/parte-06/metasetup_icon_relations_rules.png){ .icono-en-linea } resuelven a qué nodo pertenece un elemento que llega sin destino. Están pensadas para dispositivos especiales que se identifican por su puerta de enlace o por su IMEI y que se consultan a través de una API distinta de la API principal, la **API del agente**. Para que funcionen hay que tener habilitada **Enable Agent API** en la configuración general.

El alta de una relación tiene tres campos: el **Type** —**IP Gateway** o **IMEI**—, el valor de la **Relation** y la **Node Address**, que puede ser
cualquiera de los nodos registrados o un valor **Custom**. Se
guarda con **Insert relation**.

![Formulario de alta de una norma de relación, con los campos Type, Relation y Node Address, y el botón Insert relation](../../assets/img/parte-06/pfms-command-center-setup-metasetup-relations_rules-insert_relation.png){ .diagrama }

Para cargar muchas de golpe se importa un fichero CSV con una relación por línea,
en el orden `tipo,regla,nodo`:

```text
gateway,4,192.168.80.37
imei,123456789012345,192.168.80.38
```

Con **Import file** se sube el fichero. Las líneas que no
encajen con el formato se rechazan y la consola informa de cuáles.

Las relaciones guardadas se listan al pie, con filtros por tipo, valor o
dirección de nodo. Se borran de una en una con su icono, o en bloque: se marcan
las casillas y se pulsa **Delete**.

La consulta se lanza contra la API del agente con el parámetro
`get_node_addresses=1`, que es **obligatorio**, y devuelve un array JSON con la
dirección o direcciones del nodo. Para una puerta de enlace, `gateway=1`:

![Consulta a la API del agente con el parámetro gateway=1 y su respuesta en formato JSON con la dirección del nodo](../../assets/img/parte-06/pfms-command-center-setup-metasetup-relations_rules-sample_query_1.png){ .diagrama .diagrama-ancho }

Y para un IMEI `imei=2`:

![Consulta a la API del agente con el parámetro imei=2 y su respuesta en formato JSON con la dirección del nodo](../../assets/img/parte-06/pfms-command-center-setup-metasetup-relations_rules-sample_query_2.png){ .diagrama .diagrama-ancho }

Con **Node Address Default** se fija la
respuesta que se devuelve cuando no hay ninguna norma o ninguna coincide con la
consulta. Puede ser la dirección de uno de los nodos o un valor
**Custom**, por ejemplo un mensaje propio.

![Configuración de la dirección de nodo por defecto, con un nodo seleccionado y la opción Custom disponible](../../assets/img/parte-06/pfms-command-center-setup-metasetup-relations_rules-node_address_default.png){ .diagrama }

El aprovisionamiento de agentes que usa estas normas se desarrolla en [6.6 ·
Mecanismos de autoprovisión](../parte-6/6.6-mecanismos-de-autoprovision.md).

### Warp Update de los nodos

El Command Center se actualiza desde sus propias páginas de **Warp Update**,
todas en **Setup → Metasetup**. Las cuatro solo
aparecen si está activo **Enable Warp
Update** en la configuración general. El concepto de Warp Update y el
procedimiento general están en [1.4 ·
Actualizaciones](../parte-1/1.4-actualizaciones.md); aquí va lo propio del
Command Center.

- **Warp Update Online**![Icono de la opción Warp Update en línea](../../assets/img/parte-06/metasetup_icon_warp_update_online.png){ .icono-en-linea }: con una licencia de Command Center válida y salida a internet, actualiza el Command Center de forma automática.
- **Warp Update Offline**![Icono de la opción Warp Update sin conexión](../../assets/img/parte-06/metasetup_icon_warp_update_offline.png){ .icono-en-linea }: para actualizar o parchear sin internet. Los ficheros se suben en orden hasta la versión que se necesite, porque no son acumulativos, y sirve tanto para parches de consola como de servidor o combinados.
- **Warp Update Journal**![Icono de la opción Diario de Warp Update](../../assets/img/parte-06/metasetup_icon_warp_update_journal.png){ .icono-en-linea }: el historial de actualizaciones aplicadas, con la versión, la fecha y la hora y el usuario que las solicitó. Con el cuadro **Filter** se busca dentro del historial.
- **Warp Update Setup**![Icono de la opción Configuración de Warp Update](../../assets/img/parte-06/metasetup_icon_warp_update_setup.png){ .icono-en-linea }: viene preparada para la actualización en línea. Antes de tocar la **Warp Update URL**, el **Use secured Warp Update**, los datos del **Proxy** (servidor, puerto, usuario y contraseña) o los conmutadores **Allow offline patches** y **LTS updates** —que cambian qué paquetes acepta el modo sin conexión—, conviene consultar con el soporte de Pandora FMS.

!!! warning "Actualización sin conexión: copia antes"
    Aplicar parches o actualizaciones sin conexión puede dejar la consola
    inservible. Haz copia de seguridad completa antes de empezar.

En el modo sin conexión, la página muestra un código de acceso ligado a la
licencia. Se copia con el icono![Icono de copiar al portapapeles](../../assets/img/parte-06/icon_copy.png){ .icono-en-linea }, se abre el enlace de descarga en otra pestaña, se pega el código, se inicia sesión y se descargan los ficheros **de uno en uno**. De vuelta en la página, se sube cada fichero con **Browse it**. El tamaño de cada fichero tiene que ser menor que `post_max_size` y `upload_max_filesize` de `php.ini`, y el proceso se lanza con el icono verde de la esquina inferior derecha.

### Notificaciones y correo saliente

**Notificaciones.**![Icono de la opción Notificaciones](../../assets/img/parte-06/metasetup_icon_notifications.png){ .icono-en-linea } El Command Center vigila su propio estado y el del sistema, y avisa a los usuarios. Se configura en **Setup → Metasetup → Notifications**. Al hacer clic en una categoría se añaden o suscriben los usuarios o grupos que la reciben; para **System status** se puede elegir además cada aspecto técnico.

Las categorías son seis: **System status**, **Message**, **Pending task**, **Advertisement**, **Official communication** y
**Sugerence**.

El token **Enable user configuration**
permite que cada usuario active o desactive sus notificaciones de consola y de
correo desde **Operation → Workspace → Configure user notifications** en los
nodos centralizados. Para que lleguen por correo, el usuario tiene que tener su
dirección configurada y el servidor de Pandora FMS tiene que poder enviar
correo.

Hay un matiz que sorprende: si un usuario pertenece a un grupo suscrito a una
categoría, recibe las notificaciones de consola de esa categoría y **no puede
desactivarlas**, ni aunque el token anterior esté activo. Un usuario nuevo con
perfil **Pandora Management** se suscribe solo a **System status** y **Official
communication**, no a las seis; cuando el nodo ya está centralizado, entra en las
categorías del Command Center, y cada nodo centralizado gestiona las suyas por
separado.

**Correo saliente.**![Icono de la opción Correo](../../assets/img/parte-06/metasetup_icon_mail.png){ .icono-en-linea } En **Setup → Metasetup → Mail** se define el envío: la dirección de salida (**From dir**), el nombre (**From name**), el servidor SMTP (**Server SMTP**), el puerto (**Port SMTP**), el cifrado de la conexión (**Encryption**: `SSL`, `SSLv2`, `SSLv3` o `STARTTLS`) y, si el servidor lo pide, usuario y contraseña (**Email user** y **Email password**) y el método de autenticación (**SMTP authentication**: `Default`, `LOGIN`, `PLAIN`, `CRAM-MD5` o `DIGEST-MD5`). Con **Email test** se envía un correo de prueba.

!!! warning "Gmail y otros proveedores"
    Google puede bloquear la autenticación de aplicaciones que considera poco
    seguras; hay que habilitar el acceso. Mejor una cuenta creada solo para los
    avisos del servidor que una personal.

El servidor de Pandora FMS tiene que poder resolver, con su DNS, el servidor de
correo del dominio (`nslookup -type=mx my.domain`), y el servidor de correo tiene
que aceptar los envíos que le lleguen desde él. Si la autenticación no es la de
por defecto, se ajusta el token `mta_auth` en `/etc/pandora/pandora_server.conf`:
viene comentado y admite `LOGIN`, `PLAIN`, `CRAM-MD5` y `DIGEST-MD5`.

### Traducción de cadenas y gestor de archivos

**Strings translation**![Icono de la opción Traducción de cadenas](../../assets/img/parte-06/metasetup_icon_strings_translation.png){ .icono-en-linea } reescribe cadenas de la interfaz de forma personalizada. Se filtra por **Language** y por el texto (**Free text for search (*)**; en blanco, las muestra todas). Aparecen tres columnas: la cadena original, la traducción actual y la personalizada. Se rellena la tercera y se guarda con **Update**. Conviene copiar exactamente el HTML y el JavaScript que aparezcan en el texto; si se rompen, la cadena no se mostrará bien.

**File manager**![Icono de la opción Gestor de archivos](../../assets/img/parte-06/metasetup_icon_file_manager.png){ .icono-en-linea } sube y borra ficheros de la carpeta de imágenes de la instalación del Command Center.

!!! warning "No todas las imágenes están en el gestor"
    El código del Command Center reutiliza algunas imágenes de la consola normal.
    Esas no aparecen en el gestor y hay que administrarlas a mano en la
    instalación. No conviene sustituirlas a la ligera.

### Rendimiento y configuración visual propios

**Performance setup**![Icono de la opción Configuración del rendimiento](../../assets/img/parte-06/metasetup_icon_perfomance_setup.png){ .icono-en-linea } comparte la mayor parte de las opciones con la página de un nodo. ### General setup del Command Center

## Extensiones

El Command Center incorpora las mismas extensiones que una consola, con algún
matiz propio. El concepto general está en [9.10 · Creación de extensiones de
consola](../parte-9/9.10-creacion-de-extensiones-de-consola.md).

**DB interface**. Permite ejecutar consultas SQL y ver el
resultado. Es una herramienta para quien conoce SQL y el esquema de Pandora FMS;
no es para improvisar. En un Command Center, además, se elige sobre qué base se
lanza con **Select query target**: la del
propio Command Center o la de cualquiera de sus nodos.

**CSV group import**. Importa grupos desde un
fichero con los campos separados por comas o por el carácter que se elija en
**Separator**. Se selecciona el fichero con **Select a file** y se lanza con **Go**. El CSV lleva los
campos en este orden: nombre del grupo, icono, id del grupo padre y propagación
(`1` sí, `0` no).

**Cron jobs**. Permiten programar en el Command Center
operaciones periódicas, como enviar logs en formato CSV o ejecutar código PHP.

![Lista de tareas cron del Command Center, con columnas de usuario, tarea, programación, próxima ejecución, última ejecución, grupo y acciones, y el botón Create al pie](../../assets/img/parte-06/pfms-command-center-extensions-cron_jobs.png){ .diagrama .diagrama-ancho }

Con **Create**![Icono de crear](../../assets/img/parte-06/icon_plus.png){ .icono-en-linea } se añade una tarea a la lista. En la columna de acciones, cada fila se edita![Icono de editar](../../assets/img/parte-06/edit_icon_command_center.svg){ .icono-en-linea }, se borra![Icono de borrar](../../assets/img/parte-06/delete_icon_command_center.svg){ .icono-en-linea } o se activa y desactiva![Icono de activar o desactivar](../../assets/img/parte-06/disable_icon_command_center.svg){ .icono-en-linea }.

**System audit log**. El Command Center deja
registro de las operaciones que le afectan:

- Manejo de categorías.
- Registro de usuarios.
- Eventos de sistema (inicios de servicio, cron, etcétera) y errores de consultas
  lanzadas desde la interfaz de la BD.
- Modificaciones de los nodos desde el Command Center.
- Gestión de módulos (creación, registros fallidos, etcétera).
- Gestión de políticas de monitorización.
- Cambios en la configuración general.

Las preferencias de filtro se pueden guardar y recuperar; se editan![Icono de editar](../../assets/img/parte-06/icon_config.png){ .icono-en-linea } y se borran![Icono de borrar](../../assets/img/parte-06/icon_trash.png){ .icono-en-linea } con los iconos correspondientes.
