## Introducción

**Tentacle** es, a la vez, un protocolo de transferencia de ficheros y la
herramienta cliente/servidor que lo habla. Sustituyó a SCP/FTP en 2008 como
método por defecto de envío de los XML de datos de los EndPoint, y tiene
asignado el puerto IANA `tcp/41121`.

En el producto, Tentacle transporta: los XML de datos que envía cada
EndPoint, los ficheros de configuración remota, las
[colecciones](../parte-2/2.9-colecciones.md), los comandos remotos (RMM), el
tráfico de los Servidores satélite, el proxy Tentacle y la instancia
dedicada de RMM.

Existen dos implementaciones del mismo protocolo, con las mismas opciones de
línea de comandos (misma letra, mismo significado):

- **Go** (binario estático `tentacle_server`/`tentacle_client`, sin
  dependencias en tiempo de ejecución): es la implementación **por
  defecto en los paquetes de Linux** (servidor, EndPoint y Servidor
  satélite) y **la recomendada**. Atiende cada conexión con una goroutine en
  vez del hilo con espera activa de Perl.
- **Perl** (`tentacle_server` v0.6.2, `tentacle_client` v0.4.0): la
  implementación de referencia histórica del protocolo. Es la que siguen
  llevando, compilada a `.exe`, **los paquetes de Windows** (EndPoint y
  Servidor satélite).

Son intercambiables: un cliente Perl habla con un servidor Go y viceversa,
porque ambos implementan el mismo protocolo con las mismas reglas.

El capítulo se organiza en tres bloques: el protocolo en sí (independiente
de la implementación), el cliente y el servidor.

## 1. El protocolo Tentacle

El diseño es deliberadamente simple:

- Siempre inicia la conexión el **cliente**; el servidor nunca envía datos
  antes de que el cliente los pida o los confirme.
- Los comandos son texto terminado en salto de línea. No hay saludo ni
  negociación de versión: el primer mensaje que envía el cliente ya es un
  comando.
- Cuando un comando anuncia un tamaño (`SIZE <n>`), a continuación viaja un
  bloque binario de exactamente ese número de bytes, sin relleno ni
  cabecera adicional.

### Tabla de comandos

| Comando | Sentido | Respuesta correcta | Errores |
|---|---|---|---|
| `SEND <fichero> SIZE <n>` | Cliente → servidor | `SEND OK` (confirmación de aceptar) y `SEND OK` (confirmación de recibido) | `SEND ERR (invalid file name)`, `SEND ERR (file is too big)`, `SEND ERR (file already exists)`, `SEND ERR (upload not allowed)` |
| `ZSEND <fichero> SIZE <n>` | Cliente → servidor, comprimido | `ZSEND OK` (aceptar) y `ZSEND OK` (recibido) | `ZSEND ERR (invalid file name)`, `ZSEND ERR (file is too big)`, `ZSEND ERR (file already exists)`, `ZSEND ERR (upload not allowed)`, `ZSEND ERR` (fallo al descomprimir) |
| `RECV <fichero>` | Cliente ← servidor | `RECV SIZE <n>`, luego el cliente responde `RECV OK` y el servidor envía los datos | `RECV ERR (file has an invalid file name)`, `RECV ERR (file does not exist)`, `SEND ERR (download not allowed)` |
| `ZRECV <fichero>` | Cliente ← servidor, comprimido | igual que `RECV` con prefijo `ZRECV` | `ZRECV ERR (file has an invalid file name)`, `ZRECV ERR (file does not exist)`, `SEND ERR (download not allowed)` |
| `LS <filtro>` | Cliente ← servidor (modo inseguro) | `LS SIZE <n>`, el cliente responde `LS OK` y el servidor envía el listado | `LS ERR` (filtro con nombre inválido, o al abrir el directorio) |
| `MV <fichero>` | Cliente ← servidor (modo inseguro) | `MV SIZE <n>`, el cliente responde `MV OK`, el servidor envía el fichero y lo borra | `MV ERR` (nombre inválido o no existe), `SEND ERR (download not allowed)` (no permitido) |
| `PASS <digest>` | Cliente → servidor | `PASS OK` | el servidor cierra la conexión sin mensaje si la contraseña no coincide |
| `QUIT` | Cliente → servidor | cierra la conexión sin respuesta | — |
| Comando no reconocido | — | — | el servidor registra `Unknown command '<comando>'` en el log y cierra la conexión, sin avisar al cliente |

El aviso de «descarga no permitida» reutiliza siempre la cadena
`SEND ERR (download not allowed)`, sea la operación `RECV`, `ZRECV` o `MV`:
las dos implementaciones comparten esta particularidad heredada del
protocolo, no es un error de transcripción.

### Envío de ficheros (`SEND`)

El cliente anuncia `SEND <nombre> SIZE <n>`. El servidor comprueba, en este
orden, si el destino admite subida (según `download_only`), si el nombre es
válido, si el tamaño está entre 1 byte y el máximo configurado, y si ya
existe un fichero con ese nombre (con `overwrite` desactivado). Un fichero
de tamaño 0 se rechaza con el mismo mensaje que uno demasiado grande
(`SEND ERR (file is too big)`): es el comportamiento normal del protocolo,
no una particularidad de una implementación. Tras una transferencia
correcta, el cliente puede enviar un nuevo `SEND` (u otro comando) en la
misma sesión; el cierre definitivo lo marca `QUIT`.

```text
Cliente:   SEND <informe.xml> SIZE 1024
Servidor:  SEND OK
Cliente:   <1024 bytes de datos>
Servidor:  SEND OK
Cliente:   QUIT
```

### Recepción de ficheros (`RECV`)

El cliente pide `RECV <nombre>`. Si el fichero existe y el destino admite
descarga (según `upload_only`), el servidor responde `RECV SIZE <n>`; el
cliente, ya conociendo el tamaño, puede rechazar la descarga sin más trámite
(simplemente no continúa la sesión con el comando esperado). Si el cliente
confirma con `RECV OK`, el servidor envía el bloque de datos.

```text
Cliente:   RECV <informe.xml>
Servidor:  RECV SIZE 1024
Cliente:   RECV OK
Servidor:  <1024 bytes de datos>
```

### Compresión (`ZSEND`/`ZRECV`)

`ZSEND` y `ZRECV` son las variantes comprimidas de `SEND`/`RECV`: el bloque
de datos es un fichero ZIP con una única entrada (Deflate) en vez del
contenido en claro. Se activan con la opción `-z` del cliente; el resto de
la secuencia de comandos es idéntica.

### Operaciones del modo inseguro (`LS`, `MV`)

`LS` (listar ficheros que cumplen un filtro) y `MV` (descargar un fichero y
borrarlo del servidor a continuación) solo funcionan si el servidor arrancó
con la opción `-I`/`insecure`. Si el modo inseguro está desactivado — el
valor por defecto —, el servidor registra el intento y cierra la conexión
sin responder al comando.

### Autenticación con contraseña (`PASS`)

Cuando el servidor exige contraseña, `PASS` debe ser el primer comando de la
sesión. El cliente envía, en hexadecimal, el MD5 del resumen MD5 binario de
la contraseña (un doble MD5). Esto **ofusca la contraseña, no la protege**:
sobre una conexión sin TLS no añade seguridad real frente a alguien que
capture el tráfico. Para que la autenticación por contraseña aporte algo,
tiene que ir sobre una conexión cifrada.

### Cifrado

TLS envuelve la conexión completa desde el primer byte: no existe una fase
sin cifrar ni un `STARTTLS` posterior. Ambos extremos deben tener TLS
activo; no es negociable a mitad de sesión.

### Gestión de errores

Ante cualquier anomalía — comando desconocido, contraseña incorrecta, más
datos de los anunciados, un fallo interno — el servidor cierra la conexión
sin explicar el motivo al cliente. El detalle solo queda en el log del
servidor, si está activo.

### Nombres de fichero y tamaño de bloque

Los nombres de fichero no admiten los caracteres `? [ ] / \ = + < > : ; ' , * ~`
ni ninguna ruta (solo el nombre simple). El tamaño de bloque de lectura y
escritura de red es de 1024 bytes.

### Los dos proxys de Tentacle

No hay que confundirlos:

- El **servidor Tentacle en modo proxy** (`-b`/`-g` o `proxy_ip`/`proxy_port`
  en el servidor): reenvía la conexión completa a otro servidor Tentacle,
  sin almacenar nada. Se explica en la sección 3, «Modo proxy».
- El **proxy HTTP del cliente** (`-y usuario:contraseña@dirección:puerto`):
  el cliente Tentacle abre la conexión a través de un proxy HTTP con
  `CONNECT`, con autenticación Basic opcional si se indica usuario y
  contraseña. Se explica en la sección 2, «Proxy HTTP».

## 2. El cliente Tentacle

Sintaxis: `tentacle_client [opciones] [fichero] [fichero] ...`. Hace falta al
menos un fichero, salvo en modo recepción (`-g`), donde el argumento es el
nombre remoto a descargar.

### Opciones de línea de comandos

Mismas letras en las dos implementaciones:

| Opción | Argumento | Qué hace | Por defecto |
|---|---|---|---|
| `-a` | dirección | Dirección del servidor. | `127.0.0.1` |
| `-b` | dirección local | Dirección local a la que enlazar la conexión saliente. | sin fijar (la elige el sistema) |
| `-c` | — | Activa TLS sin certificado de cliente. Incompatible con `-e`. | desactivado |
| `-e` | certificado | Fichero de certificado OpenSSL del cliente; activa TLS. Incompatible con `-c`. | — |
| `-f` | CA | Verifica que el certificado del servidor está firmado por esta CA. Requiere `-e`. | — |
| `-g` | — | Modo recepción: descarga ficheros del servidor en vez de enviarlos. | desactivado (modo envío) |
| `-h` | — | Muestra la ayuda. | — |
| `-k` | clave | Fichero de clave privada OpenSSL del cliente. Requiere `-e`. | — |
| `-p` | puerto | Puerto del servidor. | `41121` |
| `-q` | — | Modo silencioso: no imprime mensajes de error. | desactivado |
| `-r` | número | Reintentos de las operaciones de red. Mínimo 1: un valor menor hace que el cliente termine con error de arranque. | `3` |
| `-t` | segundos | Tiempo de espera de las operaciones de red. Mínimo 1: un valor menor hace que el cliente termine con error de arranque. | `1` s |
| `-v` | — | Modo detallado (registra los eventos del protocolo). | desactivado |
| `-w` | — | Pide de forma interactiva la contraseña de la clave privada. Solo tiene efecto junto con `-e`. | desactivado |
| `-x` | contraseña | Contraseña del servidor (autenticación `PASS`). | vacía |
| `-y` | `usuario:contraseña@dirección:puerto` | Proxy HTTP para la conexión (`CONNECT`, con Basic si se indican credenciales). | sin proxy |
| `-z` | — | Comprime los datos en tránsito (`ZSEND`/`ZRECV`). | desactivado |

### Reglas de combinación

- `-c` y `-e` son incompatibles entre sí (dos formas distintas de activar
  TLS: sin certificado propio o con uno).
- `-f` y `-k` exigen que `-e` esté presente; sin certificado de cliente no
  tiene sentido pedir CA o clave. `-w` solo tiene efecto junto con `-e`.
- IPv6: soportado; el cliente Perl necesita además el módulo
  `IO::Socket::INET6` instalado.

### Proxy HTTP

`-y usuario:contraseña@dirección:puerto` hace que el cliente abra la
conexión hacia el proxy con un `CONNECT` al servidor Tentacle real; si se
indican usuario y contraseña, añade la cabecera
`Proxy-Authorization: Basic`. Usuario y contraseña son opcionales dentro de
la cadena.

### Códigos de salida

`0` si todas las transferencias de la línea de comandos terminaron bien,
`1` si alguna falló o si hubo un error.

### Uso desde el EndPoint y el Servidor satélite

El EndPoint y el Servidor satélite invocan el cliente Tentacle a través de
cuatro tokens de su fichero de configuración: `transfer_mode tentacle` (el
modo de transferencia), `server_ip` y `server_port` (destino) y
`server_opts` (las opciones del cliente de esta sección, tal cual, por
ejemplo `server_opts -v -r 5`). Para el detalle completo de estos tokens y
sus equivalentes de servidor secundario, ver [9.1 · Referencia completa de
configuración del
EndPoint](9.1-referencia-completa-de-configuracion-del-endpoint.md).

### Ejemplos de uso

Con el servidor en `192.168.1.1` y sin contraseña en la clave privada del
cliente:

Transferencia simple, con tamaño máximo de fichero de 1 MB en el servidor:

```sh
tentacle_server -m 1048576 -s /tmp -v
tentacle_client -a 192.168.1.1 -v /home/user/myfile.dat
```

Con autenticación por contraseña:

```sh
tentacle_server -x password -s /tmp -v
tentacle_client -a 192.168.1.1 -x password -v /home/user/myfile.dat
```

TLS sin certificado de cliente:

```sh
tentacle_server -e cert.pem -k key.pem -w -s /tmp -v
tentacle_client -a 192.168.1.1 -c -v /home/user/myfile.dat
```

TLS con certificado de cliente y contraseña:

```sh
tentacle_server -x password -e cert.pem -k key.pem -f cacert.pem -w -s /tmp -v
tentacle_client \
  -a 192.168.1.1 \
  -x password \
  -e cert.pem \
  -k key.pem \
  -v /home/user/myfile.dat
```

## 3. El servidor Tentacle

Sintaxis: `tentacle_server -s <directorio> [opciones]`, o bien
`tentacle_server -F <fichero>` para arrancar leyendo la configuración de un
fichero.

### Opciones de línea de comandos

| Opción | Token | Qué hace | Por defecto |
|---|---|---|---|
| `-a` | `addresses` | Direcciones IPv4 en las que escuchar, separadas por comas. | `0.0.0.0` |
| `-b` | `proxy_ip` | Modo proxy: dirección del servidor Tentacle inaccesible al que reenviar. | — |
| `-c` | `max_connections` | Número máximo de conexiones simultáneas. | `10` |
| `-d` | `daemon` | Ejecuta el servidor como demonio. No disponible en Windows (ver «Windows», más abajo). | desactivado |
| `-e` | `ssl_cert` | Certificado OpenSSL del servidor; activa TLS. | — |
| `-f` | `ssl_ca` | CA con la que verificar el certificado del cliente. | — |
| `-F` | — | Ruta completa al fichero de configuración. | — |
| `-g` | `proxy_port` | Modo proxy: puerto del servidor Tentacle inaccesible. | `41121` |
| `-h` | — | Muestra la ayuda. | — |
| `-I` | `insecure` | Activa el modo inseguro (`LS` y `MV`). | desactivado |
| `-i` | `filters` | Filtros de reparto por subdirectorio (`regexp:dir;regexp:dir…`). | — |
| `-k` | `ssl_key` | Clave privada OpenSSL del servidor. | — |
| `-l` | `log_file` | Fichero donde escribir el log. | salida estándar si no se indica |
| `-m` | `max_size` | Tamaño máximo de fichero, en bytes. | `64000000` |
| `-o` | `overwrite` | Permite sobrescribir un fichero existente con el mismo nombre. | desactivado |
| `-p` | `port` | Puerto en el que escuchar. | `41121` |
| `-q` | `quiet` | No imprime mensajes de error. | desactivado |
| `-r` | `retries` | Reintentos de las operaciones de red. Mínimo 1. | `3` |
| `-s` | `directory` | Directorio de almacenamiento. Obligatorio salvo en modo proxy. | — |
| `-S` | — | Gestiona el servicio de Windows (`install`\|`uninstall`\|`run`). | — |
| `-t` | `timeout` | Tiempo de espera de las operaciones de red, en segundos. Mínimo 1. | `1` |
| `-u` | `ssl_cipher` | Restringe los conjuntos de cifrado TLS 1.2 admitidos, con nombres OpenSSL separados por `:`. | negociación normal |
| `-v` | `verbose 1` | Modo detallado: registra errores. | desactivado |
| `-V` | `verbose 2` | Modo detallado extendido: registra errores y avisos informativos. | desactivado |
| `-w` | — | Pide por línea de comandos la contraseña de la clave privada. Aplica a claves PEM cifradas del formato tradicional. | desactivado |
| `-x` | `password` | Contraseña del servidor (autenticación `PASS`). | vacía |
| `-z` | `ssl_version` | Restringe la versión de TLS admitida a `TLSv1_2` o `TLSv1_3`. | negociación normal (mínimo TLS 1.2) |

### Fichero de configuración

El formato es el habitual de la casa: una línea por token con el valor tras
un espacio, y `#` comenta la línea entera. La ruta habitual del fichero es
`/etc/tentacle/tentacle_server.conf`. La línea de comandos tiene preferencia
sobre el fichero cuando se repite la misma opción en los dos sitios. No hay
recarga en caliente: un cambio en el fichero exige reiniciar el servicio.

Varios tokens no tienen opción de línea de comandos equivalente:

- `block_size`: tamaño de bloque de lectura/escritura de red, en bytes (por
  defecto, 1024 bytes; ver «Protocolo», más arriba).
- `download_only` y `upload_only`: directorios, tras aplicar `filters`,
  desde los que solo se puede descargar o solo subir, respectivamente,
  separados por `;`. Se detallan en «Filtros y directorios», más abajo.

### Plantilla del paquete frente a los valores internos

La plantilla que instala el paquete (`tentacle_server.conf.new`) no
coincide siempre con el valor por defecto que aplica el propio binario
cuando el token no aparece en el fichero. Por ejemplo, la plantilla activa
`daemon 1` aunque el valor interno por defecto es `0` (desactivado). El
resto de tokens de la tabla anterior indican, en la columna «Por defecto»,
el valor **interno** del binario, no el de la plantilla.

### Filtros y directorios

`filters` (`-i`) reparte los ficheros entrantes por subdirectorio según una
expresión regular sobre el nombre; la sintaxis es
`regexp:subdirectorio;regexp:subdirectorio;…`. Un fichero cuyo nombre no
coincide con ningún filtro se guarda directamente en el directorio de
almacenamiento. La plantilla del servidor principal reparte, entre otros,
los `.conf` a `conf`, los `.md5` a `md5`, los `.zip` a `collections`, los
`.lock` a `trans`, los `.rcmd` a `commands` y los paquetes de instalación de
EndPoint (`.agent_setup.exe`, `.agent_setup.tar.gz`) a `agent`. Sobre estos
mismos subdirectorios (ya filtrados) actúan `download_only` (`-D`) y
`upload_only` (`-U`), restringiendo qué se puede subir o descargar en cada
uno. Tras actualizar el paquete hay que reiniciar el servidor para que tome
los filtros nuevos que traiga la versión.

### Servicio systemd

El servicio principal es `tentacle_serverd.service`, con usuario `pandora`,
que arranca `tentacle_server -F /etc/tentacle/tentacle_server.conf` con
`ExecStartPre` de limpieza (`clean_tentacle_serverd`, que vacía los
temporales del `TMPDIR` fijado en `tentacle_server.env`) y dos ficheros de
entorno (`tentacle_server.env` con `TMPDIR` y
`tentacle_server_extra.env`, este último libre para ajustes locales). La
relación entre este servicio y los tokens `tentacle_service_cmd` /
`tentacle_service_watchdog` del servidor principal está en [9.3 ·
Configuración remota, Tentacle y
sincronización](9.3-referencia-completa-de-configuracion-del-servidor.md#5-configuracion-remota-tentacle-y-sincronizacion).

### Instancia RMM

RMM usa su propia instancia de Tentacle, independiente de la del servidor
principal: servicio `tentacle_rmm.service` (usuario `root`, puerto `41123`,
`ExecStartPre` con `clean_tentacle_rmm`), su propio fichero de
configuración, su propio directorio de almacenamiento
(`/var/spool/pandora/rmm_server`) y sus propios certificados TLS. Los
filtros (`filters`) reparten por extensión los ficheros de RMM en
subdirectorios propios (`rmm`, `res`, `queue`, `keepalive`, `data`), y
`download_only`/`upload_only` restringen esos mismos subdirectorios: solo
se puede descargar de `rmm`, `res` y `queue`, y solo se puede subir a
`data` y `keepalive`. La plantilla trae una contraseña de ejemplo: **debe
cambiarse antes de poner el servicio en producción**, y como cualquier
secreto, se referencia desde la configuración, nunca se copia en la
documentación ni en un repositorio.

### Modo proxy

Con `-b`/`proxy_ip` y `-g`/`proxy_port`, el servidor Tentacle no actúa como
almacén: reenvía en crudo, byte a byte, todo lo que llega de cada cliente
hacia otro servidor Tentacle (el «inaccesible» desde el punto de vista de
los clientes). Puede terminar TLS y la autenticación por contraseña en el
tramo cliente-proxy, con un tramo proxy-servidor distinto (o sin cifrar).
El Servidor satélite resuelve el mismo reenvío con sus propios tokens,
`proxy_tentacle_from`/`proxy_tentacle_to`; ver [6.2 · Servidores
satélite](../parte-6/6.2-servidores-satelite.md).

Caso práctico — EndPoints detrás de un proxy Tentacle con TLS y contraseña,
de extremo a extremo: primero se comprueba a mano cada tramo y, si funciona,
se pasa a la configuración permanente.

Pruebas manuales:

```sh
# 1. Servidor real
sudo -u pandora tentacle_server \
  -x password \
  -e tentacle_cert \
  -k tentacle_key \
  -f ca_cert -s /tmp -v

# 2. Proxy
sudo -u pandora tentacle_server -b ip_servidor -g 41124

# 3. Cliente, contra el proxy
sudo -u pandora tentacle_client \
  -a ip_proxy \
  -x password \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -v fichero
```

Configuración permanente, una vez comprobado el envío manual:

1. Servidor real (`/etc/tentacle/tentacle_server.conf`):

   ```
   password password
   ssl_cert tentacle_cert
   ssl_key tentacle_key
   ssl_ca ca_cert
   ```

2. Proxy (su propio `/etc/tentacle/tentacle_server.conf`):

   ```
   proxy_ip ip_servidor
   proxy_port 41124
   ```

3. EndPoint (`pandora_agent.conf`), apuntando `server_ip` al proxy, no al
   servidor real:

   ```
   server_opts -x password -e tentacle_client_cert -k tentacle_client_key
   server_ip ip_proxy
   ```

Cada opción del `server_opts` es independiente: si no se necesita, por
ejemplo, la contraseña, basta con omitir `-x password` de la línea.

### Seguridad: contraseña, TLS y combinaciones de certificados

La contraseña (`-x`/`password`) y TLS son ortogonales: pueden combinarse o
usarse por separado. Las cuatro combinaciones de certificados posibles son
las siguientes; todas admiten añadir contraseña de la misma forma.

**1. Servidor con certificado, cliente sin verificar** (el cliente no
comprueba la identidad del servidor):

Prueba manual:

```sh
tentacle_server -v -e tentacle_cert -k tentacle_key -s /tmp
tentacle_client -v -c -a <servidor> fichero
```

Configuración permanente — servidor:

```
ssl_cert tentacle_cert
ssl_key tentacle_key
```

Configuración permanente — EndPoint y Servidor satélite:

```
server_opts -c
```

**2. Servidor con certificado, cliente verifica contra una CA**:

Prueba manual:

```sh
tentacle_server -v -e tentacle_cert -k tentacle_key -s /tmp
tentacle_client -v -e tentacle_client_cert -f ca_cert -a <servidor> fichero
```

Configuración permanente — servidor:

```
ssl_cert tentacle_cert
ssl_key tentacle_key
```

Configuración permanente — EndPoint y Servidor satélite:

```
server_opts -e tentacle_client_cert -f ca_cert
```

**3. Servidor verifica al cliente contra una CA** (certificado de cliente
sin CA propia en el cliente):

Prueba manual:

```sh
tentacle_server -v -e tentacle_cert -k tentacle_key -f ca_cert -s /tmp
tentacle_client -v \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -a <servidor> fichero
```

Configuración permanente — servidor:

```
ssl_cert tentacle_cert
ssl_ca ca_cert
ssl_key tentacle_key
```

Configuración permanente — EndPoint y Servidor satélite:

```
server_opts -e tentacle_client_cert -k tentacle_client_key
```

**4. Verificación mutua** (servidor y cliente verifican el certificado del
otro contra una CA):

Prueba manual:

```sh
tentacle_server -v -e tentacle_cert -k tentacle_key -f ca_cert -s /tmp
tentacle_client -v \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -f ca_cert \
  -a <servidor> fichero
```

Configuración permanente — servidor:

```
ssl_cert tentacle_cert
ssl_ca ca_cert
ssl_key tentacle_key
```

Configuración permanente — EndPoint y Servidor satélite:

```
server_opts -e tentacle_client_cert -k tentacle_client_key -f ca_cert
```

En todos los casos, las rutas de certificados y claves deben ser
**absolutas** en los ficheros de configuración, y el paquete `IO::Socket::SSL`
tiene que estar instalado para usar TLS con la implementación Perl. TLS
exige, como mínimo, la versión 1.2.

Para producción, la combinación recomendada es la 4 (verificación mutua),
con contraseña añadida de forma opcional: es la única de las cuatro en la
que ambos extremos comprueban la identidad del otro contra una CA.

`retries`/`timeout` (`-r`/`-t`) no son solo parámetros de red: al limitar
los reintentos y el tiempo de espera de cada conexión, también dificultan
un ataque de fuerza bruta contra la contraseña. El log del servidor
(`-l`/`log_file`, con el detalle que dan `-v`/`-V`) es, además de
diagnóstico, el registro de auditoría de las conexiones.

### Guía rápida de certificados OpenSSL

Para generar los certificados que usan los ejemplos anteriores.

Crear una CA propia:

```sh
mkdir demoCA demoCA/newcerts demoCA/private
openssl req -new -x509 -keyout cakey.pem -out cacert.pem
mv cakey.pem demoCA/private/
mv cacert.pem demoCA/
```

Petición de certificado y firma con esa CA:

```sh
openssl req -new -keyout tentaclekey.pem -out tentaclereq.pem -days 360
cat tentaclereq.pem tentaclekey.pem > tentaclenew.pem
touch demoCA/index.txt
echo "01" >> demoCA/serial
openssl ca -out tentaclecert.pem -in tentaclenew.pem
```

Certificado autofirmado, sin CA:

```sh
openssl req -new -x509 -keyout tentaclekey.pem -out tentaclecert.pem -days 360
```

Clave RSA sin contraseña (evita tener que introducirla en el lado cliente):

```sh
openssl genrsa -out tentaclekey.pem
```

Exportar un certificado PEM a DER (necesario en algunos sistemas):

```sh
openssl x509 -outform der -in tentaclecert.pem -out tentaclecert.der
```

### Windows

En Windows, el servidor se gestiona como servicio con
`tentacle_server -S install|uninstall|run`; la opción `-d` (demonio Unix) no
está disponible en esta plataforma.
