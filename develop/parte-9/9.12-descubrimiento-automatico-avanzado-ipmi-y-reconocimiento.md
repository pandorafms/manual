# Descubrimiento automático avanzado: IPMI y tareas de reconocimiento personalizadas

El escaneo de red de Discovery resuelve la mayoría de los casos, pero no todos.
Cuando el activo habla un protocolo que el escaneo no entiende, o cuando hay que
dar de alta agentes y módulos con una lógica propia, Discovery deja ejecutar un
script. Este capítulo explica ese mecanismo y lo recorre de principio a fin con
IPMI, que es el ejemplo que viene de fábrica.

## Qué es el descubrimiento avanzado

Pandora FMS descubre activos por tres vías. Conviene elegir la adecuada antes de
escribir nada:

| Vía | Qué ejecuta | Cuándo usarla | Dónde se explica |
|---|---|---|---|
| Escaneo de red (Network scan) | El motor heurístico de Discovery, con SNMP, WMI y comandos remotos | Redes de propósito general, equipos con SNMP o WMI | 2.4 |
| Tarea de reconocimiento personalizada (Custom network scan) | Un script registrado por el usuario | Protocolos o inventarios que no cubre el escaneo, o altas con reglas propias | Este capítulo |
| Paquete `.disco` (Applications, Cloud y Custom) | Un plugin de Discovery con sus propios pasos | Integraciones de fabricante o de nube ya empaquetadas | 2.3 y 9.7 |

Las dos primeras se crean desde **Discovery → Host & Devices**. La tercera se
instala como paquete y añade sus propias secciones al menú de Discovery. No son
intercambiables: un paquete `.disco` trae la lógica hecha; una tarea
personalizada te obliga a escribirla, pero no impone un modelo de datos. El
escaneo de red se explica en [2.4](../parte-2/2.4-descubrimiento-de-redes-con-host-y-dispositivos.md);
los paquetes `.disco`, en [2.3](../parte-2/2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md)
y [9.7](../parte-9/9.7-creacion-de-plugins-de-discovery.md).

Crear o editar tareas exige permiso **AW**. Registrar los scripts exige **PM**,
porque el script se ejecuta en el servidor Discovery con los privilegios de ese
servicio.

## Tareas de reconocimiento personalizadas

### Registrar el script

El script se registra antes de crear la tarea, en **Management → Discovery →
Host & Devices → Manage scan scripts** (en la consola en español, «Gestionar
scripts de escaneo»). Cada script declara dónde está y qué datos necesita:

| Campo | Qué indica |
|---|---|
| Name | Nombre con el que aparecerá en el selector de scripts. |
| Script full path | Ruta absoluta del ejecutable en el servidor Discovery. |
| Description | Texto que se muestra como «Explanation» al crear la tarea. |
| Macro | Cada dato que el script necesita: descripción, valor por defecto, ayuda y, si es una credencial, «Hide value». |

Las macros se numeran solas (`_field1_`, `_field2_`…) y se pasan al script en
ese orden. «Hide value» convierte el campo en contraseña al crear la tarea; no
cifra el valor, solo lo oculta en pantalla. La descripción admite varias líneas
y se muestra como explicación general. Cada macro muestra además su propio
texto de ayuda como tooltip en el segundo paso, así que conviene repartir la
información: el formato común en la descripción y el de cada dato en su ayuda.

Un script propio debe ser ejecutable en el servidor Discovery: ruta absoluta,
permiso de ejecución y, si es un intérprete, la primera línea con el *shebang*
correspondiente. Los scripts internos, como IPAM, no se pueden editar desde esta
pantalla; el script IPMI Recon sí, aunque no hace falta tocarlo. El script
interno de IPAM se explica en [3.7](../parte-3/3.7-gestion-de-ip-ipam.md).

### Crear la tarea

La tarea se crea en **Management → Discovery → Host & Devices → Custom network
scan** («Escaneo de red personalizado»). El asistente tiene dos pasos. En el
primero se definen los datos comunes:

| Campo | Qué indicar |
|---|---|
| Task name | Nombre de la tarea. Debe ser único. |
| Comment | Descripción libre para identificar la tarea en la lista. |
| Discovery server | Servidor que ejecutará el script. Debe ser un servidor de tipo Discovery y estar activo; si no se elige, la tarea no se ejecuta nunca. |
| Group | Grupo al que se asignan los agentes que cree el script. |
| Interval | `Defined` para una periodicidad fija o `Manual` para ejecutarla solo a demanda. La consola recomienda no bajar de 5 minutos. |
| Generate event on error | Genera un evento si la tarea termina en error. |
| Execute alert action on error | Ejecuta una o varias acciones de alerta en ese mismo caso. |

Los dos últimos campos están en la pestaña **Actions**. Se guardan con la tarea,
pero el error no se deduce del código de salida del script: el estado lo fija el
propio script (ver «Qué recibe el script y qué debe hacer»).

En el ejemplo de este capítulo se usa una tarea llamada «IPMI datacenter A»,
sobre el grupo «Servers» y con un intervalo de 30 minutos.

![Primer paso de una tarea de escaneo de red personalizado con nombre, servidor Discovery, grupo e intervalo](../../assets/img/parte-09/custom-network-scan-definition.png)

El segundo paso elige el script y rellena sus macros:

![Segundo paso de la tarea con IPMI Recon seleccionado y sus cuatro parámetros](../../assets/img/parte-09/custom-network-scan-script.png)

Al terminar, la tarea aparece en **Discovery → Task list**, pestaña **Host &
devices tasks**. No aparece en **Custom tasks**: esa pestaña es para las tareas
de un paquete `.disco` de la sección Custom, que son otra cosa.

### Qué recibe el script y qué debe hacer

El servidor ejecuta la ruta registrada con tres bloques de argumentos, en este
orden:

1. El identificador de la tarea.
2. El identificador del grupo.
3. El valor de cada macro, en el orden en que se definieron.

Para la tarea de ejemplo, la línea de ejecución queda así:

```text
/usr/bin/perl /usr/share/pandora_server/util/recon_scripts/ipmi-recon.pl "12" "2" "192.168.100.0/24" "monitor" "s3cret" "-D LAN_2_0"
```

El script de fábrica está registrado para usar el intérprete Perl del servidor,
así que el servidor antepone `/usr/bin/perl` (o el que indique `PERL5BIN_PERL`,
con las opciones de `PERL5_OPT`). Un script propio ejecutable se lanza sin
intérprete añadido.

El servidor **no interpreta la salida** del script. No crea agentes ni módulos a
partir de lo que el script escriba en la salida estándar: el script tiene que dar
de alta sus propios hallazgos, por la API v2 (ver [13.1](../parte-13/13.1-primeros-pasos-y-autenticacion.md) y la [referencia de endpoints](../parte-13/13.4-referencia-de-endpoints/index.md))
o enviando su propio XML de datos. La salida solo se conserva para diagnóstico,
y solo cuando el servidor trabaja con `verbosity 10`: se guarda el comando en
`<directorio de logs>/discovery/task.<id>.cmd` y la salida en
`task.<id>.out`, junto a los logs del servidor.

!!! warning "La contraseña queda en el log del comando"
    Con `verbosity 10`, el servidor guarda en `discovery/task.<id>.cmd` la
    línea de comandos completa, con los valores de las macros y por tanto la
    contraseña. El fichero `.out` contiene solo la salida del script. Protege
    el directorio de logs y no dejes `verbosity 10` activo de forma permanente
    en producción.

El estado de la tarea tampoco se deduce del código de salida. Un `exit 1` no
marca la tarea como fallida ni dispara por sí solo las acciones de error: el
script es quien deja el estado que corresponda. Por eso conviene que el script
registre sus propios errores y que la tarea se compruebe por su resultado, no
solo por el estado que muestra la lista.

## Reconocimiento IPMI

IPMI (**Intelligent Platform Management Interface**) es la interfaz con la que
las placas base y las controladoras de gestión exponen temperatura, voltaje,
ventiladores, alimentación y otros sensores, aunque el sistema operativo no esté
arrancado. Pandora FMS lo monitoriza con un plugin y lo descubre con un script
de reconocimiento que viene registrado de fábrica.

### Requisitos

| Requisito | Detalle |
|---|---|
| FreeIPMI | El plugin usa `ipmi-sensors` y el script de descubrimiento usa `ipmiping` e `ipmi-sensors`. En RHEL, Rocky Linux y derivados se instala con `dnf install freeipmi`; en Debian y Ubuntu, con `apt install freeipmi-tools`. |
| Red | El servidor Discovery debe alcanzar la controladora por RMCP, UDP 623. Abrir el puerto en el cortafuegos del servidor y en el de la red del equipo. |
| Credenciales | Usuario y contraseña IPMI con permiso de lectura de sensores. Las credenciales por defecto del fabricante no siempre sirven. |
| Servidor Discovery | La tarea se ejecuta en un servidor de tipo Discovery, con `reconserver` o `discoveryserver` activo (ver [9.3](../parte-9/9.3-referencia-completa-de-configuracion-del-servidor.md)). |
| Plugin IPMI Plugin | Debe existir con ese nombre exacto. Viene registrado de fábrica y no se puede borrar; si se renombra, el script deja de encontrar el plugin con el que crea los módulos. |
| Permisos | AW para crear la tarea; PM para registrar o editar scripts. |

### El plugin y el script de fábrica

Hay dos piezas y conviene no confundirlas:

- **IPMI Plugin** lee un sensor concreto. Es el plugin que ejecutan los módulos
  que se crean después.
- **IPMI Recon** barre una red, detecta las controladoras y crea los agentes y
  los módulos. Es el script que se selecciona en la tarea.

El plugin declara cinco macros:

| Macro | Contenido |
|---|---|
| Target IP | Dirección de la controladora IPMI. |
| Username | Usuario IPMI. |
| Password | Contraseña; se guarda oculta. |
| Sensor | Identificador del sensor que se quiere leer. |
| Additional Options | Opciones adicionales para `ipmi-sensors`, por ejemplo `-D LAN_2_0`. |

El script IPMI Recon declara cuatro:

| Macro | Contenido |
|---|---|
| Network | Red que se quiere barrer, por ejemplo `192.168.100.0/24`. |
| Username | Usuario IPMI que se usará en todos los equipos encontrados. |
| Password | Contraseña IPMI; se guarda oculta. |
| Additional parameters | Opciones adicionales para `ipmi-sensors`, por ejemplo `-D LAN_2_0` para forzar IPMI 2.0. |

La opción `-D LAN_2_0` cambia el driver que usa `ipmi-sensors`; no cambia el
barrido de la red, que se hace con `ipmiping` (IPMI 1.5). Si la controladora
solo responde a IPMI 2.0, puede que el equipo no aparezca en el barrido aunque
la lectura funcione a mano.

El plugin ejecuta `ipmi-sensors` con el sensor indicado y devuelve el valor. Si
el sensor no tiene valor numérico, devuelve el *event bitmask* convertido a
decimal, que es la forma de representar los estados discretos de IPMI. El script
de descubrimiento ejecuta `ipmi-sensors` con umbrales y unidades completas para
poder crear los módulos con sus límites.

El script de fábrica está registrado para ejecutarse con el Perl del servidor
(`use_server_perl`), así que el servidor lo lanza con `/usr/bin/perl` y no exige
permiso de ejecución al fichero.

### Crear la tarea IPMI

El procedimiento es el mismo que el de cualquier tarea personalizada:

1. Abre **Management → Discovery → Host & Devices → Custom network scan**.
2. Rellena el nombre, el comentario, el servidor Discovery, el grupo y el
   intervalo. En el ejemplo: «IPMI datacenter A», grupo «Servers», 30 minutos.
3. Pasa al segundo paso y selecciona **IPMI Recon**. No selecciones un plugin:
   el script lo usa por debajo.
4. Rellena la red, el usuario y la contraseña de las controladoras. Añade
   `-D LAN_2_0` en «Additional parameters» solo si tus equipos lo necesitan.
5. Pulsa **Finish**.

La tarea queda programada. Con intervalo manual, se lanza a demanda desde la
lista de tareas con la acción de ejecución forzada.

### Qué agentes y módulos crea

El script recorre la red con `ipmiping`. Por cada dirección que responde:

1. Resuelve el nombre por DNS inverso. Si no hay nombre, usa la dirección IP.
2. Busca un agente con ese nombre. Si no existe, lo crea con el grupo de la
   tarea, sistema operativo **Network** e intervalo de 300 segundos.
3. Genera un evento de detección con el texto
   `[RECON] New Intel DCM host [nombre] detected on network [red]`.
4. Ejecuta `ipmi-sensors` contra la controladora y crea un módulo por cada
   sensor que devuelve la herramienta, con el nombre «Tipo: Sensor» (por
   ejemplo, «Temperature: CPU Temp») y la unidad que corresponda.

Los módulos son de tipo plugin y usan **IPMI Plugin**, así que cada uno vuelve a
leer su sensor en cada intervalo del agente. El tipo de módulo y los umbrales
dependen del tipo de sensor:

| Familia | Ejemplos | Módulo | Umbrales |
|---|---|---|---|
| Numéricos | Temperatura, voltaje, corriente, ventilador, refrigeración | Numérico (`generic_data`) | Copia los umbrales del sensor: aviso y crítico, invertidos para avisar al salir del rango. |
| Bandera | Seguridad física, intento de violación, firmware, interrupción crítica, error de arranque | Numérico (`generic_data`) | Umbral crítico preparado para el valor de alerta. |
| Compuestos | Procesador, fuente de alimentación, memoria, watchdog, LAN, batería | Numérico (`generic_data`) | Sin umbrales. |
| Texto | Ranura, placa, chasis, FRU, sesión, cambio de versión, `OEM Reserved` | Texto (`generic_data_string`) | Sin umbrales. |

Un tipo que no aparezca en la tabla no se descarta: el script crea el módulo con
la rama genérica que corresponda, y conviene revisar el resultado en el agente.

Mientras recorre la red, el script actualiza el estado de la tarea con el
porcentaje de progreso. Al terminar, deja el estado interno en terminado (-1),
pero no escribe el resumen de ejecución; la lista puede seguir mostrando
«Pendiente» aunque la ejecución haya acabado. Solo muestra «Hecho» cuando el
resumen no está vacío.

Un detalle importante: el script solo crea módulos cuando crea el agente. Si el
agente ya existe, no añade los sensores que falten. Para incorporar sensores
nuevos hay que añadirlos a mano o borrar el agente y volver a ejecutar la tarea.

### Sensores OEM y límites

Los sensores OEM no tienen un tipo estándar en `ipmi-sensors`, pero el
descubrimiento no los descarta: crea un módulo por cada sensor que devuelve la
herramienta. `OEM Reserved` se trata como texto (`generic_data_string`); un
tipo que no esté en la tabla se crea con el módulo genérico que aplica el
script. Si el valor necesita un comando OEM específico (`ipmi-oem`), se añade a
mano como módulo de plugin; el procedimiento está en
[9.9](../parte-9/9.9-creacion-de-plugins-remotos.md).

Antes de dejarlo programado, conviene comprobar estos límites:

- El barrido usa `ipmiping` (IPMI 1.5). Las opciones adicionales solo afectan a
  `ipmi-sensors`; un equipo que solo responda a IPMI 2.0 puede no ser detectado.
- Si las credenciales no son válidas, el equipo se detecta igual porque responde
  al ping IPMI, pero el agente se crea sin módulos. Prueba la lectura a mano
  antes de crear la tarea.
- Reejecutar la tarea sobre un agente existente no añade módulos nuevos.
- Solo se crean los sensores que devuelve `ipmi-sensors`; el registro de eventos
  (SEL), el inventario FRU y otros datos IPMI no forman parte del
  descubrimiento.

Para la monitorización remota en general, y para el resto de comprobaciones de
red, consulta [2.6](../parte-2/2.6-monitorizacion-de-redes.md). Para el
diagnóstico de una tarea que no produce lo esperado, sigue con el apartado
siguiente o con [9.13](../parte-9/9.13-troubleshooting-con-pandora.md).

## Escribir un script de reconocimiento propio

Un script propio puede estar escrito en cualquier lenguaje que el servidor
pueda ejecutar. Lo importante es cumplir el contrato:

- **Ejecutable**: ruta absoluta, permiso de ejecución y *shebang* si es un
  script interpretado. El servidor lo lanza tal cual, salvo que esté registrado
  para usar el Perl del servidor, como IPMI Recon, en cuyo caso antepone
  `/usr/bin/perl`.
- **Argumentos en orden**: identificador de la tarea, identificador del grupo y
  valores de las macros. Los valores pueden llegar vacíos; valida antes de usar.
- **Sin depender de la salida**: el servidor no lee lo que imprimas. Da de alta
  los agentes y módulos por la API ([13.4](../parte-13/13.4-referencia-de-endpoints/index.md))
  o enviando tu propio XML.
- **Idempotente**: antes de crear un agente, comprueba si ya existe; antes de
  crear un módulo, comprueba si ya está. Así puedes repetir la tarea sin
  duplicar nada.
- **Con estado propio**: deja la tarea en el estado que corresponda. El código
  de salida no basta para que la lista la marque como fallida.
- **Sin secretos en la salida**: las credenciales llegan como argumentos; no las
  imprimas en la salida ni las escribas en ficheros. Ten en cuenta que la línea
  de comandos queda en el `.cmd` con `verbosity 10` (ver el aviso anterior).

Un esqueleto mínimo en Bash:

```bash
#!/bin/bash
set -euo pipefail

task_id="$1"
group_id="$2"
network="$3"
username="$4"
password="$5"
extra="${6:-}"

# 1. Descubre los equipos de $network.
# 2. Por cada equipo, comprueba si el agente existe y créalo si falta.
# 3. Crea o actualiza sus módulos.
# 4. Registra los errores y deja la tarea en el estado correcto.
```

El alta de agentes y módulos se hace con la API; el detalle de los endpoints y
de la autenticación está en [13.1](../parte-13/13.1-primeros-pasos-y-autenticacion.md).
Este formulario no tiene un selector de credenciales del gestor de
[2.2](../parte-2/2.2-gestor-de-credenciales.md): las credenciales que necesite
el script se pasan como macros. Si el script quiere consultar el gestor por su
cuenta, tendría que hacerlo desde su propio código, fuera del alcance de este
capítulo.

## Diagnóstico

Cuando la tarea termina pero no hay agentes, o los agentes no tienen módulos, el
problema suele estar en una de estas comprobaciones:

| Síntoma | Qué comprobar |
|---|---|
| La tarea no crea ningún agente | Que el servidor Discovery exista y esté activo; que el script tenga permiso de ejecución; que la red sea alcanzable desde ese servidor. |
| El equipo no aparece en el barrido | `ipmiping` contra la dirección; UDP 623; que la controladora no sea solo IPMI 2.0. |
| El agente aparece sin módulos | Credenciales IPMI; que `ipmi-sensors` devuelva sensores a mano; que el plugin conserve el nombre «IPMI Plugin». |
| La tarea sigue en «Pendiente» aunque haya terminado | El script de fábrica no escribe el resumen de ejecución; sin resumen, la lista no muestra «Hecho». Comprueba la fecha de actualización y los agentes creados. |
| El script no se ejecuta | Ruta completa, permiso de ejecución y *shebang*; revisa el log del servidor. |
| No hay rastro de la ejecución | Sube `verbosity` a 10 de forma temporal y busca `task.<id>.cmd` y `task.<id>.out` en el directorio `discovery/` de los logs; el `.cmd` contendrá las credenciales. |

Dos comprobaciones manuales que ahorran la mitad del diagnóstico:

```sh
ipmiping 192.168.100.10 -c 2 -t 1
ipmi-sensors -h 192.168.100.10 -u monitor -p 'contraseña' -D LAN_2_0 \
  --ignore-not-available-sensors
```

La primera dice si el equipo responde al descubrimiento. La segunda, si las
credenciales y el driver son correctos y qué sensores se van a crear. Si la
segunda falla, la tarea creará el agente pero no los módulos.

Para el diagnóstico general de la monitorización remota, continúa en
[9.13](../parte-9/9.13-troubleshooting-con-pandora.md).
