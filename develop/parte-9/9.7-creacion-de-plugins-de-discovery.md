# Creación de plugins de discovery

Un plugin de Discovery es un paquete `.disco`: un ZIP con un formulario y los ejecutables que hay detrás. La consola pinta el formulario, el servidor ejecuta los comandos y, si el script devuelve datos, aparecen agentes y módulos como si alguien los hubiera dado de alta a mano. Lo difícil no es el ZIP, sino el contrato: qué campos se declaran, qué recibe el script y qué JSON tiene que devolver. Eso es lo que se documenta aquí.

Este capítulo es la referencia de autoría de paquetes `.disco`. El uso de Discovery, la creación de tareas y su ciclo de vida están en [2.3 · Monitorización y descubrimiento automático con Discovery](../parte-2/2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md). Los plugins de servidor locales y remotos, que no tienen nada que ver con esto, están en [9.8 · Creación de plugins locales](9.8-creacion-de-plugins-locales.md) y [9.9 · Creación de plugins remotos](9.9-creacion-de-plugins-remotos.md).

## Qué es un paquete `.disco` y qué no

Un paquete `.disco` es un fichero ZIP renombrado. Dentro va, como mínimo, un `discovery_definition.ini`; opcionalmente, un `logo.png` y todos los scripts, ejecutables y librerías que necesite el plugin. La consola lee el INI, valida la definición, guarda los metadatos y pinta el asistente de creación de tareas. El servidor Discovery recibe los ejecutables y lanza los comandos que declara el paquete con los valores que el usuario rellenó en el formulario.

La diferencia con otras extensiones de Pandora FMS conviene tenerla clara antes de empezar:

| Extensión | Qué añade | Dónde se documenta |
|---|---|---|
| Paquete `.disco` | Un asistente de Discovery: formulario y ejecutables que crean agentes y módulos. | Este capítulo. |
| Plugin local | Un comando que ejecuta el servidor de plugins en la máquina donde está el servidor. | 9.8. |
| Plugin remoto | Un comando que ejecuta el servidor de plugins contra un sistema remoto. | 9.9. |
| Extensión de consola | Una página o acción nueva dentro de la consola web. | 9.10. |

Un paquete `.disco` no instala nada en la máquina monitorizada. No despliega un EndPoint ni deja ficheros allí: consulta lo que haya (una API, una base de datos, un hipervisor) y trae los datos a Pandora FMS. La creación de la tarea, su intervalo, su servidor y sus alertas son cosa de [2.3](../parte-2/2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md); aquí solo se construye el paquete que esa tarea ejecuta.

## Requisitos

| Requisito | Detalle |
|---|---|
| Formato | Fichero ZIP con extensión `.disco`. La consola rechaza cualquier otra extensión. |
| Definición | `discovery_definition.ini` en la raíz del ZIP, no dentro de una carpeta. |
| Sintaxis | Formato INI de PHP: secciones entre corchetes, arrays con claves y comentarios con `;`. |
| `short_name` | Único, con letras, números, puntos, signos de guion y guion bajo. El prefijo `pandorafms.` está reservado para los paquetes oficiales. |
| Sección | `app`, `cloud` o `custom`. Es la pestaña de Discovery donde aparecerá el asistente. |
| Ejecución | Al menos un `exec`. Los ejecutables propios se declaran en `execution_file`. |
| Entorno | El intérprete y las librerías que use el script deben existir en el servidor Discovery; el paquete no los instala. |
| Permisos | Usuario administrador para subir y gestionar paquetes en **Discovery → Manage disco packages**. |
| Servidor | Un servidor Discovery activo para ejecutar las tareas, con sus tokens configurados (ver [9.3](9.3-referencia-completa-de-configuracion-del-servidor.md)). |
| Versión | Cadena de versión declarada y visible en la consola; conviene incrementarla en cada cambio. |

Nada de esto depende de una licencia Enterprise. La creación de paquetes `.disco` funciona igual en cualquier edición; los paquetes oficiales que tengan condiciones propias, como el de SAP, las aplican al ejecutarse, no al empaquetarse.

## Anatomía del paquete

Un paquete mínimo tiene esta pinta:

```text
example.http.disco
├── discovery_definition.ini
├── logo.png                  (opcional)
└── demo_http.py
```

El `discovery_definition.ini` es el contrato. El `logo.png` es opcional: si falta, la consola usa un icono genérico. Los scripts y librerías se referencian con rutas relativas al raíz del paquete. No conviene usar rutas absolutas: el paquete se copia a otro directorio y dejaría de funcionar.

La consola guarda la definición y el logo, y copia los ejecutables a los servidores Discovery. En el servidor, los ficheros declarados en `execution_file` se resuelven en `<incomingdir>/discovery/<short_name>/`, y la consola les da permiso de ejecución. Por eso todo lo que se vaya a ejecutar debe estar declarado en `execution_file` o en los scripts de contraseña; un script que no aparezca ahí puede copiarse, pero no se le aplicará el permiso de ejecución.

El INI y el logo no se copian al servidor: la definición viaja por la base de datos de la consola y el servidor solo necesita los ejecutables. Si un paquete aparece en la lista pero sus ficheros no están en el servidor, el botón de sincronizar de **Manage disco packages** vuelve a copiarlos (ver [2.3](../parte-2/2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md)).

## El fichero `discovery_definition.ini`

El INI se organiza en bloques. Tres son fijos y el resto son bloques de campos, selectores o árboles con el nombre que elija el autor:

| Bloque | Obligatorio | Para qué |
|---|---|---|
| `discovery_extension_definition` | Sí | Metadatos, ejecutables y ejecuciones del plugin. |
| `config_steps` | No | Pasos del formulario de la tarea. |
| `tempfile_confs` | No | Ficheros de configuración temporales para las ejecuciones. |
| Bloques de campos (`custom_fields`) | Si se referencian | Campos de cada paso. |
| Bloques `custom_select` y `custom_tree_data` | Si se referencian | Opciones y árboles propios. |

Dentro del INI se usan **macros**: claves de texto que empiezan y terminan con guion bajo y que solo contienen letras y números, por ejemplo `_url_` o `_param1_`. Una macro válida cumple `_…_`; los signos de guion, los puntos o los espacios no valen dentro del nombre. Al ejecutar, la macro se sustituye por su valor.

Los valores admiten los tipos habituales del INI de PHP: `STRING` para texto, `NUMBER` para números, `BOOL` para `true`/`false`, `1`/`0` o `yes`/`no`, y `VALUE` para cualquiera de ellos. En los arrays, `VALUE_N` indica que el valor puede repetirse. Las cadenas con espacios o caracteres especiales van entre comillas.

### Bloque `discovery_extension_definition`

| Parámetro | Obligatorio | Qué hace |
|---|---|---|
| `short_name` | Sí | Identificador único del paquete. Solo letras, números, puntos, signos de guion y guion bajo. El prefijo `pandorafms.` está reservado para los paquetes oficiales. |
| `section` | Sí | Sección de la consola: `app` (Applications), `cloud` (Cloud) o `custom` (Custom). |
| `name` | Sí | Nombre visible del asistente. |
| `version` | Sí | Versión visible. Se recomienda cambiarla en cada modificación, por pequeña que sea. |
| `description` | No | Descripción visible en la lista de paquetes. |
| `execution_file` | No | Array de scripts y ejecutables del paquete. La clave es una macro válida y el valor, una ruta relativa. La consola les da permiso de ejecución. |
| `exec` | Sí | Array de comandos que ejecuta el servidor. Al menos uno. Se ejecutan en orden y cada uno produce su propio resumen. |
| `passencrypt_script` | No | Ruta relativa al script que cifra contraseñas desde la consola. |
| `passencrypt_exec` | No | Comando de cifrado. Solo admite las macros `_passencrypt_script_` y `_password_`. |
| `passdecrypt_script` | No | Ruta relativa al script que descifra contraseñas desde la consola. |
| `passdecrypt_exec` | No | Comando de descifrado. Solo admite las macros `_passdecrypt_script_` y `_password_`. |
| `default_value` | No | Valores por defecto de las macros del formulario. La clave es la macro y el valor depende del tipo de campo. |

Un esqueleto mínimo:

```ini
[discovery_extension_definition]
short_name = example.http
section = custom
name = Example HTTP
version = "1.0"
description = "Checks an HTTP endpoint and creates an agent with two modules"

execution_file[_exec1_] = "demo_http.py"
exec[] = "'_exec1_' --conf '_tempConf_'"
```

`execution_file` y `exec` son arrays: se pueden declarar varias entradas con claves distintas, y `exec` las usa en el orden en que aparecen. Las rutas de `execution_file` se sustituyen por la ruta real del fichero en el servidor; por eso conviene rodearlas de comillas en `exec`, sobre todo si la ruta puede contener espacios.

`default_value` admite un valor por tipo de campo:

| Tipo de campo | Valor por defecto |
|---|---|
| `string` | Texto. |
| `number` | Número. |
| `password` | Texto. |
| `textarea` | Texto. |
| `checkbox` | `true` o `false`. |
| `select` | Un valor de la lista. |
| `multiselect` | Array JSON con los valores seleccionados, por ejemplo `["a","b"]`. |
| `tree` | Array JSON con los valores seleccionados. |

No pongas contraseñas reales en `default_value`: el valor por defecto se guarda como un valor más de la tarea y no pasa por el cifrado del formulario. Para secretos, usa un campo de tipo `password` con `encrypt_on_true` o un selector de credenciales.

Los parámetros `passencrypt_*` y `passdecrypt_*` los usa la consola, no el servidor. `passencrypt_exec` se ejecuta al guardar el formulario para convertir el texto en el valor cifrado; `passdecrypt_exec` se ejecuta al volver a mostrar el campo para recuperar el texto. El servidor recibe el valor guardado, es decir, el cifrado si el campo se cifró, así que el plugin tiene que saber descifrarlo. Si el paquete no incluye esa lógica, no marques el campo para cifrar.

### Macros del servidor

Además de las macros del formulario, el servidor sustituye estas claves en las ejecuciones:

| Macro | Valor |
|---|---|
| `__taskMD5__` | MD5 del identificador de la tarea. Útil para generar nombres de fichero únicos. |
| `__taskInterval__` | Intervalo de ejecución de la tarea, en segundos. |
| `__taskCron__` | Expresión cron de la tarea, o vacío si no usa cron. |
| `__taskGroup__` | Nombre del grupo de la tarea. |
| `__taskGroupID__` | Identificador del grupo de la tarea. |
| `__temp__` | Directorio temporal configurado en el servidor. |
| `__incomingDir__` | Directorio de entrada de datos del servidor. |
| `__consoleAPIURL__` | URL de la API de la consola. |
| `__consoleAPIPass__` | Contraseña de la API de la consola. |
| `__consoleUser__` | Usuario de la consola configurado en el servidor. |
| `__consolePass__` | Contraseña de ese usuario. |
| `__pandoraServerConf__` | Ruta completa al fichero `pandora_server.conf`. |

Estas macros solo se sustituyen en las ejecuciones del servidor. Los comandos de `script_data_fields`, que ejecuta la consola para construir formularios dinámicos, no las reciben.

## Pasos de configuración (`config_steps`)

El bloque `config_steps` define los pasos que verá el usuario después del primer paso común de la tarea. Cada paso tiene un nombre y una fuente de campos:

| Parámetro | Obligatorio | Qué hace |
|---|---|---|
| `name` | Sí | Nombre del paso. |
| `script_data_fields` | Sí, si el paso no tiene `custom_fields` | Comando que ejecuta la consola para obtener los campos del paso en JSON. |
| `custom_fields` | Sí, si el paso no tiene `script_data_fields` | Nombre del bloque de campos que se muestra en el paso. |
| `fields_columns` | No | Número de columnas del formulario: `1` o `2`. Por defecto, `2`. |

Las claves de este bloque son posicionales: si se indican, deben ser numéricas y distintas de 0; en la práctica, se numeran desde 1. Si un paso declara las dos fuentes, la consola muestra primero los campos devueltos por `script_data_fields` y después los de `custom_fields`.

```ini
[config_steps]
name[1] = Endpoint
custom_fields[1] = endpoint
fields_columns[1] = 1

name[2] = Options
script_data_fields[2] = "'_exec1_' --fields '_url_'"
```

El comando de `script_data_fields` se ejecuta en la consola, no en el servidor. La consola sustituye las macros de `execution_file` por su ruta real, le pasa los valores ya rellenados en los pasos anteriores y espera un **array JSON de objetos**, aunque solo haya un campo:

```json
[
  {
    "macro": "_mode_",
    "name": "Mode",
    "type": "select",
    "mandatory_field": false,
    "select_data": {
      "basic": "Basic",
      "full": "Full"
    }
  }
]
```

Las claves de cada objeto son las mismas que las de un campo estático, con dos diferencias: `select_data` es un objeto `valor: texto` y `tree_data` es un array de nodos, no el nombre de un bloque. Si el comando falla o devuelve algo que no es JSON, el paso muestra el error del script en lugar de los campos. Si devuelve un objeto con una única clave `error`, la consola muestra ese mensaje como error.

## Campos del formulario (`custom_fields`)

Cada bloque de campos se referencia desde un paso con `custom_fields`. Su nombre es libre, siempre que coincida con la referencia:

```ini
[endpoint]
macro[1] = _url_
name[1] = URL
type[1] = string
placeholder[1] = "http://192.0.2.10/"
```

| Parámetro | Obligatorio | Qué hace |
|---|---|---|
| `macro` | Sí | Macro donde se guarda el valor. Formato `_…_`, solo letras y números. |
| `mandatory_field` | No | `false` para que el campo sea opcional. Si se omite, el campo es obligatorio. |
| `name` | Sí | Etiqueta visible del campo. |
| `tip` | No | Texto de ayuda que se muestra junto a la etiqueta. |
| `type` | Sí | Tipo de control: `string`, `number`, `password`, `textarea`, `checkbox`, `select`, `multiselect` o `tree`. |
| `placeholder` | No | Texto de ejemplo dentro del campo, para `string` y `textarea`. |
| `show_on_true` | No | Macro de una casilla; el campo solo se muestra cuando esa casilla está activa. |
| `encrypt_on_true` | No | Macro de una casilla; el campo de contraseña se cifra al guardar cuando esa casilla está activa. |
| `select_data` | Sí para `select` y `multiselect` | Nombre de un bloque `custom_select` o uno de los selectores de Pandora. |
| `tree_data` | Sí para `tree` | Nombre de un bloque `custom_tree_data`. |

Los ocho tipos y lo que genera cada uno:

| `type` | Control | Valor que guarda |
|---|---|---|
| `string` | Caja de texto de una línea. | Texto. |
| `number` | Caja numérica. | Número. |
| `password` | Caja enmascarada. | Texto; puede cifrarse. |
| `textarea` | Caja de varias líneas. | Texto, con saltos de línea. |
| `checkbox` | Interruptor sí/no. | Booleano (`1` o `0`). |
| `select` | Desplegable de una opción. | Un valor. |
| `multiselect` | Selector múltiple. | Array JSON con los valores elegidos. |
| `tree` | Árbol de varios niveles. | Array JSON con los valores elegidos. |

Dos avisos que ahorran disgustos. El primero: la clave que lee la consola es `mandatory_field`; `required_field`, que aparece en ejemplos antiguos, se ignora y el campo queda obligatorio. El segundo: aunque `mandatory_field` sea `true`, los campos `multiselect` y `tree` aceptan que no se seleccione nada; la validación de obligatorio no se aplica a listas vacías.

`show_on_true` y `encrypt_on_true` apuntan a la macro de una casilla del mismo formulario. La casilla puede estar en otro paso, pero debe existir. Si la macro no existe o no es una casilla, el campo no se comporta como se espera.

## Selectores con datos de Pandora

Los campos `select` y `multiselect` pueden usar datos de la propia consola. El valor que se guarda en la tarea y el que recibe el script no siempre son el mismo:

| `select_data` | El selector muestra | Guarda | El script recibe |
|---|---|---|---|
| `agent_groups` | Nombres de grupos de agentes. | ID del grupo. | Nombre del grupo, o vacío si no existe. |
| `agents` | Alias de agentes. | Nombre del agente. | Nombre del agente, o vacío si no existe. |
| `module_groups` | Nombres de grupos de módulos. | ID del grupo. | Nombre del grupo, o vacío. |
| `modules` | Nombres de módulos. | Nombre del módulo. | Nombre del módulo, o vacío. |
| `module_types` | Descripciones de tipos de módulo. | Nombre del tipo. | Nombre del tipo. |
| `status` | Nombres de estados. | Constante del estado. | Constante del estado. |
| `tags` | Etiquetas. | ID de la etiqueta. | Nombre de la etiqueta, o vacío. |
| `alert_templates` | Plantillas de alerta. | ID de la plantilla. | Nombre de la plantilla, o vacío. |
| `alert_actions` | Acciones de alerta. | ID de la acción. | Nombre de la acción, o vacío. |
| `interval` | Selector de intervalo. | Segundos. | Segundos. |
| `credentials.custom` | Credenciales personalizadas. | ID de la credencial. | JSON en base64 con `user` y `password`. |
| `credentials.aws` | Credenciales de AWS. | ID de la credencial. | JSON en base64 con `access_key_id` y `secret_access_key`. |
| `credentials.azure` | Credenciales de Azure. | ID de la credencial. | JSON en base64 con `client_id`, `application_secret`, `tenant_domain` y `subscription_id`. |
| `credentials.gcp` | Credenciales de Google Cloud. | ID de la credencial. | JSON en base64 con los campos del documento de servicio. |
| `credentials.sap` | Credenciales de SAP. | ID de la credencial. | JSON en base64 con `user` y `password`. |
| `credentials.snmp` | Credenciales SNMP. | ID de la credencial. | JSON en base64 con `community`, `version`, `securityLevelV3`, `authUserV3`, `authMethodV3`, `authPassV3`, `privacyMethodV3` y `privacyPassV3`. |
| `credentials.wmi` | Credenciales WMI. | ID de la credencial. | JSON en base64 con `user`, `password` y `namespace`. |
| `os` | Nombres de sistemas operativos. | ID del sistema. | Nombre del sistema, o vacío. |

Las constantes de `status` son las de siempre: `0` normal, `1` crítico, `2` aviso, `3` desconocido y `5` no iniciado. El selector muestra los nombres, pero el script recibe el número.

El caso de `agent_groups` merece una línea aparte. El script recibe el **nombre** del grupo, no su ID. Si el paquete va a devolver `monitoring_data`, el campo `id_group` del agente necesita un ID numérico; o lo resuelve el script por su cuenta, o se omite y el agente se crea en el grupo de autocreación del servidor (`autocreate_group`, 10 por defecto), siempre que ese grupo esté configurado. Para la mayoría de paquetes, lo segundo es suficiente; si el grupo es parte del contrato, conviene resolverlo de forma explícita.

Las credenciales se guardan en el [Gestor de credenciales](../parte-2/2.2-gestor-de-credenciales.md) y el script recibe el JSON ya resuelto y codificado en base64. El campo del formulario solo muestra el identificador de la credencial; el usuario y la contraseña no se copian en la definición de la tarea. Las claves de cada tipo de credencial son las que describe [2.3](../parte-2/2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md).

## Selectores y árboles propios

Cuando las opciones no salen de Pandora, se declaran en un bloque `custom_select` y se referencia desde `select_data`:

```ini
[modes]
option[basic] = Basic
option[full] = Full
```

La clave de `option` es el valor que se guarda y el texto es lo que ve el usuario. El bloque puede tener cualquier nombre; el que importa es el que se escribe en `select_data`.

Para un árbol se usa un bloque `custom_tree_data`. Cada nivel declara sus elementos y, si tiene hijos, el bloque que los contiene:

| Parámetro | Obligatorio | Qué hace |
|---|---|---|
| `name` | Sí | Texto del elemento. |
| `selectable` | Sí en la validación actual | `true` o `false`. Si el elemento se puede seleccionar, hay que indicarlo; la validación rechaza un árbol sin este parámetro. |
| `macro` | No si el elemento no es seleccionable | Macro donde se guarda el valor del elemento. Si se omite en un elemento seleccionable, el valor va a la macro del árbol. |
| `value` | Sí si el elemento es seleccionable | Valor que se guarda. |
| `children` | No | Nombre del bloque con los elementos hijos. No puede apuntar a un bloque que ya esté por encima en el mismo árbol. |

Un árbol de dos niveles:

```ini
[resources]
name[1] = Servers
selectable[1] = false
children[1] = resources_servers

name[2] = Databases
selectable[2] = false
children[2] = resources_databases

[resources_servers]
name[1] = web01
selectable[1] = true
macro[1] = _targets_
value[1] = web01

name[2] = web02
selectable[2] = true
macro[2] = _targets_
value[2] = web02

[resources_databases]
name[1] = db01
selectable[1] = true
macro[1] = _targets_
value[1] = db01
```

Los valores seleccionados se guardan como un array JSON, por ejemplo `["web01","db01"]`, y se sustituyen en las ejecuciones como cualquier otra macro. Dos reglas más: una macro de árbol no puede coincidir con la de un campo de fuera del árbol, y un bloque no puede ser hijo de sí mismo ni de uno de sus ancestros.

## Ficheros temporales (`tempfile_confs`)

Muchos plugins necesitan un fichero de configuración en lugar de veinte argumentos en la línea de comandos. `tempfile_confs` lo genera:

```ini
[tempfile_confs]
file[_tempConf_] = "
[CONF]
url = _url_
timeout = _timeout_
mode = _mode_
log = __temp__/__taskMD5__.log
"
```

La clave es una macro válida y el valor es el contenido del fichero. Cuando esa macro aparece en una ejecución, el servidor crea un fichero temporal con ese contenido, sustituye las macros que haya dentro por sus valores y reemplaza la macro por la ruta del fichero. El fichero se reescribe en cada ejecución de la tarea; no se borra automáticamente.

El contenido puede usar cualquier macro del formulario y las macros del servidor: `__temp__`, `__taskMD5__`, `__taskInterval__`, etc. Es la forma cómoda de pasar una configuración multilínea a un script sin pelearse con las comillas del shell.

## La salida de los scripts

El servidor ejecuta cada comando de `exec` con el tiempo de espera de la tarea y recoge su salida estándar y su salida de error. El código de salida manda: si un comando termina con un código distinto de `0`, la tarea queda como fallida. Si se agota el tiempo, la tarea también falla y el resumen recoge `The execution timed out.`.

La salida estándar debe ser un JSON. El servidor lo interpreta así:

- La clave `summary` se muestra como una tabla de dos columnas: sus claves a la izquierda y sus valores a la derecha.
- La clave `info` añade una fila más a esa tabla.
- Cualquier otra clave se añade también al resumen.
- Si la salida no es JSON, se guarda como texto en el resumen.
- Si la salida está vacía y hay error estándar, se guarda el error; si tampoco hay error, se guarda `The execution returned no output. Is the server out of memory?`.

Cada comando produce su propia tabla: `Summary 1`, `Summary 2`, etc. El resumen se guarda con la tarea y se consulta desde el icono de resumen de la lista de tareas. Una ejecución fallida también deja su resumen; de hecho, es lo primero que hay que mirar cuando algo no sale.

![Resumen de una ejecución fallida, con el progreso y el error devuelto por el script](../../assets/img/parte-02/discovery-resumen-fallido.png)

Para crear agentes y módulos, el JSON añade la clave `monitoring_data`. Su estructura completa es esta:

```json
{
  "summary": {
    "SUMMARY_FIELD_1": "SUMMARY_VALUE_1",
    "SUMMARY_FIELD_N": "SUMMARY_VALUE_N"
  },
  "info": "ADDITIONAL_INFO",
  "monitoring_data": [
    {
      "agent_data": {
        "agent_name": "AGENT_NAME",
```

En `agent_data`, `agent_name` es obligatorio y debe ser único y estable: si cambia en cada ejecución, se crearán agentes nuevos en lugar de actualizar el existente. `agent_alias` es el nombre legible; si falta, se usa `agent_name`. `address` es la dirección del agente y `os` o `id_os`, el sistema operativo; si el nombre no se reconoce, se usa `Other`. `id_group` debe ser un ID numérico de grupo; si se omite, se aplica el grupo de autocreación del servidor. También se aceptan `id_parent`, `longitude`, `latitude`, `altitude`, `position_description`, `custom_id`, `url_address`, `agent_mode` y `extra_data`, aunque no aparezcan en el esqueleto.

En `module_data`, las claves imprescindibles son `name`, `type` y `data`. El `type` es el identificador de tipo de módulo (`generic_data`, `generic_data_string`, `generic_proc`, etc.; la lista completa está en [2.20](../parte-2/2.20-configuracion-comun-de-los-modulos.md)). `module_interval` es un multiplicador del intervalo del agente; si se indica `cron_interval`, este manda. Los umbrales (`min_warning`, `max_warning`, `min_critical`, `max_critical`) y sus versiones de texto (`str_warning`, `str_critical`) se aplican al crear el módulo. Las claves no reconocidas no rompen nada: se guardan como información extendida del módulo. Además del esqueleto, el procesador acepta `extra_data`, `dynamic_interval`, `dynamic_min`, `dynamic_max` y `dynamic_two_tailed`.

Un detalle que explica muchos «mi módulo no aparece»: los módulos nuevos solo se crean en agentes nuevos o en agentes en modo aprendizaje. En un agente que ya existe y no está en aprendizaje, el plugin actualiza los módulos que ya tenga, pero no añade otros nuevos. Si el paquete va a añadir módulos a agentes preexistentes, esos agentes tienen que estar en modo aprendizaje o hay que crearlos desde el propio paquete.

El contrato anterior es la vía directa: el script escribe el JSON por la salida estándar y el servidor crea los agentes. Los paquetes oficiales suelen usar la librería `pandoraPlugintools` y enviar los datos por Tentacle, que el servidor de datos procesa por la vía habitual; esa vía queda fuera de esta referencia. Para un paquete propio, el JSON es más simple y no necesita dependencias adicionales.

El paquete `example.http` comprueba una URL y crea un agente con dos módulos: el código HTTP y el tiempo de respuesta. Tiene un solo paso y usa un fichero temporal para pasar la configuración al script.

El script:

```python
#!/usr/bin/env python3
import argparse
import configparser
import hashlib
import json
import sys
import time
import urllib.parse
import urllib.request


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--conf", required=True)
    args = parser.parse_args()

    config = configparser.ConfigParser()
    config.read(args.conf)

    url = config.get("CONF", "url", fallback="")
    timeout = config.getint("CONF", "timeout", fallback=5)
    mode = config.get("CONF", "mode", fallback="basic")
    notify = config.getboolean("CONF", "notify", fallback=False)
    label = config.get("CONF", "label", fallback="")

    if not url:
        print("url is required", file=sys.stderr)
        return 2

    start = time.time()
    try:
        with urllib.request.urlopen(url, timeout=timeout) as response:
            status = response.getcode()
        elapsed = round((time.time() - start) * 1000, 2)
    except Exception as error:
        print(f"request failed: {error}", file=sys.stderr)
        return 1

    host = urllib.parse.urlsplit(url).hostname or url
    agent_name = "example_http_" + hashlib.md5(url.encode()).hexdigest()[:12]
    info = f"Mode: {mode}"
    if notify and label:
        info += f". Label: {label}"

    output = {
        "summary": {
            "URL": url,
            "HTTP status": status,
            "Response time (ms)": elapsed,
        },
        "info": info,
        "monitoring_data": [
            {
                "agent_data": {
                    "agent_name": agent_name,
                    "agent_alias": f"Example HTTP {host}",
                    "address": host,
                    "os": "Other",
                    "interval": 300,
                    "description": "Created by the example .disco package",
                },
                "module_data": [
                    {
                        "name": "HTTP status",
                        "type": "generic_data",
                        "data": status,
                        "description": "Last HTTP status code",
                        "min_warning": 400,
                        "max_warning": 499,
                        "min_critical": 500,
                        "max_critical": 599,
                    },
                    {
                        "name": "Response time",
                        "type": "generic_data",
                        "data": elapsed,
                        "unit": "ms",
                        "description": "Time to first byte",
                        "min_warning": 1000,
                        "min_critical": 3000,
                    },
                ],
            }
        ],
    }

    json.dump(output, sys.stdout)
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

El formulario muestra la URL, el tiempo de espera, el modo y la casilla; el campo «Label» aparece solo cuando la casilla está activa. Al ejecutar la tarea, el servidor crea el fichero temporal, lanza `demo_http.py --conf <fichero>`, recibe el JSON y crea el agente `Example HTTP <host>` con los módulos «HTTP status» y «Response time». El resumen de la ejecución muestra la URL, el código y el tiempo; en las siguientes ejecuciones se actualizan los mismos módulos.

El agente no lleva `id_group`: se crea en el grupo de autocreación del servidor. Si el paquete debe respetar el grupo de la tarea o el que elija el usuario, añade `id_group` con el ID numérico correspondiente.

## Instalar, probar y depurar

El paquete se construye como un ZIP normal y se renombra a `.disco`:

```sh
zip -r example.http.disco discovery_definition.ini demo_http.py
```

El ZIP debe tener los ficheros en la raíz; si se comprime la carpeta que los contiene, la consola no encontrará el INI. Después, en **Discovery → Manage disco packages**, se pulsa **Select file**, se elige el `.disco` y se sube con **Upload DISCO**. La consola valida el INI, instala el paquete y copia los ejecutables.

![Listado de Manage disco packages con los paquetes instalados, su sección y su versión](../../assets/img/parte-02/discovery-paquetes-lista.png)

La validación rechaza el paquete sin decir «casi»: si falta el bloque `discovery_extension_definition` o el `short_name`, si el `short_name` tiene caracteres no permitidos, si falta `section` o `name`, si la sección no es `app`, `cloud` o `custom`, si no hay ningún `exec` o alguno está vacío, si una clave de `default_value`, `execution_file` o `tempfile_confs` no tiene formato de macro, si un paso de `config_steps` usa una clave que no es numérica o es 0 o no tiene `name` y una fuente de campos, si un campo no tiene `macro`, `name` o `type`, si el tipo no es uno de los ocho, si un `select` o `multiselect` no tiene `select_data` o la referencia no existe, si un árbol no tiene `tree_data` o apunta a un bloque inexistente o a un ancestro, o si un `custom_select` no tiene `option`.

Si el `short_name` empieza por `pandorafms.`, la consola avisa de que el prefijo está reservado para los paquetes oficiales y pide confirmación; no lo impide. Si ya existe otro paquete con el mismo `short_name`, avisa y ofrece sobrescribirlo con todo su contenido. No hay comparación de versiones: subir el mismo `short_name` sustituye el paquete, así que cambia la versión para saber qué tienes instalado.

Tras la instalación, el asistente aparece en su sección (Applications, Cloud o Custom). Se crea una tarea como cualquier otra (ver [2.3](../parte-2/2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md)), se fuerza la primera ejecución y se revisa el resumen. Si el paquete crea agentes, aparecen en la consola con sus módulos; si no aparecen, el resumen suele decir por qué.

Para iterar, cambia el fichero, sube el paquete con el mismo `short_name` y la versión nueva. Las tareas existentes conservan sus valores; los valores por defecto nuevos se aplican a las macros que falten. Si has tocado ficheros fuera del paquete o la copia a los servidores quedó a medias, el botón de sincronizar de **Manage disco packages** vuelve a copiarlos.

Cuando algo falla, el orden de comprobación es este:

1. Ejecuta el script a mano con un fichero de configuración de ejemplo y comprueba el código de salida. Si falla ahí, no sigas: el problema es del script.
2. Comprueba que la salida es un único JSON válido: `python3 -m json.tool salida.json`, o pasa la salida por `jq` si lo tienes.
3. Revisa los permisos y el intérprete. El script debe estar en `execution_file` y tener un `#!` válido o un intérprete disponible en el servidor.
4. Revisa las rutas. El servidor resuelve los ejecutables en `<incomingdir>/discovery/<short_name>/`; no cuentes con que el directorio de trabajo de la tarea sea ese, así que usa rutas absolutas o resuélvelas desde el propio script.
5. Revisa el tiempo de espera de la tarea. El tiempo se aplica a cada comando; un script que tarda más se corta y la tarea falla.
6. Mira el log del servidor (`log_file`, por defecto `/var/log/pandora_server.log`; ver [9.3](9.3-referencia-completa-de-configuracion-del-servidor.md)). El servidor anota el comando que lanza y los errores de ejecución.

No hace falta reiniciar el servidor Discovery después de subir un paquete: la consola actualiza la definición y los ficheros, y el servidor los lee al ejecutar la tarea.

## Buenas prácticas y errores habituales

- **`short_name` estable.** Cambiarlo crea otra aplicación y deja huérfanas las tareas de la anterior. Si el paquete es una evolución, conserva el `short_name` y sube la versión.
- **Versión al día.** La consola no compara versiones, pero la lista muestra la que hay. Una versión que no cambia es una invitación a dudar de lo que está instalado.
- **Rutas relativas.** Todo lo que esté dentro del paquete se referencia desde su raíz. Las rutas absolutas funcionan en tu máquina y fallan en el servidor.
- **Ejecutables declarados.** Si un script no está en `execution_file`, no se le aplicará el permiso de ejecución. Lo mismo vale para los scripts de contraseña.
- **Dependencias dentro o documentadas.** El paquete no instala librerías. Si el script necesita `requests`, `paramiko` o un cliente de base de datos, o lo incluyes, o compruebas que existe en el servidor y lo documentas.
- **Secretos fuera del INI.** No pongas contraseñas en `default_value` ni en el fichero temporal. Usa un campo `password` con cifrado o una credencial del Gestor de credenciales.
- **Contraseñas cifradas, con descifrado.** Si usas `encrypt_on_true`, el servidor recibe el valor cifrado. El plugin tiene que descifrarlo; los scripts `passencrypt_*` y `passdecrypt_*` son para la consola.
- **`agent_name` estable.** Un nombre distinto en cada ejecución crea un agente nuevo cada vez. Usa un identificador derivado del recurso, no un número aleatorio.
- **Nombres de módulo estables.** Cambiar el nombre de un módulo crea otro módulo; el anterior se queda con sus datos y sus alertas.
- **Solo JSON por STDOUT.** Los mensajes de depuración van a STDERR o a un fichero. Un `print` de más convierte la salida en no-JSON y el resumen en texto.
- **Falla con código distinto de 0.** Si el script no puede hacer su trabajo, sal con error. Un JSON vacío con código 0 deja la tarea como correcta y el problema se descubre más tarde.
- **Resúmenes legibles.** Las claves de `summary` las lee una persona. `status_code`, `URL` o `Response time` se entienden; `res` y `v1` no.
- **Temporales únicos.** Usa `__taskMD5__` en los nombres de fichero para que dos tareas no se pisen. Borra lo que crees: los ficheros de `tempfile_confs` se reescriben en cada ejecución, pero no se borran solos, y los que cree tu script son tuyos.
- **`mandatory_field`, no `required_field`.** La consola lee `mandatory_field`; los ejemplos antiguos con `required_field` dejan el campo obligatorio aunque no lo quieras.
- **`selectable` en los árboles.** La validación actual rechaza un elemento de árbol sin `selectable`. Decláralo siempre, sea `true` o `false`.
- **Prueba el fallo.** Una URL que no responde, un JSON mal formado, un timeout y un fichero temporal con saltos de línea. Si el paquete solo se ha probado con el caso feliz, no está probado.
