# Gestión de incidencias / ITSM

Un sistema de monitorización que detecta el problema y se lo guarda para sí es
un vigilante muy competente y muy poco útil. La monitorización recoge datos; la
**gestión de incidencias** los convierte en un ticket con propietario, estado e
historial, para que alguien pueda cerrarlo y quede constancia de quién lo hizo.
Eso es lo que aporta la integración con **Pandora ITSM**: la monitorización deja
de ser un tablero que se mira y pasa a alimentar una cola de trabajo real.

Pandora ITSM es un producto aparte, con su propia licencia (ver
[Licenciamiento](../parte-1/1.5-licenciamiento.md)). Este capítulo documenta la
integración **desde Pandora FMS**: la pestaña de configuración, el menú
**Operación → ITSM**, la creación y edición de tickets, y los puntos donde la
monitorización los genera sola. La operación interna de Pandora ITSM (SLA, flujos
de trabajo, equipos de soporte, base de conocimiento, CRM, proyectos y correo
entrante) se queda en su manual. Aquí se explica lo que hay que hacer en Pandora
FMS para que esa maquinaria reciba trabajo.

Hay dos consolas y conviene tener claro cuál es la fuente de la verdad:

- **Pandora FMS** monitoriza, detecta y decide cuándo hay un problema. No es el
  dueño del ticket.
- **Pandora ITSM** guarda el ticket, su estado, su propietario, sus unidades de
  trabajo y su histórico. Es la fuente de la verdad del ticket.
- La consola de Pandora FMS muestra un resumen y permite operar sobre Pandora
  ITSM a través de su **API v2**. Si la API no responde, la sección de ITSM se
  queda mirando al tendido.

La integración tiene tres canales de entrada:

1. **Alta manual** desde la lista de tickets.
2. **Tickets automáticos** desde alertas, respuestas de eventos y eventos SIEM.
3. **Sincronización de agentes** como objetos de inventario de Pandora ITSM.

No es un helpdesk completo ni pretende serlo. Si necesitas colas, equipos,
turnos, SLA o una base de conocimiento, eso vive en Pandora ITSM. Aquí se monta
la puerta de entrada desde la monitorización.

## Puesta en marcha

### Requisitos y licencia

La licencia de Pandora ITSM es aparte de la licencia de monitorización. La
instalación conjunta que se describe más abajo es una instancia **a modo de
prueba**; para producción se despliega Pandora ITSM por separado, con su propia
base de datos y su propio usuario. Los requisitos de Pandora ITSM son los de su
manual:

| Requisito | Detalle |
|---|---|
| Disco | 10 GB mínimo, 20 GB recomendado |
| CPU | 2,4 GHz, doble núcleo |
| RAM | 1 GB mínimo, 4 GB recomendado |
| Sistema base | EL 8 (RHEL 8, Rocky Linux 8, AlmaLinux 8) o Ubuntu Server 22.04 |
| Base de datos | MySQL 8 o posterior |
| PHP | 8.2 o posterior |
| Navegador | Chrome, Edge, Firefox o Safari con HTML5; resolución mínima 1280 × 720 |
| Red | Pandora FMS debe alcanzar la API de Pandora ITSM; Pandora ITSM debe alcanzar la API pública de Pandora FMS |
| Versiones | Mantén actualizadas ambas aplicaciones: la integración usa la API v2 y las diferencias de versión se pagan con errores difíciles de diagnosticar |

La instalación conjunta se ejecuta en el servidor de Pandora FMS y añade sus
propios requisitos: conexión a internet para descargar el paquete, permisos de
escritura en el directorio de la consola y permisos del usuario de base de datos
para crear o usar la base de datos `itsm`.

### Instalación conjunta desde la consola

Desde la versión 783, la consola de Pandora FMS puede instalar una instancia de
Pandora ITSM **a modo de prueba**. La ruta es
**Ajustes → Configuración del sistema → Pandora ITSM** y el botón
**Install ITSM**. No es la vía recomendada para producción, pero sirve para
probar la integración sin montar antes un servidor aparte.

Antes de instalar, el asistente comprueba tres cosas:

- Que la base de datos `itsm` se puede crear o reutilizar.
- Que el usuario de base de datos de Pandora FMS tiene permisos suficientes.
- Que el directorio `itsm/` de la consola se puede crear o sobrescribir.

La conexión a internet no se comprueba en este paso: es un requisito previo,
porque el paso 2 descarga el paquete desde `packages.pandorafms.com`.

Si el directorio ya existe, el aviso es explícito: **se borrará y se recreará**.
No es una instalación que se pueda hacer a la ligera en un servidor con una
instancia de Pandora ITSM ya en marcha.

El proceso se muestra como una barra de progreso de nueve pasos:

| Paso | Qué hace |
|---|---|
| 1 | Comprueba y prepara el directorio `itsm/` |
| 2 | Descarga el paquete de Pandora ITSM |
| 3 | Extrae el paquete y ordena los ficheros |
| 4 | Crea la base de datos `itsm` o reutiliza la existente |
| 5 | Se conecta a la base de datos con las credenciales de Pandora FMS |
| 6 | Importa el esquema (`integria_db.sql`) y los datos iniciales (`integria_dbdata.sql`), solo si la base de datos no existía |
| 7 | Genera `itsm/include/config.php` y desactiva `install.php` |
| 8 | Crea el token de integración y configura en Pandora ITSM la autenticación contra Pandora FMS |
| 9 | Muestra el enlace a la consola de Pandora ITSM |

El paso 6 solo se ejecuta si el paso 4 ha tenido que crear la base de datos. Si
`itsm` ya existía, no se importa nada y se conserva el contenido actual.

Si la base de datos no existe y el usuario de Pandora FMS no puede crearla, el
paso 4 falla. En ese caso, el administrador de la base de datos debe conceder los
permisos antes de reintentar. Un ejemplo, con el usuario `pandora`:

```sql
GRANT ALL PRIVILEGES ON `itsm`.* TO 'pandora'@'localhost';
```

Al terminar, el asistente deja la conexión apuntando a `127.0.0.1` y activa
`ITSM_enabled`. Si Pandora ITSM se publica con otro nombre, detrás de un proxy o
en otro puerto, hay que ajustar la URL de conexión en la misma pestaña. El primer
acceso a la consola de Pandora ITSM se hace con el usuario `admin` y la
contraseña `integria`; cámbiala antes de dejar el sistema en manos de nadie.

!!! warning "Instalación conjunta no es instalación de producción"
    La instalación conjunta comparte el servidor y las credenciales de base de
    datos de Pandora FMS, y está pensada para pruebas. Para producción, instala
    Pandora ITSM por separado y conéctalo a Pandora FMS con la URL y el token que
    correspondan. Así puedes actualizar, respaldar y escalar cada producto por su
    cuenta.

### Conexión bidireccional

La integración necesita dos direcciones y las dos se configuran en la pestaña
**Pandora ITSM**:

- **Pandora FMS → Pandora ITSM**: la consola necesita la URL de la API de
  Pandora ITSM y un token. La URL tiene la forma
  `http://host/XXX/api/v2`; el token es la credencial de la API. El botón
  **Test** comprueba el `ping` de la API con esa URL y ese token.
- **Pandora ITSM → Pandora FMS**: Pandora ITSM necesita la URL pública de la API
  de Pandora FMS para leer el inventario de agentes. Por defecto se toma la
  **Public URL** de la consola o, si no está definida, la de `config.php`. El
  botón **Test** comprueba esa dirección desde Pandora ITSM.

![Pestaña Pandora ITSM con el interruptor general, las URL de conexión y los controles de sincronización de agentes](../../assets/img/parte-05/itsm-config.png){ .captura }

El modo por defecto es **global**: todos los usuarios comparten el token de la
pestaña. Si activas **Pandora ITSM configuration at user level**, el token global
se oculta y cada usuario debe poner el suyo en su perfil. Es la diferencia entre
«la integración habla con un usuario de servicio» y «cada persona habla con su
propio usuario de Pandora ITSM».

!!! tip "La URL pública no es un adorno"
    La dirección que pones en **URL connect to API Pandora FMS** la usa Pandora
    ITSM desde su servidor, no tu navegador. Si Pandora FMS está detrás de un
    proxy, una VPN o un cortafuegos, la URL tiene que ser alcanzable desde el
    servidor de Pandora ITSM. De nada sirve que el navegador llegue si el
    servidor de al lado no llega.

### Configuración a nivel de usuario

Con la configuración por usuario activa, cada persona necesita su propio token
de Pandora ITSM en el perfil de usuario (`integria_user_level_pass`). La consola
lo guarda como credencial y no lo muestra en claro. Si el campo está vacío, las
llamadas a la API se hacen sin un usuario válido y la lista de tickets puede
aparecer vacía o devolver un error de autorización.

Esta modalidad tiene dos usos claros:

- **Trazabilidad**: cada operación en Pandora ITSM queda asociada a la persona
  que la hizo, no a un usuario de servicio compartido.
- **Visibilidad**: cada usuario ve los tickets que su usuario de Pandora ITSM
  puede ver. El permiso **RR** de Pandora FMS abre la sección; el token decide
  qué hay dentro.

El token es una credencial. No se comparte por chat, no se pega en un ticket y no
se guarda en el repositorio.

### Plantillas de ticket: alertas y respuestas de eventos

La pestaña de configuración tiene dos bloques de valores por defecto que se
confunden con facilidad:

| Bloque | Cuándo se usa | Campos |
|---|---|---|
| **Alert settings** (`incident_*`) | Tickets creados por la acción de alerta **Create Pandora ITSM ticket** | Título, cuerpo, grupo, propietario, estado, prioridad y tipo |
| **Custom response settings** (`cr_*`) | Formulario de alta que abre la respuesta de evento **Create ticket in Pandora ITSM from event** | Título, cuerpo, grupo, propietario, estado, prioridad y tipo |

No son «la plantilla de la consola» y «la plantilla del agente». Son dos caminos
distintos: la alerta que se ejecuta en el servidor y la respuesta que ejecuta un
usuario desde la consola de eventos. El alta manual no usa ninguna de las dos:
arranca con prioridad `LOW`, estado `NEW` y los campos vacíos.

Los valores de la acción de alerta pueden sobrescribir los de **Alert settings**.
Si quieres un comportamiento uniforme, deja la acción con los campos vacíos y
configura la plantilla una sola vez; si necesitas tickets distintos por alerta,
rellena los campos de la acción.

### Sincronización de agentes con el inventario

La sincronización convierte los agentes de Pandora FMS en objetos de inventario
de Pandora ITSM. Los controles están en la misma pestaña:

| Control | Qué hace | Valor por defecto |
|---|---|---|
| **Number of agents to synchronize** | Cuántos agentes se procesan en paralelo | 20 (mínimo 10, máximo 1.000) |
| **Synchronize agents mode** | `All`, `Enable` o `Disable`; los grupos solo se aplican cuando hay filtro | `All` |
| **Agent groups to synchronize** | Grupos que se sincronizan cuando el modo es por grupo | Vacío (todos) |
| **URL connect to API Pandora FMS** | URL pública que usa Pandora ITSM para leer los agentes | **Public URL** o `config.php` |
| **Test** (ITSM → Pandora) | Comprueba la conexión de Pandora ITSM hacia Pandora FMS | Acción |
| Barra de progreso | Progreso de agentes procesados o error del nodo | Solo lectura |

Al guardar, la consola registra el nodo en Pandora ITSM (`/pandorafms/nodes`) con
la autenticación del servidor, la contraseña de la API, el número de agentes, los
grupos, el modo, la URL pública, la etiqueta del servidor y el identificador del
nodo. Pandora ITSM toma esos datos y sincroniza los agentes por su cuenta. La
consola consulta el estado (`/pandorafms/node/{serverAuth}`) y muestra el
progreso (agentes procesados sobre el total) o, si lo hay, el error del nodo. No
muestra el tiempo desde el inicio ni la próxima ejecución, y no permite borrar ni
reiniciar el nodo: esas operaciones se hacen desde Pandora ITSM.

En Pandora ITSM, la pestaña **Pandora FMS Inventory** (dentro de
**Setup → Setup**) muestra los nodos conectados, la ruta de conexión, el progreso,
el tiempo desde el inicio, la próxima ejecución y el estado, con operaciones de
borrado y reinicio. Si el nodo no aparece, la sincronización no ha empezado o la
conexión de Pandora ITSM hacia Pandora FMS no funciona.

!!! info "Dos inventarios que no son lo mismo"
    La sincronización desde la consola registra el nodo y hace que Pandora ITSM
    lea los agentes por la API. El **inventario remoto por EndPoints** es otra
    cosa: cada EndPoint envía un XML al servidor de Pandora ITSM y este crea los
    objetos de inventario. Ese segundo mecanismo, con los tipos de objeto y los
    campos del modelo CMDB, se documenta en
    [Integración de activos con ITSM](../parte-3/3.9-integracion-de-activos-con-itsm.md).

## La sección Operación → ITSM

El menú **Operación → ITSM** solo aparece si la integración está activada. Tiene
dos entradas:

- **Lista de entradas** (*Tickets list*): la lista de tickets.
- **Dashboard**: las estadísticas.

La traducción española de la consola llama «Lista de entradas» a *Tickets list*;
en este capítulo se usa «lista de tickets» y se cita el rótulo real cuando hace
falta. La página de la lista se titula **Ticket ITSM**, la de edición
**Editar ITSM** y la de detalle **ITSM Detallado**.

### Dashboard

El **Dashboard** es la página por defecto al entrar en **ITSM**. Muestra cuatro
gráficas de tarta:

- Incidencias por estado.
- Incidencias por prioridad.
- Incidencias por grupo.
- Incidencias por usuario.

![Cuatro gráficas de tarta con las incidencias por estado, prioridad, grupo y usuario](../../assets/img/parte-05/itsm-dashboard.png){ .captura }

No tiene filtros ni rango de fechas: muestra lo que el token de Pandora ITSM
puede ver. Si no hay tickets, la página lo dice con un **Not found incidences**.
Para el resto de dashboards de la consola, consulta
[Dashboards](5.1-dashboards.md).

### Lista de tickets

La lista es el centro de trabajo. La tabla muestra estas columnas:

| Columna | Qué contiene |
|---|---|
| **ID** | Identificador del ticket en Pandora ITSM |
| **Title** | Título; enlaza al detalle |
| **Group/Company** | Grupo del ticket y empresa del creador |
| **Status/Resolution** | Estado y resolución |
| **Priority** | Prioridad, con color |
| **Updated** | Última actualización |
| **Started** | Fecha de creación |
| **Creator** | Usuario creador |
| **Owner** | Propietario |
| **Agent** | Agente de Pandora FMS asociado, si lo hay |
| **Op.** | Editar, ver detalle y borrar |

![Lista de tickets con tres tickets de ejemplo, sus estados, prioridades y agentes](../../assets/img/parte-05/itsm-tickets.png){ .captura }

Por defecto, la lista se ordena por **Updated** descendente y pagina con el
tamaño de bloque de la consola. La tabla se puede ordenar por las columnas que
tienen sentido; las columnas de grupo/estado y las acciones no son ordenables.

El botón **Create** abre el formulario de alta. Las acciones de fila son el
lápiz (editar), el ojo (detalle) y la papelera (borrar con confirmación). No hay
un submenú «Edit»: la edición se hace desde la fila.

Los filtros son:

| Filtro | Qué busca |
|---|---|
| **Free search** | Texto libre en el identificador, el título y la descripción |
| **Agent** | Tickets asociados a un agente de Pandora FMS |
| **Status** | Estado de Pandora ITSM, más el pseudoestado **Not closed** |
| **Priorities** | Prioridad del ticket |
| **Group** | Grupo de Pandora ITSM; el grupo 1 no aparece en el selector |
| **Creation date** | Antigüedad de creación |

Hay tres detalles que conviene conocer antes de fiarse del filtro:

- **La lista arranca con el preset «Last 24 hours».** Si no has elegido fechas,
  el filtro **Creation date** aplica las últimas 24 horas; los tickets más
  antiguos no aparecen hasta que amplías el rango. No han desaparecido: están
  fuera del filtro.
- **El estado «Not closed» es un añadido de la consola**, no un estado de la API.
  Sirve para pedir los tickets que no están cerrados.
- **El filtro de fecha solo envía el límite inferior.** La consola convierte el
  rango a una antigüedad en días (`fromDate`) y no manda el extremo superior. Si
  eliges «desde el 1 de mayo», busca desde esa fecha; el «hasta» no viaja a la
  API.

La lista no tiene un selector de búsquedas personalizadas de Pandora ITSM. Ese
selector existe en el widget de dashboards, que sí puede aplicar una búsqueda
guardada.

El permiso **RR** abre la sección. Lo que ves dentro depende del token: con el
token global, todos los usuarios ven lo que ve ese usuario de servicio; con la
configuración por usuario, cada uno ve lo que su token de Pandora ITSM le
permite.

### Crear y editar un ticket

El botón **Create** de la lista abre el formulario de alta. El lápiz de una fila
abre el mismo formulario con los datos del ticket. Los campos son:

| Campo | Qué es | Notas |
|---|---|---|
| **Title** | Título del ticket | Obligatorio |
| **Type** | Tipo de incidencia de Pandora ITSM | Al cambiarlo se cargan sus campos personalizados |
| **Group** | Grupo de Pandora ITSM | Lista obtenida de la API |
| **Priority** | Prioridad | Lista obtenida de la API |
| **Status** | Estado | Lista obtenida de la API |
| **Creator** | Creador del ticket | Solo lectura y siempre vacío; el creador lo determina el usuario de Pandora ITSM del token |
| **Owner** | Propietario | Autocompletado de usuarios de Pandora ITSM |
| **Agent** | Agente de Pandora FMS | Autocompletado; registra el inventario y asocia el ticket |
| **Resolution** | Resolución | Solo se muestra cuando el estado es `CLOSED` |
| **Description** | Descripción | Editor de texto enriquecido |
| **Campos personalizados** | Campos del tipo de ticket | COMBO, TEXT, CHECKBOX, DATE, NUMERIC o TEXTAREA; pueden ser obligatorios |

![Formulario de alta de ticket con título, tipo, grupo, prioridad, campos personalizados, agente y descripción](../../assets/img/parte-05/itsm-ticket-edit.png){ .captura }

El campo **Creator** no es un desplegable ni un campo editable: es de solo
lectura y se muestra siempre vacío, también al editar un ticket. La ayuda lo
relaciona con el usuario de Pandora ITSM configurado; el creador real lo
determina el usuario asociado al token (el global o el del usuario, según la
configuración) y se ve en **Key participants** del detalle. El **Owner** sí es un
autocompletado de usuarios de Pandora ITSM. Si el tipo de ticket tiene campos
personalizados, aparecen debajo al seleccionar el tipo; los obligatorios se
validan antes de guardar.

Al guardar un ticket con un **Agent** seleccionado, la consola envía el inventario
del agente a Pandora ITSM (`/pandorafms/agents`) y asocia el ticket al objeto de
inventario (`/incidence/{id}/inventory/{idInventory}`). Si esa asociación falla,
el ticket puede haberse creado igualmente y la consola muestra el error. Si el
agente no existe como objeto de inventario, Pandora ITSM lo crea o lo actualiza
según el caso.

El alta manual arranca con prioridad `LOW`, estado `NEW`, sin grupo, sin tipo y
sin propietario. El creador no se elige en el formulario: lo determina el usuario
de Pandora ITSM del token. **No hereda las plantillas de alerta ni de respuesta
de evento.** Si quieres valores por defecto, rellénalos a mano o crea el ticket
desde una alerta o una respuesta.

Los adjuntos y los comentarios no están en este formulario. Se gestionan en el
detalle, después de crear el ticket.

### Detalle del ticket

El detalle se abre con el ojo de la fila o con el título. La cabecera muestra
`#ID - Título` y el cuerpo se organiza en bloques:

- **Dates**: creado, actualizado y cerrado (o **Not closed yet**).
- **Key participants**: creador, propietario y usuario que lo cerró.
- **Description**: la descripción del ticket.
- **Details**: estado, grupo, prioridad, resolución y tipo.
- **Comments**: las unidades de trabajo (*workunits*) del ticket; se pueden
  añadir, pero no editar ni borrar desde aquí.
- **Attached files**: subida con descripción, descarga y borrado.
- **SIEM events**: eventos SIEM enlazados con el ticket por `id_incidence`.

![Detalle de un ticket con fechas, participantes, descripción, estado y pestañas de comentarios, adjuntos y eventos SIEM](../../assets/img/parte-05/itsm-ticket-detail.png){ .captura }

El detalle **no muestra el inventario asociado**. Si necesitas ver el objeto de
inventario, se consulta en Pandora ITSM; el modelo de activos se documenta en
[Integración de activos con ITSM](../parte-3/3.9-integracion-de-activos-con-itsm.md).
La pestaña **SIEM events** se explica en [SIEM](../parte-7/7.2-siem.md).

## Tickets automáticos

### Tickets desde alertas

La alerta es la vía más habitual para crear tickets sin intervención. El comando
interno **Pandora ITSM Ticket** ya viene de fábrica y no se puede borrar ni
editar: es de sistema. La acción **Create Pandora ITSM ticket** también aparece
de fábrica, pero se puede copiar y ajustar; de hecho, se recomienda copiarla
para no tocar la original.

La acción usa siete campos y trece campos personalizados:

| Campo | Contenido |
|---|---|
| 1 | Título del ticket |
| 2 | Grupo (ID) |
| 3 | Prioridad |
| 4 | Propietario (`_ITSM_users_`) |
| 5 | Tipo (`_ITSM_types_`) |
| 6 | Estado (`_ITSM_status_`) |
| 7 | Descripción |
| 8–20 | Campos personalizados del tipo de ticket |

![Formulario de la acción de alerta Create Pandora ITSM ticket con los campos de disparo y recuperación](../../assets/img/parte-05/itsm-alert-action.png){ .captura }

Los valores no rellenados se toman de **Alert settings**. Los campos de la acción
pueden sobrescribirlos. El comando admite las macros de alerta de
[Alertas y notificaciones](5.5-alertas-y-notificaciones.md); la descripción y el
título suelen ser los sitios donde más se usan.

La opción **Create workunit on recovery** cambia el comportamiento de la
recuperación: si el estado de cierre se aplica al recuperarse la alerta, en vez
de cerrar el ticket se añade una unidad de trabajo. Es útil cuando el ticket
necesita una confirmación humana antes de cerrarse; si tu flujo espera el cierre
automático, déjala desactivada.

Cuando la alerta se ejecuta, el servidor envía a Pandora ITSM el ticket, los
campos personalizados del agente y los del inventario, el agente, el módulo, el
nodo, el modo de alerta y la opción de *workunit*. Pandora ITSM decide:

- Si el agente existe como objeto de inventario, lo actualiza; si no, lo crea.
- Si hay un ticket abierto, lo actualiza y añade una unidad de trabajo; si no,
  crea uno nuevo.
- Si el ticket está bloqueado en Pandora ITSM, no lo actualiza: crea uno nuevo.
- En la recuperación, actualiza el estado y, si está activada la opción, añade
  la unidad de trabajo.

La acción está disponible en alertas de módulo, evento, log, trap SNMP y SIEM.
La mecánica completa de comandos, acciones, plantillas y macros está en
[Alertas y notificaciones](5.5-alertas-y-notificaciones.md).

### Tickets desde respuestas de eventos

La respuesta **Create ticket in Pandora ITSM from event** aparece en el detalle
de un evento cuando la integración está activa. Es una respuesta de tipo URL:
abre una ventana nueva con el formulario de alta de ticket y aplica los valores de
**Custom response settings**.

El flujo es:

1. Abre el detalle del evento.
2. Selecciona la respuesta **Create ticket in Pandora ITSM from event**.
3. Pulsa **Execute**.
4. Se abre el formulario de alta en una ventana nueva, con los valores por
   defecto de **Custom response settings**.
5. Completa el agente, el título y lo que falte, y pulsa **Create**.

![Pestaña de respuestas de un evento con la respuesta Create ticket in Pandora ITSM from event seleccionada](../../assets/img/parte-05/itsm-event-response.png){ .captura }

Un aviso que ahorra una discusión: **el formulario no hereda el texto del
evento**. El `from_event` de la URL solo sirve para que la consola sepa que debe
aplicar los valores de la respuesta personalizada; no rellena el agente, el
título ni la descripción con los datos del evento. Si quieres que el ticket
cuente qué pasó, cópialo a mano o usa una alerta, que sí recibe las macros del
módulo y del agente.

Para ejecutar la respuesta necesitas **EW**; para abrir el formulario de ITSM,
**RR**. El selector de respuestas personalizadas se muestra también con **EM**,
pero la ejecución exige **EW**: con solo **EM**, la respuesta aparece en la lista
pero no se puede ejecutar. La mecánica de respuestas y sus macros está en
[Consola de eventos centralizada](5.4-consola-de-eventos-centralizada.md).

### Tickets desde SIEM

En el detalle de un evento SIEM, la acción **Create a ticket in Pandora ITSM**
crea un ticket y guarda su identificador en el campo `id_incidence` del evento.
El ticket aparece enlazado en la pestaña **SIEM events** del detalle y la lista
de tickets del evento se alimenta con `getListTicketsSiem`.

La creación desde SIEM no sigue el mismo camino que el alta manual: crea el
ticket y guarda su identificador en el evento, pero no registra el inventario del
agente ni asocia el ticket a su objeto de inventario, aunque el evento tenga un
agente. Si necesitas esa asociación, usa el alta manual o una alerta. El SIEM
como sistema, sus reglas y sus eventos se documentan en [SIEM](../parte-7/7.2-siem.md).

## Tickets en la vista del agente

La ficha del agente tiene dos puntos de entrada:

- **Associated tickets**, en la vista general: cuenta los tickets **no
  bloqueados** y enlaza a la lista filtrada por ese agente («See all N tickets
  related to this agent»).
- **Incidentes**, una pestaña que aparece solo si el agente tiene al menos un
  ticket. Muestra todos, bloqueados o no, con filtros de estado (por defecto
  `NEW`), prioridad, grupo y fecha de creación.

![Vista general del agente con el bloque de tickets asociados y el enlace a los tres tickets](../../assets/img/parte-05/itsm-agent-tickets.png){ .captura }

La pestaña exige el permiso **AW**. La vista general puede mostrar el bloque con
permisos de lectura del agente, pero la pestaña es la que permite gestionar.

El vínculo entre el agente y el ticket se guarda en el `externalId` del ticket:
`nodo-agente-módulo` cuando lo crea una alerta y `nodo-agente` cuando se crea o
edita a mano. El filtro por agente busca ese identificador, así que un ticket
creado por alerta y uno creado a mano aparecen juntos en la ficha del agente.
Los detalles de la ficha del agente están en
[Configuración común de los agentes](../parte-2/2.21-configuracion-comun-de-los-agentes.md).

## Widget de tickets en dashboards

El widget **Pandora ITSM tickets** (`ITSMIncidences`) lleva la lista de tickets a
un dashboard. Se configura con:

- **Limit**: número de tickets, de 0 a 100.
- **Custom search**: una búsqueda guardada de Pandora ITSM.
- **Fields to show**: ID, Title, Group/Company, Status/Resolution, Priority,
  Updated, Started, Creator y Owner.

Los campos por defecto son ID, Title, Priority y Creator. El widget solo está
disponible si la integración está activa y muestra lo que el token puede ver. No
es un editor de tickets: es una ventana de consulta. Para el resto de widgets,
consulta [Dashboards](5.1-dashboards.md).

## Permisos, buenas prácticas y diagnóstico

La tabla de permisos es la siguiente:

| Acción | Permiso |
|---|---|
| Ver la sección y la lista de tickets | **RR** |
| Crear, editar o borrar tickets | **RR** y los permisos del token de Pandora ITSM |
| Ver la pestaña **Incidentes** del agente | **AW** |
| Ejecutar respuestas de eventos | **EW** |
| Configurar comandos y acciones de alerta | **LM** o **PM** |
| Configurar la integración | **PM** o administrador |
| Poner el token de usuario | **UM** o edición del propio perfil |

El permiso de Pandora FMS abre la puerta; el usuario de Pandora ITSM asociado al
token decide qué tickets se ven y qué se puede hacer con ellos. No son dos
sistemas de permisos independientes: son dos capas que se suman.

Las buenas prácticas que evitan la mayoría de los sustos:

- **Un token dedicado para la integración global.** No uses el token de una
  persona para todo el equipo; si esa persona se va, la integración se va con
  ella.
- **Token por usuario si necesitas trazabilidad.** Es la forma de saber quién
  creó, editó o cerró cada ticket.
- **Alinea grupos, estados, prioridades y tipos con Pandora ITSM.** La consola
  pinta lo que le da la API; si los nombres no significan lo mismo en los dos
  lados, el equipo se equivoca al clasificar.
- **Plantillas cortas y con macros.** Un título con el agente y el módulo, y un
  cuerpo con el dato y el enlace, valen más que un párrafo genérico.
- **La *workunit* de recuperación, con criterio.** Si tu flujo cierra tickets
  automáticamente, no la actives; si necesita validación humana, actívala.
- **No edites el comando interno.** Es de sistema y la consola lo protege.
- **Prueba las dos direcciones después de cada cambio.** La conexión de Pandora
  FMS a Pandora ITSM y la de Pandora ITSM a Pandora FMS.
- **Usa HTTPS y una URL pública alcanzable.** La URL que ve tu navegador no
  tiene por qué ser la que ve el servidor de Pandora ITSM.
- **Reserva la instalación conjunta para pruebas.** Para producción, Pandora
  ITSM aparte, con su base de datos y su usuario.
- **Haz copia antes de instalar.** La instalación conjunta borra y recrea el
  directorio `itsm/` si ya existe.

Cuando algo falla, estas son las pistas que más veces apuntan al problema:

| Síntoma | Causa probable | Qué hacer |
|---|---|---|
| **ITSM API is not reachable** | URL, token o red | Revisa la URL (`.../api/v2`), el token y el cortafuegos; comprueba que Pandora ITSM responde |
| **Connection failed** en **Test** | La dirección no es alcanzable o la credencial no es válida | Prueba las dos direcciones; revisa la URL pública y el token |
| La lista aparece vacía o no muestra tickets antiguos | El token no ve tickets, el token de usuario está vacío, el filtro de fecha sigue en **Last 24 hours** o los filtros no devuelven nada | Revisa el usuario de Pandora ITSM, el token, el rango de fechas y los filtros |
| Error de autorización | Token caducado o sin permisos | Regenera el token y revisa el usuario |
| **Invalid response** | La URL apunta a una página HTML o a una ruta que no es la API | Usa la ruta `/api/v2`; revisa el proxy inverso |
| **Incidence not found** | El ticket se borró o el token no lo ve | Compruébalo en Pandora ITSM |
| La instalación falla en la base de datos | El usuario de Pandora FMS no puede crear o usar `itsm` | Concede permisos y reintenta |
| La instalación falla al descargar | No hay salida a `packages.pandorafms.com` | Revisa la conectividad y el proxy |
| **No write permissions in the directory** | El usuario de la consola no puede escribir en el directorio | Corrige los permisos o instala Pandora ITSM aparte |
| La pestaña **Incidentes** no aparece | No hay tickets, la integración está desactivada o falta **AW** | Revisa la integración y los permisos |
| La respuesta de evento no aparece o no se ejecuta | Falta **EW** (con solo **EM** se muestra, pero no se ejecuta) o la respuesta está en un grupo que no ves | Revisa el permiso y el grupo de la respuesta |
| El ticket se creó pero el inventario no se asoció | Fallo en la sincronización del inventario en el alta manual o desde una alerta | Revisa Pandora ITSM y el modelo de activos (3.9); el ticket puede existir igualmente |

Para el ticketing genérico con otras herramientas, consulta
[Informes, logs y correo](../parte-12/12.7-informes-logs-y-correo.md). Para la
referencia de todas las opciones de la pestaña, consulta el apartado 8 de
[Referencia completa de configuración de la consola](../parte-9/9.2-referencia-completa-de-configuracion-de-la-consola.md).

## Cierre y fronteras

La integración con Pandora ITSM resuelve un problema concreto: que el aviso de
la monitorización no muera en un correo. El ticket nace, se asigna, se actualiza
y se cierra en Pandora ITSM, y desde Pandora FMS se consulta y se opera sin
cambiar de herramienta. Lo que pasa después (SLA, turnos, equipos, base de
conocimiento, CRM, proyectos) es trabajo de Pandora ITSM y se documenta en su
manual.

Si lo que buscas es el modelo de activos y el inventario remoto por EndPoints,
está en [Integración de activos con ITSM](../parte-3/3.9-integracion-de-activos-con-itsm.md).
Si buscas la mecánica de alertas, en
[Alertas y notificaciones](5.5-alertas-y-notificaciones.md). Si buscas las
respuestas de eventos, en
[Consola de eventos centralizada](5.4-consola-de-eventos-centralizada.md). Y si
buscas el SIEM, en [SIEM](../parte-7/7.2-siem.md).
