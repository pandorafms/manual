# Actualizaciones

Actualizar Pandora FMS no es una urgencia, es mantenimiento. Y como todo
mantenimiento, se hace cuando toca y con la copia de seguridad ya hecha, no un
viernes por la tarde porque acaba de salir una versión. Este capítulo explica las
dos formas de poner al día una instalación: la automática y la manual. Y qué hay
que hacer con las piezas que no van por el mismo camino: los EndPoint y los
servidores satélite.

## Introducción

Una instalación de Pandora FMS tiene tres piezas que se actualizan juntas: la
**Consola web**, el **esquema de la base de datos** y el **servidor**. Desde la
versión 784 el servidor agrupa varios servicios en menos procesos. Así que
actualizar el servidor significa actualizar el paquete entero.

Hay dos caminos para hacerlo:

- **Warp Update**: asistentes desde la propia consola que descargan, aplican y
  verifican la actualización. Es el camino recomendado.
- **Actualización manual**: los mismos paquetes, aplicados a mano, componente por
  componente. Es más laborioso y exige más atención, pero da control total del
  proceso y sirve cuando no se puede usar el asistente.

Ninguno de los dos toca los **EndPoint** ni los **servidores satélite**: cada uno
tiene su propio mecanismo, y están al final del capítulo.

La última versión, el MR del esquema y la fecha de fin de soporte de la licencia
se consultan en **Management → About**. Merece la pena tener esa pantalla a mano
antes y después de cualquier actualización: es la que dice de dónde vienes y a
dónde has llegado.

![Panel About de la consola: versión instalada, paquete actual, versión del MR, build y fecha de fin de soporte](../../assets/img/parte-01/version-y-soporte.png){ .diagrama }

Y antes de empezar, lo de siempre, pero dicho claro: **haz un snapshot de la
máquina o una copia de seguridad de todos los componentes**. Si algo sale mal, la
forma sencilla de arreglarlo es volver atrás. Y eso solo funciona si existe el
punto al que volver.

Para que la sección de Warp Update aparezca en el menú hay que tener activado
**Enable update manager** en **Management → Settings → System Settings →
Advanced**. Si no está activado, la consola oculta todo el bloque de
actualización y parece que la funcionalidad no existe.

## Warp update

Warp Update actualiza la Consola web, el esquema de la base de datos y el
servidor de forma automática, mediante asistentes. Se accede desde
**Management → Warp Update** y tiene tres pantallas de trabajo, más una de
opciones.

**Warp Update Online** descarga e instala desde los repositorios oficiales, así
que la consola necesita salida a internet. Para usarlo hay que registrarse con
una dirección de correo electrónico. El asistente muestra la versión instalada y
las versiones a las que se puede subir: solo las LTS, o también las consecutivas,
según la configuración. Y las notas de versión, en **Show details**, antes de
decidir.

![Warp Update Online: versión instalada y aviso de que no hay actualizaciones disponibles](../../assets/img/parte-01/warp-update-online.png){ .diagrama }

**Warp Update Offline** hace lo mismo sin conexión a los repositorios. El
administrador descarga los paquetes por su cuenta y los sube al asistente. Para
descargarlos hay que introducir una dirección de correo y copiar el código de
acceso único que la consola asocia a la licencia; con ese código se entra en el
repositorio, que informa de la versión instalada, la siguiente y la última, y
permite bajar tres ficheros:

| Fichero | Qué actualiza |
|---|---|
| `package_XXX.XXX.fms` | La Consola web y el esquema de la base de datos. |
| `pandorafms_server-XXXXX.tar.gz` | El servidor. |
| `.sig` | La firma de los dos anteriores, para comprobar que no se han alterado. |

Se suben uno a uno desde el asistente (**Browse it**), se revisa que lo que
muestra en pantalla coincide con lo que se quiere aplicar, y se lanza el proceso.
Conviene actualizar primero la consola y el esquema, y después el servidor. Cada
fichero tiene que caber en los límites `post_max_size` y `upload_max_filesize` de
`/etc/php.ini`, o la subida fallará sin más explicación que un error de tamaño.

![Repositorio de Warp Update Offline: versiones disponibles para descargar y caducidad de la licencia](../../assets/img/parte-01/warp-update-offline.png){ .diagrama }

Si vienes de la LTS 777, el camino concreto —qué paquetes, en qué orden y
qué pasos no se pueden saltar— está en
[Actualización de la LTS 777 a la 800](../anexos/a6-actualizacion-de-la-lts-777-a-la-800.md).

**Warp journal** deja el rastro de lo que se ha hecho: versión actualizada, si
era servidor o consola, si vino de online u offline, quién lo lanzó y cuándo. Es
la primera parada cuando algo no cuadra después de una actualización.

Las **Options** de Warp Update son pocas y delicadas:

- **Limit to LTS updates**: limita la actualización a las versiones LTS, que son
  las de soporte extendido.
- **Allow no-consecutive patches**: solo en offline, permite saltar de versión en
  versión no consecutiva. Viene desactivado, y así está bien.
- **Warp Update URL**, **Use secured Warp Update** y **Proxy server**: no son
  campos para tocar por curiosidad. Antes de cambiarlos, se consulta con soporte.

## Actualización manual

La actualización manual usa los mismos paquetes que descarga el modo
offline, pero aplicados a mano en la terminal, con usuario **root**. El orden no
es negociable: **consola, esquema de la base de datos y servidor**. El
procedimiento es válido para EL 7, EL 8, EL 9 y Ubuntu 22.04 LTS.

### Consola

Se copia el paquete `.fms` al directorio de la consola, se
descomprime y se acepta reemplazar todo:

```bash
mv package_XXX.XXX.fms /var/www/html/pandora_console/
cd /var/www/html/pandora_console/
unzip package_XXX.XXX.fms
# a la pregunta por cada fichero reemplazado: A (All)
```

Después se actualiza el número de paquete en la base de datos, sustituyendo `XXX`
por la versión de destino:

```bash
mysql -u root -p -D pandora -e "UPDATE tconfig SET value=XXX WHERE token='current_package'"
```

### Esquema de la base de datos

Se ejecuta el actualizador del MR:

```bash
/usr/bin/php /var/www/html/pandora_console/godmode/um_client/updateMR.php
```

### Servidor

Se descomprime el paquete del servidor, se instala y se reinicia el
servicio:

```bash
tar -xzvf pandorafms_server-XXXXX.tar.gz
cd pandora_server/
./pandora_server_installer --install
systemctl restart pandora_server
```

### EndPoint

No van por Warp Update, y no hace falta ir máquina por máquina. La
forma cómoda es la **auto-actualización** con colecciones de ficheros y el
plugin `pandora_update`. Se deposita el binario nuevo del EndPoint en una
colección. El EndPoint ejecuta el plugin con el nombre de esa colección y compara
el binario de la colección con el que está ejecutando. Si son distintos, se
detiene, se reemplaza y se reinicia con el nuevo. Cada arquitectura necesita su
propia colección (un binario para Windows de 32 bits y otro para 64, por
ejemplo), y el proceso deja constancia en un log que se puede vigilar con un
módulo `async_string`. También se puede instalar la versión nueva a mano, con el
instalador de cada sistema operativo (Linux, MS Windows). En un entorno con
cientos o miles de dispositivos, eso es trabajo que la colección hace sola.

### Servidor satélite

El satélite tampoco lo toca Warp Update: se actualiza con
su propio instalador, el mismo que se usa para instalarlo. En la actualización a
la 785 hay además un paso de migración de políticas, porque los módulos de tipo
Dataserver de los agentes de Satellite pasaron a ser de tipo Satellite; hasta
completar esa migración, los cambios de política no llegan a esos agentes.

### Comprobación

Terminada la faena, se mira **Management → About** para
confirmar el paquete y el MR, y **Management → Servers** para ver la versión en
la columna **Version** de todos los servidores. Si las tres piezas no coinciden,
la actualización no ha terminado.
