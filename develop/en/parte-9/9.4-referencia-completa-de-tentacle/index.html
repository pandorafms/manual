    Full Tentacle reference (server and client)¶

    Raw technical reference for the Tentacle protocol and its two implementations (Go and Perl). It is looked up, not read from cover to cover; the rest of the site links here for any option or token of the Tentacle binary. For the EndPoint connection tokens (server_ip, server_opts…), see 9.1 · Full EndPoint configuration reference; for the tokens of the synchronization server that use Tentacle underneath, see 9.3 · Full server configuration reference.

    Introduction¶

    Tentacle is both a file transfer protocol and the client/server tool that speaks it. It replaced SCP/FTP in 2008 as the default method for sending the data XML of the EndPoints, and it is assigned IANA port tcp/41121.

    In the product, Tentacle carries: the data XML sent by each EndPoint, the remote configuration files, the collections, the remote commands (RMM), the traffic of the satellite servers, the Tentacle proxy and the dedicated RMM instance.

    There are two implementations of the same protocol, with the same command-line options (same letter, same meaning):

    • Go (static tentacle_server/tentacle_client binary, with no runtime dependencies): it is the default implementation in the Linux packages (server, EndPoint and satellite server) and the recommended one. It handles each connection with a goroutine instead of Perl's busy-waiting thread.
    • Perl (tentacle_server v0.6.2, tentacle_client v0.4.0): the historical reference implementation of the protocol. It is the one still shipped, compiled to .exe, by the Windows packages (EndPoint and satellite server).

    They are interchangeable: a Perl client talks to a Go server and vice versa, because both implement the same protocol with the same rules.

    The chapter is divided into three blocks: the protocol itself (independent of the implementation), the client and the server.

    1. The Tentacle protocol¶

    The design is deliberately simple:

    • The client always starts the connection; the server never sends data before the client asks for it or confirms it.
    • Commands are text terminated by a line break. There is no greeting or version negotiation: the first message the client sends is already a command.
    • When a command announces a size (SIZE <n>), a binary block of exactly that number of bytes follows, with no padding or additional header.

    Command table¶

    Command Direction Successful response Errors
    SEND <file> SIZE <n> Client → server SEND OK (accept confirmation) and SEND OK (received confirmation) SEND ERR (invalid file name), SEND ERR (file is too big), SEND ERR (file already exists), SEND ERR (upload not allowed)
    ZSEND <file> SIZE <n> Client → server, compressed ZSEND OK (accept) and ZSEND OK (received) ZSEND ERR (invalid file name), ZSEND ERR (file is too big), ZSEND ERR (file already exists), ZSEND ERR (upload not allowed), ZSEND ERR (failed to decompress)
    RECV <file> Client ← server RECV SIZE <n>, then the client replies RECV OK and the server sends the data RECV ERR (file has an invalid file name), RECV ERR (file does not exist), SEND ERR (download not allowed)
    ZRECV <file> Client ← server, compressed same as RECV with the ZRECV prefix ZRECV ERR (file has an invalid file name), ZRECV ERR (file does not exist), SEND ERR (download not allowed)
    LS <filter> Client ← server (insecure mode) LS SIZE <n>, the client replies LS OK and the server sends the listing LS ERR (filter with an invalid name, or when opening the directory)
    MV <file> Client ← server (insecure mode) MV SIZE <n>, the client replies MV OK, the server sends the file and deletes it MV ERR (invalid name or does not exist), SEND ERR (download not allowed) (not allowed)
    PASS <digest> Client → server PASS OK the server closes the connection without a message if the password does not match
    QUIT Client → server closes the connection without a response —
    Unrecognized command — — the server logs Unknown command '<command>' and closes the connection, without notifying the client

    The "download not allowed" notice always reuses the string SEND ERR (download not allowed), whether the operation is RECV, ZRECV or MV: both implementations share this quirk inherited from the protocol, it is not a transcription error.

    Sending files (SEND)¶

    The client announces SEND <name> SIZE <n>. The server checks, in this order, whether the destination allows upload (according to download_only), whether the name is valid, whether the size is between 1 byte and the configured maximum, and whether a file with that name already exists (with overwrite off). A file of size 0 is rejected with the same message as one that is too big (SEND ERR (file is too big)): it is the normal behavior of the protocol, not a quirk of one implementation. After a successful transfer, the client can send a new SEND (or another command) in the same session; the final close is marked by QUIT.

    Client:   SEND <report.xml> SIZE 1024
Server:   SEND OK
Client:   <1024 bytes of data>
Server:   SEND OK
Client:   QUIT

    Receiving files (RECV)¶

    The client requests RECV <name>. If the file exists and the destination allows download (according to upload_only), the server replies RECV SIZE <n>; the client, already knowing the size, can reject the download without further ado (it simply does not continue the session with the expected command). If the client confirms with RECV OK, the server sends the data block.

    Client:   RECV <report.xml>
Server:   RECV SIZE 1024
Client:   RECV OK
Server:   <1024 bytes of data>

    Compression (ZSEND/ZRECV)¶

    ZSEND and ZRECV are the compressed variants of SEND/RECV: the data block is a ZIP file with a single entry (Deflate) instead of the clear content. They are enabled with the client's -z option; the rest of the command sequence is identical.

    Insecure mode operations (LS, MV)¶

    LS (listing the files that match a filter) and MV (downloading a file and then deleting it from the server) work only if the server started with the -I/insecure option. If insecure mode is off (the default value), the server logs the attempt and closes the connection without replying to the command.

    Password authentication (PASS)¶

    When the server requires a password, PASS must be the first command of the session. The client sends, in hexadecimal, the MD5 of the binary MD5 digest of the password (a double MD5). This obfuscates the password, it does not protect it: over a connection without TLS it adds no real security against someone who captures the traffic. For password authentication to contribute anything, it has to run over an encrypted connection.

    Encryption¶

    TLS wraps the whole connection from the first byte: there is no unencrypted phase and no later STARTTLS. Both ends must have TLS active; it is not negotiable mid-session.

    Error handling¶

    On any anomaly (an unknown command, a wrong password, more data than announced, an internal failure), the server closes the connection without explaining the reason to the client. The detail only remains in the server log, if it is active.

    File names and block size¶

    File names do not allow the characters ? [ ] / \ = + < > : ; ' , * ~ or any path (only the plain name). The block size for network reads and writes is 1024 bytes.

    The two Tentacle proxies¶

    They should not be confused:

    • The Tentacle server in proxy mode (-b/-g or proxy_ip/proxy_port on the server): it forwards the whole connection to another Tentacle server, without storing anything. It is explained in section 3, "Proxy mode".
    • The client's HTTP proxy (-y user:password@address:port): the Tentacle client opens the connection through an HTTP proxy with CONNECT, with optional Basic authentication if a user and password are given. It is explained in section 2, "HTTP proxy".

    2. The Tentacle client¶

    Syntax: tentacle_client [options] [file] [file] .... At least one file is needed, except in receive mode (-g), where the argument is the remote name to download.

    Command-line options¶

    Same letters in both implementations:

    Option Argument What it does Default
    -a address Server address. 127.0.0.1
    -b local address Local address to bind the outgoing connection to. unset (chosen by the system)
    -c — Enables TLS without a client certificate. Incompatible with -e. off
    -e certificate OpenSSL certificate file of the client; enables TLS. Incompatible with -c. —
    -f CA Verifies that the server certificate is signed by this CA. Requires -e. —
    -g — Receive mode: downloads files from the server instead of sending them. off (send mode)
    -h — Shows the help. —
    -k key OpenSSL private key file of the client. Requires -e. —
    -p port Server port. 41121
    -q — Quiet mode: does not print error messages. off
    -r number Retries of the network operations. Minimum 1: a lower value makes the client exit with a startup error. 3
    -t seconds Timeout of the network operations. Minimum 1: a lower value makes the client exit with a startup error. 1 s
    -v — Verbose mode (logs the protocol events). off
    -w — Interactively asks for the private key password. It has effect only together with -e. off
    -x password Server password (PASS authentication). empty
    -y user:password@address:port HTTP proxy for the connection (CONNECT, with Basic if credentials are given). no proxy
    -z — Compresses the data in transit (ZSEND/ZRECV). off

    Combination rules¶

    • -c and -e are incompatible with each other (two different ways of enabling TLS: without a certificate of its own or with one).
    • -f and -k require -e to be present; without a client certificate it makes no sense to ask for a CA or a key. -w has effect only together with -e.
    • IPv6: supported; the Perl client also needs the IO::Socket::INET6 module installed.

    HTTP proxy¶

    -y user:password@address:port makes the client open the connection to the proxy with a CONNECT to the real Tentacle server; if a user and password are given, it adds the Proxy-Authorization: Basic header. User and password are optional within the string.

    Exit codes¶

    0 if all the transfers on the command line ended well, 1 if any failed or if there was an error.

    Use from the EndPoint and the satellite server¶

    The EndPoint and the satellite server invoke the Tentacle client through four tokens of their configuration file: transfer_mode tentacle (the transfer mode), server_ip and server_port (destination) and server_opts (the client options of this section, as they are, for example server_opts -v -r 5). For the full detail of these tokens and their secondary server equivalents, see 9.1 · Full EndPoint configuration reference.

    Usage examples¶

    With the server on 192.168.1.1 and no password on the client private key:

    Simple transfer, with a maximum file size of 1 MB on the server:

    tentacle_server -m 1048576 -s /tmp -v
tentacle_client -a 192.168.1.1 -v /home/user/myfile.dat

    With password authentication:

    tentacle_server -x password -s /tmp -v
tentacle_client -a 192.168.1.1 -x password -v /home/user/myfile.dat

    TLS without a client certificate:

    tentacle_server -e cert.pem -k key.pem -w -s /tmp -v
tentacle_client -a 192.168.1.1 -c -v /home/user/myfile.dat

    TLS with a client certificate and password:

    tentacle_server -x password -e cert.pem -k key.pem -f cacert.pem -w -s /tmp -v
tentacle_client \
  -a 192.168.1.1 \
  -x password \
  -e cert.pem \
  -k key.pem \
  -v /home/user/myfile.dat

    3. The Tentacle server¶

    Syntax: tentacle_server -s <directory> [options], or tentacle_server -F <file> to start by reading the configuration from a file.

    Command-line options¶

    Option Token What it does Default
    -a addresses IPv4 addresses to listen on, separated by commas. 0.0.0.0
    -b proxy_ip Proxy mode: address of the unreachable Tentacle server to forward to. —
    -c max_connections Maximum number of simultaneous connections. 10
    -d daemon Runs the server as a daemon. Not available on Windows (see "Windows", further down). off
    -e ssl_cert OpenSSL certificate of the server; enables TLS. —
    -f ssl_ca CA with which to verify the client certificate. —
    -F — Full path to the configuration file. —
    -g proxy_port Proxy mode: port of the unreachable Tentacle server. 41121
    -h — Shows the help. —
    -I insecure Enables insecure mode (LS and MV). off
    -i filters Distribution filters by subdirectory (regexp:dir;regexp:dir…). —
    -k ssl_key OpenSSL private key of the server. —
    -l log_file File to write the log to. standard output if not given
    -m max_size Maximum file size, in bytes. 64000000
    -o overwrite Allows overwriting an existing file with the same name. off
    -p port Port to listen on. 41121
    -q quiet Does not print error messages. off
    -r retries Retries of the network operations. Minimum 1. 3
    -s directory Storage directory. Mandatory except in proxy mode. —
    -S — Manages the Windows service (install|uninstall|run). —
    -t timeout Timeout of the network operations, in seconds. Minimum 1. 1
    -u ssl_cipher Restricts the admitted TLS 1.2 cipher suites, with OpenSSL names separated by :. normal negotiation
    -v verbose 1 Verbose mode: logs errors. off
    -V verbose 2 Extended verbose mode: logs errors and informational warnings. off
    -w — Asks for the private key password on the command line. It applies to encrypted PEM keys in the traditional format. off
    -x password Server password (PASS authentication). empty
    -z ssl_version Restricts the admitted TLS version to TLSv1_2 or TLSv1_3. normal negotiation (TLS 1.2 minimum)

    Configuration file¶

    The format is the usual one in the product: one line per token with the value after a space, and # comments out the whole line. The usual path of the file is /etc/tentacle/tentacle_server.conf. The command line takes precedence over the file when the same option is repeated in both places. There is no hot reload: a change in the file requires restarting the service.

    Several tokens have no equivalent command-line option:

    • block_size: block size for network reads and writes, in bytes (1024 bytes by default; see "Protocol", further up).
    • download_only and upload_only: directories, after applying filters, from which only downloading or only uploading is allowed, respectively, separated by ;. They are detailed in "Filters and directories", further down.

    Package template versus internal values¶

    The template installed by the package (tentacle_server.conf.new) does not always match the default value applied by the binary itself when the token does not appear in the file. For example, the template enables daemon 1 even though the internal default value is 0 (off). The rest of the tokens in the previous table indicate, in the "Default" column, the internal value of the binary, not the one of the template.

    Filters and directories¶

    filters (-i) distributes the incoming files by subdirectory according to a regular expression on the name; the syntax is regexp:subdirectory;regexp:subdirectory;…. A file whose name does not match any filter is saved directly in the storage directory. The template of the main server distributes, among others, the .conf to conf, the .md5 to md5, the .zip to collections, the .lock to trans, the .rcmd to commands and the EndPoint installation packages (.agent_setup.exe, .agent_setup.tar.gz) to agent. download_only (-D) and upload_only (-U) act on these same subdirectories (already filtered), restricting what can be uploaded or downloaded in each one. After updating the package the server must be restarted so that it takes the new filters that the version brings.

    systemd service¶

    The main service is tentacle_serverd.service, with user pandora, which starts tentacle_server -F /etc/tentacle/tentacle_server.conf with a cleanup ExecStartPre (clean_tentacle_serverd, which empties the temporary files of the TMPDIR set in tentacle_server.env) and two environment files (tentacle_server.env with TMPDIR and tentacle_server_extra.env, the latter free for local adjustments). The relationship between this service and the tentacle_service_cmd / tentacle_service_watchdog tokens of the main server is in 9.3 · Remote configuration, Tentacle and synchronization.

    RMM instance¶

    RMM uses its own Tentacle instance, independent of the one of the main server: service tentacle_rmm.service (user root, port 41123, ExecStartPre with clean_tentacle_rmm), its own configuration file, its own storage directory (/var/spool/pandora/rmm_server) and its own TLS certificates. The filters (filters) distribute the RMM files by extension into their own subdirectories (rmm, res, queue, keepalive, data), and download_only/upload_only restrict those same subdirectories: downloading is only allowed from rmm, res and queue, and uploading is only allowed to data and keepalive. The template brings a sample password: it must be changed before putting the service into production, and like any secret, it is referenced from the configuration, never copied into the documentation or into a repository.

    Proxy mode¶

    With -b/proxy_ip and -g/proxy_port, the Tentacle server does not act as a store: it forwards in raw form, byte by byte, everything that arrives from each client towards another Tentacle server (the "unreachable" one from the point of view of the clients). It can terminate TLS and password authentication in the client-proxy segment, with a different (or unencrypted) proxy-server segment. The satellite server solves the same forwarding with its own tokens, proxy_tentacle_from/proxy_tentacle_to; see 6.2 · Satellite servers.

    Practical case: EndPoints behind a Tentacle proxy with TLS and password, end to end. First each segment is checked by hand and, if it works, the permanent configuration is set.

    Manual tests:

    # 1. Real server
sudo -u pandora tentacle_server \
  -x password \
  -e tentacle_cert \
  -k tentacle_key \
  -f ca_cert -s /tmp -v

# 2. Proxy
sudo -u pandora tentacle_server -b ip_server -g 41124

# 3. Client, against the proxy
sudo -u pandora tentacle_client \
  -a ip_proxy \
  -x password \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -v file

    Permanent configuration, once the manual sending has been checked:

    1. Real server (/etc/tentacle/tentacle_server.conf):
    password password
ssl_cert tentacle_cert
ssl_key tentacle_key
ssl_ca ca_cert
    1. Proxy (its own /etc/tentacle/tentacle_server.conf):
    proxy_ip ip_server
proxy_port 41124
    1. EndPoint (pandora_agent.conf), pointing server_ip to the proxy, not to the real server:
    server_opts -x password -e tentacle_client_cert -k tentacle_client_key
server_ip ip_proxy

    Each option in server_opts is independent: if, for example, the password is not needed, it is enough to omit -x password from the line.

    Security: password, TLS and certificate combinations¶

    The password (-x/password) and TLS are orthogonal: they can be combined or used separately. The four possible certificate combinations are the following; all of them allow adding a password in the same way.

    1. Server with certificate, client without verification (the client does not check the identity of the server):

    Manual test:

    tentacle_server -v -e tentacle_cert -k tentacle_key -s /tmp
tentacle_client -v -c -a <server> file

    Permanent configuration, server:

    ssl_cert tentacle_cert
ssl_key tentacle_key

    Permanent configuration, EndPoint and satellite server:

    server_opts -c

    2. Server with certificate, client verifies against a CA:

    Manual test:

    tentacle_server -v -e tentacle_cert -k tentacle_key -s /tmp
tentacle_client -v -e tentacle_client_cert -f ca_cert -a <server> file

    Permanent configuration, server:

    ssl_cert tentacle_cert
ssl_key tentacle_key

    Permanent configuration, EndPoint and satellite server:

    server_opts -e tentacle_client_cert -f ca_cert

    3. Server verifies the client against a CA (client certificate without a CA of its own on the client):

    Manual test:

    tentacle_server -v -e tentacle_cert -k tentacle_key -f ca_cert -s /tmp
tentacle_client -v \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -a <server> file

    Permanent configuration, server:

    ssl_cert tentacle_cert
ssl_ca ca_cert
ssl_key tentacle_key

    Permanent configuration, EndPoint and satellite server:

    server_opts -e tentacle_client_cert -k tentacle_client_key

    4. Mutual verification (server and client verify the certificate of the other against a CA):

    Manual test:

    tentacle_server -v -e tentacle_cert -k tentacle_key -f ca_cert -s /tmp
tentacle_client -v \
  -e tentacle_client_cert \
  -k tentacle_client_key \
  -f ca_cert \
  -a <server> file

    Permanent configuration, server:

    ssl_cert tentacle_cert
ssl_ca ca_cert
ssl_key tentacle_key

    Permanent configuration, EndPoint and satellite server:

    server_opts -e tentacle_client_cert -k tentacle_client_key -f ca_cert

    In all cases, the certificate and key paths must be absolute in the configuration files, and the IO::Socket::SSL package has to be installed to use TLS with the Perl implementation. TLS requires version 1.2 at minimum.

    For production, the recommended combination is 4 (mutual verification), with a password optionally added: it is the only one of the four in which both ends check the identity of the other against a CA.

    retries/timeout (-r/-t) are not only network parameters: by limiting the retries and the timeout of each connection, they also make a brute-force attack against the password harder. The server log (-l/log_file, with the detail given by -v/-V) is, in addition to diagnostics, the audit record of the connections.

    Quick OpenSSL certificate guide¶

    To generate the certificates used by the previous examples.

    Create your own CA:

    mkdir demoCA demoCA/newcerts demoCA/private
openssl req -new -x509 -keyout cakey.pem -out cacert.pem
mv cakey.pem demoCA/private/
mv cacert.pem demoCA/

    Certificate request and signing with that CA:

    openssl req -new -keyout tentaclekey.pem -out tentaclereq.pem -days 360
cat tentaclereq.pem tentaclekey.pem > tentaclenew.pem
touch demoCA/index.txt
echo "01" >> demoCA/serial
openssl ca -out tentaclecert.pem -in tentaclenew.pem

    Self-signed certificate, without a CA:

    openssl req -new -x509 -keyout tentaclekey.pem -out tentaclecert.pem -days 360

    RSA key without a password (it avoids having to enter it on the client side):

    openssl genrsa -out tentaclekey.pem

    Export a PEM certificate to DER (needed on some systems):

    openssl x509 -outform der -in tentaclecert.pem -out tentaclecert.der

    Windows¶

    On Windows, the server is managed as a service with tentacle_server -S install|uninstall|run; the -d option (Unix daemon) is not available on this platform.
