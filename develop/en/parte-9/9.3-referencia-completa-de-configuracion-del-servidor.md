# Full server configuration reference

> Raw technical reference for `pandora_server.conf`: every token the server
> recognises, with its real default value. It is looked up, not read from cover
> to cover; any other chapter links here when it needs to refer to a server
> parameter.

## Introduction

`pandora_server.conf` is the only configuration file of the Pandora FMS server.
Its path is configurable at installation; by default,
`/etc/pandora/pandora_server.conf`. The format is the usual one: one token per
line, value after a space, and `#` to comment a whole line or to leave an
example token disabled.

A change in the file is not applied on the fly: the service has to be restarted.

```sh
systemctl restart pandora_server
```

The exception is remote configuration: with `remote_config 1` (see "Remote
configuration, Tentacle and synchronization", further down), the whole file can
be edited from the web console. The server checks now and then whether there
are changes; when it finds them, it generates a restart event, reloads the
configuration and restarts itself.

The tokens exclusive to the satellite servers (`pandora_satellite.conf`) are not
in this reference: they have their own chapter, [6.2 · Satellite
servers](../parte-6/6.2-servidores-satelite.md), which links here for what they
share with the main server.

The "default value" of each table is the one the server itself applies when the
token does not appear in the file. The sample template shipped with the package
(`pandora_server.conf.new`) does not always match that value: when it differs in
a relevant way, the table says so explicitly, never as if it were "the" default
value.

## 2. Server activation and number of threads

Each internal server has a switch (`0`/`1`) and, where it applies, a number of
threads of its own. "Default" is, as in the rest of this chapter, the value the
server itself assumes when the token does not appear in the file; the
installation template (`pandora_server.conf.new`) may bring a different value for
that same token. For example, `discoveryserver` comes enabled in the template
although the internal default value is `0`, and the other way round,
`snmpconsole` comes disabled in the template although the internal default value
is `1`.

| Server | Activation token | Default | Threads token | Default |
|---|---|---|---|---|
| Data (XML) | `dataserver` | `1` | `dataserver_threads` | `2` |
| Network (TCP, remote commands, WMI; ICMP and SNMP if the high-performance one is disabled) | `networkserver` | `1` | `network_threads` | `3` |
| High-performance network (ICMP with `fping` and SNMP with `pandorafsnmp`, in bulk) | `networkhpserver` | `1` | `networkhpserver_threads` | `4` |
| SNMP console | `snmpconsole` | `1` | `snmpconsole_threads` | `1` |
| SNMP (legacy: it no longer starts a server of its own; it only turns on the check that `snmptrapd` keeps receiving traps) | `snmpserver` | `0` | `snmp_threads` | `3` |
| ICMP (legacy: no effect; it is run by the high-performance network server) | `icmpserver` | `0` | `icmp_threads` | `3` |
| WMI (legacy: no effect; it is run by the network server) | `wmiserver` | `1` | `wmi_threads` | `2` |
| Plugin (legacy: no effect; it is run by the Heavy server) | `pluginserver` | `1` | `plugin_threads` | `2` |

| Inventory (legacy: no effect; it is run by the Heavy server) | `inventoryserver` | `1` | `inventory_threads` | `2` |
| Web (legacy: no effect; it is run by the network server) | `webserver` | `1` | `web_threads` | `1` |
| Events | `eventserver` | `0` | `eventserver_threads` | `1` |

| MADE (anomaly detection) | `madeserver` | `0` | `madeserver_threads` | no value in the code; the template brings `2` (see "Additional server blocks") |
| SIEM | `siemserver` | `0` | `siemserver_threads` | `4` |

The reason behind this distribution (why so many servers of their own
disappeared and what each real server does today) is in
[Compatibility and migration to the new server
architecture](../anexos/a3-compatibilidad-y-migracion-a-la-nueva-arquitectura-de-servidores.md).
