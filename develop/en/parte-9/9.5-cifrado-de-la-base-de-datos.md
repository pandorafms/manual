# Database encryption

An unencrypted database is honest to the point of indiscretion: whoever gets a
dump takes away, along with the monitoring data, every password Pandora FMS
stores on behalf of third parties. Database encryption shuts that mouth: it
encrypts at the source the fields that hold passwords and secrets, so that a
`mysqldump` lost, stolen or badly filed gives nothing readable away.

## What it is and what it protects

It is an **Enterprise** feature. The algorithm is 128-bit Rijndael in ECB
mode, the same as AES-256-ECB through OpenSSL in the Web console, with a
256-bit key derived from the MD5 of the encryption passphrase
(`encryption_passphrase`) entered in the configuration. That passphrase is not
stored anywhere in the database, neither it nor the key that comes out of it:
it lives only in the configuration files of each node. If it is lost, there is
no way back: the encrypted passwords remain unreadable forever. Once
configured, encryption is transparent: the Web console and the server encrypt
when saving and decrypt when reading, with nobody having to do anything else.

What it protects, grouped by functional area:

| What is encrypted | Detail |
|---|---|
| Monitoring | Passwords of plugin modules and SNMPv3 credentials of modules, network components and policies. |
| Inventory | Passwords of the Enterprise inventory modules. |
| Custom fields | Agent custom fields marked as password type. |
| Console configuration | Mail server (SMTP) password; LDAP/Active Directory administration password (primary and secondary server) and the option to save a local copy of that password; historical database password; console replication database password; API access password; update proxy password; Pandora RC access password; remote command Web console password; automatic access hash password between nodes; credentials of the remote authentication sources of the Pandora FMS and Babel Enterprise type. |
| High availability | Database replication password between High Availability nodes. |
| Server export | Password of the data export server to another remote Pandora FMS. |
| Command Center | Connection data of each registered node (passwords of its databases, of its API and of its console). |
| Plugins | Hidden plugin macros. |
| Credential manager | The data of the stored credentials (users, passwords, keys and other access data of each type), see [Credential manager](../parte-2/2.2-gestor-de-credenciales.md). |

**What it does NOT protect:** the access password of the Web console users
uses a separate mechanism, with a non-reversible hash, and does not depend on
this feature. Neither do the passwords that the [Satellite
server](../parte-6/6.2-servidores-satelite.md) stores in its configuration:
they have their own key (`credential_pass`) and their own mechanism,
independent of this chapter.

## Requirements

| Requirement | Detail |
|---|---|
| Edition | Pandora FMS Enterprise. Without it, `encryption_passphrase` has no effect and the passwords are stored unencrypted. |
| Access | Administrator access to the configuration files of the Web console (`config.php`) and of the server (`pandora_server.conf`) of each node and of the Command Center. |
| Service stop | The Pandora FMS server must be stopped on each node and on the Command Center while `pandora_encrypt_db` runs. |
| Encryption passphrase | The same string in `config.php` and in `pandora_server.conf`, and the same on all the nodes and on the Command Center. |

## Enabling encryption

The steps are repeated on the Command Center and on each node, in this order:

1. Stop the Pandora FMS server.
2. Add the same `encryption_passphrase` in `config.php`
   (`/var/www/html/pandora_console/include/config.php`, with the line
   `$config["encryption_passphrase"]="passphrase";`) and in
   `pandora_server.conf` (`encryption_passphrase passphrase`); in the latter
   it is commented out by default.
3. Run `pandora_encrypt_db /etc/pandora/pandora_server.conf` (the full syntax
   is in [Reference for
   `pandora_encrypt_db`](#reference-for-pandora_encrypt_db)).
4. Restart the server.

## Changing the encryption passphrase

If the encryption passphrase has been compromised, replacing it in the
configuration files is not enough: you have to decrypt with the old passphrase
and encrypt again with the new one.

1. Decrypt with the current passphrase:
   `pandora_encrypt_db -d /etc/pandora/pandora_server.conf`.
2. Change `encryption_passphrase` in `config.php` and in
   `pandora_server.conf`, on all the nodes and on the Command Center.
3. Encrypt again: `pandora_encrypt_db /etc/pandora/pandora_server.conf`.

Neither of the two steps uses the `-m` option: it is a legacy option from the
migration between old versions and is not part of this procedure; using it
here leaves some fields encrypted twice, with the old passphrase and with the
new one, and unusable. More detail in [Reference for
`pandora_encrypt_db`](#reference-for-pandora_encrypt_db).

## Removing encryption

1. Stop the server on the Command Center and on each node.
2. Decrypt: `pandora_encrypt_db -d /etc/pandora/pandora_server.conf`.
3. Comment out `encryption_passphrase` in `config.php` and in
   `pandora_server.conf`, on all the nodes and on the Command Center. In
   `config.php` the line looks like this:
   `# $config["encryption_passphrase"]="passphrase";`; in
   `pandora_server.conf`, `#encryption_passphrase passphrase`.
4. Restart the server.

Keeping encryption enabled is recommended. Removing it leaves in plain text
everything listed in
[What it is and what it protects](#what-it-is-and-what-it-protects).

## Consequences and precautions

- **Identical passphrase everywhere.** A node or the Command Center with a
  passphrase different from the rest will not be able to read the fields
  encrypted with another passphrase. The failure is silent: no visible
  exception is raised, you simply get meaningless bytes where a password
  should be.
- **Passphrase lost, credentials lost.** There is no way to recover a
  forgotten encryption passphrase or to decrypt without it. Keep a backup of
  `config.php` and `pandora_server.conf`, the files that contain it, separate
  from the database backup, not next to it.
- **Protection against double execution.** The tool remembers whether it has
  already encrypted or decrypted the database and refuses to repeat the same
  operation twice in a row: you have to decrypt before encrypting again, and
  vice versa.
- **High availability.** The [réplica de Alta
  Disponibilidad](../parte-6/6.9-alta-disponibilidad-ha.md) works at database
  level: it copies the already encrypted fields as they are, without
  decrypting them or encrypting them again. It is the correct and expected
  behaviour; there is no need to run `pandora_encrypt_db` on the replica node.
- **Backups.** A backup of the database includes the encrypted fields as they
  are, and that is how it should be. To restore it you also need the
  encryption passphrase, which lives in the configuration files: keep it safe
  and separate, but available on the day you have to restore. A backup
  without its passphrase is only good for what is not a password.

## Reference for `pandora_encrypt_db`

| Field | Value |
|---|---|
| Installed path | `/usr/bin/pandora_encrypt_db` (server package; it is deleted when uninstalling it). |
| Usage | `pandora_encrypt_db [-d] [-m] <path to pandora_server.conf>` |
| `-d` | Decrypt instead of encrypt. |
| `-m` | Legacy option for the migration from version 749 to 750: when used, the tool leaves untouched the additional fields of the credential manager credentials, both when encrypting and when decrypting. It is not part of the normal encryption, decryption or passphrase change procedure; use it only if you know exactly why you need it, never to change the encryption passphrase. |
| Prerequisite | `encryption_passphrase` must exist in the indicated configuration file; if it is missing, the script ends with a warning that password encryption is disabled. |
