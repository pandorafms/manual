# Credential manager

Any task that has to connect to something with a username and password (a cloud
resource, a network device, a Windows machine) ends up asking for those
credentials in some form. Typing them every time is the most effective way to
end up with the same password copied in twenty places and forgotten in nineteen.
The credential manager avoids that spread: credentials are stored once in the Web
console, under an identifier, and from there whoever needs them uses them.

## What it is for

The manager centralises the username and the password (and, depending on the
credential type, some additional field) so that they are not repeated in every
Discovery wizard, every NCM task or every Deployment Center deployment. Those
tasks do not store the values, but the identifier of the credential, and they
retrieve it when they run: when the password changes, it is updated once in the
manager and all of them use the new one on their next run. Modules and policies
work in a different way, as explained in
[Where they are used](#where-they-are-used).

In the Web console it is in **Setup → Credential store**.

## Access and permissions

Entering the credential manager requires holding the **PM** and **UM**
permissions at the same time; with only one of the two, the Web console denies
access and that denial is audited. Scope also depends on the group: each
credential belongs to one, and if that group has propagation to child groups
enabled, the visibility filter includes them. The **All** group is a separate
case: its credentials are available to any user, with no need to belong to it,
but **creating or editing a credential in the All group additionally requires
the administrator permission of that group** ("ALL group manager"). A console
administrator sees and filters by any group without any of these restrictions.

## Creating, editing and deleting credentials

A credential identifier only accepts valid ASCII characters, and any space
becomes a hyphen when saving. Both the identifier and the credential type are
**fixed at the moment of creation**: when editing it later, the Web console
shows both fields but disabled, so there is no way to reuse an existing
credential for another type or to rename it; a new one has to be created.
Deleting a credential repeats the same visibility check as accessing it: if the
user has no permission over that credential by group or by ACL, the deletion is
rejected even if they know its identifier.

## Credential types

The form changes its fields depending on the credential type chosen:

| Type | Form fields |
|---|---|
| Custom | Account ID, password |
| AWS | Access key ID, secret access key |
| Azure | Account ID, application secret, tenant or domain name, subscription ID |
| Google | Full service account JSON (pasted whole) |
| SAP | Account ID, password |
| WMI | Username, password, namespace |
| SNMP | Version; community (v1/v2); in v3 also: security level, user, authentication method and password, privacy method and password |

**Google** is a special case: the form does not ask for a username or a password,
but for the whole JSON of the service account to be pasted. On saving, the Web
console extracts the service email and the key identifier from that JSON, only to
show them in the listing; when the credential is used, the full JSON is reused,
not those two loose values.

## Where they are used

The credential manager has no equivalent through the API or the command line:
every credential is created, edited and consumed from the Web console. The points
where a stored credential is used are:

- The **Discovery** wizards ([Automatic monitoring and discovery with
  Discovery](2.3-monitorizacion-y-descubrimiento-automatico-con-discovery.md)),
  both Host & Devices and Cloud: the task stores the identifier and retrieves the
  credential when it runs.
- **NCM** ([Network configuration management
  (NCM)](../parte-3/3.6-gestion-de-configuracion-de-equipos-de-red-ncm.md)), for
  access to the managed network devices.
- The **Deployment Center** ([Automatic agent distribution and
  installation](../parte-6/6.4-distribucion-e-instalacion-automatica-de-agentes.md)),
  when deploying EndPoints.
- The module editor and the SNMP or WMI modules of a
  [monitoring policy](2.10-politicas-de-monitorizacion.md): the credential
  selector only **fills in the form** of the module or the policy with the stored
  values; it is not linked live to the credential. If the credential changes
  later, the module does not find out, and it has to be applied again by hand.
- The **AWS** reports.

## Credentials and encryption

If the database does not have encryption enabled, the credential manager screen
itself warns that whatever is stored there will be kept unencrypted, with a link
to the encryption documentation. It is worth heeding that warning: a password
store in the clear is, above all, a gift for anyone who gets a copy of the
database. Encryption is an **Enterprise** feature. Enabling, changing or removing
the encryption passphrase is explained in
[Database encryption](../parte-9/9.5-cifrado-de-la-base-de-datos.md).
