    SNMP trap monitoring¶

    An SNMP trap is a notice the device sends on its own initiative, without waiting for anyone to ask it anything. It is the other side of the polling explained in Network monitoring: there Pandora FMS asks every so often; here it listens, and finds out about a downed port or a UPS switching to battery the moment it happens, without waiting for the next query. This chapter explains how to receive traps, where to see them, how to alert on them, filter them, translate them, forward them, protect against storms and generate test traps.

    What a trap is and how it reaches Pandora FMS¶

    The SNMP polling explained in Network monitoring is Pandora FMS asking; a trap is the device speaking on its own, with nobody asking it, at the moment something happens: an interface that goes down, a CPU that spikes, a UPS that changes state. Reception works in two steps: the system daemon snmptrapd writes every trap that reaches it to a log file —/var/log/pandora/pandora_snmptrap.log in a standard installation— and the Pandora FMS server reads that file.

    To enable it, in pandora_server.conf:

    snmpconsole 1

    Then snmptrapd has to accept the traps that are going to arrive. Its configuration lives apart, in /etc/snmp/snmptrapd.conf, with the syntax of net-snmp itself:

    authCommunity log public
disableAuthorization yes

    With those two lines, snmptrapd accepts and logs any trap that arrives with the public community. For SNMPv3 traps the user that sends them also has to be registered, with its engineID:

    createUser -e 0x0102030405 user_v3 SHA password AES

    The -e <engineID> is mandatory: without it, snmptrapd only accepts INFORM from SNMPv3 (the ones that carry confirmation) and discards the TRAP proper, which is what the vast majority of devices send.

    If snmptrapd is to be started and stopped by hand, instead of letting the Pandora FMS server itself manage it, the snmp_trapd manual token in pandora_server.conf marks that management as manual; from then on snmptrapd has to be launched with a specific log format so that the server keeps understanding it (see 9.3 · Full server configuration reference for the rest of the trap tokens).

    The reception port is the standard one for SNMP traps, 162/UDP.

    Minimal snmptrapd.conf to start with

    authCommunity log public
disableAuthorization yes
    With this and snmpconsole 1 on the server, any trap that arrives through the public community already shows up in the trap console.

    The trap console¶

    Operation → Monitoring → SNMP → SNMP console. Each row is a trap received, with columns for severity, source SNMP agent, enterprise string (the main OID of the trap), repetition counter, subtype, user, date, whether it has an associated alert, status and actions. The filters cover alert, severity, free text or by alias, status, group by field and a window of hours back —8 by default—, besides the trap type. From here, traps already dealt with are validated or deleted, and a new agent can be registered directly from the source IP of a trap that does not have one yet. A separate statistics tab summarises which sources and which enterprise strings generate the most volume. The icon of each row unfolds the full detail of the trap —all its variable bindings, not only the ones that fit in the column— without leaving the console.

    Traps are purged after a configurable number of days, just like the rest of the platform data (see "Max. days before delete traps" in 9.2 · Full console configuration reference).

    Which device sends the most traps

    In the trap console, grouping by SNMP agent sorts the list by source and shows at a glance which of the monitored devices is generating the most traps; the statistics tab does the same as a chart, with no need to count rows by hand.

    Trap alerts¶

    A trap alert looks for matches in the fields of the trap received, not in a module: OID (partial, or exact if it ends in $), trap type and subtype, value, IP of the source agent, variable bindings, and an action to trigger. The variable bindings —the data the trap carries besides the main OID— are compared against up to twenty numbered regular expressions, and their value is then available in the _snmp_f1_ to _snmp_f20_ macros to use them in the text of the alert itself. When a task has several alerts with a different position, they are evaluated in that order and only that same position keeps being checked while it keeps firing; it does not jump to the next one until it stops matching.

    linkDown of a specific switch

    OID 1.3.6.1.6.3.1.1.5.3$ (exact match of linkDown), the switch IP as source, and in the alert message the _snmp_f2_ macro with the index of the affected interface, taken directly from the variable bindings of the trap.

    Authentication failure

    OID 1.3.6.1.6.3.1.1.5.5$ (authenticationFailure), with no other filter than that one: any device that receives an unauthorised SNMP request —from any NMS, not only Pandora FMS— fires the alert.

    This is the essential part of associating an alert with a trap. All the fields, the actions, the templates and the scales of trap alerts are explained in depth in Alerts and notifications.

    Filtering traps¶

    Before saving anything, the server can discard traps by regular expression: if there are several filters in the same group, all of them have to match to discard the trap. They are managed from Monitoring → SNMP → SNMP filters.

    Discarding the traps of a noisy device

    A filter with the source IP of the device and no other criterion discards all its traps outright, without them even showing up in the console.

    Translating and customising traps¶

    From the factory, the translation of the enterprise string (the manufacturer OID, in the SNMP sense of the term) comes enabled; the one of the variable bindings comes disabled, and it has to be deliberately switched on with translate_variable_bindings 1 on the server if their content is to be seen already translated instead of raw. Both translations depend on having the MIB of the corresponding manufacturer loaded; to upload them, see the MIB manager.

    The SNMP trap editor (Operation → Monitoring → SNMP → SNMP trap editor) allows customising how an already identified trap looks: OID, Custom OID (a regular expression compared against the variable bindings, for the cases where the OID alone is not enough to identify the trap), severity, text and description. It only affects the traps that arrive after saving the change, never the ones already received.

    Renaming a proprietary trap

    A trap with OID 1.3.6.1.4.1.9.9.41.2.0.1 (Cisco, ciscoTrapSyslog) is edited so that it appears as "Cisco Syslog" with warning severity, instead of the raw OID it brings by default.

    Forwarding traps¶

    Every trap received can be forwarded to another management system, over v1, v2c or v3, with the snmp_forward_trap, snmp_forward_ip, snmp_forward_version, snmp_forward_community, snmp_forward_secName, snmp_forward_secLevel, snmp_forward_authProtocol, snmp_forward_authPassword, snmp_forward_privProtocol, snmp_forward_privPassword and snmp_forward_engineid tokens (see 9.3 · Full server configuration reference). Forwarding to localhost or to 127.0.0.1 is not supported: the server rejects it on start-up.

    Forwarding to a central NMS over v2c

    snmp_forward_trap 1
snmp_forward_ip 10.0.0.5
snmp_forward_version 2
snmp_forward_community public
    Every trap this Pandora FMS server receives is also forwarded to the NMS at 10.0.0.5, without ceasing to be processed locally.

    Apart from forwarding to another system, the general option Forward SNMP traps to an agent (if it exists) (Setup → System settings) decides what to do when the source IP of the trap matches that of an agent that already exists: with Yes, and change status, the trap is written as text in a module called SNMPTrap of that agent —created the first time a trap reaches it— and its status is updated too, so it can be dealt with like any other module when it comes to setting alerts or generating events; with Yes, but do not change status, it is logged the same way but without touching the module status; with No, do not forward, the trap stays only in the trap console.

    Integrating the traps of a UPS into the rest of the monitoring

    With Yes, and change status enabled and the UPS agent registered with its real IP, every trap it sends also stays in its SNMPTrap module, ready to have a text alert set on it just like on any agent module.

    Buffering for unreliable links¶

    Traps travel over UDP and with no confirmation: if the link between the devices and the Pandora FMS server goes down, the traps sent during the outage are lost. For sites with an unreliable link there is an alternative: a local snmptrapd at the site receives the traps and writes them to its log, and an EndPoint at that same site collects them with the grep_snmptrapd plugin and sends them to the server along with the rest of its data, with the reliability of the normal Pandora FMS transport. On the central server, the data server adds those traps to a separate file, the one indicated by the snmp_extlog token, and the trap console reads it just like the usual log.

    Requirement Detail
    Local snmptrapd At the remote site, receiving the traps from the devices
    Local EndPoint On the same machine, with the grep_snmptrapd plugin pointing at the log of that snmptrapd
    snmp_extlog on the server A file the Pandora FMS server can write to, different from the normal trap log (see 9.3 · Full server configuration reference)

    Processing the traps directly from the snmptrapd log is more efficient, so this setup only pays off when connectivity really is a problem.

    Traps from a site with an unstable link

    At the site, snmptrapd writes to /var/log/pandora/pandora_snmptrap.log and the local EndPoint carries in its configuration: 

    module_plugin grep_snmptrapd /var/log/pandora/pandora_snmptrap.log
    On the central server, pandora_server.conf includes snmp_extlog /var/log/pandora/pandora_snmptrap_ext.log. If the link goes down for an hour, the EndPoint keeps the deliveries that could not go out (its send buffer comes enabled from the factory) and, when the link comes back, the traps of that hour show up in the console.

    Protection against trap storms¶

    So as not to drown in traps when a device starts repeating the same notice without stopping, the server can limit how many traps from the same source it processes in an interval, and mute that source once the limit is exceeded (see 9.3 · Full server configuration reference for the tokens and their default values —disabled from the factory—).

    Stopping a storm from a faulty switch

    With the protection enabled and a limit of 50 traps in 600 seconds, as soon as the switch exceeds that rate the server stops processing its traps until the configured silence period passes, with no effect on the rest of the sources.

    Generating test traps¶

    The SNMP trap generator (Operation → Monitoring → SNMP → SNMP trap generator) builds and sends a test SNMPv1 trap —Cold start, Warm start, Link down, Link up, authentication failure, EGP neighbour loss or one of the manufacturer's own— to check that an alert or a filter reacts as expected, without depending on the real device doing anything.

    Simulating a linkDown and watching the alert fire

    With the alert of linkDown of a specific switch already created, the generator sends a Link down trap with the switch IP as source: if everything is configured right, the alert fires just as if the port had really gone down.
