    Network discovery with Host & Devices¶

    Host & Devices is the Discovery section that explores networks: it walks a range of addresses, asks every machine that answers what it is and what it is called, and registers it as an agent, with its modules, its relationships with the rest of the network and, if wanted, a map. It is the shortest path between "I have a network" and "I have a monitored network", and the only part of Discovery that comes built in from the factory, with no packages to install.

    Once the agents are created, Host & Devices steps aside: day-to-day monitoring is left in the hands of the network, WMI or plugin servers. What Discovery is in general, what a task is, where the task list is or what the Discovery server does is told in Automatic monitoring and discovery with Discovery; here it is taken as read.

    What Host & Devices offers¶

    It is in Management → Discovery → Host & Devices, and creating tasks in it requires write permission (AW) over the group. It gathers five options:

    Option What it is for
    Network scan The main option: explore one or several networks and register whatever answers.
    Import CSV Register agents from an inventory that already exists in a spreadsheet.
    EndPoint deployment Install EndPoints on machines that have already been located.
    Custom network scan Launch a discovery script of your own instead of the standard scan.
    Manage scan scripts Register those scripts of your own (requires PM).

    Network scan: first steps¶

    The usual case. When creating the task:

    • Task name and an optional description.
    • Discovery server that will run it and group it will belong to.
    • Networks: one or several, in CIDR format (192.168.10.0/24) or by fully qualified domain name, separated by commas, or loaded from a file with one network per line.
    • Interval: defined (with a time selector; 300 seconds by default) or manual, for tasks that are only launched by hand.
    • SNMP credentials to try, from the credential manager (see Credential manager): with none configured, the scan tries SNMP v1 and the public community by default; with credentials of your own, it tries with them (see Device discovery).

    Once the task is saved, it appears in the task list and runs according to its interval: it will create the agents it has to and their initial modules, unless results review is active.

    A whole /24 network

    Network: 192.168.10.0/24. With the default detection options (see below), the task scans the 254 possible addresses, tries SNMP with the public community and with the additional credentials given, and registers one agent per machine that answers.

    The agents a network scan creates are remote agents, with no configuration file behind them: they are good for SNMP or WMI monitoring from the server, but they do not accept local monitoring policies or mass configuration changes until an EndPoint is installed on top of them (see Deploying EndPoints from Discovery).

    Repeating the scan of a network that is already known does not duplicate what already exists. Discovery looks every machine up by its agent name and, if it finds it, updates its data —interval, operating system version and last contact, among others— instead of creating a new agent; if its IP address has changed, it adds it as an additional address without touching the one it already had. Modules follow the same logic: only the ones the agent is still missing are created (for example, a new network interface), never the ones it already has.

    Reviewing the results before creating agents¶

    With Review results on, the machines the scan finds do not become agents right away: they stay pending in a list and the user chooses which ones to register. It is worth turning it on in the first scan of an unknown network, or in large networks where nobody wants two hundred new agents showing up unattended.

    The option turns itself on —and can no longer be turned off— when the number of agents the task would create, calculated from the size of the configured networks, exceeds what the licence covers: in that case, reviewing the results stops being an option and becomes the only way not to run into the limit.

    The machines a scan finds go through an intermediate result status before becoming an agent: without results review on, the server itself registers them as soon as the task finishes; with it on, they stay pending until someone accepts them from the Web console.

    The review screen presents a tree with one node per discovered agent and, hanging from it, its detected modules; each one is checked separately, with buttons for "Select all", "Deselect all", "Expand all" and "Collapse all". The agents and modules that already existed before the scan appear disabled in the tree —they are already checked, but they cannot be unchecked— to make it clear that they are not going to be duplicated. The same screen also decides whether the task must generate the network map ("Create network map").

    Accepting the review creates nothing on the spot: the task goes back to the queue with the selection saved, and it is the Discovery server that, on its next run, registers the checked agents and modules.

    What the scan detects¶

    All these options are extras: whatever has been checked, every machine that answers the scan always receives a Host Alive module —an ICMP ping—, the minimum that guarantees the new agent says whether it is alive or not. SNMP, WMI and the rest of the options in this table add modules on top of that minimum; they do not replace it.

    Option What it adds By default
    Scan SNMP network interfaces Network interface modules and data for the topology scan of network maps Enabled
    Scan SNMP known hardware SNMP modules according to the device manufacturer, identified by its Private Enterprise Number Enabled
    Scan WMI devices WMI modules on MS Windows machines Disabled
    Resolve hosts names Name resolution of the machines found Enabled
    Guess hosts OS Operating system detection (it can make the scan quite a lot longer) Disabled
    Scan additional information Additional information, visible later in the agent description (it can also make the scan longer) Disabled

    SNMP credentials (v1, v2c or v3) and WMI credentials are typed in the form itself or chosen from the credential manager.

    Topology and network map¶

    With Create network map —on by default—, Discovery works out which machine hangs from which, assigns them a parent agent and generates a network map with the result (see Network topology maps). Parent detection, on by default, follows the network routes up to five hops before giving up.

    Importing agents from CSV¶

    For when the inventory already exists in a spreadsheet, Import CSV registers agents from a file, without going through a scan. The form lets you choose the server that will be assigned to the created agents, the field separator (comma by default), whether the agent alias must also be used as its name and whether the default basic monitoring is added to it (enabled by default).

    The file carries one row per agent with these columns, in this order:

    Column Content
    1 Agent name or alias
    2 IP address
    3 Operating system identifier
    4 Interval, in seconds
    5 Group identifier
    6 Comments (optional)
    7th onwards Identifiers of the network components to apply

    The operating system and group identifiers are the ones the Web console already uses in its own management listings; the network component ones are those of the component library. The import rejects a row if the agent name already exists, if the group given does not exist or if the row is missing mandatory columns.

    An example with four machines: a Linux web server and a Linux database, a Windows domain controller and a switch. Comma separator, no header row:

    web01,192.168.10.21,1,300,13,Main web server,37,39
db01,192.168.10.30,1,300,8,MySQL in production,39
dc01,192.168.10.5,9,300,2,Domain controller
sw-core,192.168.10.1,18,300,9,,3,53

    Read column by column, the first line creates the agent web01, with IP 192.168.10.21, Linux operating system (1), interval of 300 seconds, in the Web group (13), with the comment "Main web server" and two modules created from the network components Check HTTP (80) (37) and Check SSH (22) (39). The switch leaves the comment empty —the comma is kept so the columns do not shift— and receives the SNMP components Sysname (3) and System Uptime (53). The identifiers in the example are the ones a new installation brings (operating systems Linux 1, Windows 9, Switch 18; groups Servers 2, Databases 8, Network 9, Web 13); in an installation with history they may have changed, so it is worth checking them in the console before preparing the file.

    Three details that save trouble

    • No header. All lines are processed as agents; a row of titles would end up in the report as a failed line (its "group" does not exist).
    • Default monitoring already adds availability and latency. With Add default monitoring on, there is no need to list the Host Alive and Host Latency components: they would be duplicated.
    • Report lines are counted from zero. If the result says "Line 2", it is the third line of the file.

    Deploying EndPoints from Discovery¶

    After discovering machines, EndPoint deployment lets you install an EndPoint on them directly: over SSH on Unix systems (Linux, BSD, Solaris, AIX, HP-UX) and over WinRM —or its encrypted variant, Secure WinRM— on MS Windows. The full detail, including installer and credential registration, is in Automatic agent distribution and installation.

    Custom network scan¶

    When the standard scan is not enough, Custom network scan launches a script of your own in its place. The script is registered beforehand in Manage scan scripts (PM only), giving its name, the full path of the executable on the server, a description and the fields it needs —each one with its own help text, a default value and the option of hiding it if it is a credential—.

    When creating the task, the data common to any Host & Devices task are asked for —name, comment, Discovery server, group, interval (600 seconds by default), event and alert action in case of failure— and, in a second step, the script already registered that is to be run, with its fields filled in.

    A freshly made installation already brings two registered scripts, with nobody having to register them by hand:

    • IPMI Recon explores a network looking for IPMI management controllers with the credentials given, for the cards that are managed through that channel instead of through the normal network (see Advanced automatic discovery (IPMI, etc.)).
    • IPAM Recon checks which addresses of a network managed by IPAM are available and gives them a name, and associates the result with that IPAM network (see IP address management (IPAM)).

    What the script has to do by itself

    The Discovery server runs the script handing it the task identifier, the group one and the value of each configured field, but it does not interpret what the script writes on its output: it neither creates agents nor modules from it. That output is only kept, for diagnosis, when the server works with verbosity 10: it goes to the server log and to a copy per task in the discovery/ directory, next to the logs. A custom scan has, therefore, to register its own findings —through the API or by sending its own data XML— inside the script itself; Discovery only launches it and marks the task as failed or finished according to the exit code it ends with.

    How it discovers the network: the heuristic¶

    Finding the machines that answer on a network is only the first step; Discovery also tries to work out how they are connected to each other, in order to raise the complete network map. It does so with a heuristic of several steps, each one built on the previous one.

    Routes to the targets¶

    For every target network, Discovery launches a traceroute and adds, as additional networks to explore, the ones of the intermediate hops it keeps finding along the way. In the simple scan, that traceroute points at the address 8.8.8.8 —to try to "go out" to the Internet—, and all the networks the Discovery server itself is connected to directly are added too. The mask of a network discovered this way is fixed at /24 unless it can be determined more precisely, in which case it may stay as wide as the real data indicates.

    Device discovery¶

    With the networks already gathered —plus the ones given by hand in an advanced configuration—, Discovery uses nmap to locate the machines that answer on each one and to test whether they have the SNMP port open. The credentials chosen for the task are tried on the ones that do (see What the scan detects): with no credential of your own configured, the scan tries SNMP v1 and the public community by default; with credentials of your own, it tries with them. The ones that work stay in cache, so as not to repeat the test on every round. WMI, on the other hand, is not detected by nmap: if Scan WMI devices is on, it is queried directly with the WMI credentials of the task.

    Gateway discovery¶

    For every network, Discovery tries to work out its gateway by querying the route table of the devices that answered over SNMP: the IP address that appears most often as a hop in that table, among all the SNMP devices of the network, is taken as its gateway. If no device reveals it over SNMP, Discovery falls back on an order of likely addresses within the network: first .1, then .254, .100 and last .10. That network gateway does not prevent the specific devices whose real gateway can be determined from being assigned their own.

    Additional IP addresses, MAC and switches¶

    On every device with SNMP, Discovery queries its additional IP addresses and crosses them with the interface and IP-MAC resolution tables to know which MAC address corresponds to which IP and to which interface. With the table of MAC addresses learned by the switches it gathers more addresses and, on the way, marks as a switch any device that has data in that table. Those same tables —the IP-MAC resolution one and the switches one— also serve to work out through which interface each neighbouring device has been reached, data that is needed later to trace the map connections. When the device supports it, Discovery also adds whatever it finds through CDP and through LLDP, two protocols meant precisely for a machine to announce to its neighbours who it is.

    Name resolution and operating system detection¶

    With Resolve hosts names on —it is by default—, Discovery tries to give every machine a name by reverse DNS; if it does not manage it, it tries over SNMP and, as a last resort, by what CDP or LLDP may have told. That order is not entirely strict: when it finishes scanning the whole network, Discovery reviews again the names seen by CDP and LLDP and, if any of them matches a device already named by DNS or SNMP, it overwrites it without asking —a deliberate simplification of the mechanism itself: a name from a more trusted source is worth more even if it arrives late—. With Guess hosts OS on —off by default, because it makes the scan quite a lot longer—, operating system detection is down to nmap.

    Additional information¶

    With Scan additional information on —off by default, for the same reason as operating system detection—, Discovery looks for a description of the device: first over SNMP; if there is none, it falls back on nmap probing some usual ports in search of a title or a service identification; and here too whatever CDP and LLDP contribute is added, with the same caveat as before: they can overwrite data already obtained from another source.

    Building the network map¶

    With all that information gathered, Discovery rebuilds the connections between devices in several steps:

    1. If a device has several network interfaces and in some of them there appear IP addresses that are not from its own network, it looks that address up in the network it belongs to, to replicate the information of that interface there.
    2. It marks as trunk interfaces the interfaces of the routers and switches through which more than one device has been reached.
    3. It counts, for every non-trunk interface of every device, how many devices have been discovered through it.
    4. If the count gives exactly one, and that other device sees in turn a single connection that matches the origin, it traces a direct connection between the two.
    5. If the count gives more than one and any of the candidates on the other side turns out to be a trunk interface, it creates an aggregation node —a "bridge"— that gathers that interface and all the ones on the other side, except the trunk ones.
    6. The interfaces left with no connection in the count are reviewed in case any of their candidates is already connected to a bridge: if so, they are linked to the same point.
    7. The trunk interfaces still to be connected are linked to an existing bridge or to a new one, depending on whether or not there is some device on that side already connected to one.
    8. A device that, after all this, still has no connection is not left orphaned: a bridge connected to its gateway is created and the device joins it directly, without going through any specific network interface.

    The result is the network map that Host & Devices shows (see Topology and network map): it may not match other maps already saved in the Web console if these have been edited by hand or have gone a long time without being updated.

    Deep-scan intermediate transit networks and Scan secondary networks attached to hosts, the two in the advanced options of the scan (see just below), widen which networks enter the first two steps of this heuristic —device and gateway discovery— and whether the neighbours that appear outside the current network are added as new networks to explore.

    Advanced scan options¶

    Option What it does By default
    Advanced mode Replaces the automatic network scan with the ones the user indicates; it requires traceroute and route installed on the Discovery server Simple mode
    Blacklist of IPs and networks Addresses or networks excluded from the scan, in the same format as the networks to scan (or a file) Empty
    Deep-scan intermediate transit networks Widens discovery to the intermediate networks the path to the targets goes through Disabled
    Scan secondary networks attached to hosts Widens discovery to other networks connected to the machines already found Disabled
    Apply autoconfiguration rules Applies the self-provisioning rules to the created agents (see Self-provisioning mechanisms) Disabled
    Event and alert action on failure Generates a critical event or launches alert actions if the task ends with an error (see Discovery task alerts) Disabled
