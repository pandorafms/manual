# Collections

A `module_plugin` often needs something more than the command written in its
configuration: a script, a binary, a configuration file of its own. Copying
that file by hand on every agent that is going to use it works the first time
and becomes a problem the second, when it has to be updated on twenty machines
at once. A **collection** is Pandora FMS's answer to that problem: a package
of files that is uploaded once to the Web console and deployed, compressed, to
the EndPoints that need it.

A collection can be assigned to an individual EndPoint, to a monitoring policy
—which propagates it to all its agents— or to a Satellite server. The Web
console prepares the package; each recipient is in charge of receiving it. This
chapter goes through how a collection is created and edited, how it is applied
and synchronised, and what changes depending on where it is assigned from.

## Creating and managing a collection in the console

In the Web console, collections are created in **Management → Configuration →
Collections**. The creation form asks for a name, a group, a description and an
optional short name: if it is left empty, the console generates one with a
timestamp (`fc_<timestamp>`). That short name is not a cosmetic detail, it is
the identifier that later appears as a directory in the console and on each
EndPoint, so it is worth setting it by hand and making it say something.

| Requirement | Detail |
|---|---|
| At least one file in the collection | An empty collection does not get to generate the compressed package |
| Shape of the short name | Only letters, numbers, `_` and `-`; if left empty, one is generated automatically with a timestamp |
| ZIP compression utility on the console server | Needed to generate the package when applying changes |
| Compressed package size not above the configured limit | See the warning below |

With the collection already created, editing adds its resources: uploading a
file, creating a directory or creating a text file that is edited directly from
the console itself, without going through the administrator's computer. All of
that is stored on the console side, in an attachment directory with the short
name of the collection.

There is a size limit for the final compressed package (`collection_max_size`).
When applying the changes, the Web console first creates a temporary ZIP. If it
exceeds the limit, it does not publish it in the remote configuration path and
does not compute its MD5; the collection is left pending application. Its
content has to be reduced and the changes applied again.

!!! example "A collection for an Apache plugin"
    The `apache_plugin` collection holds a single file, the script
    `pandora_apache_v1r1.pl` that Pandora FMS brings installed by default: it
    is the package that an Apache `module_plugin` expects to find on the
    EndPoint before it can run.

## Synchronising the changes: applying a collection

Adding or modifying resources of a collection does not deploy it on its own:
the Web console shows a yellow triangle icon in the list next to any collection
with changes pending application. When it is applied, the console server
compresses the whole directory into a ZIP, computes its MD5 and leaves both
files in the remote configuration path, ready for the EndPoints to download on
their next cycle.

A collection can be in three states: pending application (the changes have not
been published), correct (the ZIP and the MD5 are up to date) and lost
directory, if the directory of the collection disappears from the console side.

The short name of the collection does not only identify the package: it is also
the name of the base directory of the collection on the console side
(`/pandora_console/attachment/collection/<short_name>`), which can hold
subdirectories without any problem.

## Assigning a collection to an EndPoint

In the Web console it is assigned from **Resources → Manage agents**, the
**Collection** tab of the EndPoint. The tab lists the collections available
according to the group of the EndPoint and a button to add them; the
synchronisation state of each one is shown with a warning icon if it is still
empty or has not been applied.

Without remote configuration enabled on the EndPoint, the Web console cannot
deliver the collection to it —this was already explained in
[Monitoring with EndPoints](2.1-monitorizacion-con-endpoints.md)— so that
requirement is not repeated here. A few minutes after it is assigned, the
EndPoint itself should appear listed in the agents tab of the collection,
confirming that it already has it.

!!! example "Assigning the Apache collection to an EndPoint"
    With `apache_plugin` already created and applied, it is assigned to the
    `Servidor-Apache-01` EndPoint from its Collection tab: on the next remote
    configuration cycle, the EndPoint downloads the package.

## Where the collection ends up on the EndPoint

Each EndPoint keeps its collections in a subdirectory of its own inside its
collections folder, with the short name of the collection as the subdirectory
name: on Windows,
`%ProgramFiles%\pandora_agent\collections\<short_name>`; on Unix or on the Go
EndPoint, `/usr/share/pandora_agent/collections/<short_name>` in a package
installation, or in general the `collections/<short_name>` subdirectory next to
the configuration file of the agent itself. That each collection has its own
subdirectory is no coincidence: it prevents two different collections from
stepping on each other if they share the name of some file. A `module_plugin`
references a file of the collection with its full path.

Uncompressing the package does not work the same on all EndPoints. The Perl
EndPoint (Unix) and the Windows EndPoint invoke an external `unzip` utility —on
Windows it is included from version 3.2 of the EndPoint, inside
`%ProgramFiles%\pandora_agent\utils`—. The Go EndPoint, on the other hand,
uncompresses in memory with its own standard library, without depending on any
external binary installed on the system.

As for the transfer mode the package arrives with, there is no restriction of
its own for collections: they use the same mode configured for the rest of the
remote configuration of the EndPoint (see
[Monitoring with EndPoints](2.1-monitorizacion-con-endpoints.md)), with no
distinction for collections in particular.

!!! example "Full path of a file of the collection"
    The script of the `apache_plugin` collection on a Unix EndPoint installed
    from packages is left in
    `/usr/share/pandora_agent/collections/apache_plugin/pandora_apache_v1r1.pl`,
    and that is how the `module_plugin` that uses it references it.

## How it stays synchronised: MD5 control

The MD5 of the collection package is computed in the Web console when applying
changes and is sent to the EndPoint along with the ZIP. On every cycle, the
EndPoint compares that remote MD5 with the one it has stored locally: if they
match, it does nothing; if they do not match, it downloads and uncompresses the
whole collection again.

This has a practical consequence worth keeping in mind: if the files of a
collection already deployed on an EndPoint are edited by hand, those changes
survive as long as the collection does not change in the console. As soon as it
changes, the next synchronisation overwrites the whole collection and those
local modifications are lost.

The cleanup of collections that no longer appear in the configuration does not
guarantee an immediate deletion. The Perl EndPoint runs `check_collections` on
every cycle, except in `debug` mode; it skips the deletion if there are broker
agents or it cannot open the collections directory. The Go EndPoint also checks
on every cycle, but it skips the entries whose name starts with `.` and may
fail to read or delete files. On Windows, the collections check calls
`purgeDiskCollections`, which skips the deletion if there are broker agents.
When the assignment is removed from the Web console, it stops appearing in the
corresponding remote configuration. Deleting a collection from the Web console
does not guarantee either that it disappears immediately from the EndPoint: the
removal of the local files depends on the cleanup running and being able to
complete.

## Collections and monitoring policies

From the Web console, a collection can also be assigned to a whole monitoring
policy instead of to an individual EndPoint, with the same underlying mechanism
but propagated to all the agents of the policy. It is managed from the
**Collections** tab of the policy: adding or removing an existing collection
and applying the policy so that the change queue propagates it to all its
agents. The rest of the management of a policy —applying it, the change queue,
its other tabs— is outside this chapter; see
[Monitoring policies](2.10-politicas-de-monitorizacion.md).

## Collections on the Satellite server

A Satellite server can also receive collections from the Web console:
**Management → Servers → Manage satellite server**, **Collections** icon: a
list of collections available with an actions column to add or remove them.
When a collection is added, the Web console writes
`file_collection <short_name>` in the remote configuration of the Satellite and
updates the **MD5 of that configuration file**. The Satellite compares that MD5
to detect changes in its configuration; when processing `file_collection`, it
queries the **MD5 of the package** of the collection separately. If it differs
from the local one, it downloads the ZIP and uncompresses it with the
configured utility. They are not the same MD5, nor the same code that an
EndPoint uses to receive collections.

With the configuration included in the package of the Satellite server
(`agent_conf_dir /etc/pandora/conf`), the collections are left in
`/etc/pandora/satellite_collections/`. The path is derived from
`agent_conf_dir/../satellite_collections` and can be changed with
`collection_dir`. The [public collections
wiki](https://pandorafms.com/manual/!current/es/documentation/pandorafms/technical_annexes/28_pfms_file_collections#colecciones_de_ficheros_en_servidor_satelite)
also states that path.

## Collections from the Command Center

Since Pandora FMS 729 OUM, collections can also be managed centrally from the
Command Center Web console: **Centralised management → Agent management**, the
**Collections** tab. The operation is the same as in the console of a node; the
only thing that changes when operating from the Command Center is that
synchronisation towards the nodes is done through its own synchronisation
mechanism between node and Command Center.

## Permissions

The management of collections in the Web console —creating, editing, applying,
assigning— requires agent write permission (AW) on the group of the collection.
The list of available collections is filtered by the groups where the user has
that permission, plus the All group.

| Requirement | Detail |
|---|---|
| Viewing the list of collections | It is filtered by the groups with agent write permission (AW), plus the All group |
| Creating, editing, applying or assigning a collection | Agent write permission (AW) on the group of the collection |
