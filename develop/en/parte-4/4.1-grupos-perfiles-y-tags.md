# Groups, users, profiles and tags

Pandora's web console is designed so that **several users can work on the same
installation without seeing each other**. That is possible because the permission
system is *multitenant*: one server, one database, and each user seeing and
touching only what belongs to them.

There is no mystery to it, but there are two pieces you need to understand before
creating the first user: **groups** and **profiles**.

A **group** decides *what* a user sees. A **profile** decides *what they can do*
with it. The combination of the two, assigned to a user, is the permission. And
since the same user can have different profiles in different groups, you can set
up anything from the technician who only looks at their department to the
administrator who sees everything.

## The permission model

**Groups** are sets of elements with their own rules, and they exist to control
access to agents and everything that hangs off them. The rule to be clear about
from the start: **an agent belongs to a single group**, but **a user can have
access to several groups**.

There is an exception worth knowing from the start: an agent can also be in
**several secondary groups** at the same time, and then users from all of them see
it. We cover it in detail below.

**Profiles** define which operations a user can perform. They are a set of access
bits (view, write, manage alerts, administer...) assigned per group. Thus, the
same user can be read-only in the "Production" group and administrator in the
"Laboratory" group, which is exactly what a well-built multitenant environment
requires.

Hence the warning that has caused more than one scare: **a user with no profile
and no group cannot log in**. It is not a bug, it is by design. Before creating
users, it is better to have the groups and profiles decided, not the other way
around.

| Requirement | Detail |
|---|---|
| Groups defined | The user needs at least one group to access |
| Profiles defined | The user needs at least one profile assigned in that group |
| Administrator user | A user marked as administrator (*superadmin*) bypasses the ACL and has access to everything |

## Agent groups

Groups work as **containers** for agents: a department, a company, a site, a
customer. They are the basis of multitenancy, because they allow differentiated
visibility over the same inventory. The menu is in **Management → Resources →
Manage groups**.

When creating a group (**Create group**), these are the fields that matter:

- **Name.** If you are going to use the group in automatic EndPoint provisioning,
  leave it without spaces or strange characters. They are supported, but you save
  yourself trouble.
- **Parent.** A group can hang off another. Permissions can propagate to children
  (see **Propagate ACL** below).
- **Password.** Optional. It restricts agent self-creation: only those that bring
  that same password are created. Useful so that nobody invents agents in a group
  that is not theirs. Do not use spaces or symbols.
- **Alerts.** If checked, the group's agents can send alerts. It is the quick
  switch to cut the module alerts of an entire group: when off, the server does not
  evaluate them, but data and status events carry on as usual. It applies to the
  agent's primary group and does not travel down to child groups. How it fits with
  the other valves is in
  [Protection against event storms and events in process](../parte-5/5.5-alertas-y-notificaciones.md#protection-against-event-storms-and-events-in-process).
- **Propagate ACL.** If active, child groups inherit the parent's permissions. The
  **All** group has it enabled by default.
- **Custom ID.** Your own identifier to integrate it with an external system (a
  CMDB, for example).
- **Contact** and **Other.** Contact information and notes, available in the
  `_groupcontact_` and `_group_other_` macros.
- **Max agents allowed.** Agent limit for the group. Default `0`, which means no
  limit.

Each group can have its own **visual theme** in **Group settings → Style
configuration**. If a user belongs to several groups with their own theme, the
console applies the one from the first group other than **All** that has it
configured. And the theme the user chooses in their preferences overrides the
group's.

### Secondary groups

An agent belongs to a group, yes, but Pandora FMS allows it to belong **as well**
to other groups: these are the **secondary groups**. The agent keeps its main
group and the necessary secondary ones are added.

What it is for, with the case that explains itself: an agent lives in
"Applications", but the "Networks" team also needs to see it. Instead of
duplicating the agent or putting everything in a common group, "Networks" is
marked as a secondary group and users with permission in "Networks" start seeing
that agent just like the "Applications" users. It is the clean way for **two users
with different permissions to access the same agent without sharing a group**.
They are set in the **Advanced** tab of the agent form (see
[2.21](../parte-2/2.21-configuracion-comun-de-los-agentes.md#secondary-groups)).

They are assigned on the agent record, in the **Secondary groups** field, under
**Resources → Manage agents**. They can also be changed from bulk agent
operations. A detail that avoids confusion: the main group cannot be repeated as a
secondary one; the form itself prevents it.

What changes when an agent has secondary groups:

- **Visibility.** The agent is visible to anyone with permission in its main group
  **or** in any of its secondary groups. The relationship applies to everything
  that hangs off the agent: modules, events, alerts, SNMP traps, inventory and
  reports.
- **Filters.** In the event and alert views there is a **Search in secondary
  groups** checkbox, so that the search takes secondary groups into account. If a
  user is only related to the agent through a secondary group and that checkbox is
  off, they may not see its information. Enabling it has a cost: it forces the
  server to cross-reference more data.

Three warnings that save support calls:

- **The *Tree view* can show the agent repeated.** If an agent is in several
  groups, it appears once per group. That is normal, not an error.
- **Deleting a group deletes its links as a secondary group.** If that group was
  marked as secondary on an agent, those agents stop belonging to it.
- **It has a performance cost.** It is an optional feature: if no agent uses
  secondary groups, the console skips the additional cross-references. As soon as
  it is used, many lists and counters add work. Use it with judgement, not as a
  substitute for good group organization.

### The All group

The **All** group does not exist as such in the database: it is a **code-controlled**
group with the reserved identifier `0`. Depending on the context, it means *all*
groups or *any* of them, and it saves you from ticking groups one by one. It is the
piece that makes "this user administers everything" easy to say.

### Deleting a group is irreversible

Here it is worth reading twice before clicking. **Deleting a group cannot be
undone.** And what is worse: the agents it contained **still exist and keep
working**, but they stop appearing anywhere in the web console. They are left
orphaned.

To recover them, you have to reassign them to a new group from the CLI, with a
command like:

```bash
pandora_manage /etc/pandora/pandora_server.conf \
  --update_agent "pandora.internals" "group_name" "New_group" "use_alias"
```

The destination group **must not have spaces or symbols**. Before deleting a
group, check how many agents it has.

### Importing groups from CSV

If you need to create many groups at once, they can be imported from a file in
**Management → Admin tools → Extension manager → CSV import group**. The file has
the fields in this order, separated by the character you choose (comma by
default):

```
Group name, icon, parent id, propagation (1 or 0)
```

Choose the file with **Select a file**, adjust the **Separator** and click **Go**.

### Group recursion in the views

**Propagate ACL** and **group recursion** sound the same and are not. Propagate
ACL decides whether permissions go down the group tree. Recursion is something
else: it is a checkbox that appears in the filters of many views (events, reports,
policies...) and makes the view also include the **subgroups** when you choose a
group.

It is convenient when you filter by a parent group and want to see everything that
hangs off it, but it is not free: the console itself warns that it can affect
performance. Enable it when you need it, not out of habit.

## Users

Users are managed in **Management → Profiles → Manage users**. When creating or
editing one, these are the fields worth knowing:

- **Administrator user.** A *superadmin* is not governed by the internal ACL: they
  have access to everything. A standard user is governed by the permissions
  assigned to them.
- **Login Error.** If checked, the user can only log in through the API, not
  interactively through the web console.
- **Local user.** Forces authentication against Pandora FMS's own database. Other
  authentication methods exist (see Part 04 · External authentication).
- **Session timeout based on.** Enabled by default. It closes the session if there
  is no activity for the configured time.
- **Session timeout (mins).** The default value is `0`; in that case the value
  from the general authentication configuration is used. To make the session never
  expire, set `-1`. Note: a screen left open with auto-refresh does not count as
  inactivity.
- **Language.** The language in which that user will see the console. By default,
  the system's.
- **Block size for pagination.** How many rows per page that user sees.
- **Timezone.** The time zone used to show data to them.
- **Login allowed IP list.** If enabled, it limits login to a list of addresses or
  ranges separated by commas. The `*` wildcard allows any address.
- **Homescreen.** The user's start screen on login: by default, a visual console,
  the event list, the group view, the tactical view, the alert detail or an
  external link. Be careful about setting a dashboard from a group that is not
  theirs as the start screen: they will only see the dashboards of the groups they
  belong to.
- **Profiles/Groups assigned to this user.** Here the user's profiles and groups
  are assigned; this is what really gives them permissions.

Each user can adjust part of their own record in **Operation → Workspace → Edit my
user**, but **not** their group permissions. There is also the **API Token** to
authenticate through an HTTP header with a *bearer token*.

### Notifications

Pandora FMS has a notification system for users, with group management so you do
not go crazy administering them. It is configured in **Management → Settings →
System Settings → Notifications**, and there are six categories:

- **System status.** Generated by the Pandora FMS server itself.
- **Message.** Messages between users.
- **Pending task.** Pending tasks from features such as Discovery.
- **Advertisement.** Notices and proposals from Pandora FMS.
- **Official communication.** Official communications for extraordinary matters.
- **Suggestions.** Suggestions and tips.

The **ENABLE USER CONFIGURATION** switch decides, for each category, whether users
can turn those notifications on or off in **Operation → Workspace → User
notifications**, both in the console and by email.

Two rules that explain almost every surprise:

- For them to arrive by email, the user must have their email address configured
  **and** the server must know how to send email.
- If a whole group is subscribed to a category, its users receive those console
  notifications and **cannot turn them off**, even if the user configuration
  switch is active. Group membership weighs more than personal preference.

A *superadmin* ends up in **all** categories, whether they want to or not, **when
created or edited from the web console**. A *superadmin* created or modified **by
CLI** is not added to the notification system: if someone "does not receive
anything", start by checking where the account was created.

#### Browser push notifications

In addition to console and email notifications, Pandora FMS can launch **pop-up
notifications to the operating system** through the browser used to access the
console. They are enabled in **Management → Settings → System Settings →
Notifications → Web Push notifications**.

The requirement that breaks more than half the attempts: **HTTPS is needed**. If
the console runs over HTTP, the browser itself rejects the notifications. And even
with HTTPS, they do not work in incognito mode or in Chromium or Chrome's guest
mode, nor if the browser profile has them blocked. Pandora FMS only notifies in
**the browser profile used to log in** to the console, not in the others.

When you enable the **Enable Web Push Notifications** switch, the browser asks the
user whether to allow them. The **Send test notification** button checks that it
works, but use it sparingly: the message reaches **all** registered subscriptions,
not just yours. Each stored subscription does not identify its owner.

If a user wants to remove them, there are several ways: clear the browsing data of
that profile, block notifications in the profile, delete the profile (carefully,
it takes the other sites with it) or create a new profile and say **No** when
asked.

## Profiles

Profiles define what a user can do. They are managed in **Management → Profiles →
Manage profiles**. Five come out of the box and you can create as many as you need:

| Profile | What it is for |
|---|---|
| **Operator (Read)** | The read-only one: view without touching |
| **Operator (Write)** | The daily operation one: view and write |
| **Chief Operator** | Extended operation |
| **Group coordinator** | Group coordination, with group and user management |
| **Pandora Administrator** | Full platform administration |

Exactly which bit each one carries is the table below: a profile is nothing more
than a combination of those bits.

A profile is a collection of **access bits**. These are the ones the product ships
with and what each one enables:

| Bit | What it allows |
|---|---|
| **AR** | View agent data (all views), tactical view, group view, view users, SNMP console, *Tree view*, extension groups and search bar |
| **AW** | Agent management view, agent and `.conf` editing, bulk operations, create agent, duplicate remote configuration, view and manage policies, manage filters |
| **AD** | Manage service downtimes and disable an agent, module or alert |
| **LW** | Assign already-created alerts and manage alerts |
| **LM** | Define and modify alert templates and actions |
| **LF** | Force alerts and force module checks |
| **UM** | User management |
| **DM** | Database maintenance |
| **ER** | View events |
| **EW** | Validate and comment on events, manage filters and run responses |
| **EM** | Delete events, change owner and reopen events |
| **RR** | View reports and graphs, apply report templates and view *Cronjobs* |
| **RW** | Create visual consoles, reports and combined graphs; view, edit, run and create *Cronjobs* |
| **RM** | Create report templates; view, edit, run, create and delete *Cronjobs* |
| **MR** | View network maps |
| **MW** | Edit network maps and delete your own |
| **MM** | Delete any network map |
| **VR** | View visual consoles |
| **VW** | Edit visual consoles and delete your own or any |
| **VM** | Manage visual consoles |
| **NR** | View NCM data |
| **NW** | Operate NCM |
| **NM** | Administer NCM |
| **PM** | Pandora administration: manage responses, event columns, *update manager*, inventory modules, modules, SNMP console, profiles, servers, audit, *setup*, extensions and all kinds of *Cronjobs* |
| **GW** | Group management: a non-*superadmin* user can only edit the group of their profile, and the children if the group has **Propagate ACL** |

There are also combinations that enable specific functions: **EW** allows
executing event responses (the selector is also shown with **EM**, but execution
requires **EW**); the “Create ticket in Pandora ITSM from event” response opens the
ticket creation form, which requires **RR** in Pandora FMS. **IW** is no longer
used. **LM + AR** or **AW + LW** allow validating alerts.

A warning that saves arguments: ***superadmins* are exempt from the ACL**, even if
they have the administrator profile assigned. The ACL only binds everyone else.

## Assigning permissions

Permissions are granted from the user edition, assigning **groups and profiles** on
the record. And here it is worth keeping in mind the coexistence rules between
administrators and user managers (**UM** permission), because they are the source
of half the questions:

- A manager with **UM** on the **All** group can manage any user, whatever group
  they belong to.
- A manager only sees and edits the profiles and groups of **the users they can
  see**, that is, of the groups they manage with UM.
- A manager **without** UM on a group cannot even see which users belong to that
  group.
- A manager **cannot remove UM** from another user who has the same permissions on
  the same group. Only an administrator can touch that.
- An administrator can create other administrators and manage anyone.

When the last profile/group relationship of a user who is also going to be deleted
is about to be removed, the console warns first. It is worth reading the warning.

### Hierarchy

Permission propagation to child groups is controlled with **Propagate ACL** in the
parent group. If you want to cut it for a specific user, when assigning the
permission check **No hierarchy** and the ACL does not go down the tree.

The group hierarchy is independent of **secondary groups**, which are something
else and are explained in "Secondary groups".

## Tags and extended per-tag permissions

Groups and profiles give permissions "in bulk": a whole group, a complete profile.
To fine-tune further there are **module tags**. With them you can decide that a
user sees some modules and not others **within the same group**, which is exactly
what group permissions cannot reach.

### What a tag is and where it applies

A tag is a named mark that is defined once and reused. They are created in
**Management → Resources → Module tags**, and the screen asks for:

- **Name.** The tag identifier. It does not accept commas.
- **Description.**
- **URL.** A help link that must exist before you set it.
- **Email** and **Phone.** Contact data used later in the alerts associated with
  the tag (see below).

The tag list shows, for each one, how many **modules** and how many **policy
modules** carry it. Managing them requires an administration profile; in a Command
Center with **centralized mode**, the information is read-only and is managed from
the Command Center itself.

And a nuance that saves useless searches: **tags are assigned to modules, not to
agents or groups.** They are set (and removed) on the module record, in the
categorization section, **Tags** field. Since a policy module can also carry them,
tags travel with the policy and apply to all agents that receive it. There is also
a bulk operation to tag modules and policy modules at once. A module can carry
several tags.

### Per-tag permissions (ACL)

Here is the trick. In the user's profile and group assignment there is a **Tags**
selector, next to the group and the profile. The rule is simple:

- If left **empty**, the user sees **all** modules in that group.
- If one or more tags are filled in, the user sees **only the modules that carry
  those tags** within that group.

The restriction is **per combination of profile, group and tags**: the same user
can see some modules in one group and different ones in another. Tags
**complement** group access, they do not replace it: the group and the profile are
still required.

Two warnings worth their weight in gold:

- **A profile without tags opens everything.** If the user has several profiles on
  the same group and **any** of them does not restrict by tags, the user sees all
  modules. The most permissive restriction wins.
- **Tags propagate with the group.** If the group has **Propagate ACL** enabled,
  the tag restriction also goes down to child groups.

### Limits, cost and viewer

The tag-based security mode **has a performance cost**: it forces modules to be
cross-referenced with tags on every query. It is designed to give access to
**small portions** of information, so it is not advisable to go beyond **two or
three tags** per combination of user, profile and group. For serious segmentation,
groups are the reasonable choice; tags are a scalpel, not a sledgehammer.

And a nuance that prevents misunderstandings: in some global views (tactical view,
group view, tree counts) the totals show **all** modules, not only those the user
sees through their tags.

To explore monitoring by tag there is the **Tag view**, available in Enterprise
installations, in **Monitoring → Views**.

### Tags in alerts

Since a tag stores an email and a phone number, alerts can use that data from the
module that carries it. They are useful when the notification has to reach whoever
actually looks after that system, not always the same inbox:

- `_moduletags_` and `_name_tag_` replace the **names** of the module's tags.
- `_email_tag_` replaces the **emails** of the module's tags.
- `_phone_tag_` replaces the **phones** of the module's tags.

In other words: tagging a module not only fine-tunes permissions, it can also say
who to notify when that module goes wrong.

For fine-grained control by pages and menus, beyond groups, profiles and tags,
there is the advanced ACL system, covered in Part 04 · Advanced security and
visibility.
