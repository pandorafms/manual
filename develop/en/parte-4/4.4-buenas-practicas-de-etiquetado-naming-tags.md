# Naming and tagging best practices

The previous three chapters explain **how** groups, profiles and tags work. This
one is about **how to use them well**. There is no single right way, but there are
decisions that become expensive later: a badly chosen name or one tag too many
sticks around for years, and changing it afterwards costs more than thinking about
it on day one.

## Why it matters

A small installation organizes itself. An installation with hundreds of agents does
not: if the names are a mess, every search is a lottery and every report, a
negotiation. Naming and tags are what allow you to **find** an element, **group**
it for reports and **delegate** it with permissions without exposing what should
not be exposed. The sooner the convention is fixed, the less there is to undo.

## Naming conventions

The golden rule is boring and it works: **a predictable name is worth more than a
pretty one**. These are the guidelines that prevent real problems.

**Agents.** A pattern that usually works is `SERVICE-ENVIRONMENT-NN`, for example
`WEB-PROD-01` or `DB-PRE-03`. It does not matter which pattern you choose; what
matters is that it is **consistent** and that the name says at a glance what it is
and where it lives. Avoid **spaces** in the name of the group they go into (see
below) and be consistent with capitalization: the console search may normalize the
alias, and a `Web-Prod-01` does not appear the same as a `WEB-PROD-01`.

**Modules.** The module name should say **what it measures and in what units**, not
what the metric is called in the source system: `CPU usage (%)` is easier to
understand than `hrProcessorLoad`. If the module belongs to a service, include it
in the name (`Apache requests/s`).

**Groups.** Here there is a recommendation that is not aesthetic, it is
functional: to use the group name in **automatic agent provisioning**, it should
**not have spaces or extended characters**. It is supported, but it is a known
source of failures: there are documented cases where a group with spaces in its
name is not assigned when the agent is autocreated. A `Networks-DC1` avoids the
problem; `Networks DC 1` invites it.

**Other identifiers.** The same criterion applies to anything used as a key in
integrations or scripts:

- The **group password** (to restrict agent self-creation) must not have spaces or
  symbols.
- The **credential store identifier** goes without spaces or special characters.
- In the CLI, **group** and **calendar** names do not accept spaces or special
  characters.
- **Custom fields** with very long names are cut off in some views: a short,
  descriptive name is better.

And two details that surprise:

- In **visual consoles**, a name that starts with `_`, `,`, `[` or `(` makes the
  element appear in the left menu. It is a feature, not a whim: if you do not want
  that behavior, do not start the name with those characters.
- **Control characters** and some **accents** cause problems when saving depending
  on where (custom fields, policies with a specific encoding). If a name has to
  travel through the API, the CLI or scripts, leave it in plain ASCII.

## Using tags

Tags **complement** groups, they do not replace them. The way to get it right is to
be clear about what each one is for:

- **Groups organize the hierarchy and permissions.** They are the main structure,
  and the ones used to delegate (secondary groups included).
- **Tags fine-tune.** They mark modules with a cross-cutting criterion that does
  not match the hierarchy: by technology, by criticality, by owner.

Criteria that save trouble:

- **Do not turn tags into a second hierarchy.** If a tag reproduces a group, it is
  redundant.
- **Few and stable.** The tag security mode has a performance cost and the console
  recommends not going beyond two or three per combination of user, profile and
  group. A tag nobody uses is just debt.
- **Name them the same as in the rest of the installation.** If you call production
  tags `prod`, do not call them `Production` somewhere else.
- **Remember where they apply**: to **modules** (and policy modules), not to agents
  or groups.

## Anti-patterns and an example

The mistakes that repeat the most:

- **The name that says nothing.** `Agent1`, `test`, `test2`: a month from now,
  nobody knows what they are or whether they can be deleted.
- **The date or the name of whoever set it up** as an identifier. The system
  changes hands; the name stays.
- **Mixing languages and capitalization** in the same inventory (`web`, `WEB`,
  `Web`).
- **Using spaces or symbols** in anything that will go through an integration.
- **Tagging for the sake of tagging**, until the tag permission system starts to
  slow down.
- **Duplicate groups** with almost identical names.

An example convention, applied to an environment with two sites and two
environments:

| Element | Convention | Example |
|---|---|---|
| Agent | `SERVICE-ENVIRONMENT-SITE-NN` | `WEB-PROD-MAD-01` |
| Group | `SERVICE-SITE` (no spaces) | `WEB-MAD` |
| Module | `What it measures (unit)` | `CPU usage (%)` |
| Tag | Technology or criticality, in lowercase | `apache`, `critical` |

It is not the only valid one, and it does not need to be. What matters is that it
exists, that it is written down and that everyone follows it. That is the real work
of this chapter.
