# Modules and network

The checks and the network protocol: modules that do not start or do not
answer, ICMP, WMI, SNMP and traps.

A module stores a single metric and its value is interpreted by thresholds.
Almost every problem in this section is a matter of the module's own
configuration or of a check that does not get to run properly.

## I cannot change the type of a module

It is the behaviour of the product: once created, the type of a module cannot
be changed. If you got the type wrong, the module has to be deleted and created
again, and its history is lost with it. That is why it pays to get it right the
first time, or to try the definition on a test agent before taking it to
production.

## Can local modules be used in templates?

No. Module templates are for **network components**. To apply local modules to
many agents at once there are **policies**, which also carry alerts and also
accept network modules.

## Ping (ICMP) modules do not work

The network problem is separated from the processing one:

**Network.** The machine is off or offline; there is a cut in the segment; or an
intermediate element (firewall, proxy) blocks ICMP. From the server, `ping` or
`fping` to the destination tells whether the problem is in the network.

**Processing.** If the module interval is very low, the runs queue up and the
module does not arrive in time. It also drags if the server is queued in
general. Measure before lowering intervals: since version 784 ICMP supports up
to **15 seconds**, but that comes at a cost on large machines.

## An ICMP module is critical even though there is connectivity

Pandora FMS does not use the classic `ping`: it uses **fping**, which is more
efficient. The server's **`icmp_checks`** token decides how many pings it
launches per module and comes at **1** by default, so only the first one counts.
If the network loses the first packet now and then, the module goes critical
for no reason.

Raise it to a higher value so that the result does not depend on a single
attempt.

## WMI modules do not work

WMI has to be enabled on the Windows machine, not only in Pandora FMS:

1. Open **Computer Management → Services and Applications → WMI Control**.
2. In the namespace properties (you can start with `root`), on the **Security**
   tab, grant the **Remote Enable** permission to the account used for the
   queries.
3. Allow it through the Windows firewall.

In Pandora FMS, the default WMI client is **`pandorawmic`**, configurable with
the server's `wmi_client` token. It needs the credentials of a user with
permissions on the machine being queried.

## WMI does not work from a satellite server

When the satellite server runs as a **local user** on Windows, some remote WMI
queries fail for security reasons. The solution is to run the satellite service
with an **administrator account** of the domain or of the machine. It is changed
in the service properties, or with `sc.exe config`, and the service is
restarted.

## The web check is critical and the website works

Three usual causes:

- The Pandora FMS server **cannot reach the URL**: DNS, proxy or firewall.
- The **content has changed** and no longer matches the string the module looks
  for (`check_string`). A redesign of the page breaks the module even if the
  service is perfect.
- The connection is cut halfway through (a proxy with authentication, for
  example).

To see what is happening exactly, debugging is added to the module itself:

```
task_begin
get https://www.example.com
cookie 1
resource 1
check_string <string_that_must_appear>
debug /tmp/request.log
task_end
```

When it runs again, the file shows the error in detail.

## SNMP interfaces are up but the console shows them down

Before touching the module, confirm that the data arrives:

- Query the status from the server with `snmpget` or with the console's **SNMP
  browser**. If it shows as up there and not in the module, the problem is in
  the module.
- Check the **server load**. With few resources, SNMP checks are lost and the
  status you see is the last one that arrived, not the real one.

## The `_modulegraph_nh_` macro does not work

That macro inserts the module graph into an alert email, and to draw it the
console requests the image from itself. If it comes out broken, access to the
API is missing. The API password has to be defined in the console
(**Management → Settings → System Settings → General setup**) and
**`console_api_pass`** has to be uncommented in the server configuration, with
the same password.

In addition, the public URL configured in the environment (`public_url`) must be
reachable from the server. If it is configured through NAT and the server cannot
reach it, make the host name in that URL resolve locally: add it to `/etc/hosts`
pointing to `127.0.0.1` or the server's local IP.

## WMIC and PandoraWMIC

**WMIC** is the WMI command-line interface that comes with Windows. Pandora FMS
uses it **only to query** (for example, `PROCESS GET NAME` returns the running
processes), never to change anything on the machine.

**PandoraWMIC** is the client the server uses by default (`wmi_client
pandorawmic`), designed for those monitoring queries.

## A server plugin does not initialise

Server plugins run on the Pandora FMS server itself, just as they are configured
in **Servers → Plugins**. To debug it, it is launched by hand in the terminal
with **the same user the server runs as** (by default `root`) and the same
parameters.

The output has to be **a single datum**, and of the type declared when creating
the module (numeric or alphanumeric). If the type does not match, the module
does not start (the exception is the incremental type, which shows the output as
it is). Also, the command must finish without errors: if the *errorlevel* is not
0, the server discards the result.

## The agent sends data but it does not show up in the console

It is usually the time. If the clock of the machine where the agent runs is off,
the timestamps appear shifted with respect to the server and the data can be
hard to find in the view or in the graphs.

Check the offset between the two machines and synchronise them over **NTP**.
Then, check the next interval and look at the server log if the data still does
not show up.

## Adding a MIB to Pandora FMS

MIBs are loaded from the **Web console** itself. In the SNMP monitoring menu
there is the MIB loading section (**Monitoring → SNMP → MIB uploader**). From
there, as many files as needed are uploaded, one after another. A MIB is a text
file. It can be opened with any editor to check that it is the one for the right
manufacturer and model.

## After loading the MIB, the console still does not recognise the OIDs

Loading the MIB in the console is not enough: the operating system has to know
where it is. Check which directories **net-snmp** is looking at:

```bash
net-snmp-config --default-mibdirs
snmpget -Dparse-mibs 2>&1 | grep directory
```

If the directory where the MIB was left does not appear in that list, move it to
one that does. Or add yours to the net-snmp configuration.

## The SNMP wizard does not find the device OIDs

Before fighting with the wizard, ask the device directly from the server.
`snmpwalk` walks through what it exposes and `snmpget` requests a specific OID:

```bash
snmpwalk -v1 -c 'COMMUNITY' 192.0.2.10
snmpget  -v1 -c 'COMMUNITY' 192.0.2.10 1.3.6.1.2.1.43.5.1.1.1.1.0
```

Replace `COMMUNITY` and `192.0.2.10` with the values of your device.

If the device answers these commands, the problem is in the MIB or in the
wizard. If it does not answer, it is in the network or in the SNMP community.
And whatever you do in the console makes no difference.

## The traps do not arrive

The first place to look is the Pandora FMS trap log:

```bash
tail -f /var/log/pandora/pandora_snmptrap.log
```

If the message **"No access configuration - dropping trap"** appears, the trap
daemon has its access configured but does not authorise that community. It is
fixed by adding the community to the `snmptrapd` configuration file and
restarting:

```bash
echo "authCommunity log <configured_community>" >> /etc/snmp/snmptrapd.conf
systemctl restart pandora_server
```

The community must match the one the device sends. Do not use `public` in
production unless that is really the configured community.

Also, the Pandora FMS **SNMP console server** comes **disabled** by default:
check that in `/etc/pandora/pandora_server.conf` the **`snmpconsole`** token is at
**1**. A stopped internal server gives no error, it simply does not do its job.

## "couldn't open udp:162"

Port 162 is taken by the operating system's `snmptrapd`, so Pandora FMS cannot
listen. The system trap service is stopped and Pandora FMS is restarted. If it
happens again after a restart, the system one is disabled:

```bash
systemctl stop snmptrapd
systemctl disable snmptrapd
systemctl restart pandora_server
```

## On Debian and Ubuntu only numeric OIDs work

Debian and Ubuntu ship the MIB tree disabled, so their SNMP only understands
numeric addresses and the console does not resolve names. It is reconfigured in
two steps. First, install the MIB downloader. Then, leave the SNMP configuration
file clean (`/etc/snmp/snmp.conf`, with no active lines).

```bash
apt-get install snmp-mibs-downloader
```

## Deleting old traps

If what you want is a one-off cleanup, it can be done from **Admin tools → DB
Interface** with a statement on the `ttrap` table:

```sql
SELECT COUNT(*) FROM ttrap WHERE timestamp < '<YYYY-MM-DD 00:00:00>';
DELETE FROM ttrap WHERE timestamp < '<YYYY-MM-DD 00:00:00>';
```

Replace the date with the right one and review the result of the `SELECT` before
running the `DELETE`.

So that they do not pile up again, the console has the setting **"Max. days
before deleting traps"** in **Management → Settings → System Settings →
Performance** (token `trap_purge`). From then on, traps older than that are moved
to the historical database and then purged.
