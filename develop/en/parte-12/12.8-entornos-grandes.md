# Large environments

Command Center, several nodes and high availability: what changes when the
environment grows.

This section gathers the incidents that appear when coordinating several nodes,
distributing the load and configuring high availability.

## The server of a node does not start in a Command Center

The server of each node connects to the database configured in its own
`pandora_server.conf`. If it does not start, check that connection first. For a
replication incident at the Command Center, see the question "The events do not
arrive at the Command Center" further below.

1. **The database engine of the node is running.** Check the MySQL, MariaDB or
   Percona service that node uses.
2. **The node reaches the host indicated by `dbhost`.** Test the connection from
   the server of the node itself with the `dbname`, `dbuser` and `dbhost` values
   of its configuration.
3. **The user can access from that host.** If the credentials are correct but
   the connection is rejected, review the database permissions of the node.

The connection values and the passwords are checked in the configuration file of
the server; they are not copied here.

## Deleting agents in a Command Center in centralized mode

In an environment with centralized management enabled, agent administration
between nodes is coordinated from **Centralised management → Agent management**.

For the definitive deletion of an agent, it is necessary to act according to its
origin:

- If it is an **EndPoint**, uninstall or stop the service on the machine so that
  it does not send XML again, and delete it in the console of its node or
  through the bulk agent operations.
- If it was discovered by a satellite server or generated by a remote plugin,
  delete the definition on the satellite or the source check before deleting it
  in the console.

Deleting an agent only on the screen without stopping its source makes the
server create it again as soon as it receives the next data packet.

## How an agent is deleted

It depends on where the agent comes from, and deleting it in the console is not
always enough:

| Agent type | How it is removed |
|---|---|
| **Fake** | The one created by hand in the console: it is deleted there and that is it |
| **EndPoint** | The one installed on the machine: it is deleted in the console and the EndPoint is uninstalled, if you do not want to see it again |
| **Broker** | It is created by the main agent of the device: if it is deleted only in the console, it will show up again |
| **From satellite** | It is created by a satellite server from its configuration: the definition has to be removed on the satellite |
| **From plugin** | It is generated by a plugin when it runs: as long as the plugin keeps creating that XML, the agent comes back |

The general rule is simple: **if something else generates the agent, delete it at
the source**. In the console they can be deleted in batches from the bulk agent
operations.

## Several servers and high availability

Pandora FMS supports **several data and network servers against the same
database**, sharing out the load. With that the number of agents grows without
changing product. Three pieces hold the whole together:

- **A well-sized MySQL.** It is the usual bottleneck: without memory and without
  fine tuning, the extra servers are of no use.
- **MySQL cluster** for high availability and to share out the load of the
  database.
- **The high availability tool** (`pandora_ha`), which can watch the server and
  try to recover it. Its installation and start-up depend on the packaging and
  on the runbook of the cluster.

The servers of the same installation and their distribution of work are
explained in
[Introduction and architecture](../parte-1/1.2-introduccion-y-arquitectura.md).

## Centralized mode: what it is and what to check before enabling it

**Centralized mode** allows the Command Center to manage groups of agents, tags,
alerts, users, policies and collections in several nodes. It is enabled by
merging the environment with the **Merging tool** (see [6.3 · Command
Center](../parte-6/6.3-command-center.md)); from then on, the Command Center
becomes the configuration source for the nodes.

!!! warning "Check it twice before enabling it"
    If the environment had already been running for a while with the Command
    Center and several nodes separately, it is normal for each one to have
    **different things** created (groups, tags, policies). When the mode is
    enabled, the Command Center becomes the source of configuration. Whatever
    was in the nodes may end up overwritten or misaligned.

    With the environment running, it is worth **taking an inventory beforehand**
    of what is in each node, deciding which version is the good one and enabling
    it in a window, with a backup of all the databases.

## The events do not arrive at the Command Center

Event replication is configured in **each node**, not in the Command Center. If
the events of a node do not show up above, it is checked:

1. **The data of the replication database** in **Setup → Enterprise** of the
   node: server, database name and user (`replication_dbhost`,
   `replication_dbname`, `replication_dbuser`). If they are wrong, the node has
   nowhere to write.
2. **The connectivity** of the node towards that database.
3. **The server log of the node**, where each replication leaves its trace (one
   line for each batch of replicated events). If nothing appears there, the
   problem is in the configuration. If it appears, but the Command Center does
   not show them, the problem is in the reading.

In the console of the node itself the date of the last replication can be seen,
which is the quickest check.

## The history of a module is not seen in the Command Center

When the graph of a module is opened in the Command Center and an error of the
type **"Error connecting to database history at …"** appears, the Command Center
lacks **privileges on the historical database** of that node.

The Command Center connects to the history with **the user, the host, the
password and the database name that the node has configured** for its history.
The permission is granted on the history machine, to that user and for the IP of
the Command Center. If the node changes those data, the permission has to be
updated.

The passwords are checked in the configuration of each installation; here they
are not published.

## Recovering a downed node in an HA environment

In high availability, when a node goes down or the network is cut, the **slave
takes over** as master. When the downed node comes back, its database has been
left out of sync. It has to be **resynchronised from the current master** before
returning it to service. It is what is known as a "broken node".

The procedure, in short:

1. Put the downed node in **standby** in the cluster, so that it does not try to
   take on work.
2. **Stop its MySQL** and set its data directory aside.
3. Make a **copy of the master** and restore it on the downed node.
4. Resynchronise with the cluster and return the node to service.

!!! warning "A DBA operation"
    This is done with the cluster tools (Percona XtraBackup, and
    Pacemaker/Corosync for the cluster) and with a window ahead. A wrong step
    leaves both nodes without service, so it is worth following the high
    availability runbook and not improvising on a production environment.

The parameters of the high availability service are in the server file:
**`ha_interval`**, **`ha_hosts`**, **`ha_dbuser`** and **`ha_dbpass`**.
