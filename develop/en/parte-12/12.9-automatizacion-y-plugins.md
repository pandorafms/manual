# Automation and plugins

Making Pandora FMS work on its own: command line, API, macros and plugins.

Two ways of working with Pandora FMS without going through the screen: the
**CLI**, which runs on the server itself, and the **API**, which is called from
outside. Both serve to automate and to do in bulk what by hand would be endless.

## What the CLI is and how it is used

It is a command line administration tool that runs **on the Pandora FMS
server**. It is used to create and delete users, agents and modules, to
configure alerts and policies, to manage events and much more, so it is the
natural way to automate tasks with scripts.

It is run on the server with `pandora_manage` and the server configuration:

```bash
/usr/bin/pandora_manage \
    /etc/pandora/pandora_server.conf OPTION PARAMETERS
```

Replace `OPTION` and `PARAMETERS` with the arguments of the operation you are
going to run.

A real example: create a group called "Virtual" inside another one called
"Servers":

```bash
/usr/bin/pandora_manage /etc/pandora/pandora_server.conf \
    --create_group 'Virtual' 'Servers'
```

The list of operations is long (agents, modules, alerts, templates, policies,
events, users, profiles, collections, visual consoles…). It is complete, with the
syntax of each one, in the
[administration CLI reference](../parte-9/9.11-referencia-completa-del-cli-de-administracion.md).

## What the API is and how it is protected

The API is a PHP file of the console that is called over HTTP, with `curl` or
from a web tool. It has **three security layers**, and all three have to be
configured before using it:

1. **Allowed IP addresses.** In **Management → Settings → System Settings →
   General setup**, the **"IP list with API access"** field accepts one IP per
   line. The wildcard `*` opens the API to anyone, and it is not advisable.
2. **API password.** In the same place, the **"API password"** field.
3. **User credentials.** Each call also identifies the Pandora FMS user who
   makes it, with their password.

As the API password travels in the call itself, it is worth making them over
**HTTPS** so that the channel goes encrypted.

A test call, the simplest one, to check that everything is in its place:

```
https://console.example.com/pandora_console/include/api.php?info=version
```

Replace `console.example.com` with the name of your console.

The passwords are not published here: each installation sets its own in the
console.

## Creating and validating events through the API from another machine

The product brings a tool to launch events against the API **from a remote
system**, without the need to touch the database or to have an EndPoint
installed: **`/usr/bin/pandora_revent`**.

```bash
/usr/bin/pandora_revent \
    -p https://console.example.com/pandora_console/include/api.php \
    -u 'API_PASSWORD,USER_NAME,USER_PASSWORD' \
    -create_event \
    -name "Event name" -group 0 -type "system" -status 0 -severity 4 \
    -user "USER_NAME" -owner_user "USER_NAME" -source "Commandline" \
    -user_comment "Event comment"
```

The `-u` parameter carries the three credentials together, separated by commas:
the API password, the user and their password.

The same tool **validates** events, which is the useful thing to close them from
outside:

```bash
/usr/bin/pandora_revent -p https://console.example.com/pandora_console/include/api.php \
    -u 'API_PASSWORD,USER_NAME,USER_PASSWORD' -validate_event -id EVENT_ID
```

Replace the example values with the host and the credentials of your
installation.

When run **without options**, it shows its help with the full syntax.

## Macros in the alerts

A macro is a string surrounded by underscore characters (`_macro_`). The console
replaces it with a text when it launches the action of an alert. They are used
so that the notice says which agent it comes from, which module fired it and
with what value, without writing it by hand.

The groups that are used the most:

| Group | Examples |
|---|---|
| Agent | `_agentname_` (name), `_agentalias_`, `_address_` (its address), `_agentstatus_`, `_agentos_`, `_agentgroup_`, `_agentcustomfield_n_` |
| Module | `_module_` (name), `_data_` (the value that fired), `_modulegraph_nh_` (the graph) |
| Alert | `_alert_name_`, `_alert_priority_`, `_alert_text_severity_` |

The full list is in the help of the console itself. The macros are replaced in
the subject and in the body of the action. Without them, each alert would have
to carry the message written by hand.

## Custom macros

Besides the built-in ones, your own can be defined. It is the way for a notice
to say something specific to your environment.

They are created in the **edition of the module itself**, in the **"Custom
macros"** section. **Key and value** pairs are added, and the key is written
between underscore characters. For example:

```
_key_          _technology_
value          the log system
```

After that, that macro is referenced in the alert like any other:

```
The agent reports new content in _technology_
```

and the console replaces it with the value that **that module** has configured.
As the value lives in the module, each one can carry its own.

## Agent plugins

An agent plugin is a program or script that runs **on the monitored machine**.
It returns a piece of **XML** that the agent inserts in the packet it sends to
the server. A single plugin can return data from **several modules**.

It is added in two ways:

- In `pandora_agent.conf`, with a line:
  ```
  module_plugin /path/to/plugin
  ```
- From the console, in the configuration of the agent, in the **plugins**
  section (the puzzle piece icon): the full path of the plugin is indicated.

From there it works like one more local module. It can be written in any
scripting language; if it needs libraries (for example, Java), they have to be
distributed with it.

## Server plugins

A server plugin is a script that runs **on the Pandora FMS server itself**, not
on the monitored machine. It returns **a single value** (numeric, boolean or
text) and parameters can be passed to it.

- They live by default in `/usr/share/pandora_server/util/plugin`, and the
  product already brings a few as an example (for example, `iface_bandwith.pl`).
- They are registered in **Servers → Plugins**: name, type (standard or
  Nagios), maximum *timeout*, the command and its parameters (which accept
  macros).
- **Who runs them**: the **Heavy Server**. There is no `pluginserver` server to
  activate, as the old entries said. The Heavy Server comes active by default
  and takes care of plugins, NCM and inventory.

The quickest way to debug them is to launch them by hand in the terminal, with
the same parameters. Almost all of them bring help with `-h`, `-help` or without
arguments.

!!! warning "The timeout is the usual trap"
    If the plugin takes longer than the configured *timeout*, it is cut and the
    module is left with no data. Measure how long the script takes and leave
    some margin.

## The plugin module shows up as "Unknown"

When a plugin defines its own modules, the XML it generates has to respect the
**`module_interval`** that you have configured. If the plugin does not declare
it, the console waits for the data at another pace. The modules end up in
**Unknown** even though the plugin is working.

It is corrected in the plugin itself: that the XML includes the interval with
which it runs. It is a small adjustment that prevents a cascade of false
unknowns.
