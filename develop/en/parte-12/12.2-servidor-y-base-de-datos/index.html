    Server and database¶

    The two pieces everything else depends on: the server that processes and the database that stores. When one fails, the other notices.

    The Pandora FMS server is an application with several internal servers. When it does not start, restarts on its own or goes down, the log says why. Almost everything is solved by reading it before touching anything.

    The server does not start¶

    The first thing is the two log files:

    • /var/log/pandora/pandora_server.log
    • /var/log/pandora/pandora_server.error

    The specific error shows up there. Also check MySQL, which is indeed a dependency of the server. tentacle_serverd is a separate service: if it is stopped, the EndPoints will not be able to deliver data over Tentacle, but that alone does not prevent pandora_server from starting.

    The server restarts in a loop¶

    When something kills it and brings it back up every few minutes, the suspect is the start-up time. The server_keepalive token in /etc/pandora/pandora_server.conf is 45 seconds by default. If the server takes longer than that to become operational, the high availability system does not see it as active and restarts it, and so on in a loop.

    The usual cause is having raised the threads of the internal servers (*_threads): the more threads, the longer it takes to start. It is fixed by raising server_keepalive so that it covers that start-up.

    The server goes down¶

    The same log is checked and, if nothing appears, these causes are ruled out in order:

    • Not enough memory. The server runs out of RAM and the system kills it.
    • MySQL. A database that runs slow or goes down drags the server with it.
    • Full nodes. In a Command Center, a node with no space stops responding.
    • A half-finished update. Wrong packages or a database schema update that did not finish.

    "Segmentation fault" when starting the server¶

    It may appear when more threads have been assigned than the hardware can initialize and sustain. Check the *_threads tokens in the file and reduce the ones that were raised without a measurement to justify it. There is no fixed equivalence between threads and modules: it depends on the check type, the interval, the concurrency and the hardware. Measure before raising them again.

    Enabling or stopping internal servers¶

    Each internal server is turned on and off with its token in /etc/pandora/pandora_server.conf: 1 enables it and 0 disables it. The ones needed according to the use case are explained in Introduction and architecture.

    After changing the file, the service must be restarted:

    systemctl restart pandora_server

    A stopped internal server gives no error: it simply does not do its job, so if something "is not processed" and the token is set to 0, you already know where to look.

    Running the database purge by hand¶

    Maintenance is installed in /etc/cron.hourly/pandora_db and calls the tool with the server configuration:

    /usr/share/pandora_server/util/pandora_db.pl /etc/pandora/pandora_server.conf

    Old Enterprise installations also had an executable in /usr/bin/pandora_db; today the right path is the one in util/.

    If it has never been run, the first pass can take hours: launch it in the background and do not cut it short.

    The kernel warns of "possible SYN flooding on port 41121"¶

    The Tentacle port is 41121/TCP. A high count of TIME_WAIT connections can be a clue, but it does not on its own prove that the SYN queue is saturated. Also look at the SYN_RECV connections and the retransmission counters before changing kernel parameters:

    netstat -an | grep TIME_WAIT | wc -l

    Some current deployments set tcp_max_syn_backlog to 65536. It is not a universal value and does not on its own fix a network or capacity problem: first identify where connections are being dropped.

    net.ipv4.tcp_max_syn_backlog = 65536

    Do not use tcp_tw_recycle

    The net.ipv4.tcp_tw_recycle parameter that old guides recommended was removed from the Linux kernel in version 4.12. Do not look for it and do not add it.

    In the database, the usual causes are maintenance that is not run, a damaged table, slow storage or a badly sized data retention.

    How to back up the database¶

    The product brings its own tool: pandora_backup.sh, in /usr/share/pandora_server/util/. The console path is passed with -c; the backup destination, with -d:

    # Backup (database + console files)
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console -d /tmp

# Restore the database from a backup
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console \
    -s /path/to/the/backup/pandorafms_backup_date.tar.gz

# Restore files and configuration too (in addition to the database)
/usr/share/pandora_server/util/pandora_backup.sh \
    -c /var/www/html/pandora_console \
    -s /path/to/the/backup/pandorafms_backup_date.tar.gz -f

    The console path passed with -c is also necessary when restoring: the tool uses it to read the database credentials. Without -f, it restores the database, but not the console files or the configuration. With -f it also restores those files and the spool; -b excludes the database. Restoring the database deletes and recreates the configured database. Check the file and make a copy of the current state before continuing.

    If you prefer to do it by hand, the database and the user are usually called pandora. The restore example assumes the database already exists:

    mysqldump -u pandora -p pandora > /path/pandora_backup_date.sql
mysql -u pandora -p pandora < /path/pandora_backup_date.sql

    Credentials are checked in /etc/pandora/pandora_server.conf, in the dbuser, dbpass and dbname fields. They are not copied here.

    The database runs slow¶

    Before touching the MySQL configuration, rule out these four causes, in order:

    1. Maintenance is not running. The package leaves the script in /etc/cron.hourly/pandora_db, which calls /usr/share/pandora_server/util/pandora_db.pl with the server configuration. If it has been lost or cron does not run, the database grows without limit. Run it by hand and see if it reports an error.
    2. The retention does not match the use. Review the purge periods and, in large environments, whether old data should be moved to a historical database. There is no universal period: it depends on how much data is collected and how much needs to be queried.
    3. Storage. Check latency, free space and read and write load. A saturated disk affects both MySQL and the server.
    4. MySQL fine tuning. Parameters such as innodb_buffer_pool_size or innodb_io_capacity are tuned to the real size of the machine and the data volume. There are no universal values: you start from a recommendation for the server size and measure.

    The console warns of "Database maintenance"¶

    That warning means that maintenance is not running. The database needs that script every hour: it purges old data, compacts and moves to the historical database whatever corresponds.

    Check that it exists and works:

    /usr/share/pandora_server/util/pandora_db.pl /etc/pandora/pandora_server.conf

    If the script answers that "another instance seems to be running", the MySQL named lock indicates that another connection is running maintenance. The lock is released when it finishes or the connection closes. Check whether there is another active run and review its logs; do not delete by hand a supposed lock indicator in the configuration table.

    Database error when starting the server¶

    If the server log shows a connection failure on start-up (DBI connect ... failed), check these two points first:

    • The password or the user are not correct. Test by hand with mysql -u pandora -p -h 127.0.0.1 -D pandora and compare them with the dbuser, dbpass and dbname fields of /etc/pandora/pandora_server.conf.
    • The configured host is localhost and the socket does not match. Some MySQL packages use /var/lib/mysql/mysql.sock instead of /tmp/mysql.sock. The current default value of dbhost is 127.0.0.1, which uses TCP; if your installation uses localhost, check the real path of the socket first before changing it.

    In current versions dbhost comes with 127.0.0.1, which avoids localhost resolution problems over IPv6.

    The database does not respond and there is too much data¶

    There is no universal number of records from which the database stops responding. The data volume, the write rate, the queries, the retention and the hardware all play a part. Before rebuilding anything, review the MySQL log, the space and the load; confirm that maintenance works and that the purge and historical policy matches what you need. Make a copy before any repair. A rebuild or restore of the database must be planned with a DBA: do not delete the data directory or the database blindly.

    "Table is marked as crashed and should be repaired"¶

    REPAIR TABLE is only useful for engines that support that operation, such as MyISAM. The main Pandora FMS tables use InnoDB: check the engine and the specific error first before attempting a repair:

    SHOW TABLE STATUS LIKE 'table_name';

    If the table uses MyISAM, REPAIR TABLE table_name; may be appropriate. If it uses InnoDB, that is not the procedure: keep the error log and check the engine diagnostics or restore a validated copy with a DBA.

    Corruption in the database¶

    Before attempting a repair, identify the engine of the table. mysqlcheck --auto-repair is only useful for engines that support that operation, such as MyISAM; it does not repair InnoDB. The main Pandora FMS tables use InnoDB. Keep the error log, make a copy and check the recovery procedure for that engine with a DBA. Do not delete /var/lib/mysql or recreate the database as a first attempt.

    "PROCESS privilege" error when making a dump¶

    In MySQL 8, if mysqldump fails for lack of the PROCESS privilege when reading tablespaces, first try to skip them with --no-tablespaces:

    mysqldump --no-tablespaces -u pandora -p pandora > /path/backup.sql

    That way there is no need to grant PROCESS globally to the application user just to make a copy. If your version does not accept the option, check with the DBA before changing the privileges.

    Maintenance also processes the historical database¶

    The standard hourly maintenance manages the historical database when it is configured. The server reads the connection parameters saved in the main database configuration and connects with the host, the database and the user indicated there. There is no need to create another cron task with a manual copy of pandora_server.conf. Check that the historical database is enabled and that the configured connection works.
