# Agents and systems

The **EndPoint** collects data from the machine. This section covers start-up,
the XML queues and the monitoring specific to Windows and Linux: PowerShell,
services and logs.

## The new EndPoint does not show up in the Web console

Check these in order:

1. **The agent points to the right server.** In `pandora_agent.conf`, the
   **`server_ip`** token carries the Pandora FMS server address and
   **`server_port`** the Tentacle port, which is **41121**. If the port is not
   that one, the agent writes into the void.
2. **The server accepts new agents.** In `/etc/pandora/pandora_server.conf`, the
   **`autocreate 1`** token makes the agents that arrive without a previous
   registration create themselves, in the group set by **`autocreate_group`**.
   With `autocreate` at 0 and an agent that does not declare a group, its data
   is discarded without further notice.
3. **The network.** The EndPoint is the one that starts the connection to the
   server, so the firewall has to let **41121/TCP** through from the machine to
   the server.

## Testing Tentacle from the command line

The client starts the connection to the Tentacle server, by default on port
**41121/TCP**. For a test, send a valid data file from the agent machine:

```bash
tentacle_client -a 192.0.2.10 -v /path/to/the/agent.data
```

Replace the IP and the path with those of your environment. Run the test on a
test machine or with a real data XML: the server receives the file and processes
it. If it fails, check that `tentacle_serverd` is active, that it listens on the
expected port and that the firewall allows the traffic. The password,
certificate, alternative port and proxy options are in the
[Tentacle reference](../parte-9/9.4-referencia-completa-de-tentacle.md).

## The EndPoint service does not start on Windows

Check two things before touching anything:

- **It was installed without administrator permissions.** The installer has to
  run as administrator and the service needs **SYSTEM** permissions. If not, it
  does not start.
- **There is a stray `PandoraAgent.exe` in the installer folder.** If the
  installer finds an executable in its own path, the service points to that one
  and not to the one in the agent folder, so it fails at start-up. Before
  installing, leave the folder clean.

To tell a service problem from an EndPoint problem, run the start-up script in
the `scripts` folder with **Run as administrator**. If it starts that way, check
the account configured in the service properties.

## The XML files pile up in `data_in`

The files that EndPoints leave in `/var/spool/pandora/data_in` pile up when
processing cannot keep up. The checking order is:

1. **The server is running.** With the server stopped, the queue grows and that
   is it. Check it with `systemctl status pandora_server`.
2. **How many BADXML files there are.** They are files the server has not been
   able to read:
   ```bash
   ls /var/spool/pandora/data_in | grep -c BADXML
   ```
   If there are many, they are cleaned up and the cause is looked for (next
   section).
3. **The Data server threads.** The **`dataserver_threads`** token in
   `/etc/pandora/pandora_server.conf` is **1** by default. On a server with many
   machines, raising it speeds up the emptying of the queue.

## There are BADXML files

A BADXML is an XML the server has not been able to parse, almost always because
a module has put in a value that breaks the file. The error is located without
guessing:

```bash
xmllint TempTHXDF01.211810.data_BADXML
```

The command points to the exact line. With that, go to the XML, see which module
generates that content and correct the module so that it returns a valid data
item. The BADXML files already generated can be deleted: the agent will send
them again, corrected, in the next interval.

## A lot of data arrived at once and the server is running behind

After a server outage, the EndPoints have kept collecting data and the queue
fills up at once. The server has a processing mode designed for that: the
**`dataserver_smart_queue`** token, which **already comes enabled** in current
versions (`1`). If the installation is old and it is at 0, set it to 1. And if
the volume is high, raise the **`dataserver_threads`**.

## The data arrives duplicated

It is not that the server duplicates it: there is something repeated at the
source. Check in this order:

- **Two agents with the same name.** It is the most common case. To locate them,
  temporarily add to that agent a module that returns the machine IP (`ipconfig`
  on Windows, `ip address` on Linux) and see how many IPs answer with the same
  name.
- **Two modules with the same name inside the agent**, or a module and a plugin
  that obtain the same data.
- **A module that returns more than one value.** Run it by hand on the machine
  and check that its output is a single data item.

## The agent inventory does not arrive

Since version 784 **there is no inventory server of its own**: that task was
absorbed by the **Heavy Server**, which comes active by default
(`heavyserver 1`). If the inventory does not show up, check that the EndPoint has
its inventory plugin enabled and that the Heavy Server is running. The old
`inventoryserver` token no longer exists.

## Configuring the EndPoint from the console

It can be done if the agent allows it: the **`remote_config`** token in
`pandora_agent.conf` is **1** by default, so the agent accepts its configuration
being changed from the Web console. If someone set it to 0, from then on it
stops accepting remote changes and the file has to be edited by hand.

## Characters better avoided in agent and module names

So that the internal paths and commands do not get confused, it is better to
avoid **`/`**, **`\`**, **`|`**, **`%`**, **`#`**, **`&`** and **`$`** in the
name of an agent or a module. They are characters the system interprets in paths
and executions, and having problems with them is a matter of time.

## Basic Windows monitoring

Once the EndPoint is installed, the quickest way is not to write modules by
hand:

- Apply one of the **policies** the console brings for Windows machines, which
  already includes the basic set of checks.
- Or use the **module templates** in the agent configuration, in the
  **Module templates** section.

When the policy or the template is applied, the modules are written into the
agent configuration file. They start reporting in the next interval. For
specifics of your environment, own modules (or scripts and plugins) are added on
top of that base.

## Basic Linux monitoring

It is the same path: policies per operating system that the console brings, or
module templates from the agent configuration. With that they already report
CPU, memory, disk, processes and the usual services; the specific part is added
by hand or with a plugin.

## Running a PowerShell script in a module

The Windows EndPoint knows how to run PowerShell. It is given the path of the
executable and the script:

```
module_begin
module_name Module_name
module_type generic_data
module_exec C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -Command "C:\Path\script.ps1"
module_end
```

The module **type** is chosen according to what the script returns:

| Type | What it is for |
|---|---|
| `generic_data` | A numeric data item |
| `generic_data_string` | An alphanumeric data item |
| `generic_proc` | A boolean value (1 or 0) |

If the script returns text, `generic_data` is not valid: the module will show up
as Unknown.

## Starting or stopping a service or a process

There are two mechanisms, and it is better not to confuse them:

- **Postconditions**: the module, besides measuring, runs something when a
  condition on its value is met. `module_condition` carries an operator, a value
  and the response command. The syntax and the operators are detailed in the
  [EndPoint reference](../parte-9/9.1-referencia-completa-de-configuracion-del-endpoint.md).
- **Windows watchdog**: `module_proc` can relaunch a crashed process with
  `module_watchdog` and `module_start_command`. `module_service` watches a
  Windows service and restarts it directly. It is also explained in the
  [EndPoint reference](../parte-9/9.1-referencia-completa-de-configuracion-del-endpoint.md).

## Monitoring Windows logs

The Windows EndPoint brings three ways:

- **Logevent**: reads the Windows **system events**; the category of interest is
  chosen.
- **Regexp**: looks for a pattern inside a specific **log file**.
- **Log plugins**: the same search, with a script, useful when the format is
  custom.

## Monitoring Linux logs

The two plugins used are:

- **`grep_log`**: given a path, it looks for the content you indicate and
  creates the module with the result.
- **`grep_log_module`**: the same, but it also **sends the log to the Pandora
  FMS log collector** with *Syslog* as source, so that it stays in the viewer.

The practical difference: the first one measures, the second one also archives.

## User variables when the EndPoint does not run as root

If the EndPoint runs with a user other than `root`, the modules that depend on
that user's environment can fail. Check:

1. That the user's **home** exists.
2. That it has a **valid shell** (for example, `/bin/bash`); for security, it
   comes disabled.
3. That the **environment variables** it needs are in its `$HOME/.bashrc` (that
   file does not exist by default: it has to be created).
4. That the file is readable and that the whole home belongs to that user.

With the four things in order, the EndPoint inherits the environment on
start-up.
