    Reports, logs and email¶

    This section gathers the incidents about reports, collections, the log viewer and email.

    PDF reports are not generated¶

    The PDF of a report is put together by the console with Chromium in headless mode. So the first thing is not PHP, it is the rendering engine:

    • Check that Chromium is installed on the server.
    • Review the Chromium path setting in Management → Settings → System Settings → General setup: it has to point to the real binary (by default, /usr/bin/chromium-browser).
    • If you have just touched the PHP configuration, restart the web service so that it picks it up.

    Notice

    Old entries talked about curl and allow_url_fopen to generate the PDFs. That was the previous mechanism: today the report is rendered by Chromium, and that is where you have to look first.

    Not enough memory when generating a report or when updating¶

    The error you see comes from PHP, not from Pandora FMS:

    Fatal error: Allowed memory size of XXXXX bytes exhausted

    The limit is raised in php.ini (/etc/php.ini or /etc/php/8.x/apache2/php.ini depending on the system), in the memory_limit variable, and if the process takes too long, also max_execution_time. Then restart the web service.

    Do not raise the value without a measure: a huge memory_limit can bring the machine down when several requests coincide. Raise just enough and check.

    File collections do not work¶

    The agent needs unzip to decompress the collections. On Linux it is a dependency of the agent package, so check that it is installed and that the user the agent runs as finds it in its PATH.

    If it still does not apply, look at the collections directory of the agent, /etc/pandora/collections. Each downloaded collection leaves an .md5 file next to its folder:

    • If there is an .md5 without a folder that corresponds to it, delete it.
    • In the next cycle, the agent will download the collection again and decompress it.

    On Windows there is nothing to install: unzip travels with the agent.

    "Unable to create the collection"¶

    When you create a collection from the console, that error is usually about paths or permissions. The two paths the process uses are reviewed:

    • The collections folder of the server: data_in/collections.
    • The attachments folder of the console: the Attachment directory configured in Management → Settings → System Settings → General setup (by default, the attachment of the console).

    Both have to exist and be readable and writable by the web server user. If the console attachments path does not match the real one, the collection is not created no matter how good the permissions are.

    The alerts fire but the email does not arrive¶

    It is reviewed in this order:

    1. Where the email is configured. The console or the server file are valid, but not both at once: if they live together, they overwrite each other.
    2. The credentials of the account. If someone changed the password, the sending stops working with no further notice.
    3. The permissions of the account. Many providers require enabling access from third-party applications.
    4. The server log. With verbosity at 10 the email errors show up in /var/log/pandora/pandora_server.log. If the MTA is Postfix, its trace is in /var/log/maillog.

    The emails arrive with the wrong sender¶

    The default sender is pandora@localhost, which many mail servers reject. It is changed with the mta_from token of /etc/pandora/pandora_server.conf:

    mta_from Pandora FMS <pandora@yourdomain.com>

    After the change, the server is restarted.

    It does not send email with authentication¶

    First check that there is an MTA on the server, that the service is started and that the SMTP port is open. Then, that the email parameters are right in one of the two places:

    Token (in pandora_server.conf) What it is for
    mta_address Mail server address
    mta_port Port (25 by default)
    mta_user and mta_pass User and password, if the server asks for them
    mta_auth Authentication system (LOGIN, PLAIN, CRAM-MD5, DIGEST-MD5)
    mta_from Sender that the recipient will see

    The alternative is to configure it in the console, in Management → Settings → System Settings → General setup, in the email section. We insist: one of the two, not both.

    Name resolution error when sending email¶

    In the console log an error of this type appears:

    PHP Warning: fsockopen(): php_network_getaddresses: getaddrinfo failed:
Temporary failure in name resolution

    It is a problem of the DNS of the server, not of Pandora FMS. The name resolution of the system (/etc/resolv.conf) is reviewed, and that the name of the mail server resolves from that machine. Restarting the web service can unblock the sending for a while, but it does not fix the cause.

    The times do not add up¶

    The mismatch can be in three different layers and it is worth checking all of them before touching anything:

    Layer How it is checked
    System date, and the time zone with timedatectl
    MySQL SELECT now(); and SELECT @@global.time_zone, @@session.time_zone;
    PHP A loose file that prints date("Y/m/d H:i:s O e")

    Once the layer that is out of step is located, correct it there: the time zone of the system, the one of the database server or the one of PHP. The timestamps may appear shifted in the console; check the server log if data is missing too.

    The log viewer shows nothing¶

    The logs are stored in OpenSearch. If the viewer is empty, it is checked:

    1. The OpenSearch service is running.
    2. There is connection from the Pandora FMS server to port 9200.
    3. The syslog server is enabled. The syslogserver token comes as 0 by default in pandora_server.conf: without it, nobody processes the logs.
    4. The size of the indexes. Huge indexes make the viewer slow or prevent it from loading; they are reviewed and whatever needs rotating is rotated.

    Configuring rsyslog for the syslog server¶

    The syslog server needs to receive the logs of the devices in a file and then process them. On the server, rsyslog has to be installed and, in /etc/rsyslog.conf, the reception over UDP and TCP on port 514, in addition to the file where the messages are written.

    OpenSearch, not Elasticsearch

    Old entries say that the logs are sent to Elasticsearch. The store the current documentation uses is OpenSearch.

    Integrating a ticketing tool¶

    The usual way is opening and closing incidents with alerts: the alert action calls the tool. An email to the ticketing inbox works, and so does a script or a command line call.

    For the incident to also be closed when the service recovers, it is necessary to know the closing method and to save the ticket identifier when creating it, in the database or in an exchange file. That identifier is the only thing the recovery alert needs to close the right ticket.
