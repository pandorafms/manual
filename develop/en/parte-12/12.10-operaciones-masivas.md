# Bulk operations

Deploying agents, changing configurations and cleaning up in batches, without
going one by one.

They are powerful operations, so **make a backup before the first one**.

## Deploying agents in bulk

Pandora FMS does it from the **deployment centre of Discovery**, and two things
have to be ready before using it:

1. **An agent repository**: in **Configuration → EndPoints repository** the
   installers are uploaded, one per operating system.
2. **The credential store**: in **Configuration → Credential store** the users
   and passwords of the target machines are saved. It is the same store that
   Discovery uses.

With that, the deployment goes through the machines, installs the agent of their
system and leaves it reporting. It is the difference between preparing a hundred
machines by hand and reviewing the result of a hundred installations.

## Updating the configuration of all the agents

There are two cases and they are solved in a different way:

- **Modules, plugins and alerts**: it is done with **policies**. They are
  applied to the agents of the same operating system and the modules are written
  in their configuration without touching them one by one.
- **Special parameters of the agent file**: here you have to go to the server.
  It is worth **making a copy first** of two directories:
  `/var/spool/pandora/data_in/conf` (where the server saves the configuration of
  each agent) and `/var/spool/pandora/data_in/md5` (the checksums). With the
  backup done, the bulk change is applied and the agents are left to pick it up.

## Deleting the agents that have never reported

The candidates can be located through the database: they are the agents whose
modules are **all uninitialised**. First run a read-only query to identify them.
The database uses InnoDB and its tables are related: do not delete rows directly
from `tagente`.

```sql
SELECT id_agente, nombre, notinit_count, total_count
FROM tagente
WHERE notinit_count = total_count;
```

That condition covers the two typical cases: the agent for which no module was
created and the one that has them all in **not initialised** status. Review the
list and delete the agents from the agent operations in the console, so that the
product also cleans the related tables.

## Changing the IP of many modules at once

If a device changes address and hundreds of modules monitor it, they are not
touched one by one. It is updated from **Admin tools → DB interface**:

```sql
UPDATE tagente_modulo SET ip_target = '10.0.0.1' WHERE ip_target = '10.0.0.2';
```

The new address goes in `ip_target` and the old one in the `WHERE`. It is worth
running a `SELECT` first with the same `WHERE` to see how many modules are going
to be touched. Make a copy of the database before running the `UPDATE`.

## Cleaning `data_in` when it has filled up with XML

If the directory piles up thousands of files, they are processed without losing
data. The XML files are moved to a temporary directory and returned **in
batches**:

```bash
mkdir -p /tmp/xml
mv /var/spool/pandora/data_in/*data /tmp/xml
ls -rt /tmp/xml | grep data | head -20 | xargs -i% mv /tmp/xml/% /var/spool/pandora/data_in
```

The last command returns 20 each time: it is repeated until the temporary
directory is empty, letting the server process them between one batch and the
next. Do not delete the XML files if they can contain data you need to recover.

## Deleting an agent from a satellite server

An agent created by a satellite server **does not disappear by deleting it only
in the console**: the satellite creates it again. It has to be removed at the
source:

1. Delete it from the hosts file of the satellite (by default
   `/etc/pandora/satellite_hosts.txt`, or the one its configuration indicates in
   `host_file`).
2. Delete the configuration file of that agent in the directory of the satellite
   (by default `/etc/pandora/conf`, or the one it has configured in
   `agent_conf_dir`).

After that, in the console, delete the agent.

## Uploading larger files from the console

When the console rejects a file (for example, when adding it to a collection),
there are two limits to raise:

- **PHP**: the `upload_max_filesize` value (and `post_max_size`) in `php.ini`,
  and restart the web service.
- **The console**: the **Collection size (Bytes)** setting in **Management →
  Settings → System Settings → General setup** (token `collection_max_size`). It
  comes with one million bytes by default.

If only one is changed, the other one keeps cutting.
