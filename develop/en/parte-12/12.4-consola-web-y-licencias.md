# Web console and licences

Getting into the console and keeping it in shape: access, security settings and
the licence that enables the platform.

The Web console is the gateway to the platform. Here the access, display,
security and licence problems are gathered.

## I have lost the administrator password

The console does not bring a "forgot password" by email for the administrator,
so it is solved from the server, with the management tool:

```bash
/usr/bin/pandora_manage /etc/pandora/pandora_server.conf \
    --create_user temporary_admin CHANGE_THIS_PASSWORD 1
```

That creates a temporary administrator user. Log in with it, change the password
of the original user and **delete the temporary user**, so as not to leave an
open door.

!!! warning "Do not leave the temporary user"
    The original entry proposed creating it with the password `none`. Do not do
    it: set a real password and delete the account as soon as you finish.

## Changing a user's password from the command line

With the same `pandora_manage`, without creating new accounts:

```bash
/usr/bin/pandora_manage /etc/pandora/pandora_server.conf \
    --update_user USER_ID password NEW_PASSWORD
```

The command also works for other user fields: email, phone, language, theme
(`id_skin`), full name and whether the user is an administrator.

## The console shows up blank or with MySQL errors

Four causes, in order of frequency:

- **Missing PHP packages or extensions.** The console needs extensions such as
  `php-mysqlnd`, `php-gd`, `php-mbstring`, `php-xml`, `php-zip`, `php-ldap` and
  `php-snmp`. If one is missing, the page may be blank or return a 500 error.
  Install them and restart Apache or PHP-FPM.
- **A half-finished update or installation.** Some console file was left
  corrupt. The console packages are reinstalled in **the same version** that was
  already installed.
- **MySQL connection problems.** The engine is not running, it is not listening
  on the configured host or port, the credentials in `include/config.php` are not
  valid, or the user does not have permissions on the database. Check the
  connection manually with `mysql` and look for the error in the PHP or Apache
  log.
- **Schema MRs are missing.** If there are also MySQL errors, the most likely
  thing is that the database was left at a previous MR. The missing ones are
  applied.

If that does not fix it, the console is reinstalled from scratch keeping
`include/config.php`, the content of `attachment` and the custom images.

## I cannot get in and the disk is full

When the disk fills up, MySQL cannot write, the console does not open and the new
data stops being processed. What has eaten it up is looked for:

- **Backups** that pile up and nobody deletes. It is the first thing to look at.
- **Logs** that are not being purged.
- **Files with an anomalous size.** They are moved or deleted, carefully.
- **The database.** Text modules (`generic_data_string`) are the ones that grow
  the most: they store long strings that repeat on every interval.

## The graphs do not show text

If the graph comes out without axes or values, the font with which the text is
drawn is missing. The path is declared in the console configuration, in the
**`fontpath`** setting. It has to be checked that the font exists at that path
and that the web server user can read it.

!!! note "Notice"
    The old entries talked about the `$config_homedir` variable. **That setting
    no longer exists**: if no texts appear on the graphs, look at `fontpath`.

## The console responds slowly

There are two places to look at, and they are told apart with the log and with
the consumption:

1. **The web server.** If the Apache processes consume 100% of CPU or memory, the
   problem is there: resources are missing, or `php.ini` falls short of memory
   (`memory_limit`). PHP limit errors appear in the Apache log or in
   `pandora_console.log`.
2. **MySQL.** If the web server has room to spare and the console is still slow,
   the bottleneck is in the database. See
   [Server and database](12.2-servidor-y-base-de-datos.md).

## I lost the two-factor authentication code generator

Two-factor authentication (2FA) is disabled for a user from the server:

```bash
/usr/bin/pandora_manage /etc/pandora/pandora_server.conf \
    --disable_double_auth '<user>'
```

It works both if you are the one who has lost the generator and if you are the
administrator and someone else asks you. If what you want is to turn it off for
the whole console, there is the **`double_auth_enabled`** setting in the
`tconfig` table, but for a single account the command is cleaner.

## Console themes and a copy of the styles

Themes are changed from the **Web console**, in the user preferences. Before
touching icons or custom styles it is better to make a copy: the product brings
**`styles_backup.sh`** in the server utilities folder (`pandora_server/util/`),
which exports the icons and the CSS to `pandora_console/styles_backup` in two
compressed files with date and time.

## Putting the console on HTTPS

The console is served over HTTPS with a web server certificate:

1. Have the certificate and its key ready (`.crt` and `.key`). **Do not use
   self-signed ones**: they are not trustworthy for the user and they do not
   avoid the warnings.
2. Configure Apache to listen on 443 and point to those files
   (`SSLCertificateFile` and `SSLCertificateKeyFile`).
3. Restart the web service.
4. If you want **nobody** to get in over HTTP, enable the setting that forces the
   use of HTTPS in **Management → Settings → System Settings → General setup**.

## AD or LDAP authentication does not work

Pandora FMS supports both, and they share almost all the configuration. If the
users cannot get in, check:

- **Server and port** of the LDAP or of the domain.
- **The search function**: *Local Command* uses the `ldapsearch` command (it has
  to be installed on the Pandora FMS server); *PHP function* uses the console's
  own engine. The normal thing is *PHP function*, and *Local Command* only makes
  sense in very large environments.
- **The base domain and the organisational units / groups**: this is where
  everybody gets it wrong. The search path has to point exactly to where the
  users are.

## Console time zone

The console uses the system zone; if it is not defined, it falls back to the
European one. If the data shows up with another time, set the **time zone in
Management → Settings → System Settings → General setup** (`timezone` setting).

The old entries proposed editing `include/config_process.php` and forcing
`date_default_timezone_set`. It still works, but it is plan B: better to leave it
consistent with the operating system.

## Notifications: managing and deleting them

- **Deleting them**: from **Workspace → Messages → Message list**, where they can
  all be deleted.
- **Configuring them**: in **Management → Settings → System Settings →
  Notifications** they are activated or deactivated per type and assigned to
  users or groups. Each user also has their own configuration of what they want
  to receive.

## Where PHP failures show up

There are two places, and it is better to look at both:

- **The web server log**: `error_log`, or `ssl_error_log` if the console runs
  over HTTPS. Check in `/etc/php.ini` that error logging is active and that the
  path is defined.
- **The console's own log**: it has to be enabled in **Management → Settings →
  System Settings → General setup → Enable console log**, and it is written to
  `pandora_console/log/console.log`.

To debug temporarily, the PHP reporting can be raised from the console's
`include/config.php`:

```php
error_reporting(E_ALL);
```

When you finish, bring it back down: in production it is not advisable to leave
that level.

## Priority of custom fields in alerts

When the same field (`_field1_` to `_field20_`) is defined in several places, the
alert engine applies this order of precedence:

| Alert type | Order of precedence |
|---|---|
| Conventional alerts | action > alert template |
| SNMP alerts | SNMP alert configuration > action > command default values |

In conventional alerts, whatever is defined in the **action** overrides what
comes in the **template**. In SNMP alerts, the **SNMP alert** configuration has
the highest priority; if it is empty, the value of the **action** is taken, and as
a last resort the default values of the **command**.

## WUX modules that do not initialise

**WUX** modules (Web User Experience) run web transactions in a real web client
through Selenium. The periodic checks are performed by the Pandora FMS internal
**WUX Server**. If the modules are left uninitialised, check:

1. **The WUX server is enabled on the server.** In
   `/etc/pandora/pandora_server.conf`, the **`wuxserver`** token must be at
   **`1`** (by default it comes disabled at `0`).
2. **Connectivity with Selenium.** The Pandora FMS server must reach the host and
   port configured in `wux_host` and `wux_port` (by default `localhost:4444`).
3. **The Pandora FMS server log** (`pandora_server.log` and
   `pandora_server.error`) and **Selenium's own log**, where session or
   transaction failures are detailed.

## "Console and server in a different version"

That notice appears when the console and the server are not in the same version.
Even if the platform works, it is not a healthy situation: they have to be
aligned.

- The console version is seen in the console **footer**.
- The server version, in **Servers → Manage servers**.

The right thing is to update **both** to the same version; the order is in
[Updates](../parte-1/1.4-actualizaciones.md).

## Making the server start up on its own after a crash

In modern systemd distributions, the **`pandora_server.service`** service itself
includes an automatic restart directive (`Restart=always`) through the daemon
supervisor. To make sure that the service starts with the operating system and
recovers if the process goes down:

```bash
systemctl enable --now pandora_server
systemctl status pandora_server
```

In multi-host high availability deployments (active/passive cluster), Pandora FMS
also has the cluster tool **`pandora_ha`**, which watches the database heartbeat
of the nodes and manages the switchover according to the high availability
runbook.

## What licence do I have

The licence type and its expiry date are checked in the console itself, in
**Management → Setup → License** (*Licence*). That screen is the one that rules:
it shows the contracted limit, what is in use and which modality is active.

The possible models (perpetual or subscription, by agents or by modules) and which
pieces need a separate licence are explained in
[Licensing](../parte-1/1.5-licenciamiento.md). Here there is no talk of prices or
commercial tiers.

## The licence has expired: how to renew it

The process is the same as the one for the first installation, with the new key:

1. The provider sends the **AuthKey** for the new period.
2. In the console, go to **Management → Setup → License** and choose **Request
   new license**.
3. Enter the **AuthKey** in the authentication key field and press the **online
   validation**.

The console generates the licence, validates it against the server and leaves it
installed. If the installation has no internet access, the same dialog allows
activating it by hand; the complete procedure is in
[Licensing](../parte-1/1.5-licenciamiento.md).

## I have updated and I want to go back

**There is no supported way back.** An update is not undone by reinstalling the
old packages: if something went wrong, what is done is **restoring the backup or
the machine snapshot**, which is exactly what is asked for before starting (see
[Updates](../parte-1/1.4-actualizaciones.md)).

That is why the usual recommendation: snapshot before touching anything, and the
update in a window with room to go back to the starting point.

!!! warning "Notice"
    Reinstalling old packages "on top" leaves the installation in a state that is
    not supported. If there is a need to go back, restore the complete copy or
    snapshot, including the database and the console files.
