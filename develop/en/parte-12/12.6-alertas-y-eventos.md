# Alerts and events

This section gathers the problems that repeat the most with alerts. Sometimes
they do not fire when they should. Other times they fire too much. And other
times the notice does not arrive in good shape. All the checks are done from the
**Web console**, in **Alerts** and **Management → Settings**, except where
something else is indicated.

## The alert does not fire even though the value is bad

It is almost always the **minimum number of alerts** of the template. That field
says how many bad values in a row are needed to fire. The count is this:

- With **minimum 0**, the alert fires on the first bad value.
- With **minimum 1**, **two** bad values are needed within the period set by the
  **time threshold**.

If the module reports isolated spikes and the alert does not fire, the minimum
is set correctly. The problem is not the alert: it is that the module
oscillates. Lower the minimum to 0 or adjust the threshold period. And check the
module's **Flip Flop protection**: it requires several checks in a row before
changing status.

## Neither alerts nor events are triggered

Before touching the template, rule out that something is silencing them. It is
checked in this order:

- The **Event storm protection** is not active in **Management → Settings →
  System Settings → General setup**. If it is, the platform dampens events when
  they arrive in a flood and it may seem that they are not triggered.
- The **agent** is not in quiet mode.
- The **module** is not either.
- The **group** the agent belongs to does not have alerts or events disabled.

If the four things are fine, the alert has to fire. Check the server log to see
whether the event is evaluated at all.

## The alert fires every five minutes

The template has two limits that are worth telling apart: the **maximum number
of alerts** and the **time threshold**. For a problem that persists to warn only
once a day: **time threshold at one day**, **minimum at 0** and **maximum at 1**.
That way the alert fires on the first bad value. And it does not repeat until
the threshold has passed, however long the module stays bad.

## What each limit of the template means

The three fields are easily confused and they do different things:

| Field | What it controls |
|---|---|
| **Minimum number of alerts** | How many times the condition must repeat for the action to run the first time |
| **Maximum number of alerts** | How many alerts can be sent in a row within the same interval |
| **Time threshold** | Time that must pass, with the wrong status still active, before warning again |

An example with the threshold at 24 hours. The alert warns once. It does not
repeat until a day has passed, even if the module stays in a bad state all that
time.

## The alert email arrives without line breaks

It is a formatting problem of the message body, not of the sending. In the alert
**action** (or in the advanced fields of the template if they are defined
there), the text has to be wrapped between the `<pre>` and `</pre>` tags:

```html
<pre>
Hello, this is an automated email coming from Pandora FMS

This alert has been fired because a CRITICAL condition in one of your monitored items:

Agent: _agent_
Module: _module_
Module description: _moduledescription_
Timestamp: _timestamp_
Current value: _data_

Thanks for your time.
Best regards,
Pandora FMS.
</pre>
```

The macros (`_agent_`, `_module_`, `_data_` and the rest) are replaced on
sending. Without the tags, the email client joins all the lines.

## The graph does not appear in the alert email

The graphs attached to the notices are rendered by the server with a headless
rendering engine. If they do not come out, it is checked in this order:

1. **The engine binary is installed and correctly pointed to.** The setting is
   **Chromium path** in **Management → Settings → System Settings → General
   setup**, and by default it is `/usr/bin/chromium-browser`. If the engine is
   not installed on the server, there is no graph.
2. **The API configuration is correct.** Check the API call the console uses to
   request the graph.
3. **Name resolution (DNS).** If the console calls itself by a name that does
   not resolve, the API fails. To settle the question, use its IP address.
4. **What is outside:** a proxy or a firewall in between.
5. **What is inside:** SELinux and `iptables` on the server itself.

!!! note "Notice"
    The old procedure talked about **PhantomJS**. That engine is no longer used:
    rendering is done by Chromium, with the **Chromium path** setting.
