# Version and support policy

Updating a monitoring environment in production is not like updating a laptop.
Pandora FMS is spread across pieces: console, server, database, EndPoints,
satellites and, in a Command Center, several nodes. "Updating Pandora" is not
an action, it is a decision: which pieces move, in which order and with how much
room to go back. The good news is that not everything has to be updated at once.
The bad news is that some pieces do have to move together.

## Introduction

The pieces of an installation do not have the same tolerance for lagging behind:

- **Console, database schema and server** are one unit. They are updated together
  and to the same version. Mixing them is asking for trouble.
- **EndPoints** can run behind the server for a while. They report their version in
  every XML and the server stores it, so an estate with EndPoints on several
  versions is the normal thing in any installation with a history. That said: new
  features do not work until the EndPoint is updated. For SIEM, for instance,
  EndPoints are recommended to be at least on 783. And updating thousands of
  EndPoints is a deployment in itself, not a restart.
- **Satellite servers** do not accept just any combination: a 785 satellite is not
  compatible with earlier versions of Pandora, and the other way round the new
  satellite features simply do not work. They are updated with their own
  installer, not with Warp Update.
- **In a Command Center**, every node is an installation and the Command Center sits
  above them. After updating, the environments have to be re-centralised, so the
  maintenance window belongs to the whole set, not to each piece on its own.

The practical consequence is the same in every case: choose **a target version**,
decide **which pieces go into the window** and do it with the backup in front of
you. The procedure is not repeated here: it is in [Updates](1.4-actualizaciones.md).

## LTS version

**LTS** (*Long Term Support*) versions are released **once a year** and prioritise
stability and validation: they gather what the intermediate versions have already
been through and consolidate it into a better tested base. They are the
recommended ones for production.

Their support goes beyond that year:

- They are maintained with **LTS patches**: security fixes, relevant issues and
  critical bugs, published **as needed**.
- An LTS is supported **for two years**, and that support **can be extended by
  another two** through a **long-term support contract**, which may involve
  additional cost.
- And what it does **not** include: features from newer versions. A patch brings
  security and critical fixes. It does not bring down to the LTS improvements that
  only exist in newer versions.

Two nuances that are often confused and are worth being clear about:

- The **support expiry date** shown in **Management → About** is the
  **licence's**, not the version's: it is tied to the licence payment. It tells you
  whether the installation is covered, not when you have to update.
- What usually sets the real limit is not Pandora, it is the **operating system**.
  If the vendor stops supporting it or stops publishing security patches, the
  longest-lived LTS is left without solid ground. Before stretching the support of
  a version, look at the system's life calendar.

If there is no specific reason for the opposite, this is the choice. And to stay on
this track without having to think about it, Warp Update has the **Limit to LTS
updates** option, which discards intermediate versions when updating.

**Supported operating system.** The current LTS (800) is installed on RHEL/Rocky
**9 and 10** and on Ubuntu **22.04**:

| Version | RHEL / Rocky | Ubuntu |
|---|---|---|
| 800 LTS (current) | 9 and 10 | 22.04 |

The full matrix, which changes with every version and every system, is in the
[support and version policy](https://pandorafms.com/en/policy-support-versions-os/).
And it refers **only to the server** and its associated elements: database, high
availability, reporting consoles, Command Center, historical database,
OpenSearch. **Support for agents and EndPoints does not change** with it.

## Feature Release (FR) version

**Feature Release** versions are published **roughly every two months** and bring
in new features, improvements and fixes. They are meant for those who need
continuous access to the evolution of the product.

When it makes sense in a real environment, because choosing it has a price:

- When a specific feature is needed **before** it reaches the LTS, and waiting for
  the yearly cycle is not an option.
- When there is a **pilot** environment where the new thing can be tested without
  putting what sustains the service at risk.
- When the team accepts that every two months there is an update to review, test
  and apply.

What is not a good idea is running a critical environment on FR without that room
for testing: you notice it exactly when there is no way back.

Choosing one or the other is not a decision for life: every year, when the LTS
comes out, it is time to review whether that FR is worth keeping or whether it no
longer brings anything the LTS does not have. And when in doubt, the rule is the
usual one: stability is not negotiable in what sustains the service; new things are
tested where you can go back.

## Patches

Between one version and the next you do not wait for the following release: fixes
arrive as **patches**. A patch corrects something specific (a vulnerability, a
relevant issue or a critical bug) without changing version family.

**How they are named.** The version number rules and the patch adds a consecutive
number: LTS **800** receives **800.1**, **800.2** and so on. **Feature Release**
versions also have patches, following the same logic, but **only in specific
situations**.

**Where to see what each one brings.** Every version has its release notes page,
and that is where each patch is detailed:

- Release notes, version by version: for instance LTS
  [800 "Aquarius"](https://pandorafms.com/es/notas-de-version/800-lts-aquarius/).
- Updates and release notes index:
  [pandorafms.com/en/releases](https://pandorafms.com/en/releases/).
- Full product changelog:
  [pandorafms.com/en/changelog](https://pandorafms.com/en/changelog/).
- Operating system support and version policy:
  [pandorafms.com/es/politica-soporte-versiones-os](https://pandorafms.com/es/politica-soporte-versiones-os/).

**How they are distributed.** Always with Warp Update, and that is where the
convenience is: the full circuit is in [Updates](1.4-actualizaciones.md).

- **Connected**: from the console, **Warp Update → Update online**. The wizard
  downloads and applies the patch.
- **Disconnected, or with every package reviewed beforehand**: packages are
  downloaded by hand and uploaded to the wizard (**Warp Update Offline**) or
  applied with the manual procedure. It is the mandatory route in isolated
  environments and the usual one where security requires auditing before
  installing.
