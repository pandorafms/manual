    Inventario¶

    Hay una pregunta que en cualquier departamento de sistemas aparece tarde o temprano, casi siempre en mal momento: «¿y nosotros qué tenemos?». No qué está en verde ni qué alerta ha saltado esta mañana, sino qué máquinas hay, con qué procesador, qué software llevan instalado, quién tiene cuenta en ellas y qué servicios levantan al arrancar. Contestarla a mano es arqueología: se abre una sesión aquí, se mira un uname allá y se reza para que nadie haya instalado nada que no tocaba. El inventario de Pandora FMS existe para no tener que hacer esa arqueología: recoge esos datos solo, de cada equipo monitorizado, y los deja consultables y exportables.

    Qué es el inventario¶

    El inventario es la parte de Pandora FMS que responde a «qué hay», no a «cómo está». Es una distinción que hay que dejar clara desde el principio: un módulo de monitorización tiene umbrales, estados y alertas; un dato de inventario no. Nadie va a recibir un aviso porque un equipo tenga instalada la versión 1.2 de una librería. El inventario es una fotografía, y su valor está en poder comparar fotografías: qué cambió desde ayer, qué software nuevo apareció, qué usuario se dio de alta sin que nadie lo supiera.

    Por eso el inventario es independiente de la monitorización. Se recoge aparte, se guarda aparte y se consulta aparte, aunque viva en la misma consola y alimente los mismos informes. Un equipo puede estar perfectamente monitorizado y no tener ni un dato de inventario, y al revés.

    Los datos se pueden recoger por dos caminos:

    • De forma local, con el EndPoint instalado en la máquina. El EndPoint ejecuta los plugins de inventario y envía el resultado.
    • De forma remota, con los módulos de inventario que ejecuta el servidor de Pandora FMS contra una máquina de la red: queries WMI, órdenes por SSH o cualquier script que devuelva el formato esperado.

    El inventario alimenta listados e informes: desde un listado de software instalado en toda la flota hasta un informe de cambios de configuración de un dispositivo de red. De eso se habla más abajo.

    Módulos de inventario: el catálogo¶

    Todo empieza por un módulo de inventario. Es la pieza que define qué se recoge, y tiene tres datos que importan: un nombre, el sistema operativo al que aplica y una lista de campos separados por punto y coma. Cuando el módulo recoge datos, cada línea del resultado se parte por esos campos y se muestra como una tabla. Si el formato dice Model;Size, la consola sabrá que la primera columna es el modelo y la segunda el tamaño.

    Pandora FMS trae un catálogo de módulos por defecto bastante amplio, repartido por sistemas operativos. Estos son los principales:

    Sistema operativo Qué se puede inventariar
    Linux Procesador, memoria, tarjetas de vídeo y de red, discos, CD-ROM, software instalado, servicios de arranque, sistemas de ficheros, procesos, usuarios, direcciones IP y rutas
    Windows Todo lo anterior más monitores, placa base, parches instalados, impresoras, servicios instalados, productos y claves de Microsoft (MS-Products, product_ID, product_key)
    Solaris Procesador, memoria, tarjetas de red y software
    Cisco Configuración del dispositivo, interfaces (por script local o por SSH) e información general
    Android Software instalado

    El catálogo es lo que la consola ofrece; qué recoge el EndPoint por su cuenta y qué se pide en remoto se ve en los dos apartados siguientes.

    Hay un detalle que provoca más de un rato perdido y que conviene decir en voz alta: el sistema operativo del módulo tiene que coincidir con el del EndPoint. Si un módulo está marcado como Windows y se intenta asignar a un EndPoint Linux, no aparecerá en la lista. No es un error de la consola: es que el módulo está pensado para otro sistema.

    Dónde se gestiona todo esto: Gestión → Configuración → Módulos de inventario (Management → Configuration → Inventory modules).

    Inventario local con los EndPoints¶

    El camino local es el más cómodo cuando el EndPoint ya está instalado: la propia máquina se mira a sí misma y envía el resultado. No hay que abrir puertos ni guardar credenciales de nadie.

    Linux¶

    En Linux, el EndPoint lleva un plugin llamado inventory. Se activa con una línea en el fichero de configuración pandora_agent.conf:

    module_plugin inventory 1 cpu ram video nic hd cdrom software init_services filesystem users route

    La línea se lee en tres partes. Primero la activación del módulo. Después un número que es cada cuántos días se ejecuta: si se pone 0, el inventario se envía en cada ejecución del EndPoint. Y al final, la lista de objetos que se quieren recoger. Si se deja solo el número, se recoge todo lo disponible:

    module_plugin inventory 1

    Los objetos que entiende el plugin son: cpu, ram, video, nic, hd, cdrom, software, init_services, filesystem, process, users, ip, route y kernel.

    Requisito Detalle
    lshw o hwinfo instalado El plugin los usa para el hardware. Sin ninguno de los dos, solo se recogen software, servicios de arranque, sistemas de ficheros, procesos y rutas
    Permisos de root Algunos objetos (por ejemplo, el listado de usuarios o el hardware) necesitan privilegios elevados

    El plugin apunta en la propia máquina cuándo se ejecutó por última vez, de modo que el intervalo en días se respeta aunque el EndPoint arranque muchas veces al día.

    Windows¶

    En Windows el inventario local no se activa con una sola línea, como en Linux. Aquí cada objeto de inventario es un módulo aparte, y cada módulo llama a su propio script. El EndPoint trae la muestra en el fichero de configuración (comentada); se descomenta lo que se quiera usar y se reinicia el EndPoint. Cada módulo tiene esta forma:

    module_begin
module_plugin cscript.exe //B //t:20 "%PROGRAMFILES%\Pandora_Agent\util\cpuinfo.vbs"
module_end

    Los scripts que trae el EndPoint de Windows cubren, cada uno, un objeto:

    Objeto Script del EndPoint
    Procesador cpuinfo.vbs
    Memoria raminfo.vbs
    Discos diskdrives.vbs
    CD-ROM cdromdrives.vbs
    Tarjeta de vídeo videocardinfo.vbs
    Tarjetas de red ifaces.vbs
    Monitores monitors.vbs
    Impresoras printers.vbs
    Software instalado software_installed.vbs
    Productos y KB de Microsoft ms_products.exe
    Usuarios userslogged.vbs
    Clave e ID de producto productkey.vbs, productID.vbs

    Un detalle que hay que mirar antes de dejarlo así: la muestra que viene de fábrica añade module_absoluteinterval 7d a cada módulo, lo que hace que el inventario se ejecute una vez cada siete días, al margen del intervalo del EndPoint. Si se quiere que el inventario siga la frecuencia normal del EndPoint, se quita esa línea. Un inventario a la semana se queda viejo enseguida.

    Los módulos locales aparecen solos¶

    Aquí está la diferencia práctica con el inventario remoto, y merece la pena subrayarla porque ahorra bastante trabajo: los módulos locales no se asignan a mano en la consola. Basta con que el módulo exista en el catálogo con el sistema operativo correcto y con que la ejecución esté definida en el fichero del EndPoint. Cuando llega el primer dato, la consola crea el módulo en la ficha del agente y lo deja visible en su pestaña Inventario.

    Crear módulos locales propios¶

    Además de los que vienen de serie, se pueden crear módulos de inventario propios para Linux y Windows. El procedimiento es el mismo que el remoto, pero con dos salvedades: no se rellenan los campos Intérprete ni Código, y hace falta un script que devuelva un XML con esta estructura:

    <inventory>
  <inventory_module>
    <name>NOMBRE_DEL_MODULO</name>
    <type>generic_data_string</type>
    <datalist>
      <data>DATO1;DATO2;DATO3</data>
    </datalist>
  </inventory_module>
</inventory>

    El nombre tiene que ser exactamente el mismo que se le puso al módulo en la consola, y cada <data> es una línea con los campos separados por ; tal como se declararon en el Formato.

    El script se declara en pandora_agent.conf como un plugin más: el EndPoint ejecuta el comando y mete su salida tal cual en el XML que envía al servidor, así que el script solo tiene que imprimir el bloque <inventory> por la salida estándar. En Linux, un script de shell y la línea que lo lanza quedan así:

    #!/bin/sh
# /etc/pandora/plugins/mi_inventario.sh

echo "<inventory>"
echo "  <inventory_module>"
echo "    <name>MiInventario</name>"
echo "    <type>generic_data_string</type>"
echo "    <datalist>"
echo "      <data>uno;dos</data>"
echo "      <data>tres;cuatro</data>"
echo "    </datalist>"
echo "  </inventory_module>"
echo "</inventory>"

    # pandora_agent.conf
module_plugin /etc/pandora/plugins/mi_inventario.sh

    El directorio de plugins del EndPoint (/etc/pandora/plugins) está en el PATH, así que el script también se puede llamar por su nombre (module_plugin mi_inventario.sh). En Windows, la línea sigue el mismo patrón que los módulos de serie, con module_begin y module_end, y el script imprime el mismo XML:

    # pandora_agent.conf
module_begin
module_plugin cscript.exe //B //t:20 "%PROGRAMFILES%\Pandora_Agent\util\mi_inventario.vbs"
module_end

    Y el aviso de orden: hay que crear el módulo en la consola antes de reiniciar el EndPoint, o el dato llegará y no habrá dónde guardarlo.

    Inventario remoto: crear el módulo y asignarlo¶

    El camino remoto es el que se usa cuando no hay EndPoint en la máquina: un dispositivo de red, un servidor del que no queremos instalar nada o un equipo al que solo se llega por SSH. Aquí el que trabaja es el servidor de Pandora FMS, que ejecuta el script del módulo contra el destino y guarda el resultado.

    Crear el módulo¶

    Se hace en Gestión → Configuración → Módulos de inventario, con el botón Crear. Los campos del formulario son estos:

    Campo Detalle
    Nombre Obligatorio; el identificador del módulo
    Descripción Texto libre
    SO Obligatorio; debe coincidir con el del destino
    Intérprete El intérprete con el que se ejecuta el script (Shell, Perl…). Se deja en blanco solo para los módulos locales
    Formato Obligatorio; los campos que devuelve el módulo, separados por ;
    Modo bloqueo Interruptor; el resultado del módulo se trata como un único bloque (ver más abajo)
    Modo script Elige entre Modo script (se indica una Ruta del script) y Usar código en línea (se escribe el Código directamente)

    El aviso clásico, y sigue vigente: si se deja el Formato en blanco, el módulo no se guarda y se pierde lo escrito. Es el campo que más se olvida y el que más molesta cuando se olvida.

    Qué tiene que devolver el script¶

    Aquí está la diferencia con el inventario local, y conviene tenerla clara porque es la que rompe los primeros intentos: el script remoto no devuelve un XML. El XML con <inventory> es cosa del EndPoint; el módulo remoto devuelve texto plano, con un registro por línea y los campos separados por ;, en el mismo orden que el Formato del módulo. El servidor guarda esa salida tal cual y la consola la pinta como una tabla, usando el Formato como cabecera.

    El script recibe como argumentos el destino (el valor del campo Destino) y después, o los campos personalizados en el orden en que se crearon, o el usuario y la contraseña. Con eso consulta la máquina remota y saca una línea por elemento.

    Un ejemplo mínimo: un módulo con Formato Campo1;Campo2, Intérprete /bin/sh y este Código:

    #!/bin/sh
# $1 es el destino; después llegan los campos personalizados o el usuario y la contraseña
destino="$1"

# ... aquí se consulta $destino ...

echo "uno;dos"
echo "tres;cuatro"

    Eso deja dos registros, uno por línea, con dos campos cada uno. Un módulo real hace exactamente lo mismo, solo que rellena cada línea con lo que devuelva la consulta: el módulo de CPU de Windows que trae Pandora imprime una línea por procesador con nombre;velocidad;descripción, y el de Cisco saca una sola línea con IP;hardware;número de serie;IOS.

    Si el módulo está en Modo bloqueo, la salida no se parte en registros: se guarda entera como un único bloque de texto, que es lo que luego se compara en la vista de diferencias.

    Asignarlo al EndPoint¶

    La asignación se hace en la ficha del agente, en la pestaña Inventario (Gestión → Recursos → Gestionar agentes → agente → Inventario). El formulario de alta pide:

    Campo Detalle
    Módulo El módulo de inventario a añadir; solo aparecen los que coinciden con el SO del EndPoint
    Intervalo Cada cuánto se ejecuta (por defecto, una hora)
    Destino IP o nombre de la máquina de la que se saca el inventario
    Usar campos personalizados Sustituye usuario y contraseña por campos propios con nombre
    Usuario y Contraseña Credenciales del destino; admiten macros de campo personalizado del EndPoint

    Con Usar campos personalizados se crean campos con un nombre, se les da valor y se marca Es una contraseña en los que deban guardarse ofuscados. Esos campos se pasan al script en el mismo orden en que se crearon. Cuando el módulo ya está asignado, la tabla de la pestaña permite Forzar una ejecución inmediata (útil para no esperar al intervalo), editarlo o eliminarlo.

    Por debajo, el servidor arma el comando con el intérprete, la ruta del script o el código en línea, el destino y las credenciales (o los campos personalizados), y lo ejecuta con un tiempo de espera configurable. Si el comando falla, el inventario de ese ciclo simplemente no se actualiza.

    Ver los datos de inventario¶

    Hay dos formas de mirar el inventario, y cada una sirve para una cosa.

    La pestaña Inventario del agente¶

    En la vista de un agente, la pestaña Inventario muestra todos sus módulos, uno debajo de otro. Arriba hay un selector de Módulo, un selector de Fecha (por defecto, Ahora) y un buscador. Cada módulo se pinta como una tabla, con el Formato como cabecera y un Total de registros al pie. Es la vista para mirar una máquina concreta con calma.

    El selector de fechas necesita una explicación, porque desconcierta la primera vez. Solo aparece una fecha cuando hubo cambios. Pandora FMS guarda inventario únicamente cuando el dato cambia respecto a la última vez, así que si un equipo lleva una semana igual, en el selector no habrá una entrada por día. Es una decisión de diseño, no un fallo: guardar la misma foto cada hora sería ruido.

    La vista global¶

    En Operación → Monitorización → Inventario (Operation → Monitoring → Inventory) se ve el inventario de toda la flota de una vez. Los filtros son grupo (con opción de incluir subgrupos), agente, módulo, búsqueda libre, ordenar por agente, fecha y estado del agente.

    Por defecto la vista está en modo Información básica, que enseña una fila por agente con sus datos generales: alias, IP, grupo, sistema operativo, versión, intervalo, último contacto, campos personalizados… Al elegir un módulo concreto, la tabla cambia y muestra los datos de ese módulo, con una columna de marca de tiempo y otra de agente para saber de quién es cada fila.

    El botón Exportar a CSV descarga lo que esté filtrado en ese momento, con el separador de CSV que esté configurado en la consola.

    Los cambios generan eventos¶

    Cada vez que el inventario de un módulo cambia, el servidor genera un evento de configuración con las altas y las bajas: qué registro apareció y cuál desapareció. Es la materia prima de los informes de cambios, y también la razón por la que un módulo muy movido (el listado de procesos, por ejemplo) puede inundar la consola de eventos. Para eso existe la lista negra que se cuenta en el apartado de mantenimiento.

    Diferencias entre versiones de inventario¶

    Hay módulos cuyo resultado no tiene sentido trocear en filas. La configuración de un dispositivo de red, por ejemplo: es un bloque de texto y lo que interesa es compararlo con el de la ejecución anterior, no verlo línea a línea como una tabla.

    Para eso está el Modo bloqueo. Al activarlo en un módulo, su resultado se guarda entero como un bloque de texto, y en la vista del agente aparece un botón de vista de diferencias junto al nombre del módulo:

    Esa vista pone las dos versiones en dos columnas y resalta lo que cambió. Es la herramienta para responder a «¿alguien ha tocado este router desde la semana pasada?».

    Alertas de inventario¶

    El inventario también sirve para vigilar lo que no debería estar ahí. Para eso están las alertas de inventario, que se configuran en Gestión → Alertas → Alertas de inventario (Management → Alerts → Inventory alerts).

    La idea es la misma que la del resto de Alertas y notificaciones, con una diferencia de fondo: no se disparan sobre un módulo de monitorización, sino sobre el contenido del inventario de un grupo de agentes. Son, por tanto, globales: se aplican a un grupo, no agente por agente.

    El formulario tiene estos campos:

    Campo Detalle
    Nombre y Descripción Identificación de la alerta
    ACL de grupo Visibilidad de la alerta
    Módulos de inventario El módulo cuyo contenido se vigila
    Condición Cómo se decide si salta: Coincidencia, Lista negra o Lista blanca
    Umbral de tiempo Tiempo mínimo entre disparos
    Acción Qué se ejecuta cuando salta
    Grupos de alertas Los grupos de agentes sobre los que se evalúa (la condición real)
    Deshabilitar evento Si se activa, la alerta no genera además un evento

    Hay que distinguir bien ACL de grupo de Grupos de alertas, porque los dos hablan de grupos y no significan lo mismo: el primero es quién puede ver la alerta, el segundo es a qué agentes se aplica. Un despiste aquí deja la alerta sin efecto o disparando donde no toca.

    Las tres condiciones funcionan así:

    • Coincidencia (Match). Se rellenan los campos del módulo (por ejemplo, el nombre y la versión de un software) y salta cuando una línea del inventario casa con todos ellos. Los campos admiten expresiones regulares, y un campo vacío equivale a «cualquier valor» (.*). Es la condición para «avísame si aparece esta versión concreta de este programa».
    • Lista negra (Black list). Se elige un campo del módulo y se escribe una lista de valores, uno por línea. Si el inventario contiene alguno de ellos, salta. Es la condición para «esto no debería estar instalado».
    • Lista blanca (White list). Igual, pero al revés: el valor del inventario tiene que estar en la lista, y si no está, salta. Es la condición para «solo estos están permitidos».

    Y Deshabilitar evento tiene su gracia cuando el inventario dispara muchas alertas de golpe: evita que cada una genere además un evento y deje la consola de eventos como un árbol de Navidad. La alerta se sigue disparando y ejecutando su acción; lo que se ahorra es el evento.

    Estas alertas son la forma de detectar versiones vulnerables de un programa, software no autorizado o cuentas de usuario que nadie debería tener.

    Inventario en informes y políticas¶

    El inventario no vive aislado: alimenta los informes y se puede desplegar por políticas.

    En informes hay cuatro elementos que tiran del inventario:

    • Inventario de agentes, el listado de agentes con sus datos generales.
    • Inventario de módulos, el listado de módulos con sus datos.
    • Inventario, el inventario completo con filtros.
    • Inventario de cambios, las altas y bajas registradas.

    La mecánica de plantillas e informes se cuenta en Informes.

    Y en políticas, los módulos de inventario se pueden aplicar a grupos de agentes igual que se aplica un módulo de monitorización, con su intervalo. En la pestaña Inventario del agente, los módulos que vienen de una política se marcan con un icono. Las políticas se explican en Políticas de monitorización.

    Mantenimiento del inventario¶

    Dos ajustes que conviene conocer para que el inventario no se convierta en un problema de espacio o de ruido.

    El primero es el borrado por antigüedad. En Gestión → Ajustes → Configuración del sistema → Rendimiento está el campo Nº de días máximo antes del borrado de datos de inventario, que por defecto son 21 días. Pasado ese plazo, el servidor va borrando el histórico de inventario más antiguo. Si se necesita guardar más tiempo para auditorías, se sube; si se quiere aligerar la base de datos, se baja.

    El segundo es la lista negra de cambios. Hay módulos cuyo contenido cambia en cada ejecución (el listado de procesos es el ejemplo de manual) y que, por tanto, generarían un evento de configuración cada vez. Para evitarlo, esos módulos se marcan en una lista y sus cambios dejan de generar evento.

    La lista está en Gestión → Ajustes → Configuración del sistema → Configuración general, en la pestaña Comportamiento, dentro del apartado Eventos. Es un selector doble: a la izquierda quedan los módulos que están fuera de la lista negra y a la derecha los que están en la lista negra, y se pasan de un lado a otro con las flechas.

    De fábrica vienen ya excluidos el procesador, los procesos y el módulo de seguridad, en sus versiones de Linux y de Windows.

    Con esto, el inventario queda completo: se recoge solo, se consulta de un vistazo, avisa cuando algo no cuadra y no llena la base de datos más de lo necesario. Que es exactamente lo que se le pide a una herramienta que responde a la pregunta «¿qué tenemos?».
