    Monitorización con EndPoints¶

    El EndPoint es el software que se instala dentro de la máquina a monitorizar para sacarle el máximo partido: procesos, servicios, ficheros, lo que solo se ve desde dentro. Pandora FMS mantiene tres, uno en Go, otro en Perl y otro en C++ para Windows, que comparten formato de configuración y protocolo de envío pero difieren en lo que cada sistema operativo permite. Este capítulo cubre qué hace un EndPoint, cómo se dan los primeros pasos con él y cómo se gestiona su configuración desde la consola web sin tocar el fichero a mano cada vez.

    Qué es un EndPoint¶

    Un EndPoint hace, en bucle, siempre lo mismo: lee su fichero de configuración, ejecuta los módulos que tiene definidos, junta el resultado en un XML y lo envía al servidor por Tentacle. Ese ciclo se repite cada interval segundos, sin más ambición ni más misterio. La complejidad, si la hay, está en decidir qué módulos ejecutar, no en el mecanismo de entrega.

    Conviene no confundir dos cosas que se llaman parecido. El agente es el contenedor lógico que existe en la consola web: un nombre, unos módulos, un histórico. El EndPoint es el proceso instalado en la máquina que alimenta a ese agente con datos. La mayoría de las veces van de la mano —un EndPoint, un agente—, pero el agente puede existir sin ningún EndPoint detrás, recibiendo datos por otra vía: monitorización remota (SNMP, WMI, comprobaciones de red desde el servidor o desde un Satellite Server), inserción por API o un plugin de discovery. La pregunta que decide entre instalar un EndPoint o tirar de monitorización remota es simple: ¿necesitas algo que solo se ve desde dentro de la máquina —un proceso, un fichero de log, el uso de CPU real, un script propio— o te basta con lo que se ve desde fuera? Lo segundo no requiere tocar la máquina destino; lo primero, sí.

    La instalación del EndPoint está en Instalación online del EndPoint y sus variantes offline. Aquí se parte de que ya está instalado y en marcha.

    Los tres EndPoints: Go, Perl y Windows¶

    EndPoint Lenguaje Sistemas Servicio Configuración
    Go Go Linux x86_64 systemd (pandora_agent_daemon) /etc/pandora/pandora_agent.conf
    Unix (Perl) Perl Otros Unix: AIX, HP-UX, Solaris, BSD, macOS; y Linux en arquitecturas sin binario Go systemd (pandora_agent_daemon) /etc/pandora/pandora_agent.conf
    Windows C++ MS Windows Servicio PandoraFMSAgent pandora_agent.conf en la carpeta de instalación

    En Linux, el EndPoint Go es hoy el que se instala por defecto y el recomendado, y tiene buenos motivos para serlo. Es un único binario autocontenido, compilado de forma estática y sin librerías externas: no pide intérprete, ni módulos, ni versiones concretas de nada instalado en la máquina. Lo poco que usa del sistema son las herramientas que cualquier Linux trae de serie (sh, ps, df) y el cliente Tentacle, que viaja en el mismo paquete. Eso lo hace ideal para desplegar a escala en los sistemas con los que es compatible: se copia, se arranca y funciona, sin sorpresas de dependencias de una máquina a otra. Y como Go compila de forma cruzada para muchos sistemas operativos y arquitecturas, el mismo código puede generar binarios para otras plataformas sin reescribir nada; hoy el paquete oficial se distribuye para Linux x86_64.

    Un binario, cero dependencias

    Para desplegar EndPoints en muchas máquinas Linux x86_64, el EndPoint Go es la opción más cómoda: no hay que preparar el sistema antes de instalarlo.

    El EndPoint Perl entra en juego en dos situaciones: sistemas Unix que no son Linux (AIX, HP-UX, Solaris, los BSD, macOS) y arquitecturas Linux para las que no hay binario Go, que hoy son x86, armv7l y aarch64. El instalador en línea detecta la arquitectura solo y cambia a compilación de Perl desde fuentes sin que haga falta pedirlo expresamente. En Windows, el único candidato es el EndPoint nativo en C++.

    Los tres hablan el mismo idioma hacia el servidor: mismo formato de pandora_agent.conf, misma sintaxis module_begin / module_end, mismo XML de datos y mismo transporte Tentacle. Lo que cambia de uno a otro —qué tipos de módulo soporta, si tiene watchdog, cómo se reinicia— se señala sección a sección conforme aparece.

    Primeros pasos con un EndPoint recién instalado¶

    Un EndPoint recién instalado registra el agente en la consola web en cuanto envía su primer XML: no hay que crearlo a mano. Lo hace posible la autocreación de agentes del servidor (autocreate 1 en pandora_server.conf), que viene activada por defecto en todos los entornos. El agente aparece en el grupo que declara el EndPoint —si ese grupo no existe, en el grupo de reserva que fija autocreate_group en el servidor— con el intervalo y los módulos que trae de fábrica la plantilla de configuración: en Linux y Windows, un puñado de módulos básicos (carga de CPU, conexiones TCP y plugins de uso de disco, de memoria y de red), suficientes para comprobar de un vistazo que el envío funciona. El intervalo por defecto es de 300 segundos (cinco minutos); cambiarlo es cuestión de editar interval en el fichero de configuración.

    Si el agente no aparece

    Con autocreate 0 en el servidor, los datos de un agente que no existe en la consola se descartan. Es una opción de seguridad para entornos donde solo se admiten agentes dados de alta a mano; si el EndPoint envía y el agente no aparece, es lo primero que conviene revisar.

    En Linux, el EndPoint corre como servicio systemd con el nombre pandora_agent_daemon:

    systemctl start pandora_agent_daemon
systemctl stop pandora_agent_daemon
systemctl restart pandora_agent_daemon

    El script de arranque antiguo de /etc/init.d sigue presente en algún paquete, pero está retirado: se limita a avisar de que hay que usar systemctl y termina sin hacer nada. No lo uses ni documentes procedimientos sobre él.

    En Windows, el EndPoint corre como el servicio PandoraFMSAgent:

    NET START PandoraFMSAgent
NET STOP PandoraFMSAgent

    La configuración vive en /etc/pandora/pandora_agent.conf en Linux y Unix —el mismo fichero para el EndPoint Go y el Perl; en una instalación con ruta propia, en <prefijo>/etc/pandora/— y en pandora_agent.conf dentro de la carpeta de instalación en Windows (por defecto, C:\Program Files\pandora_agent). Cualquier cambio manual en ese fichero exige reiniciar el servicio para que se aplique; si la configuración remota está activa, además hay que tener en cuenta lo que se explica más abajo, porque un cambio local puede acabar sobrescrito.

    Parámetros esenciales de pandora_agent.conf¶

    De los muchos tokens que admite pandora_agent.conf, estos son los que se tocan el primer día. El resto —módulos aparte— está en la referencia completa de configuración del EndPoint.

    Parámetro Qué hace Por defecto
    server_ip IP o FQDN del servidor de Pandora FMS al que reporta el EndPoint. localhost
    interval Segundos entre ciclo y ciclo de recogida y envío. 300
    group Grupo al que se asigna el agente en la consola web. Sin valor en el código; las plantillas de instalación traen Servers.
    agent_alias Nombre visible del agente en la consola. Si se deja vacío, toma el nombre de máquina (hostname). No confundir con agent_name, el identificador interno que usa el servidor para no duplicar agentes: cambiar el alias no renombra el agente. Vacío (hostname)
    remote_config Permite editar esta configuración y sus módulos desde la consola. Se trata en detalle en la siguiente sección. 0 en el código; las plantillas de instalación lo dejan en 1
    debug Con 1, el EndPoint registra más detalle en su log y, tras enviar cada XML, conserva una copia en la carpeta temporal (con el sufijo sent) en lugar de borrarla. Los datos se envían igual: sirve para ver qué se manda exactamente, no para probar a escondidas. 0

    Configuración remota desde la consola web¶

    Viene activada de fábrica

    Las plantillas de instalación de Linux y de Windows traen remote_config 1: cualquier EndPoint instalado con el paquete estándar permite, desde el primer minuto, que alguien con acceso a la consola edite su configuración y sus módulos sin tocar la máquina. El instalador en línea solo cambia ese valor si se le pasa explícitamente la variable PANDORA_REMOTE_CONFIG; si no se toca nada, queda activa. Si el token remote_config falta directamente del fichero, el valor que asume el código es 0, pero eso no es lo que trae la instalación estándar: es la situación de un fichero editado a mano y recortado. Antes de dar por hecho que un EndPoint está cerrado a cambios remotos, comprueba el token.

    Con la configuración remota activa, la consola puede sustituir el pandora_agent.conf del EndPoint entero y crear o modificar módulos locales sin que nadie se conecte a la máquina. El mecanismo por debajo es el mismo en los tres EndPoints, con matices: cada ciclo, el EndPoint calcula el MD5 de su configuración actual y lo compara con el que hay en el servidor.

    • Si el servidor no tiene todavía un MD5 para ese agente, el EndPoint sube su configuración local: es el primer contacto, y la consola parte de lo que ya había en la máquina en vez de exigir escribirlo de cero.
    • Si el MD5 del servidor difiere del local, el EndPoint descarga la configuración nueva y la deja como su fichero activo.
    • Si coinciden, no pasa nada: es el caso normal, ciclo tras ciclo.

    Desactivarla es tan simple como poner remote_config 0 y reiniciar el servicio; a partir de ahí, los cambios solo entran editando el fichero a mano en la máquina.

    Dos piezas más de la configuración que conviene conocer desde el principio: los custom fields del agente, que el EndPoint puede declarar en su fichero (custom_field1_name, custom_field1_value y sucesivos) y que, con la configuración remota activa, también se editan desde la consola; y los grupos protegidos por contraseña: si el grupo de la consola exige contraseña, el EndPoint tiene que declararla con group_password para que el servidor cree el agente en ese grupo.

    Un campo personalizado solo se rellena si ya existe en la consola con ese mismo nombre (Recursos → Campos personalizados); si no existe, el servidor descarta el valor sin más. Allí se define también su tipo: texto libre, lista de valores, contraseña (la consola la muestra con asteriscos) o enlace. Para un campo de tipo enlace, el EndPoint envía un par con el texto y la dirección:

    custom_field1_name Documentación
custom_field1_value ["Manual del servidor","https://intranet.example.com/srv01"]

    Una diferencia entre EndPoints, y no menor: el EndPoint Perl aplica la configuración remota con cualquier transfer_mode (tentacle, ssh, ftp o local), mientras que el EndPoint Go solo lo hace con tentacle o local; con ssh o ftp no descarga configuración remota.

    Autoconfiguración de EndPoints¶

    La configuración remota tiene una extensión natural para despliegues grandes: la autoconfiguración, que aplica grupo, políticas o configuración extra a cada EndPoint nuevo en cuanto se registra, según reglas definidas de antemano, sin tocarlos uno a uno. Se explica en detalle en Mecanismos de autoprovisión.

    Monitorizar lo básico del sistema¶

    Antes de pensar en scripts propios o en integraciones exóticas, conviene cubrir lo obvio: cuánta CPU y memoria libre hay, cuánto disco queda, si un proceso o un servicio siguen vivos. Es el 80 % de lo que se pide a un EndPoint, y buena parte llega hecha: sin configurar nada, la plantilla con la que se instala ya recoge lo básico.

    Lo que sale de fábrica Linux (Go y Perl) Windows
    Uso de CPU Módulo CPU Load (con vmstat), más CPU IOWait y Load Average Módulo CPU Load (consulta WMI)
    Uso de cada disco (%) Plugin pandora_df_used Plugin df_percent_used.vbs
    Uso de memoria (%) Plugin pandora_mem_used (incluye swap) Plugin mem_percent_used.vbs
    Tráfico de red Plugins pandora_netusage y net_usage Plugin network.vbs
    Conexiones TCP Módulo TCP_Connections Módulo TCP_Connections
    Servicios conocidos Plugin autodiscover --default: detecta los servicios habituales (bases de datos, servidores web…) y vigila su estado, su CPU y su memoria Igual, con autodiscover.exe --default
    Información de hardware (CPU, RAM, discos, interfaces) Plugin hardware_info, una vez al día Igual, con hardware_info.exe

    Aun así, conviene saber cómo se hace cada cosa a mano: para vigilar un disco, un proceso o un servicio concretos, para ajustar umbrales o para sustituir la plantilla por una propia. Lo que sigue describe los módulos nativos de cada EndPoint: primero lo común a los tres y después lo que cambia según el sistema operativo.

    Módulos comunes a todos los EndPoints¶

    Go, Perl y Windows comparten estos cinco módulos con la misma sintaxis:

    Módulo Qué mide
    module_cpuusage Porcentaje de uso de CPU.
    module_freememory Memoria libre, en MB.
    module_freepercentmemory Memoria libre, en %.
    module_freedisk Espacio libre en una partición o unidad, en MB.
    module_freepercentdisk Espacio libre en una partición o unidad, en %. 
    module_begin
module_name CPU
module_type generic_data
module_cpuusage
module_end

module_begin
module_name Memoria libre
module_type generic_data
module_freememory
module_end

module_begin
module_name Memoria libre (%)
module_type generic_data
module_freepercentmemory
module_end

module_begin
module_name Disco / libre (%)
module_type generic_data
module_freepercentdisk /
module_end

    module_freedisk y module_freepercentdisk necesitan saber qué unidad mirar: en Linux y Unix, el punto de montaje tal cual aparece en df (/, /var); en Windows, la letra de la unidad (C:). El resto de la fila —qué disco, qué partición— no se adivina: si el punto de montaje o la letra no existen en la máquina, el módulo no genera dato.

    module_cpuusage admite opcionalmente el número de núcleo a medir (0 el primero, 1 el segundo…); sin valor, o con all, agrega el uso de todos los núcleos en uno solo.

    Monitorización específica de Linux y Unix (EndPoints Go y Perl)¶

    En Linux y el resto de Unix, module_proc y module_service son el mismo módulo con dos nombres: buscan, entre los procesos en marcha, uno cuya línea de comando completa —tal como la muestra ps aux, desde el nombre del binario en adelante— coincida exactamente con el parámetro. El resultado es 1 si hay una coincidencia y 0 si no la hay; no es un recuento de procesos, así que da igual que haya una instancia del proceso corriendo o cinco. No existe modo asíncrono ni watchdog: si el proceso muere, el próximo ciclo lo refleja, y ahí acaba la vigilancia.

    module_begin
module_name SSHD activo
module_type generic_proc
module_service /usr/sbin/sshd -D
module_end

    La línea de comando entera, no solo el nombre

    module_service sshd no encuentra nada si el proceso real corre como /usr/sbin/sshd -D. Hay que copiar la línea tal como la enseña ps aux, incluidos los argumentos.

    Dos módulos exclusivos de Unix añaden detalle sobre ese mismo proceso: module_cpuproc (uso de CPU) y module_memproc (memoria residente, en MB). Ambos exigen el mismo tipo de coincidencia exacta que module_proc, y si el proceso no está corriendo, el módulo no genera dato ese ciclo. También es exclusivo de Unix module_occupiedpercentdisk, la contrapartida de module_freepercentdisk: el porcentaje ocupado en vez del libre.

    module_begin
module_name SSHD, uso de CPU
module_type generic_data
module_cpuproc /usr/sbin/sshd -D
module_end

module_begin
module_name Disco / ocupado (%)
module_type generic_data
module_occupiedpercentdisk /
module_end

    Para todo lo que no cubre un módulo nativo está module_exec: ejecuta el comando o script que se le pase y toma su salida estándar como dato. En Linux y Unix se ejecuta a través de /bin/sh, y en algunos sistemas (Debian y derivados, sobre todo) ese /bin/sh es dash, no bash: si el comando usa sintaxis propia de bash ([[ ]], arrays, source…), falla en silencio o con un resultado distinto al esperado en una terminal interactiva. La forma segura de evitarlo es envolver el comando en bash -c.

    module_begin
module_name Conexiones establecidas
module_type generic_data
module_exec bash -c "ss -tn state established | wc -l"
module_end

    Monitorización específica de MS Windows¶

    En Windows, module_service y module_proc dejan de ser el mismo módulo y cada uno mira una cosa distinta.

    module_service comprueba el estado de un servicio por su nombre corto —el interno, el que aparece en la columna «Nombre de servicio» del administrador de servicios, no el nombre para mostrar—, entre comillas si lleva espacios. Devuelve 1 si el servicio está en marcha y 0 si está parado o no existe.

    module_begin
module_name Spooler de impresion
module_type generic_proc
module_service Spooler
module_end

    module_proc busca por nombre de proceso, con la extensión .exe incluida (notepad.exe, no notepad), y a diferencia de Unix sí devuelve el número de instancias en marcha, no un simple sí/no.

    module_begin
module_name Instancias de notepad
module_type generic_data
module_proc notepad.exe
module_end

    Ambos módulos admiten en Windows un modo asíncrono (module_async): en vez de esperar al siguiente intervalo, el EndPoint vigila los cambios de estado y envía el dato en cuanto se producen. En los servicios se apoya en las notificaciones del registro de eventos del Administrador de control de servicios; en las ediciones de Windows que no las ofrecen (las Home), el EndPoint cambia solo a comprobar el estado cada 10 segundos. Los módulos asíncronos no se admiten en agentes broker.

    Sobre el modo asíncrono se monta el watchdog (module_watchdog yes), que convierte el módulo en un vigilante activo. Ojo al valor: sin él, el watchdog no se activa.

    • Servicios. Si el servicio se detiene, el EndPoint lo vuelve a arrancar él mismo; no hace falta indicar ningún comando.

      module_begin
module_name Spooler de impresion
module_type generic_proc
module_service Spooler
module_async yes
module_watchdog yes
module_end

    • Procesos. Hay que decirle cómo relanzarlo con module_start_command (sin él, el EndPoint descarta el módulo y lo anota en su log). module_startdelay y module_retrydelay fijan, en milisegundos, la espera antes del arranque y entre reintentos, y module_retries el número de intentos. El proceso se lanza como el propio servicio del EndPoint, es decir, como SYSTEM; para lanzarlo en la sesión del usuario que tenga abierto el escritorio, se añade module_user_session yes.

      module_begin
module_name Notepad
module_type generic_proc
module_proc notepad.exe
module_async yes
module_watchdog yes
module_start_command c:\windows\notepad.exe
module_startdelay 3000
module_retrydelay 2000
module_retries 5
module_end

    Windows no tiene module_cpuproc, module_memproc ni module_occupiedpercentdisk: para el uso de CPU o memoria de un proceso concreto en Windows hay que recurrir a module_perfcounter o a module_wmiquery (ver más abajo).

    Crear módulos propios¶

    Lo primero que se decide al crear un módulo es su tipo (module_type): le dice al servidor qué clase de dato recibe y cómo calcular su estado. Estos son los que se usan en un EndPoint:

    Tipo Qué recibe Cómo se interpreta
    generic_data Un número. El valor tal cual; el estado sale de los umbrales. Es el tipo por defecto.
    generic_proc 1 o 0. Estado directo: 1 es normal y 0, crítico. Para «¿está vivo?».
    generic_data_string Un texto. El texto tal cual; el estado sale de los umbrales de texto.
    generic_data_inc Un contador que solo crece. La velocidad de cambio por segundo entre dos lecturas (bytes/s, peticiones/s…).
    generic_data_inc_abs Un contador que solo crece. La diferencia absoluta entre dos lecturas, sin dividir por el tiempo.
    async_data, async_proc, async_string Lo mismo que sus equivalentes generic_*. Datos que no llegan a intervalos fijos (eventos, cambios de estado). Nunca pasan a desconocido: si no llega dato en el doble de su intervalo, vuelven a normal (async_recovery 1 en el servidor, el valor por defecto).
    log Líneas de log. No es un dato de monitorización: va a la recolección de logs.

    Los dos incrementales necesitan una lectura anterior para calcular nada, así que el primer dato que envían se descarta. La lista completa de tipos de módulo de Pandora FMS, incluidos los de la monitorización remota, se trata en Introducción y arquitectura.

    Todo módulo, nativo o propio, se declara con el mismo envoltorio: module_begin abre la definición, module_end la cierra, y entre medias van module_name (obligatorio), el módulo de datos en sí (module_exec, uno de los módulos nativos anteriores…) y, opcionalmente, module_description, module_type (por defecto, generic_data, un valor numérico) y los tokens de umbral: module_min_warning, module_max_warning, module_min_critical, module_max_critical marcan los rangos de advertencia y crítico; module_str_warning y module_str_critical hacen lo mismo por comparación de texto o expresión regular para módulos de tipo cadena. module_unit añade una unidad al valor mostrado en la consola web (%, GB…) y module_group agrupa módulos relacionados bajo un mismo epígrafe en la vista del agente. Los tres EndPoints admiten estos tokens con el mismo nombre y el mismo efecto.

    module_begin
module_name Disco /var libre (%)
module_type generic_data
module_freepercentdisk /var
module_min_warning 20
module_min_critical 10
module_unit %
module_group Disco
module_end

    Por defecto, cada módulo se ejecuta en todos los ciclos del EndPoint, es decir, cada interval segundos. Para espaciarlo está module_interval, que no se mide en segundos, sino en ciclos: es un multiplicador del interval general. Con interval 300 (cinco minutos), un módulo con module_interval 4 se ejecuta uno de cada cuatro ciclos, cada 20 minutos. Sirve para comprobaciones costosas o que no cambian a menudo, sin tocar el ritmo del resto de módulos.

    module_begin
module_name Paquetes pendientes de actualizar
module_type generic_data
module_exec apt list --upgradable 2>/dev/null | grep -c upgradable || true
module_interval 12
module_end

    Si lo que se necesita es un intervalo fijo en tiempo, independiente de interval (una vez al día, cada hora), está module_absoluteinterval, que se explica en Monitorización programada.

    Para lo que ningún módulo nativo cubre, module_exec acepta cualquier comando o script instalado en la máquina y convierte su salida estándar en el dato del módulo; es la puerta de entrada a los plugins locales, cuyo desarrollo se trata en Creación de plugins locales.

    Dos reglas antes de los ejemplos. La primera: el comando debe devolver un único valor, en una sola línea. La segunda, la que más disgustos da: si el comando termina con un código de salida distinto de 0, el EndPoint descarta el dato aunque haya escrito algo. En Linux y Unix el comando se lanza con sh -c; en Windows, con cmd.exe /c.

    Usuarios con sesión abierta en un servidor Linux, con aviso a partir de cinco:

    module_begin
module_name Usuarios conectados
module_type generic_data
module_exec who | wc -l
module_min_warning 5
module_end

    ¿Hay copia de seguridad de las últimas 24 horas? El módulo devuelve 1 o 0 y, como es de tipo generic_proc, el 0 pone el módulo en crítico sin definir umbrales:

    module_begin
module_name Backup reciente
module_type generic_proc
module_exec [ -n "$(find /backup -name '*.tar.gz' -mtime -1)" ] && echo 1 || echo 0
module_end

    En Windows, ¿está el equipo esperando un reinicio para terminar de aplicar actualizaciones? reg query devuelve un código de error cuando la clave no existe, que es justo el caso normal, así que el && … || convierte el resultado en un 1 o un 0 que siempre termina bien:

    module_begin
module_name Reinicio pendiente
module_type generic_data
module_exec reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired" >nul 2>&1 && echo 1 || echo 0
module_min_warning 1
module_end

    El código de salida, siempre bajo control

    Un grep -c que no encuentra nada escribe 0, pero sale con código 1 y el EndPoint tira el dato. Si un comando puede fallar en el caso normal, fuerza la salida con && echo … || echo … o termina la tubería con un comando que siempre acabe bien, como wc -l.

    Crear módulos desde la consola web¶

    Con la configuración remota activa (ver más arriba), la consola web permite crear y editar estos mismos módulos locales sin tocar pandora_agent.conf a mano: el formulario genera los mismos tokens que se han visto en esta sección y el EndPoint los recoge en su siguiente comprobación de configuración remota. Sin configuración remota, la única vía es editar el fichero directamente en la máquina.

    Monitorización avanzada de MS Windows¶

    El EndPoint Windows añade un puñado de módulos que no tienen equivalente en Go ni en Perl, porque dependen de tecnologías propias de Windows.

    module_wmiquery ejecuta una consulta WQL contra WMI y module_wmicolumn indica qué columna del resultado tomar como valor del módulo:

    module_begin
module_name Memoria fisica libre (KB)
module_type generic_data
module_wmiquery SELECT FreePhysicalMemory FROM Win32_OperatingSystem
module_wmicolumn FreePhysicalMemory
module_end

    Si la consulta devuelve varias filas, el módulo recoge un dato por fila; para un valor único conviene que la consulta devuelva una sola.

    module_perfcounter lee directamente un contador de rendimiento de Windows (los mismos que muestra el Monitor de rendimiento). Los nombres de los contadores van en el idioma del sistema: el ejemplo es para un Windows en español. Para contadores que expresan una tasa («por segundo»), module_cooked 1 entrega el valor ya calculado en vez del contador en bruto.

    module_begin
module_name Bytes recibidos por red
module_type generic_data
module_perfcounter \Interfaz de red(*)\Bytes recibidos/segundo
module_cooked 1
module_end

    El visor de sucesos de Windows se lee con module_logchannel (el recomendado) o con module_logevent, que se mantiene por compatibilidad. Ambos filtran por registro (module_source, el único obligatorio), tipo, código de evento, aplicación o patrón, y su uso principal es la recolección de logs, que tiene capítulo propio: Recolección y monitorización de logs.

    Por último, module_exec_powershell ejecuta el comando o script indicado a través de PowerShell (powershell -C "<comando>"), para todo lo que se resuelve mejor con un cmdlet que con un comando de cmd.exe:

    module_begin
module_name Servicios detenidos
module_type generic_data
module_exec_powershell (Get-Service | Where-Object {$_.Status -eq 'Stopped'}).Count
module_end

    Plugins de EndPoint¶

    Un plugin local se parece a module_exec en que es un programa instalado en la máquina que el EndPoint ejecuta en cada ciclo, pero con una diferencia importante: no devuelve un dato, sino módulos enteros. El plugin escribe en su salida el XML de uno o varios módulos (nombre, tipo, dato, descripción…) y el EndPoint lo añade tal cual a su fichero de datos. Por eso un solo plugin como pandora_df_used crea un módulo por cada disco que encuentra. Los tres EndPoints lo admiten con module_plugin, y como con module_exec, si el plugin termina con un código de salida distinto de 0, su salida se descarta.

    La forma más corta es una línea suelta, que se ejecuta en cada ciclo:

    module_plugin nagios_plugin_wrapper Disco_tmp /usr/lib/nagios/plugins/check_disk -w 20% -c 10% -p /tmp

    Si hace falta ajustar cómo se ejecuta, module_plugin también va dentro de un bloque module_begin / module_end, junto a los tokens que controlan la ejecución: module_interval (cada cuántos ciclos del EndPoint: 2, uno de cada dos), module_absoluteinterval (un intervalo propio, como 1d), module_timeout (segundos de margen antes de darlo por fallido) o module_crontab. En ese caso no hace falta module_name ni module_type: nombre, tipo y dato los pone el propio plugin en su XML. Las plantillas de instalación ya lo hacen así:

    module_begin
module_plugin hardware_info
module_absoluteinterval 1d
module_end

module_begin
module_plugin autodiscover --default
module_timeout 30
module_end

    El paquete de Linux y Unix trae ya varios plugins listos para usar en su carpeta de plugins —algunos, como pandora_df_used o autodiscover, ya han salido en la tabla de monitorización por defecto— y basta con citarlos por su nombre, sin ruta. Entre ellos está nagios_plugin_wrapper, que ejecuta un plugin de Nagios ya escrito (su primer argumento es el nombre del módulo; el resto, la llamada al plugin con sus parámetros) y convierte su código de salida y su texto en un módulo de Pandora FMS, sin reescribir nada. En Windows, los plugins que trae el paquete son scripts VBScript y ejecutables sueltos en la carpeta util\ (los mismos df_percent_used.vbs, mem_percent_used.vbs o autodiscover.exe de la tabla anterior); un plugin propio en PowerShell se invoca igual que cualquier otro comando, con module_plugin:

    module_plugin powershell.exe -File "%ProgramFiles%\pandora_agent\util\mi_plugin.ps1"

    Escribir un plugin propio, en cualquier lenguaje, se trata en Creación de plugins locales.

    Colecciones de ficheros¶

    Para no copiar un plugin a mano en cada máquina están las colecciones: paquetes de ficheros que se suben una vez a la consola web y se asignan a los EndPoints que los necesiten, que los descargan y los dejan listos para que un module_plugin los use. Los tres EndPoints las admiten; cómo se crean, se asignan y se usan desde las políticas se explica en su capítulo, Colecciones.

    Configuración remota, requisito previo

    Las colecciones se distribuyen por el mismo canal que la configuración remota (ver Configuración remota desde la consola web): sin ella activa, no hay forma de empujar una colección al EndPoint.

    Monitorización avanzada con el EndPoint¶

    Monitorización condicionada¶

    Una precondición (module_precondition) decide si el módulo llega a ejecutarse; una condición (module_condition) evalúa el resultado ya obtenido. Ambas comparten la misma sintaxis, en los tres EndPoints:

    Forma Sintaxis Se cumple cuando
    Comparación numérica <operador> <valor> <comando> El valor cumple <operador> <valor>. Operadores: >, <, = y != (no hay >= ni <=).
    Intervalo (<mínimo>,<máximo>) <comando> El valor está entre los dos límites, sin incluirlos.
    Expresión regular =~ <patrón> <comando> El valor coincide con <patrón>.

    Lo que cambia es de dónde sale el valor y qué hace el comando:

    • En una precondición, el EndPoint ejecuta primero el <comando> y compara su salida. Si un módulo tiene varias, deben cumplirse todas; si falla alguna, el módulo no se ejecuta ese ciclo.
    • En una condición, el valor es el dato que acaba de obtener el módulo. Si se cumple, el EndPoint lanza el <comando> aparte, como acción de respuesta (reiniciar algo, limpiar un directorio…); el dato del módulo no cambia.

    Una precondición para no dar falsas alarmas: el módulo comprueba si hay copia de seguridad reciente en un recurso de red montado en /backup, pero solo si ese recurso está montado. Si no lo está, el módulo no se ejecuta ese ciclo, en lugar de marcar en crítico una copia que no ha podido ni mirar:

    module_begin
module_name Backup reciente
module_type generic_proc
module_precondition = 1 mountpoint -q /backup && echo 1 || echo 0
module_exec [ -n "$(find /backup -name '*.tar.gz' -mtime -1)" ] && echo 1 || echo 0
module_end

    Una condición como acción de respuesta: el módulo mide cuánto está ocupado el disco raíz y, si pasa del 90 %, el EndPoint borra los logs comprimidos de más de 30 días. El dato se envía igual; el borrado es un efecto aparte:

    module_begin
module_name Disco / ocupado (%)
module_type generic_data
module_occupiedpercentdisk /
module_condition > 90 find /var/log -name '*.gz' -mtime +30 -delete
module_min_warning 85
module_end

    Monitorización intensiva¶

    La monitorización intensiva sirve para enterarse antes de que algo cae sin multiplicar los datos que se envían. Se activa con el token global intensive_interval, en segundos y más corto que interval: el EndPoint pasa a dar una vuelta cada intensive_interval segundos. En cada vuelta ejecuta los módulos marcados con module_intensive_condition, pero solo envía su dato cuando cambia si cumplen o no la condición, o cuando vence su intervalo normal. Con intensive_interval a 0 (el valor por defecto) vale lo mismo que interval y no hay monitorización intensiva. La condición usa la misma sintaxis que las de la tabla anterior, sin comando.

    # Parte general del fichero
interval 300
intensive_interval 10

module_begin
module_name Ping puerta de enlace
module_type generic_proc
module_exec ping -c 1 -W 1 192.168.1.1 >/dev/null 2>&1 && echo 1 || echo 0
module_intensive_condition = 0
module_end

    Monitorización programada¶

    Hay dos formas de que un módulo no siga el ritmo normal del EndPoint.

    module_absoluteinterval le da un intervalo propio, en tiempo real y no en ciclos como module_interval. Admite un número con sufijo (30s, 15m, 6h, 1d) o, sin sufijo, un número de ciclos de interval. Por debajo, el EndPoint lo traduce a ciclos redondeando hacia arriba: con interval 300, un module_absoluteinterval 7m se ejecuta cada dos ciclos, es decir, cada 10 minutos. Así que no conviene esperar más precisión que la del propio interval.

    Lo que lo distingue de verdad de module_interval es la memoria: los tres EndPoints guardan la hora de la última ejecución del módulo en un fichero de referencia (.ref), de modo que el intervalo se respeta aunque el EndPoint se reinicie. Un módulo diario se ejecuta una vez al día, no una vez al día más una por cada reinicio. El valor especial once hace que el módulo se ejecute una sola vez y lo convierte en asíncrono.

    module_begin
module_name Certificado web: dias hasta caducar
module_type generic_data
module_exec echo $(( ( $(date -d "$(openssl x509 -enddate -noout -in /etc/ssl/certs/web.pem | cut -d= -f2)" +%s) - $(date +%s) ) / 86400 ))
module_absoluteinterval 1d
module_end

    module_crontab va un paso más allá: el módulo solo se ejecuta cuando la hora coincide con una expresión cron de cinco campos (minuto, hora, día del mes, mes, día de la semana); el resto de ciclos no hace nada. Es lo adecuado para lo que tiene sentido a una hora concreta, como un cierre nocturno o un informe semanal.

    module_begin
module_name Informe semanal generado (lunes, 9:00)
module_type generic_proc
module_exec [ -f /var/reports/weekly.done ] && echo 1 || echo 0
module_crontab 0 9 * * 1
module_end

    Postprocesado, flip-flop y otros ajustes del módulo¶

    Un puñado de tokens, comunes a los tres EndPoints, afinan cómo se trata el dato una vez obtenido, sin tocar cómo se obtiene:

    Token Qué hace
    module_postprocess Factor por el que el servidor multiplica el valor numérico al recibirlo (para convertir bytes en MB, por ejemplo). El EndPoint lo envía tal cual junto al dato.
    module_ff_interval, module_ff_type, module_each_ff, module_min_ff_event* Ajustan el flip-flop: cuántos cambios de estado seguidos hacen falta para que el servidor dispare un evento, en vez de uno por cada cambio.
    module_timeout Segundos de margen para que el comando o plugin del módulo termine antes de darlo por fallido.
    module_save <variable> Guarda el valor del módulo en la variable de entorno indicada, para que la usen los módulos que se ejecutan después.

    module_async, ya visto en la monitorización de servicios y procesos de Windows, es exclusivo de ese EndPoint: convierte el módulo en un vigilante que avisa en cuanto cambia de estado, en vez de esperar al ciclo. Ni Go ni Perl lo implementan.

    El EndPoint como punto de monitorización de red¶

    Chequeos remotos desde el EndPoint¶

    Un EndPoint también puede vigilar otra máquina de la red desde donde está instalado, sin que esa máquina tenga EndPoint propio. La diferencia entre sistemas es de fondo, no de matiz: Windows trae módulos nativos para esto; en Linux y Unix, con Go o con Perl, no existen equivalentes y se construyen con module_exec.

    En Windows, module_ping lanza un ping contra el host indicado y da 1 o 0 según si obtiene respuesta; module_ping_count y module_ping_timeout ajustan el número de intentos y el tiempo de espera. module_tcpcheck comprueba si un puerto TCP responde, con module_port para indicar cuál y module_timeout para el margen de espera. module_snmpget lanza una consulta SNMP y toma el valor devuelto como dato del módulo, con module_snmp_version, module_snmp_community, module_snmp_agent (el host) y module_snmp_oid.

    module_begin
module_name Ping a la pasarela
module_type generic_proc
module_ping 192.168.1.1
module_ping_count 2
module_ping_timeout 1
module_end

module_begin
module_name Puerto web del servidor
module_type generic_proc
module_tcpcheck 192.168.1.10
module_port 443
module_end

    En Linux y Unix, el mismo resultado se consigue con module_exec, apoyado en las herramientas del sistema. Aquí aplica la misma regla que en cualquier otro module_exec: el código de salida decide si el dato se envía, así que hay que forzarlo explícitamente en vez de fiarse del del comando.

    module_begin
module_name Ping a la pasarela
module_type generic_proc
module_exec ping -c 1 -W 1 192.168.1.1 >/dev/null 2>&1 && echo 1 || echo 0
module_end

module_begin
module_name Puerto web del servidor
module_type generic_proc
module_exec nc -z -w 2 192.168.1.10 443 && echo 1 || echo 0
module_end

module_begin
module_name Uptime por SNMP
module_type generic_data
module_exec snmpget -Ovq -c public -v 2c 192.168.1.10 sysUpTime.0
module_end

    Para monitorización de red desde fuera de la máquina destino —sin necesidad de ningún EndPoint— está la monitorización remota, en Monitorización de redes.

    Modo broker¶

    Un EndPoint en modo broker deja de reportar como un único agente y pasa a generar y enviar, en el mismo ciclo, uno o varios agentes adicionales: cada broker_agent <nombre> en pandora_agent.conf levanta un agente hijo con su propia configuración, derivada de la del EndPoint principal (mismo servidor, mismo intervalo, mismo modo de transferencia), pero con su propio nombre y sus propios módulos. Es lo que permite, por ejemplo, que un único EndPoint instalado en una pasarela reporte datos de varios dispositivos que hay detrás de ella, cada uno como su propio agente en la consola.

    Los tres EndPoints lo admiten. En el EndPoint Windows, los agentes broker no admiten módulos asíncronos: un módulo con module_async en la configuración de un broker se descarta.

    broker_agent Router-planta-1
broker_agent Router-planta-2

    Modo proxy¶

    En modo proxy, el EndPoint deja de limitarse a enviar sus propios datos y pasa también a hacer de intermediario Tentacle para otros EndPoints de su red que no llegan directamente al servidor. Al arrancar con proxy_mode 1, levanta su propio servidor Tentacle local (tentacle_server) escuchando en proxy_address y proxy_port (por defecto, todas las interfaces y el puerto 41121, el mismo que el del servidor), y reenvía lo que recibe hacia server_ip y server_port. proxy_max_connection limita las conexiones simultáneas que acepta (por defecto, 10) y proxy_timeout el tiempo de espera de cada una (por defecto, 1 segundo). Los EndPoints que se apoyan en el proxy solo necesitan apuntar su server_ip a la máquina que hace de proxy, en vez de al servidor real.

    # En el EndPoint que hace de proxy
proxy_mode 1
proxy_address 0.0.0.0
proxy_port 41121

    Servidor secundario¶

    secondary_mode decide si el EndPoint envía también sus datos a un segundo servidor, además del principal (server_ip), y en qué circunstancia:

    Valor Comportamiento
    never (por defecto) Solo se envía al servidor principal.
    on_error Se intenta primero el principal; solo si falla, se envía al secundario.
    always Se envía a los dos servidores, siempre.

    El servidor secundario se configura con su propio juego de tokens en espejo —secondary_server_ip, secondary_server_port, secondary_transfer_mode, secondary_server_ssl, secondary_server_path, secondary_server_user, secondary_server_pwd—, independientes de los del servidor principal. Es la vía para no dejar de reportar cuando el servidor principal no está disponible, o para alimentar a la vez dos instalaciones de Pandora FMS distintas, sin depender del modo proxy ni de una arquitectura distribuida completa.

    secondary_mode on_error
secondary_server_ip 10.0.0.5
secondary_transfer_mode tentacle

    Acciones remotas sobre el EndPoint¶

    Los EndPoints Perl y Windows pueden escuchar órdenes por un pequeño servidor UDP: se activa con udp_server 1 (viene desactivado), escucha en udp_server_port (41122 por defecto) y solo atiende a las direcciones de udp_server_auth_address (0.0.0.0, el valor por defecto, admite cualquiera). El EndPoint Go no tiene servidor UDP.

    Las órdenes que entiende son pocas y deliberadamente limitadas:

    Orden Qué hace Perl Windows
    REFRESH AGENT Fuerza una ejecución inmediata del ciclo: el EndPoint recoge y envía sus datos sin esperar al intervalo. Sí Sí (ver nota)
    START PROCESS <nombre> / STOP PROCESS <nombre> Ejecuta el comando definido en process_<nombre>_start / process_<nombre>_stop. Sin ese token, la orden se rechaza. Sí Sí
    START SERVICE <nombre> / STOP SERVICE <nombre> Arranca o para el servicio de Windows indicado, solo si está autorizado con service_<nombre> 1. No Sí 
    udp_server 1
udp_server_port 41122
udp_server_auth_address 10.0.0.20
process_backup_start /usr/local/bin/run_backup.sh
process_backup_stop /usr/local/bin/stop_backup.sh

    udp_server 1
udp_server_auth_address 10.0.0.20
service_spooler 1
process_informe_start C:\scripts\informe.bat

    Tres palabras en Windows

    El EndPoint Windows exige que toda orden tenga exactamente tres palabras; por eso, para refrescarlo, la orden es REFRESH AGENT *. Es la forma que usa la acción de alerta «Restart agent» que viene de serie; si una orden de dos palabras no hace nada en un EndPoint Windows, este es el motivo.

    Desde el servidor, las órdenes se envían con udp_client.pl (/usr/share/pandora_server/util/udp_client.pl <ip> 41122 "<orden>"), que es lo que usan el comando de alerta «Remote agent control» y la acción «Restart agent».

    Para ejecutar comandos o scripts arbitrarios en el EndPoint desde la consola, sin depender de este servidor UDP ni de acciones predefinidas, está la ejecución remota de comandos y scripts: Ejecución remota de scripts y comandos.

    Otras técnicas de monitorización¶

    Tres mecanismos más, de uso puntual, completan lo que un EndPoint puede aportar más allá de sus módulos:

    • KeepAlive. Un módulo de tipo keep_alive que se pone en crítico cuando el agente deja de enviar datos. Se crea solo desde la consola web (aunque no haya configuración remota) y no deja rastro en pandora_agent.conf.
    • Command Snapshot. Un módulo de tipo texto que recoge la salida completa de un comando largo (ps aux, netstat -n) para verla en la consola tal cual, como una captura. Requiere activar la opción Command line snapshot en la configuración de la consola web. Con el EndPoint Go no sirve: module_exec solo toma la primera línea de la salida.
    • Monitorización de imágenes. Un módulo de tipo texto (generic_data_string o async_string) cuyo dato es una imagen codificada en base64 (data:image/jpeg;base64,…), que la consola muestra como imagen en lugar de como texto. Normalmente lo genera un plugin.

    El EndPoint también participa en dos áreas con capítulo propio: el inventario del sistema, en Inventario, y la recogida de logs, en Recolección y monitorización de logs.

    Vigilar ficheros de texto con module_regexp¶

    module_regexp vigila un fichero de texto buscando las líneas nuevas que cumplen module_pattern (una expresión regular); module_pattern_exclude descarta las que, cumpliéndolo, coincidan además con este otro. Lo que devuelve depende del tipo: con generic_data, cuántas líneas coinciden; con generic_proc, 1 si hay alguna; con generic_data_string, las líneas. Los tres EndPoints lo admiten con los mismos tokens, incluido module_pattern_exclude: pese a lo que dice alguna documentación antigua, no es exclusivo de Linux, también funciona en el EndPoint Windows. Solo Windows añade module_noseekeof: con 1, el módulo revisa el fichero entero en cada ejecución en lugar de solo lo añadido desde la anterior.

    module_begin
module_name Errores en el log de la aplicacion
module_type generic_data_string
module_regexp /var/log/miapp/error.log
module_pattern ERROR
module_pattern_exclude ERROR_CONOCIDO
module_end

    Es el mecanismo mínimo para vigilar un fichero suelto; para una recogida de logs en serio —centralizada, con múltiples fuentes y búsqueda posterior— está Recolección y monitorización de logs.

    Cómo funciona por dentro¶

    Todo lo anterior —módulos, plugins, colecciones— desemboca en el mismo mecanismo de entrega. Conviene entenderlo una vez, porque explica de un plumazo por qué el agente aparece solo en la consola, qué hace debug 1 de verdad y por qué un buffer lleno no tira datos a la basura.

    El XML de datos y la autocreación. Cada ciclo, el EndPoint junta el resultado de todos sus módulos en un único documento XML, envuelto en una etiqueta <agent_data> con los atributos del agente (nombre, alias, grupo, intervalo, versión…) y un <module> por cada módulo, con su nombre, tipo y dato. Ese fichero se escribe primero en la carpeta temporal con el nombre <hash del agente>.<timestamp>.data y desde ahí se envía; no se genera el XML directamente sobre la marcha en el envío, así que siempre queda un rastro en disco mientras dura el ciclo. Es este mismo XML el que el servidor procesa para crear el agente y sus módulos la primera vez que aparecen (autocreate 1, ya visto en Primeros pasos con un EndPoint recién instalado): no hay dos formatos distintos, uno para el alta y otro para el día a día.

    Modo aprendizaje, normal y autodeshabilitado. Que un módulo nuevo del XML acabe en la consola depende también del modo del agente, que se elige al editarlo en la consola web:

    Modo Qué hace con el XML
    Modo de aprendizaje (por defecto) Crea los módulos nuevos y actualiza los datos del agente (dirección IP, intervalo, versión del sistema operativo y del EndPoint, campos personalizados) y la configuración de los módulos que ya existen, salvo los que vienen de una política.
    Modo normal Solo procesa datos de módulos que ya existen: los nuevos se descartan y los datos del agente que manda el XML no sobrescriben los de la consola.
    Modo autodeshabilitado Igual que el de aprendizaje, pero el servidor deshabilita el agente cuando todos sus módulos (sin contar los asíncronos) pasan a desconocido, y lo vuelve a habilitar solo en cuanto llegan datos nuevos. Pensado para máquinas que aparecen y desaparecen.

    Es la primera sospecha cuando alguien añade un module_begin al EndPoint, comprueba que el XML sale bien y el módulo no aparece nunca: el agente está en modo normal y el servidor, obediente, lo ignora.

    Transferencia: Tentacle, SSH, FTP y local. El envío en sí lo hace un programa externo que el EndPoint lanza contra el fichero .data, según transfer_mode: los tres EndPoints admiten los cuatro modos —tentacle (por defecto), ssh (con scp), ftp y local (una copia de fichero, para cuando el EndPoint corre en la misma máquina que el servidor)— con el mismo repertorio en Go, Perl y Windows.

    Tentacle, el modo por defecto

    tentacle es el que traen las plantillas de instalación, y su cliente viaja en el propio paquete del EndPoint; ssh y ftp dependen de que la máquina tenga scp o un cliente FTP.

    Con Tentacle, dos tokens activan opciones del cliente: server_ssl 1 añade -c (cifrado) a la llamada de tentacle_client, y server_pwd añade -x <clave> (contraseña compartida con el servidor). Ambos se traducen igual en los tres EndPoints.

    El buffer de XML. Si el envío del ciclo falla —servidor caído, red cortada—, por defecto el EndPoint tira ese XML: la próxima vuelta genera uno nuevo y el dato perdido no vuelve. xml_buffer 1 cambia esa política: el fichero .data que no se pudo enviar se queda en temporal y el EndPoint reintenta enviarlo, junto con el de la vuelta siguiente, en el próximo ciclo. La política se aplica por igual en Go, Perl y Windows, con los mismos tres límites, todos con el mismo valor por defecto (1024, en el sentido que indica cada uno):

    Token Límite
    temporal_min_size Megabytes libres mínimos en la partición de temporal; por debajo, no se guarda nada nuevo en el buffer.
    temporal_max_files Número máximo de ficheros .data acumulados en temporal.
    temporal_max_size Megabytes máximos ocupados por esos ficheros en conjunto.

    Con xml_buffer 0 (el valor por defecto) estos tres límites no se llegan ni a comprobar: el EndPoint no acumula nada que no se pueda enviar en el acto.

    debug, otra vez. Ya salió en Parámetros esenciales de pandora_agent.conf: con debug 1 el envío no cambia —el dato sale igual, ciclo tras ciclo— pero el EndPoint deja de comprobar configuración remota y colecciones en cada vuelta y conserva cada .data enviado con el sufijo sent en vez de borrarlo, para poder revisarlo después.

    autotime. Por defecto, el EndPoint pone en el XML la hora local de la máquina en la que corre (timestamp). Con autotime 1, ese atributo desaparece del XML y es el servidor quien pone su propia hora de recepción al procesar el dato. Sirve para EndPoints en máquinas cuyo reloj no es de fiar —una máquina virtual mal sincronizada, un dispositivo sin NTP— y que, de otro modo, generarían datos con una marca de tiempo desplazada. El comportamiento es idéntico en los tres EndPoints.

    Solución de problemas¶

    La mayoría de los problemas con un EndPoint se reducen a una de estas comprobaciones, en el orden en que conviene hacerlas.

    1. ¿Aparece el agente en la consola? Si no aparece nada, revisa autocreate en el servidor (ver Primeros pasos con un EndPoint recién instalado) y que el EndPoint llega al servidor: el puerto de Tentacle (41121 por defecto) tiene que estar accesible entre las dos máquinas.
    2. ¿El fichero de configuración es el que crees? Con la configuración remota activa, un cambio hecho a mano en la máquina puede quedar sobrescrito por el servidor en el siguiente ciclo si el MD5 no coincide (ver Configuración remota desde la consola web). Compara el fichero local con el que muestra la consola antes de dar por perdido un cambio.
    3. ¿El plugin o el module_exec tienen los permisos y la ruta correctos? Un plugin propio o un script fuera de la carpeta de plugins necesitan la ruta completa, y el fichero, permiso de ejecución (chmod 755 en Linux y Unix).

    4. ¿La salida y el código de salida son los que espera el EndPoint? Ejecuta el comando o el plugin a mano, en la misma cuenta con la que corre el EndPoint, y revisa dos cosas: que el código de salida es 0 (si no lo es, el EndPoint descarta el dato aunque haya escrito algo bueno) y que la salida es exactamente lo que se espera —un solo valor para module_exec, un XML completo y válido para un plugin—. Para comprobar el XML de un plugin, xmllint es más fiable que mirarlo a ojo. Como un plugin escribe uno o varios <module> sueltos, sin elemento raíz, hay que envolverlos antes de validarlos:

      (echo "<plugin>"; ./mi_plugin; echo "</plugin>") | xmllint --noout -

    5. Modo debug. Con debug 1 (ver Parámetros esenciales de pandora_agent.conf), cada .data enviado se conserva con el sufijo sent en la carpeta temporal, así que se puede abrir y comprobar exactamente qué generó cada módulo o plugin ese ciclo, sin esperar a que llegue a la consola.

    6. El log del EndPoint. En Linux y Unix, /var/log/pandora/pandora_agent.log por defecto (logfile en pandora_agent.conf); en Windows, pandora_agent.log en la carpeta de instalación, y pandora_debug.log junto a él si el modo debug está activo.
    7. Reiniciar el servicio después de cualquier cambio manual en el fichero de configuración: systemctl restart pandora_agent_daemon en Linux y Unix, NET STOP / NET START PandoraFMSAgent en Windows (ver Primeros pasos con un EndPoint recién instalado).
    8. Ejecutar el EndPoint a mano, sin el servicio. Cada EndPoint tiene su propia forma de correr fuera del servicio, útil para ver los mensajes según se producen: el EndPoint Go admite pandora_agent --once /etc/pandora para un único ciclo de recogida y envío; el EndPoint Windows admite PandoraAgent.exe --process para correr como proceso de usuario en vez de como servicio, y --test-ssh / --test-ftp para probar por separado esos dos modos de transferencia con la configuración actual.

    Permisos del EndPoint, no solo del plugin

    En Linux, el servicio pandora_agent_daemon corre como root salvo que se fije pandora_user en la configuración; en Windows, el servicio corre como SYSTEM. Un comando que funciona en una terminal interactiva puede fallar dentro del EndPoint si depende de variables de entorno o permisos que solo tiene el usuario que abrió esa terminal.

    Para lo que no es específico del EndPoint —errores del servidor, de la consola web o de otros componentes—, está la guía general de resolución de problemas.
